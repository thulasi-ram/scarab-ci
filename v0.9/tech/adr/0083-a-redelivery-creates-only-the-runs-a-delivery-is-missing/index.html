    Context

    Section titled “Context”

    A verified webhook delivery runs in its own task (finish_delivery, scarab-server/src/lib.rs) holding one of 64 permits. The task records the delivery id once per delivery (delivery_is_fresh → ConnectionRegistry::record_delivery, an INSERT ... ON CONFLICT DO NOTHING into webhook_deliveries (forge, id, at), migration 0024). A second delivery with the same id is answered 200 duplicate delivery and does nothing. Then ingest_event resolves the repository’s connection (connections.resolve), reads .scarab/ (read_event_pipelines), compiles every file, and for each Pipeline whose trigger matches (DeliveryTrigger::decide) either creates a Run (admit_and_create_run → persist_run_from_ir) or records a refusal.

    0.7.1 added, around that:

    • a delivery that recorded nothing because the forge could not be read deletes its id (forget_delivery) and answers 502, so a redelivery is processed;
    • a delivery that created some Runs while a Pipeline file could not be read keeps its id and answers 202 with "incomplete": true;
    • a redelivery of an id whose task is still running on the same server is answered 503 (RunningDelivery, an in-process set);
    • a delivery that finds no free permit within 10 s is answered 503 with nothing recorded.

    Three windows still lose Runs, because the id means “this delivery is done” from the moment it is recorded:

    1. Partial delivery. Runs of a.yaml and b.yaml are created, c.yaml could not be read. The id stays recorded; a redelivery is a duplicate; c.yaml never runs.
    2. Server death. The server stops after the id is recorded and before (or while) the Runs are created. A redelivery is a duplicate.
    3. Another replica. A redelivery reaches replica B while replica A still runs the first try. B finds the id recorded and answers duplicate delivery; if A then fails, nothing repairs it.

    What the code does today, checked for this ADR:

    • Run creation is not one transaction. persist_run_from_ir writes the Run’s first row (Db::begin_run_creation, runs.creating = TRUE, out of the scheduler’s work list), then about twenty separate writes (tenant, number, origin, IR, events, Steps, …), then finish_run_creation (UPDATE runs SET creating = FALSE WHERE id = $1, with no other condition). A write that fails ends the Run Failed (fail_run_creation); a server that stops in between leaves the Run Pending, and the leader’s sweep ends it Failed after 10 minutes (sweep_unfinished_creations, unfinished_creation_bound_ms, reason “the server stopped while creating this Run”). creating stays TRUE on such a Run, and it cannot be rerun (RerunError::CreationUnfinished).
    • The first row may be written with the Policy decision. When run.create Policies apply, the Postgres policy store writes the allow decision and the Run’s first row in one transaction (record_run_create_decision, scarab-db-postgres/src/policies.rs); the default implementation (the in-memory store) writes the decision alone and begin_run_creation writes the row.
    • A refusal is several writes. record_refused_run inserts into refused_runs (no unique key; best effort, a failed write is logged), and enqueue_refusal_status queues a failure commit status. The status’s idempotency key contains run_id_for(event, path), which is a new random id for every webhook event, so two tries queue two posts. A Policy denial and a missing-approval-gate refusal each write a decision row first (consult_run_create).
    • Commit statuses are ordered per Run only. A post that fails stays on the outbox and is retried; status_post_superseded compares a post with its own Run’s generation and status, never with another Run’s.
    • Newest-wins. A push or pull request Run that targets no Environment and is not a deploy Run gets a supersede_key (<org>/<repo>:<ref or pr-N>:<pipeline>), and a Run created later cancels the older non-terminal Runs with that key (created_at <).
    • Follow-ups already work this way. An on: upstream Run gets an id derived from the upstream Run, its generation, its verdict and the Pipeline path (run_id_for, git-bug 149b4db); a redelivered run_finished skips a path whose Run exists.
    • Which events reach ingest_event. Push, pull request, tag, release and comment (Event::Comment). Cron fires, manual and API dispatches, and follow-ups have their own paths and are not changed here. There is no check-suite or “re-run” event handling.
    • Where .scarab/ is read (config_ref): a push at after, a pull request at its head commit, a tag or release at refs/tags/<tag>, a comment at HEAD. The last two move.
    • A pull request’s changed paths are asked live, by pull request number, not at the event’s commit (pull_request_files), and a push’s compare can time out; an unknown list counts as true (ADR-0081 §6). Two tries of one delivery can decide a when: differently.
    • webhook_deliveries is never pruned. It also answers the connection page’s “last delivery” (last_delivery_at, max(at) per forge, with no index on at).
    • The in-memory store (scarab-testkit) keeps runs, refused runs, the outbox and webhook_deliveries under one Mutex; one lock is its transaction.

    What the forges do:

    • GitHub. “If you request a redelivery, the X-GitHub-Delivery header will be the same as in the original delivery” (GitHub docs, Best practices for using webhooks). “You can redeliver webhook deliveries that occurred in the past 3 days”, and “GitHub does not automatically redeliver failed deliveries” (Redelivering webhooks).
    • Forgejo (source, branch forgejo). Deliver (services/webhook/deliver.go) makes one request and records the result; nothing retries it. Replay (ReplayHookTask, models/webhook/hooktask.go) copies the payload into a new hook task, and CreateHookTask gives it a new UUID; X-Forgejo-Delivery, X-Gitea-Delivery and X-GitHub-Delivery all carry that UUID (services/webhook/shared/payloader.go). A Replay is a new delivery id.

    So today a GitHub Redeliver is always answered duplicate delivery, and a Forgejo Replay starts every Run again.

    Decision

    Section titled “Decision”

    1. The key is (connection, delivery id, Pipeline file path), and every decision is recorded

    Section titled “1. The key is (connection, delivery id, Pipeline file path), and every decision is recorded”

    A delivery outcome is recorded per Pipeline file a delivery decided, with the key (connection_id, delivery_id, pipeline):

    • connection_id is the id of the forge connection that serves the event’s repository, as ingest_event already resolves it (ResolvedRepo.connection.id). Today one webhook secret per forge kind serves the whole server, so ids of two connections of one kind share one space; with the connection in the key, two connections cannot answer for each other’s deliveries, and the key stays right if secrets become per connection (org scoping, git-bug 19b0a45). The forge kind is stored beside it for pruning (§8).
    • pipeline is the file path under .scarab/ as read_event_pipelines lists it (.scarab/build.yaml), not the name:: two files can declare the same name:, a file can omit it, and every try lists .scarab/ at the same commit (below). build.yaml and build.yml are two keys, as they are two Pipelines today.
    • No trigger kind in the key. One delivery is one event, so one trigger kind.
    • Matrix: a matrix expands Steps inside one Run at compile time (CONTEXT.md Matrix), so it adds nothing to the key.
    • Follow-ups (on: upstream) are not started by a webhook delivery; they keep their derived Run ids. Each Run a delivery creates starts its follow-ups once, when it ends.
    • Comment commands are Event::Comment deliveries and get the same key.

    The delivery-level row (webhook_deliveries, §7) keeps its key (forge, id): it is read before the connection is resolved, and a GUID or UUID is not reused across connections in practice.

    One commit per delivery. The first try resolves the commit it reads .scarab/ at and stores it on the delivery row (webhook_deliveries.config_sha). Push and pull request deliveries store the event’s commit. A comment delivery (HEAD) and a tag or release delivery (refs/tags/<tag>) resolve the ref once with ForgePort::latest_commit. Every later try reads .scarab/ at the stored commit. Without this, a comment’s redelivery after a rename on HEAD (deploy.yaml → release.yaml) would find no outcome for the new path and run /deploy a second time. If the ref cannot be resolved, this try reads .scarab/ at the symbolic ref, as 0.7.1 did, nothing is stored, and the next try resolves it again; the rename case stays open only on a forge where the lookup never works.

    Every decision is recorded. A redelivery must not decide a Pipeline again: a pull request’s paths are asked live, a compare can time out the second time, and an unknown list counts as true, so a Pipeline the first try did not match could become a Run on the second.

    Outcome for one Pipeline outcome Side effects in the same transaction
    A Run created run, with the Run id the Run’s first row
    Refused at admission (Environment, Policy, yanked library, event field, forge token, sandbox, missing approval gate) refused, with reason_kind and the refused_runs id refused row, failure status
    A when: that cannot be decided refused, reason_kind = when refused row, failure status
    Does not compile refused, reason_kind = compile refused row, failure status when its on: may name the event
    Matched, not run because another file does not compile not_run, reason_kind = compile failure status naming the broken file
    Matched on a later try, but the head has moved (§5) not_run, reason_kind = not_head failure status “no longer the head of <ref>”
    Trigger does not match no_match none
    Every Step excluded by its when: all_excluded none
    Ref not allowed by the Environment (silent today) ref_not_allowed none
    File, or its invoke: library, could not be read not recorded none; read again by the next try
    An error from the store or from admission not recorded none; the delivery stays unfinished and the answer is 502

    reason_kind takes the values refused_runs.reason_kind takes today, plus when and not_head.

    The last row covers an error from Run creation, including a write that fails after the Run’s first row (that Run ends Failed, and the next try replaces it under §4). The Pipeline is left undecided and the try goes on with the files after it. One that repeats, such as a concurrency group that cannot be rendered (concurrency_group_key), repeats on every redelivery; see Not solved.

    Not keyed: the path-filter note (record_path_filter_note) and the follow-up record (record_followups), written on a Run after its creation finished by the try that created it. If that try stops in between, a redelivery skips the Pipeline and neither is written; both are best effort today, and the follow-up drain reads .scarab/ itself when the record is missing. The cron index (schedules::index_push) writes only when the push is still the default branch’s head, so a redelivery of an old push writes nothing.

    2. The outcome row is written in the transaction of the Run’s first row or of the refusal

    Section titled “2. The outcome row is written in the transaction of the Run’s first row or of the refusal”

    New table webhook_delivery_pipelines:

    No foreign keys: a key on runs would make every outcome insert lock a runs row, and retention (§8) removes outcomes with their delivery, not with their Run.

    Where each outcome row is written:

    • A Run. In the transaction that inserts the Run’s first row (insert_creating_run): Db::begin_run_creation gains an optional DeliveryPipeline key, and so does RunCreationRow for PolicyStore::record_run_create_decision, which writes the decision, the first row and the outcome row together. That is the only Run transaction there is; §4 covers a Run whose later writes never landed.
    • A refusal or not_run. A new Db::record_delivery_refusal(key, reason_kind, refused, status) writes, in one transaction, the outcome row, the refused_runs row (when there is one) and the failure commit status outbox row (when there is one). refuse_uncompiled_delivery, refuse_undecided_when and the admission-refusal branch of trigger_runs_from_files call it for webhook deliveries in place of record_refusal followed by enqueue_refusal_status.
    • no_match, all_excluded, ref_not_allowed. Db::record_delivery_outcome(key, outcome), one insert.
    • In-memory store. The same writes under its one lock.

    A primary-key violation is not an error to the caller. The port answers Claimed with the outcome already recorded, and nothing of the losing write remains. With the Postgres stores that includes the Policy allow decision. The first outcome written wins, whatever the second try decided.

    A failed outcome write (other than a key violation) leaves that Pipeline undecided and the delivery unfinished, like an unreadable file. Today a refused row that fails to write is only logged; on the webhook path it now keeps the delivery open for a redelivery.

    The key is passed only on the webhook path (ingest_event → trigger_runs_from_files). Dispatch, cron and follow-up callers pass none and behave as today.

    3. A try reads the outcomes first and decides only what is missing

    Section titled “3. A try reads the outcomes first and decides only what is missing”

    trigger_runs_from_files reads the delivery’s recorded outcomes once (Db::delivery_outcomes(connection_id, delivery_id)), before compiling. A recorded path is not compiled, decided or created again; Runs and refusals among them are listed in the answer as earlier. This is the check the follow-up path already makes with run_status(run_id_for(..)).

    The compile rule across tries. ADR-0009’s rule is that a file that does not compile stops every Run of the delivery. Across tries it reads: if any file of the delivery is broken, recorded (refused with reason_kind = compile) or found by this try, every Pipeline of the delivery not yet decided is decided as the first try would have decided it with that file broken: not_run with its failure status where its trigger matches, no_match where it does not. Example: the first try records c.yaml as compile, a.yaml and b.yaml as not_run, and cannot read d.yaml. The redelivery reads d.yaml; because c.yaml’s compile refusal is recorded, d.yaml becomes not_run (if it matches), never a Run.

    Runs a first try created before a later try found a broken file (possible only when the broken file was unreadable on the first try) are not touched; the broken file is recorded as compile and the Pipelines still undecided become not_run. That is the 0.7.1 behaviour of a partial delivery, carried forward.

    The read is an optimisation. Two tries that both pass it are separated by the primary key (§2).

    4. A Run whose creation did not finish is replaced by a redelivery

    Section titled “4. A Run whose creation did not finish is replaced by a redelivery”

    An outcome run can point at a Run whose first row exists and whose creation never finished (runs.creating = TRUE): the server stopped, the try stalled, or a later write failed. A redelivery looks at it:

    • Creation finished (any status): the Pipeline is decided; skipped.
    • Still creating, Pending, and younger than the unfinished-creation bound (10 minutes, the scheduler’s unfinished_creation_bound_ms, moved to a constant both read): another try may be writing it now. The Pipeline is left alone, and the answer is 409 (§7).
    • Creation unfinished and older than the bound, or already ended Failed: the try ends it with fail_run_creation (a compare-and-set from Pending; a conflict means it is already Failed) and creates a new Run, subject to §5. The new Run’s first-row transaction also:
      • locks the old Run (SELECT ... FOR UPDATE) and goes on only while it is still creating, no longer Pending and not replaced; otherwise it rolls back and the Pipeline counts as Claimed. A stalled try that finished the Run first (which needs Pending) keeps it. A refusal that overwrites the outcome of an unfinished Run takes the same lock and check;
      • moves the outcome row: UPDATE webhook_delivery_pipelines SET run_id = $new WHERE <key> AND run_id = $old, which must update one row; zero rows means another try replaced it first, the transaction rolls back and the Pipeline counts as Claimed;
      • marks the old Run replaced: new column runs.replaced_by set to the new Run’s id.

    What the mark does:

    • Statuses. status_post_superseded answers “superseded” for every post of a Run whose replaced_by is set, so a failure post of the old Run still on the outbox (the forge was failing, the usual reason for a redelivery) is dropped instead of landing after the new Run’s success. A post the forge already accepted before the replacement committed is older than every post of the new Run, which is created after it.
    • A stalled try cannot finish the old Run. finish_run_creation becomes a compare-and-set: UPDATE runs SET creating = FALSE WHERE id = $1 AND creating AND status = 'pending' AND replaced_by IS NULL. Zero rows means the Run was ended or replaced while the try stalled; the try writes no path-filter note or follow-up record for it and reports the Pipeline as decided by another try. Without this, a try paused past the bound would clear creating on a Failed Run and a human Rerun would give a second Run for one (delivery, Pipeline).
    • Rerun. ensure_creation_finished also refuses a Run with replaced_by set, and the refusal names the replacement.

    The bound only decides how long a redelivery is answered 409 before it replaces. It compares the Run’s created_at, taken on the creating server, with the redelivering server’s clock, so clock skew between replicas lengthens or shortens that wait; the compare-and-set finish keeps a wrong guess from producing two live Runs.

    The old Run stays in the Runs list as Failed, with its reason and a link to its replacement. A creation that fails for a reason that repeats gives one more Failed Run per redelivery; redeliveries are made by hand, so that is bounded by the operator.

    5. A later try creates nothing for a push or pull request whose head has moved

    Section titled “5. A later try creates nothing for a push or pull request whose head has moved”

    A redelivery can arrive up to 3 days after its event (GitHub). Without a rule, a Run it creates would be the newest by created_at and cancel a newer push’s Run through newest-wins, or, for a Pipeline that targets an Environment, deploy the older commit after the newer one. Neither can happen in 0.7.1, where a redelivery is processed only when the first try recorded nothing.

    Owner decision (2026-11-22): on a try after the first, a push or pull request Pipeline that would create a Run first checks whether its commit is still the head, and when it is not, creates nothing.

    • Which try. The first try is the one whose insert created the delivery row (§7); it behaves as today. Every other try applies this rule.
    • Which events. Push, pull request, and a comment on a pull request. Tag and release deliveries always run. A comment that is not on a pull request has no head and always runs, at the commit its first try pinned (§1). Whether a comment is on a pull request is read from its payload (GitHub issue.pull_request, Forgejo is_pull).
    • How “head” is decided. From the delivery rows, with no forge call and no Run: the first try stores the scope (head_scope: the repository and the ref, or the repository and the pull request number) and its commit (head_sha) on the delivery row, beside config_sha, before it reads any file. The head has moved when another delivery row has the same head_scope, a different head_sha, and a later at. It is asked once per later try. A newer delivery counts whatever it decided, nothing included, and whether or not its trigger matched this Pipeline: a newer push stops an older push’s redelivery for every Pipeline.
    • A comment on a pull request. The first try reads the pull request’s head (ForgePort::pull_request_head, GET pulls/<n>, head.sha) and stores the pull request as head_scope and that commit as head_sha. A later try applies the rule against that pull request: a delivery of it (its own events or another comment on it) that arrived later at another commit means the head moved. If the head cannot be read, the comment is pinned with no head and runs on a later try as a comment not on a pull request does. Only the first try reads the head: a comment its first try left unpinned (its HEAD could not be resolved, or the try stopped first) is pinned by a later try with no head, for good, because the pull request’s head by then need not be the one the comment arrived at.
    • Clocks. The delivery row’s at and its lease are written with the store’s clock: Postgres now() (the database’s), and in the in-memory test store a clock the tests set. Both sides of the comparison are at values, so there is one clock.
    • What is recorded. not_run with reason_kind = not_head, a failure commit status on the delivery’s commit reading “no longer the head of <ref>” (or “of pull request #<n>”; a comment has no commit to post on), and the Pipeline counts as decided.
    • A replacement under §4 applies the same check. When the head moved, no new Run is created: the outcome run naming the unfinished Run is overwritten with not_run / not_head (only while it still names that Run), the unfinished Run is ended Failed and is not marked replaced, and the delivery can finish.

    “Head” here means “no newer delivery of this ref or pull request”. This replaces the earlier reading (“no newer Run of this Pipeline”): a newer push whose trigger did not match this Pipeline now stops the older push’s redelivery too. What it gives up is under Not solved.

    6. Two replicas, one delivery

    Section titled “6. Two replicas, one delivery”

    RunningDelivery (the in-process set) is removed: it existed because 0.7.1 forgot ids, and the database now decides across replicas (§7’s try lease, §2’s primary key).

    Two tries of one delivery at once, on one replica or two, when both get past the lease (one of them expired, or the second came in after the first ended):

    • Both may read the forge and compile. Reads have no effect beyond the forge’s rate limit.
    • For each Pipeline, both may reach §2’s write; one inserts, the other gets Claimed.
    • Side effects in the winning transaction happen once: the Run’s first row, the run.create allow decision (written with it on Postgres), the refused row, the refusal or not_run status.
    • Side effects after the first row belong to the one Run that exists: its later writes, its path-filter note, its follow-up record, and every commit status, check or notification, which are outbox rows a Run transition writes, keyed by Run and generation.
    • Side effects before the transaction, which can happen twice:
      • a run.create deny decision and the decision row of a missing-approval-gate refusal (ADR-0078) are written by consult_run_create before the refusal transaction, so a race, or a server that stopped between the two, leaves two decision rows for one refusal in the org’s decision log. The log records consultations, and both happened; the refusal itself is recorded once.
      • with a policy store that does not write the Run’s first row (the default trait implementation, used by the in-memory store; production pairs both on one Postgres), the loser’s allow decision is written alone and names a Run id that is never created.
      • tracing lines.

    The 64-permit semaphore and the shutdown drain stay as they are.

    7. The delivery row: fast path, try lease and answers

    Section titled “7. The delivery row: fast path, try lease and answers”

    webhook_deliveries keeps one row per delivery, keyed (forge, id), and gains:

    • unfinished BOOLEAN NOT NULL DEFAULT FALSE;
    • config_sha TEXT, the commit of §1;
    • head_scope TEXT and head_sha TEXT, the ref or pull request of §5 and its commit;
    • try_until BIGINT, the lease of the try processing the delivery, and try_token TEXT, the token the try that holds it gets: only that try ends it, so a try whose lease lapsed and was taken by a later try leaves the later try’s lease alone.

    A try:

    1. inserts the row with unfinished = TRUE and try_until = now + 10 minutes (the database clock), and is then the first try; or finds the row;
    2. on a found row with unfinished = FALSE, answers 200 duplicate delivery with no forge read, as today;
    3. on a found unfinished row, takes the lease: UPDATE ... SET try_until = now + 10 minutes WHERE <key> AND unfinished AND (try_until IS NULL OR try_until < now). Zero rows means another try holds it, and the answer is 409;
    4. when it ends with every Pipeline decided (no unreadable file, no Pipeline left to another try, no error), sets unfinished = FALSE; it clears try_until in every case. So do the answers that act on no Pipeline: installation events, unsupported or ignored events, a repository not enabled or unreachable.

    The lease matches the unfinished-creation bound. A try that stops leaves the lease to expire; a try that runs past it can overlap a later one, which §2’s primary key and §4’s compare-and-set keep from creating two Runs.

    The unfinished default is FALSE so that every row written before this migration, and every row a 0.7.1 replica writes during a rolling update, reads as finished: those deliveries have no outcome rows, and running their trigger again would create their Runs a second time.

    forget_delivery and its 502 path go: nothing is ever deleted to let a redelivery in.

    The answers (owner decision, 2026-11-22, for the 502 and 409 rows):

    Case 0.7.1 This ADR
    Finished delivery again 200 duplicate delivery same
    Every Pipeline decided, some by this try 202 run_ids 202 run_ids, plus earlier: [{pipeline, run_id | refused}] when an earlier try decided some
    Every Pipeline decided by earlier tries (could not happen) 200 duplicate delivery, and the row is marked finished
    Nothing created, forge unreadable 502, id deleted 502, row left unfinished
    Some decided, a Pipeline left undecided (unreadable, failed outcome write, store error) 202 incomplete: true, id kept 502, body run_ids, refused, earlier, undecided: [pipeline], incomplete: true; row left unfinished
    Another try holds the lease, or a Pipeline’s Run is still being created by another try (§4) 503, same replica only 409 this delivery is being processed by another try; redeliver later, on any replica
    No free permit in 10 s 503, nothing recorded same
    No delivery id, registry wired 400 same

    A 409 from step 3 is answered before any forge read. A 409 from §4 comes after the other Pipelines are decided. The OpenAPI response lists on both webhook endpoints gain 409 and change their 502 text.

    8. Retention

    Section titled “8. Retention”

    The retention sweeper (retention.rs) prunes deliveries under its leader lease, in a new sweep_webhook_deliveries: it selects up to 1,000 webhook_deliveries rows whose at is older than the retention period and whose try lease is not live (a try still running may record outcomes), and, in one transaction, deletes them and every webhook_delivery_pipelines row with their (forge, delivery_id). A delivery and its outcomes go together, so no later try of a delivery can find some of its outcomes and not others.

    The period (owner decision, 2026-11-22) is SCARAB_RETENTION_WEBHOOK_DELIVERY_DAYS, default 30, with the chart value retention.webhookDeliveryDays. A value under 7 days is refused at start with an error naming the floor: under GitHub’s 3-day redelivery window a Redeliver would find no outcomes and create every Run again, and 7 days leaves room for clock and sweep timing.

    Pruning webhook_deliveries does not weaken the replay guard of ADR-0046: the delivery id is outside the HMAC (§10). last_delivery_at reads max(at), which the newest rows keep.

    webhook_deliveries has grown since 0024 without pruning, so the first passes on an old database delete many rows, 1,000 deliveries at a time.

    9. Migration

    Section titled “9. Migration”

    • 0104 (in a transaction, SET LOCAL lock_timeout = '5s' as 0101 does):

      • CREATE TABLE webhook_delivery_pipelines and its index (a new table, no lock on another);
      • ALTER TABLE runs ADD COLUMN replaced_by TEXT, first, so that while it waits for runs the migration holds no lock on webhook_deliveries;
      • ALTER TABLE webhook_deliveries ADD COLUMN unfinished BOOLEAN NOT NULL DEFAULT FALSE, ADD COLUMN config_sha TEXT, ADD COLUMN head_scope TEXT, ADD COLUMN head_sha TEXT, ADD COLUMN try_until BIGINT, ADD COLUMN try_token TEXT.

      Since Postgres 11 a constant default is stored in the catalog, and a nullable column without a default needs none, so no row is rewritten. Each ALTER takes an ACCESS EXCLUSIVE lock for that moment and waits at most 5 s for it. runs is written by every scheduler tick, so on a busy database the wait can time out; the start then fails with canceling statement due to lock timeout and the Pod’s restart retries, as for 0101.

    • 0105 (-- no-transaction, as 0100): CREATE INDEX CONCURRENTLY IF NOT EXISTS webhook_deliveries_at_idx ON webhook_deliveries (at), added to CONCURRENT_INDEXES so an invalid index is rebuilt at start. Writes go on while it builds. The sweeper and last_delivery_at use it. The §5 lookup reads runs by tenant, ref or pull request number, and Pipeline name; whether it needs its own index is decided from its query plan when it is built.

    • No backfill. Runs carry no delivery id, so outcome rows cannot be derived for past deliveries; the FALSE default makes them read as finished (§7).

    • Rollback: crates/scarab-db-postgres/rollback/0104_revert.sql, in the format of 0099_revert.sql: drop webhook_delivery_pipelines, the index, the three webhook_deliveries columns and runs.replaced_by, and DELETE FROM _sqlx_migrations WHERE version IN (104, 105). A 0.7.1 server then reads every recorded delivery as done, including unfinished ones, which is its behaviour today, and a replaced Run becomes an ordinary Failed Run whose creation did not finish.

    10. Accepted risk: a resend under a new delivery id

    Section titled “10. Accepted risk: a resend under a new delivery id”

    Owner decision (2026-11-22): nothing is built for this. A new delivery id is a new delivery.

    • The id is a header outside the HMAC on both forges; the signature covers the body only. Someone holding a captured signed body can send it again under a new id, and Scarab processes it as a new delivery. That is true before this ADR too.
    • With §5, such a resend is a first try and creates Runs as any delivery does: the Pipelines its trigger matches, at its commit, with newest-wins cancelling the older Runs of the same ref. For a push or pull request whose commit is the current head, that re-runs the head’s Pipelines. A resend of an older commit’s body creates Runs that a newer push’s Runs then stand beside; this ADR does not close that, as 0.7.1 does not.
    • A Forgejo Replay is this case by design: a new id, the same body, so its Runs start again.

    11. What changes for operators and forges

    Section titled “11. What changes for operators and forges”
    • A GitHub Redeliver of a delivery that left a Pipeline undecided (a forge read failed, the server stopped, another replica was mid-way) creates what is missing and nothing else, unless the head has moved (§5). A Redeliver of a finished delivery is still duplicate delivery.
    • A delivery that stopped part-way on one replica can be redelivered to any replica.
    • A Forgejo Replay has a new delivery id, so it starts the delivery’s Runs again, as today.
    • The webhook answers change as in §7: a partial delivery is 502 instead of 202, and a delivery another try is processing is 409 on any replica instead of 503 on the same one. Neither forge retries on its own, so the change shows in the forge’s delivery list and in anything that watches it.
    • During a rolling update from 0.7.1, a delivery a new replica answered 502 and left unfinished is answered duplicate delivery if its redelivery reaches a 0.7.1 replica, where 0.7.1 alone would have deleted the id and processed it. Redelivering again once the rollout ends repairs it.
    • Two migrations, a rollback file and a new retention setting (SCARAB_RETENTION_WEBHOOK_DELIVERY_DAYS, chart retention.webhookDeliveryDays, default 30, floor 7).
    • Whether this ships as 0.7.2 or 0.8.0 is the owner’s call.

    Consequences

    Section titled “Consequences”
    • Windows 1, 2 and 3 of the Context are closed for every Pipeline a redelivery reaches, on GitHub within its 3-day redelivery window, except where §5 refuses a Pipeline whose head has moved.
    • A delivery is processed again on redelivery unless it finished, so an unfinished one costs its forge reads again. A finished one costs one primary-key lookup, as today.
    • webhook_delivery_pipelines holds one row per Pipeline file per delivery, matched or not, until the delivery is pruned.
    • refused_runs gets at most one row per (delivery, Pipeline) on the webhook path; a refusal’s commit status is queued once per (delivery, Pipeline).
    • RunningDelivery, claim_delivery, forget_delivery and refuse_unread_delivery’s delete go. finish_run_creation becomes a compare-and-set.
    • The org decision log can hold two decision rows for one refusal after a race (§6).

    Not solved

    Section titled “Not solved”
    • Run creation stays many writes. A Run whose creation stops part-way is detected and replaced (§4); it is not prevented. Making persist_run_from_ir one transaction would mean a transactional Db port across about twenty methods.
    • No repair without a redelivery. Neither forge retries, so an unfinished delivery stays unfinished until someone redelivers it (GitHub: within 3 days). A server-side sweep that re-runs unfinished deliveries would have to store their signed payloads; not decided here.
    • A delivery Scarab never received (the server was down for longer than the forge waits) has no row at all; the forge shows it failed.
    • An admission error that repeats (a concurrency group that cannot be rendered) leaves the same Pipeline undecided on every try, so the delivery never finishes. Recording it as a refusal is a change to admission, not to delivery handling.
    • What the head rule does not see (§5). It orders deliveries by arrival, with no ancestry data, so a forge that delivers two pushes out of order refuses the redelivery of the real head. A newer commit known only from a 0.7.1 replica’s row during a rolling update (no head_scope) or from a Run with no delivery (a dispatch, a cron fire, a follow-up) does not stop an older delivery’s redelivery.
    • A resend under a new id (§10), Forgejo Replay included.
    • Follow-up refusals (a chain loop or cap) are recorded again when a run_finished is delivered twice; their status is not, through the derived id. Pre-existing, not on the webhook path.
    • Installation events are not keyed; applying one twice is idempotent today.

    Rejected options

    Section titled “Rejected options”
    • Keep the delivery-level id and delete it on any failure. 0.7.1 does this for “nothing created”. It cannot cover a partial delivery or a server that stopped, which are the cases left.
    • Record only Runs and refusals, and decide the rest again (this ADR’s first draft). A pull request’s paths are asked live and an unknown list counts as true, so a Pipeline the first try did not match could become a Run on the second.
    • A late redelivery creates its Run without the supersede key, so it cancels nothing. An Environment Pipeline would still deploy the older commit after the newer one (owner decision, 2026-11-22).
    • A late redelivery creates its Run as the first try would have. It cancels a newer push’s Run through newest-wins (owner decision, 2026-11-22).
    • Decide “head” with a forge call (the ref’s current commit). One more request per Pipeline left to create, a failure mode of its own, and it answers “is this the branch tip”, where newest-wins needs “is there a newer Run of this Pipeline”.
    • Derive webhook Run ids from (forge, delivery id, path), as follow-ups do, and let the runs primary key be the unique constraint. Run ids would then be computable by anyone who sees delivery ids in the forge’s delivery list, against the rule that Run ids in URLs are not guessable; a UUIDv7 needs a time that a redelivery can reproduce; and refusals have no Run id to key on.
    • Write the outcome row at finish_run_creation instead of with the first row. Two replicas would then both create a whole Run and the loser would have to undo one, posting a failure for it.
    • Key by the Pipeline’s name:. Not unique and optional (§1).
    • Key by the forge kind only. Two connections of one kind would share one id space.
    • Make the whole delivery one transaction. Forge reads and compiles would run inside an open transaction for up to tens of seconds.
    • Key Forgejo deliveries by the SHA-256 of the body, so a Replay repairs instead of running again. Two events with the same body become one: a tag deleted and pushed again at the same commit can send the same bytes, and the second push would be answered duplicate delivery with no sign to the user. It also removes Replay as a way to run a delivery again, and during a rolling update a 0.7.1 replica keys by UUID while a new one keys by digest. Forgejo keeps one key per delivery id.

    Owner decisions (2026-11-22)

    Section titled “Owner decisions (2026-11-22)”
    1. A late redelivery creates nothing for a push, pull request, or comment on a pull request whose head has moved, decided from Scarab’s Runs; tags, releases and other comments always run; the first try behaves as today (§5). The comment rule is the orchestrator’s correction of 2026-11-22.
    2. Answers: a partial delivery is 502 with what ran and what did not; a delivery another try is processing is 409 on any replica; the overload answer stays 503 (§7).
    3. Retention: 30 days by default, a setting with a chart value, never under 7 days (§8).
    4. A resend under a new delivery id is an accepted risk; nothing is built (§10).

    Test plan

    Section titled “Test plan”

    Classical, against the in-memory store and the compose Postgres (just test rust webhook); the forge is the existing FakeForge.

    • Partial delivery repaired (window 1): c.yaml’s read fails, a.yaml and b.yaml start Runs, the answer is 502 naming c.yaml under undecided; the redelivery of the same id starts c.yaml only, and its answer lists a.yaml and b.yaml under earlier. A third delivery is duplicate delivery with zero forge calls.
    • A recorded no-match stays one (red team B1): the first try decides a.yaml no_match on known pull request paths and leaves c.yaml unread; on the redelivery the FakeForge answers the pull request’s files with an error; a.yaml is not created.
    • A recorded compile refusal stops later files (red team B2): first try c.yaml broken, d.yaml unreadable; the redelivery reads d.yaml, which matches; it is not_run, with no Run.
    • One commit per comment delivery (red team A5): the first try reads at the commit HEAD resolved to; between tries HEAD moves to a commit where the file is renamed; the redelivery reads at the stored commit and creates nothing new.
    • A late redelivery (owner decision 1): push P1 with c.yaml unreadable; push P2 creates a c.yaml Run; the redelivery of P1 records not_run (not_head), posts its failure on P1’s commit and leaves P2’s Run running. The same for a pull request whose head moved, and for a comment on a pull request whose pull request got a Run at a new commit. A redelivery of P1 with no newer c.yaml Run creates it. A tag redelivery creates it, and so does a comment that is not on a pull request.
    • Server stopped between rows (window 2): a store hook stops the try after begin_run_creation of b.yaml; the redelivery within the bound answers 409 and creates nothing; with the clock past the bound it ends the old Run Failed, creates a new one, the outcome row names the new Run and the old Run’s replaced_by names it too.
    • A stalled try cannot finish a replaced Run (red team A3): the stopped try of the last case resumes; finish_run_creation updates no row, the old Run stays Failed and a Rerun of it is refused.
    • A replaced Run’s queued status is dropped (red team A4): the old Run’s failure post fails once and stays queued; the new Run posts success; the retried old post is dropped.
    • Try lease: a redelivery while the first try holds the lease answers 409 before any forge call; after the lease expires it proceeds.
    • Two tries at once (window 3): two ingest_event calls of one delivery past the lease, interleaved with the testkit’s interleave_point at the outcome write (constructed, not raced): one Run per Pipeline, one refused_runs row and one refusal status per refused Pipeline.
    • Postgres: the same cases against the compose database, plus the primary-key race: two connections insert one key; the loser’s transaction leaves no runs row and no policy_decisions row.
    • Old rows: a webhook_deliveries row inserted without unfinished (as 0.7.1 writes it) is a duplicate.
    • Retention: a delivery past the period is deleted with all its outcomes; a period of 6 days is refused at start; last_delivery_at still answers.
    • Migration: 0104 and 0105 apply on a database holding 0.7.1 rows; 0104_revert.sql brings it back and a second run of it changes nothing.

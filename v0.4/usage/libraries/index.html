    Libraries

    Install a library into your org from a git commit, use it with invoke lib:, upgrade it after reading the diff, and yank a version that must stop running.

    An org admin installs a library once, and every Pipeline in the org can use it:

    A library is a YAML file with kind: library (see Reuse: invoke). Scarab stores the file it installed and compiles Pipelines against that copy, so a Pipeline never fetches anything, and the org decides when a library changes.

    Install a library

    Section titled “Install a library”

    Settings › Libraries › Install library, or the API. Install library asks for a file in a git repository, a ref (a branch, tag or commit) and a name, and Fetch and review opens the review page (/orgs/<org>/settings/libraries/review), which every library goes through, Scarab’s own included.

    The part before // is the repository and the part after it is the file. Scarab reads a branch or tag at the commit it points to when you fetch, and the review page shows that commit. The installation is pinned to that commit and to the content you reviewed: a branch that moves later changes nothing until you upgrade. The API takes the same two fields, source and ref, or a source that ends in @<full commit id>.

    Installing takes two steps:

    1. Fetch and review. Scarab reads the file, checks that it is a library, that it invokes only lib: and plugin: targets (never file:), and that every library it invokes is installed in the org. It stores the file as a version, keyed by its SHA-256, and shows you the content. Nothing is installed yet. An org keeps its 50 most recent fetches that were never installed; an older one is deleted and has to be fetched again before you install it.
    2. Install. Scarab installs the version you reviewed, by its hash. This asks you to confirm with your passkey.

    The name. Pipelines name a library lib:<name>. The name defaults to <owner>::<repo>::<file>, the file name without .yaml or .yml: the file above installs as acme::scarab-libs::deploy-helm. You can type another name at install, such as deploy-helm or platform/helm. A name is parts of letters, digits, ., _ and -, joined by :: or /, each part starting with a letter, digit or _, at most 255 bytes; it is case-sensitive. When the default does not fit that rule (a file name starting with . or -), the fetch asks you for a name. Each name names one installation in the org. A name says nothing about where the library came from: the installation records its source, and Policies match on the source. The libraries allowed and blocked lists, under Libraries › Library policies, are such rules: see Library and plugin policies.

    Where Scarab reads from. A public repository on github.com, or on the host of a Forgejo connection, is read without credentials, over https only, from public addresses only, with no redirects and a 1 MiB limit. Any other host is refused. For a private repository, pick a connection of the installing org, and Scarab reads the file through it. A connection of another org, or one with no org yet, is refused, and through a GitHub App connection Scarab reads only repositories your org owns. When the connection cannot reach the repository (a GitHub App that is not installed on it, for example), Scarab reads the file without credentials instead, which works for a public repository; for a private one, give the connection access to it. See Forge connections.

    Upgrade

    Section titled “Upgrade”

    Each installed library has its own page, reached from its row under Settings › Libraries (/orgs/<org>/settings/libraries/<id>/manage, where the id is the installation’s and stays the same across upgrades). Its Upgrade asks for the newer commit of the same file. Scarab shows the diff from the installed version, and Upgrade on the review page installs it. The upgrade names the version it replaces, so if someone else changed the installation after you fetched, it fails and you fetch again to see the current diff.

    A Run keeps the version it was created with. Its inlined Steps record the version’s hash in origin, and a Rerun or Retry uses the stored Steps, so upgrading changes only Runs created after it.

    Remove

    Section titled “Remove”

    Remove deletes the installation. It needs no passkey. Pipelines that invoke it then fail to compile with “lib:acme::scarab-libs::deploy-helm is not installed in this org”; Runs already created keep their Steps. The stored version stays, so those Runs still show what they ran.

    Yank a version

    Section titled “Yank a version”

    Yank a version when it must stop running, for example because an image it pins has a known vulnerability. Give a reason; every refusal shows it. Once a version is yanked in your org, Scarab refuses:

    • a new Run whose Steps or gates come from it, at Run creation;
    • each launch of a Step that comes from it, including Reruns and Retries of Runs created before the yank (the Step fails with a configuration error naming the version and the reason);
    • approving or releasing a gate that comes from it; a timer gate from it fails with the reason when its timer runs out;
    • a debug Pod of a Step that comes from it.

    A Policy cannot allow a yanked version, in audit mode or with except_projects. A yank applies to one org. Yanking needs no passkey; lifting a yank does.

    The usual fix is an upgrade to a version that pins the patched image, then a yank of the old one.

    Install Scarab’s clone library

    Section titled “Install Scarab’s clone library”

    lib:thulasi-ram::scarab-ci::clone checks out the Run’s repository (Checking out the repository). It is the file libs/clone.yaml in Scarab’s repository, and an org admin installs it like any other library. Scarab installs no library into an org by itself, a new org included, and gives no library more trust because Scarab published it.

    1. Settings › Libraries › Install library, with the file github.com/thulasi-ram/scarab-ci//libs/clone.yaml and a Scarab release tag as the ref, such as v0.4.0. Use a release tag: each Scarab release checks that the file at its tag pins a published scarab-clone image by digest. Scarab reads it from github.com without credentials.
    2. Keep the default name, thulasi-ram::scarab-ci::clone (the repository’s owner and name and the file name), which is the name Scarab’s docs and errors use. Review the file and install it. Confirm with your passkey.
    3. On a Forgejo or GitHub token connection, also trust its source with forge credentials (below). Without that, a Run that invokes it is refused with the reason. On a GitHub App connection this step is not needed.

    The library pins the scarab-clone image by digest. To run checkouts from a mirror’s image, install a copy of libs/clone.yaml that pins the mirror’s image, and trust the mirror’s source instead. Its default name names the mirror’s repository; type thulasi-ram::scarab-ci::clone as the name to keep Pipelines unchanged.

    Install Scarab’s build library

    Section titled “Install Scarab’s build library”

    lib:thulasi-ram::scarab-ci::build builds an image with rootless BuildKit and pushes it with crane (Building an image). It is the file libs/build.yaml in Scarab’s repository. It has two steps: image builds in the build sandbox and holds no registry credential, and push pushes and holds it. Install it the same way as the clone library, then give its source the trust its steps need:

    1. Settings › Libraries › Install library, with the file github.com/thulasi-ram/scarab-ci//libs/build.yaml and a Scarab release tag as the ref.
    2. Keep the default name, thulasi-ram::scarab-ci::build. Review the file and install it. Confirm with your passkey.
    3. Trust its source for the build sandbox (below). Without that, a Run that invokes it is refused with the reason.
    4. To push, trust its source with the registry credential (below), so its push step receives the REGISTRY_AUTH secret. Without that the push runs anonymously and fails at a registry that needs a login. To push to the forge’s own registry (GHCR, the Forgejo package registry) with no REGISTRY_AUTH secret, also trust its source with forge credentials (below). The build step never receives a credential, so it pulls only public base images.
    5. If a placement profile grants push access (a ServiceAccount with a push role, say), the operator marks it registry_auth_only: true, and Pipelines route it to the push step with placement_profiles: { push: [<profile>] }. Scarab applies a marked profile only to that step, and only when the launch found that step eligible for a registry credential (step 4, in a Run that is not a fork pull request), whether or not a REGISTRY_AUTH secret exists (Placement & resources).

    The push step runs as root, because crane’s image has no other user, so an org Policy that denies run-as-root refuses every Run that invokes the library.

    The library pins the rootless BuildKit image and the crane image by digest. A newer BuildKit or crane is a new version of the file: upgrade the installation, and trust carries over because the source is the same. To run a different builder, or BuildKit with other flags, install your own library and trust its source instead. It gets the sandbox on the same terms as Scarab’s.

    Upgrading from the build step kind. The release that ships this library removes the build: step kind, with no release in between that accepts both. A Pipeline with a build: step fails to compile until you rewrite the step. The error for each such step holds its replacement, written from the step’s own build:, needs, when, timeout, resources and placement_profiles, ready to paste:

    ${{ outputs.image.image }} reads the same result as before: BuildKit’s metadata, whose containerimage.digest is the digest of the image built. ${{ outputs.image.push }} is new: the pushed reference and digest, set only when the image was pushed; deploy by outputs.image.push.digest. A step that reads outputs.image.image also receives the build step’s workspace, image layout included. cache: registry is gone, because writing a registry cache needs the push credential in the build step; use cache: s3 or no cache. A step of a Run created before the upgrade that has not launched yet fails when it would launch, and again on each retry or rerun, with the same replacement; start a new Run once the Pipeline is changed. A Pipeline that fails its check creates no Run and posts no commit status yet; the error shows in the repository’s Runs list in Scarab.

    Trusting a library with forge credentials

    Section titled “Trusting a library with forge credentials”

    A step with forge_token receives a forge credential (Pipeline syntax). On a Forgejo or GitHub token connection that credential is one long-lived token, so only a step from a library installed from a source your org trusts receives it. No source is trusted by default, Scarab’s clone library included. An org admin trusts a source on the library’s page under Settings › Libraries (Trust source), or with the API:

    grant is forge_credentials when you leave it out.

    Trust is for the source without a commit, so it holds when you upgrade the library from the same source, and each upgrade still shows you its diff. Trusting needs a step-up; removing trust (DELETE …/library-trust?source=<source>&grant=forge_credentials) does not. Each row under Settings › Libraries says whether its source is trusted, and a trusted source no installed library comes from is listed below them.

    On a GitHub App connection Scarab mints a token for one repository each time a step launches, so any step may ask for one and no trust is needed.

    After an upgrade. Scarab 0.3.0 trusted its clone library without a trusted-source entry. Migration 0090 adds that entry for every org that had the clone library from 0.3.0’s release manifest, for the source it was fetched from, listed as trusted by scarab:migration-0090. Those orgs keep cloning after the upgrade, and an admin can remove the entry like any other.

    Trusting a library for the build sandbox

    Section titled “Trusting a library for the build sandbox”

    A step with security: { sandbox: rootless-buildkit } runs as uid 1000, not privileged, with seccomp and AppArmor unconfined, which rootless BuildKit needs. Only a step from a library installed from a source your org trusts for the build sandbox gets it. A step written in a Pipeline file, or reached through invoke: file:, never does, and a library that a trusted library invokes needs its own trust. No source is trusted by default, Scarab’s build library included. An org admin trusts a source on the library’s page under Settings › Libraries (Build sandbox › Trust source), or with the API:

    Each grant is separate: trusting a source with forge credentials or the registry credential does not trust it for the build sandbox, and the reverse. Trust is checked when a Run is created and again each time the step launches, so removing it (DELETE …/library-trust?source=<source>&grant=build_sandbox) stops retries and reruns too. A DELETE that names no grant removes every grant of the source. Trusting needs a step-up; removing trust does not.

    Trusting a library with the registry credential

    Section titled “Trusting a library with the registry credential”

    A step with registry_auth: true may receive the Run’s registry credential: the REGISTRY_AUTH secret (Repo scope, then Org scope), or the credential the forge derives for its own registry. Only a step from a library installed from a source your org trusts with the registry credential receives one; a step written in a Pipeline file, or reached through invoke: file:, runs your repository’s own command and never does. The forge-derived credential can write packages, so it needs the source trusted with forge credentials as well. No source is trusted by default:

    A step that may not have the credential is not refused: it runs without one, and a push fails at the registry. Each launch checks the trust again. A fork pull request never receives a registry credential. Settings › Libraries shows this trust on the library’s page under Registry credential.

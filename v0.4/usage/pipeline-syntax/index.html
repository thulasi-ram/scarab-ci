    Pipeline Syntax

    How to write a Scarab pipeline: triggers, inputs, steps, CEL expressions, matrix, invoke, results, gates, deploys, and retries.

    The model, in brief

    Section titled “The model, in brief”

    A step is the basic unit of work: an OCI image plus a command (the step contract), which Scarab runs as a single Kubernetes Pod. A pipeline is a group of steps, plus how they are triggered and wired together. Structurally a pipeline is a flat recursive DAG (Pipeline → Step).

    You write YAML, with CEL for expressions. Scarab compiles it to a typed IR, and the IR (not the YAML) defines what a valid pipeline is. invoke reuses a library by inlining it into the caller’s DAG at compile time. matrix is a modifier that fans a step out over a set of inputs.

    Compilation is static: the whole DAG (every matrix combination, every inlined library step) is materialised and validated at submit time, so a cycle, a dangling needs, or an empty matrix dimension is rejected up front, never discovered mid-run.

    Keys are strict at every level of that schema. A key Scarab does not know (a misspelling, a field borrowed from another CI system, a knob from a newer version) is a compile error that names the key and the ones that were expected. It is never silently ignored:

    Ignoring unknown keys would be worse: resources: { cpu_milis: 500 } would parse cleanly, report ok, and then run the step with no CPU request at all, with nothing to show the setting was dropped.

    A repo’s CI lives in .scarab/. A triggered pipeline is a YAML file such as .scarab/ci.yaml; its file name is the default display name (ci.yaml reads as ci, overridable with a top-level name:). Reusable libraries (files marked kind: library) live under .scarab/lib/ by convention and are pulled in with invoke. Start from Run locally to submit your first pipeline.

    Commit .scarab/, and never blanket-ignore it

    .scarab/ is tracked source: it is read from the triggering commit, so an ignored pipeline file is a pipeline that does not exist. The catch is that a local scarab-server also writes its development object store inside that directory (SCARAB_OBJECT_DIR defaults to ./.scarab/objects). That tempts a blanket /.scarab ignore rule, which then silently swallows git add .scarab/ci.yaml. Ignore only the runtime path instead:

    The rest of this page goes through each part: triggers and inputs, the step shape, wiring and reuse, deploys, and the operational settings.

    Triggers: on:

    Section titled “Triggers: on:”

    on: maps a trigger kind to a filter. The kinds Scarab understands are push, pull_request, tag, release, comment, cron, manual, api, and upstream. An empty on: means the pipeline has no automatic triggers: it runs only when launched explicitly.

    Each kind takes an optional when: CEL guard over the event context, so a trigger can fire selectively:

    Changed files: event.changed_paths

    Section titled “Changed files: event.changed_paths”

    A when: can read the files a push or pull request changed, as event.changed_paths: a sorted list of repository paths. This Pipeline builds an image only when something under docker/ci-tools/ changed:

    Where the list comes from:

    • push: the added, modified and removed files of every commit in the webhook payload. A renamed file is listed under both names.
    • pull_request: the forge’s pull request files API, asked once per delivery and only when a Pipeline whose pull_request trigger matches reads event.changed_paths. A repository that does not use it makes no extra API calls. The list is the pull request’s files when Scarab handles the webhook, which can differ from the event’s head commit if the pull request moved since.
    • Every other trigger (tag, release, comment, cron, manual, api, upstream) has no list.

    Sometimes the list is unknown: the trigger has none, the push created the branch or deleted it, the push was forced (detected on GitHub only), the payload lists only some of the pushed commits (GitHub lists at most 2048, Forgejo only the first few and the total), 3,000 or more files changed, or the forge’s files API returned an error or did not answer within 5 seconds. Unknown is not the same as an empty list. While the list is unknown, a when: that needs it counts as true, so the Run starts, and the Run’s activity log says why:

    To a when:, the field is always there and only its value is unknown, so has(event.changed_paths) is true either way and cannot test for an unknown list.

    The rest of the expression still decides when it can: event.branch == 'main' && event.changed_paths.exists(…) is false on another branch whether or not the list is known. A when: that does not read event.changed_paths is unaffected. The same rule applies to a step’s when:: a step that needs an unknown list runs.

    Forced-push detection is GitHub only: Forgejo’s push payload does not say whether a push was forced. For a forced push to Forgejo, the list holds the files of the commits the push added, not the files of commits it dropped.

    The list is not stored with the Run, and a template cannot read it: ${{ event.changed_paths }} is a compile error, because anyone who can push chooses the paths.

    Manual dispatch is opt-in: a pipeline is dispatchable from the UI/API only if it declares on: manual. The trigger context also feeds each run’s provenance and Headline (the trigger title shown against the run).

    Scheduled Runs: on: cron

    Section titled “Scheduled Runs: on: cron”

    on: cron starts a Run on a schedule. schedule: takes one cron expression or a list:

    A schedule has five fields, minute hour day-of-month month day-of-week, read in UTC. A field is *, a number, a range a-b, any of those with a step /n, or a comma-separated list. Months may be written jan-dec and days sun-sat; day-of-week 0 and 7 are both Sunday. When both day fields are set (neither starts with *), a day matches if either matches. The macros @hourly, @daily, @weekly, @monthly and @yearly are accepted too.

    The Pipeline check refuses a schedule that does not parse, that never fires (0 0 30 2 *), or that can fire less than 5 minutes apart (*/2 * * * *).

    A cron Run builds the head of the repository’s default branch. Its ref is refs/heads/<default branch>, so an Environment’s allowed_refs treats it as it treats a push to that branch, and its Headline is the schedule. when: applies, and the event context has event.schedule, event.branch, event.ref and event.sha. A cron Run has no launch inputs: every input the Pipeline declares needs a default, or the Run is refused.

    How a schedule is found and fired:

    • A push to the default branch records the schedules of every Pipeline file in it.
    • At each slot Scarab reads the default branch from the forge again, then its head, then the Pipeline at that head. The Run starts only if the Pipeline there still declares the schedule. A schedule removed, a Pipeline file deleted, or a default branch renamed takes effect at the next slot, even when the webhook for that change was lost.
    • A schedule added in a push whose webhook was lost is not seen until the next push to the default branch, or the next slot of another schedule in the same repository.
    • Each Pipeline gets at most one Run per minute, however many server replicas run and however many of its schedules name that minute. After the server was down, a missed slot fires once, not once for each slot it missed.
    • When the forge cannot be read within a minute after the slot (it is down, or it rate-limited Scarab), the slot is skipped. It is listed with the repository’s refused runs, as is a slot whose Pipeline no longer compiles.

    A repository’s Schedules tab lists each schedule with its next slot and the last one that fired, and links to the runs it started. On the Runs tab, the scheduled filter shows only those runs.

    After another pipeline: on: upstream

    Section titled “After another pipeline: on: upstream”

    on: upstream starts a Run when a Run of another pipeline in the same repository finishes. pipeline: names that pipeline: its name:, or its file name without .scarab/ and the extension. status: says which endings start it: succeeded (the default), failed, or a list of both.

    Use it to split a build from its deploy. In one pipeline, a deploy step makes the whole Run a Deploy Run, so a newer push no longer cancels its build (Deploys), and a rejected or expired deploy gate fails the Run the build is in. With ci on push and deploy on upstream, newest-wins still cancels stale ci Runs, and only the deploy Run waits for approval.

    The follow-up Run:

    • builds the commit the upstream Run built, and runs on its ref, so an Environment’s allowed_refs applies to it as it applied to the upstream. A follow-up of a pull request Run has the ref refs/pull/<n>/head; the when: above keeps deploy to the main branch.
    • has the upstream Run’s actor, and the Headline <pipeline> <status>, such as ci succeeded.
    • sees event.pipeline, event.status, event.run, event.ref, event.branch, event.sha and event.chain (the pipeline names that led to it) in when:. A template may read event.run, event.ref, event.branch and event.sha (Trigger values).
    • is cancelled by newest-wins as a push is: a newer follow-up of the same pipeline on the same branch or pull request cancels an older one still running, unless it is a Deploy Run or names an Environment.

    These start no follow-up:

    • a Run of a pull request from a fork;
    • a cancelled Run;
    • an ending of a Run that was rerun since. When the Rerun finishes, it starts the follow-up again.

    A pipeline already in the chain of Runs that led to it (a follows b and b follows a) is refused, and so is a follow-up of a chain 8 pipelines long. Both are listed with the repository’s refused runs. Only pipelines in the same repository can be followed.

    Commit statuses

    Section titled “Commit statuses”

    Each pipeline posts its own commit status to the forge, named scarab/<pipeline> (its name:, or its file name), so two pipelines on one commit do not overwrite each other. Two pipelines with the same name: share one status. A branch protection rule requires scarab/<pipeline> for each pipeline it waits for. A deploy pipeline whose Environment does not exist or does not admit the Project starts no Run, and its status is a failure that says why (see Environments).

    Interface: interface.inputs (and outputs)

    Section titled “Interface: interface.inputs (and outputs)”

    A pipeline declares its typed launch parameters under interface.inputs. An invoke caller fills in the same interface with with:, so launching and reuse share one contract. A bare string is shorthand for a required string; the map form sets the type, whether it is required, a default and a description:

    • type is one of string (default), boolean, number, choice. A choice needs a non-empty options list.
    • required defaults to true. An optional parameter (required: false) must carry a default, so every parameter always has a resolved value.
    • An optional validate: CEL predicate over the resolved value (bound as value) rejects a launch with a bad value (fail-closed).

    Resolved parameters are read in steps as ${{ inputs.<name> }} and are also injected into the step environment as SCARAB_PARAM_<NAME>. A choice, boolean or number parameter may be written into a command, as above; a string parameter reaches a step only through env: (see Values in commands and scripts). A library additionally declares the outputs it exposes to its caller, and inside a library ${{ inputs.<name> }} reads the caller’s with:, not the Run’s launch parameters (see Reuse: invoke).

    Steps: the step shape

    Section titled “Steps: the step shape”

    The step contract is an OCI image plus a command; everything else is a modifier. env is a list of [NAME, VALUE] pairs; artifacts publishes globs of files the step wrote to /scarab/artifacts/. A step names the secrets it needs with secrets: [KEY, ...]; each one is a file, /scarab/secrets/KEY (resolution, scoping and the env form are covered under Environments & gates).

    A step asks for privilege above the hardened baseline under security:. run_as_root is self-service (root inside the unprivileged sandbox, with its capabilities already dropped, does not escape it); add_capabilities and privileged are governed and take effect only if the environment whitelists the image digest.

    Without run_as_root, a step runs with runAsNonRoot and no user id of its own, so the image’s USER must be a non-zero number (USER 65532). The kubelet cannot check that a user name is not root, so an image whose USER is a name, such as curlimages/curl, fails to start with CreateContainerConfigError. The step fails as a configuration error whose message says to use a numeric user. Scarab does not override the image’s user: rebuild the image with a numeric USER, use an image that has one, or ask for run_as_root.

    Some steps are kinds with no image that the engine runs on your behalf (you set no image/command):

    • gate: manual: a durable approval/wait point (see Environments & gates).
    • invoke: file:.scarab/lib/...: reuse at compile time (see Reuse: invoke).

    Checking out the repository

    Section titled “Checking out the repository”

    Scarab’s clone library, lib:thulasi-ram/clone, checks out the Run’s repository at the commit the Run is pinned to. An org admin installs it like any other library; no org has it until then (Install Scarab’s clone library). On a Forgejo or GitHub token connection its source must also be trusted with forge credentials (see forge_token).

    depth is "1", a number of commits, or full. The library’s one step is checkout/git, and needs: [checkout] reaches it, so later steps inherit the checked-out workspace as usual. It works the same on GitHub and Forgejo.

    The clone step kind is gone. A clone: step fails the pipeline check with a message that names invoke: lib:thulasi-ram/clone.

    Building an image

    Section titled “Building an image”

    Scarab’s build library, lib:thulasi-ram/build, builds an image from the Run’s workspace with rootless BuildKit and pushes it when you ask. An org admin installs it and trusts its source for the build sandbox; no org has it until then (Install Scarab’s build library).

    The library has two steps, and needs: [image] reaches the second:

    • image/image builds. It runs BuildKit in the build sandbox and holds no registry credential. When the image is to be pushed, it writes the image as an OCI image layout to .scarab-build/oci in the workspace, after removing anything an earlier step left at that path. An image that is not pushed stays in BuildKit.
    • image/push needs image/image and pushes the layout with crane. It holds the registry credential, runs no code from your repository, and removes the layout from its own workspace when it is done, so a step that needs only image does not receive it. With push: false it exits without pushing.

    A step that reads outputs.image.image needs the build step too, and so receives the layout through the build step’s workspace. To deploy, read outputs.image.push.digest, which needs only the push step, or limit what the step receives with inputs:.

    The image travels from the build step to the push step through the workspace, so pushing a large image costs a transfer through the Data Depot. A build that does not push writes no layout.

    Its inputs:

    Input Default What it is
    image (required) The image reference to build, such as ghcr.io/acme/app:1.2.0. No ,.
    context . The build context, relative to the workspace. No absolute path, no .., no ,.
    dockerfile Dockerfile The Dockerfile, relative to the context, with the same rules.
    push false Push the image after building it.
    build_args empty Build arguments, one KEY=VALUE per line. No , in a value.
    cache none Where BuildKit imports and exports its layer cache: none or s3.
    cache_bucket empty For cache: s3, the bucket.
    cache_region empty For cache: s3, the bucket’s region.
    cache_name empty For cache: s3, the cache’s name in the bucket; BuildKit’s default when empty.
    insecure_push false Push over plain HTTP. For a test or development registry with no TLS only. crane then also skips TLS verification, so the push Step refuses it (exit 2) when it holds a registry login.

    Its outputs:

    • outputs.image.push is set only when the image was pushed: {"ref": "<repository>@sha256:…", "digest": "sha256:…"}, as crane reported the push. Deploy by this digest. When nothing was pushed (push: false, a fork pull request, or a Run locked out of its Environment’s secrets) there is no such result, and a step that reads it fails before it launches, so read it only where the image is pushed.

    • outputs.image.image is what BuildKit wrote with --metadata-file: a JSON object whose containerimage.digest is the digest of the image it built. crane pushes the layout’s manifest unchanged, so this is also the digest in the registry, unless the Dockerfile changed the layout after BuildKit wrote it (a RUN shares the build step’s Pod). In env: it becomes that object’s compact JSON text.

    • The registry credential. Only the push step asks for registry_auth: true. It receives a credential only when the org trusts the library’s source with the registry credential (Libraries); a step written in your Pipeline file never receives one. Each time it launches, Scarab resolves the REGISTRY_AUTH secret (Repo scope, then Org scope) and mounts it as /scarab/registry/config.json, with DOCKER_CONFIG pointing at that directory. It is never an environment variable, and Scarab replaces it with *** in the step’s log. With no REGISTRY_AUTH secret, the step gets the credential the forge derives for its own registry (GHCR, the Forgejo package registry), and only when the org also trusts the library’s source with forge credentials. With neither, the build still runs and pulls public base images, and the push fails at the registry. The build step never receives a credential: BuildKit runs without its process sandbox, so a RUN in your Dockerfile could read anything the build step holds. For the same reason the build step cannot pull private base images.

    • No registry cache. The library offers no cache: registry: writing a cache to a registry needs the push credential in the build step. The S3 cache is reached with the build Pod’s own identity, such as a ServiceAccount a placement profile sets; Scarab passes no credential.

    • A fork pull request, or a Run locked out of its Environment’s secrets, gets no registry credential, and Scarab sets SCARAB_FORK_PR=true on both steps, so the build exports no layer cache and writes no layout, and the push step pushes nothing, whatever push says. The build still imports the cache. No Pipeline or library may set SCARAB_FORK_PR.

    • Paths stay in the workspace. The inputs are checked against their rules when the Pipeline compiles and again when each step launches. The build step resolves the context and the Dockerfile and stops before BuildKit runs if either leads outside /workspace, through a symlink committed in the repository for example. The push step stops before crane runs if the layout leads outside /workspace or holds a symlink, or anything that is not a regular file or a directory: a step before it could plant a symlink to /scarab/registry/config.json, which crane would upload.

    • The sandbox. The build step runs as uid 1000, not privileged, with seccomp and AppArmor unconfined, which rootless BuildKit needs. Only a step from an installed library whose source the org trusts for the build sandbox gets it; a step written in your Pipeline file never does. A sandboxed step may not have secrets:. The push step runs in the default restricted Pod shape, as root, because crane’s image has no other user; an org Policy that denies run-as-root therefore refuses every Run that invokes the library.

    • Placement per step. A list in the invoke step’s placement_profiles reaches both steps. A map from the library’s step id to a list routes each list to its own step, so build-node placement and the S3 cache identity reach only the build step. An operator marks a profile that grants push access (a ServiceAccount with a push role, an init container that logs in) registry_auth_only. Scarab applies a marked profile only to a step with registry_auth that the launch found eligible for a credential, which here is the push step of a Run that is not a fork. Named on any other step it fails that step’s launch, so a list that holds one fails the build step: route it with the map form. On a fork’s push step it is left out, and the step pushes nothing.

    • Other architectures. BuildKit builds for the architecture of the node it runs on. Invoke the library once per architecture, each naming the profile for those nodes and pushing its own tag:

      Joining the tags into one multi-architecture image (crane index append, docker buildx imagetools create) pushes to the registry, so that step needs the registry credential too, which only a step from a trusted library receives. Scarab has no library for it yet; until it does, the join step comes from a library of your own whose source the org trusts with the registry credential. A list of profiles still reaches both steps, which a per-architecture build needs; keep the push profile in the map’s push entry.

    The build step kind is gone. A build: step fails the pipeline check with one error that holds its replacement, an invoke: lib:thulasi-ram/build step written from the old step’s fields. The local executor refuses the build library’s build step; it needs the Kubernetes executor.

    Forge credentials: forge_token

    Section titled “Forge credentials: forge_token”

    A step that needs to talk to the Run’s repository asks for a forge credential:

    Scarab mints the credential each time the step’s attempt launches, a rerun or retry included, and mounts it as two files: /scarab/secrets/forge-token and /scarab/secrets/forge-username. It is never an environment variable. When the attempt ends, the Kubernetes Secret that holds it is deleted, even if the Pod is kept, and a token GitHub minted is revoked, by whichever Scarab server sees the end.

    Whether a step may have one is decided when the Run is created; a Run that asks for more is refused with the reason. Each launch checks again, from the connection and the org’s trust as they are then: a step that may no longer have the token fails with the reason, and nothing is minted.

    • On a GitHub App connection, which mints a short-lived token for one repository, any step may ask. On a Forgejo or GitHub token connection, which hands out one long-lived token, only a step from a library installed from a source an org admin trusted receives it, and no source is trusted by default, Scarab’s clone library included (Libraries). A repository’s own steps never read that token. Such a step also starts with an empty workspace: no file another step wrote is present while the token is mounted.
    • The forge connection must be served over https://. A Run with a step that asks for forge_token on a connection whose base URL is http:// is refused: the token is never sent over plain HTTP.
    • A fork pull request always gets read, whatever the step asks for.
    • write needs a GitHub App connection, and a Run governed by an environment that restricts the refs it deploys from. Where that environment has approvers, put a gate: manual in the step’s needs.
    • The image and command of a step with forge_token are written out in full: a ${{ … }} in either is a compile error. An input, a result or an event value reaches the step only through env:, and only under a name of the form SCARAB_<NAME> (upper-case letters, digits and _) that Scarab does not set itself. Other names can make the value run as code: git runs GIT_SSH_COMMAND, and the loader reads LD_PRELOAD. A literal value may use any name.
    • A library input that reaches a step with forge_token must be a boolean, a number, a choice, or a string with a validate: rule.
    • A step with forge_token may not have a cache.
    • An invoke step’s placement_profiles is never carried onto a step with forge_token.

    The local executor refuses a step with forge_token; it needs the Kubernetes executor.

    The clone uses the forge connection’s token only for the repository being cloned, and only over https. Submodules are fetched without it, so a private submodule fails the step; make it public or vendor it. LFS objects come from the repository’s own LFS endpoint, and an lfs.url in .lfsconfig is ignored.

    Fan-out: matrix

    Section titled “Fan-out: matrix”

    matrix fans one authored step into the cartesian product of its dimensions, expanded statically at submit time. An exclude list of CEL predicates (evaluated against each combination’s own coordinate) drops combinations:

    Each instance gets a deterministic id like test[arch=amd64,os=linux], and a downstream needs: [test] fans in over every surviving instance.

    A matrix can have at most 65,536 combinations before exclude, and 256 exclude predicates. All the matrices of one pipeline, counting a library’s matrix each time the library is inlined, can have at most 1,048,576 combinations, and at most 262,144 exclude checks (combinations times predicates).

    Expression limits

    Section titled “Expression limits”

    Each CEL expression in a pipeline (a when: guard, a matrix exclude predicate, an input’s validate: predicate, or the inside of one ${{ … }}) can be at most 4096 bytes long, with brackets ((, [ and { together) nested at most 64 deep. Brackets inside string literals and // comments don’t count. A pipeline over either limit is rejected at submit time, and the error names the step, the field and the limit (the expression is cut short here):

    The CEL parser recurses once per nesting level and once per operator in a chain such as a + b + c, so these limits bound how much stack one expression can use on the server.

    Size limits

    Section titled “Size limits”

    A pipeline or library file can be at most 1 MiB, and the libraries one pipeline invokes can hold at most 16 MiB in all, each counted once however often it is invoked. The compiled pipeline can be at most 16 MiB of JSON: each step a library inlines stores the library’s inputs, and each matrix leg stores a copy of its step, so a small file can compile to a large pipeline. A pipeline over any of these limits is rejected at submit time, and the error names the file or step and the limit. The server also stops a compile that takes longer than 10 seconds, and the trigger fails with that reason.

    Reuse: invoke

    Section titled “Reuse: invoke”

    invoke inlines a library into the caller’s DAG at compile time; it is not a runtime call. The invoked steps are namespaced by the invoke step’s id (deploy/plan, deploy/url), and matrix on an invoke step fans out the whole subgraph.

    The target always has a prefix that says where it comes from:

    invoke: Target
    file:<path> a library file in the repository, read at the caller’s ref
    lib:<publisher>/<name> a library installed in your org
    plugin:<installation>/<gate> a gate a plugin installed in your org resolves (Plugin gates)

    A file: path is repo-relative: no leading /, no .., and no remote or cross-repo forms (a library from elsewhere is installed in the org and invoked as lib:). A bare path is a compile error that tells you to add file:, and url: is refused: Scarab does not invoke from a URL. A lib: target resolves to the version your org installed (Libraries); a name the org has not installed fails with “lib:<publisher>/<name> is not installed in this org”.

    A library is a YAML file marked kind: library. It has no on: triggers and never runs on its own: Scarab does not trigger it or list it for dispatch, even directly under .scarab/. It declares its contract with interface (the inputs it takes and the outputs it exposes) and the caller supplies inputs with with::

    The interface is checked at compile time: every required input present, no unknown extras, each value of its declared type, and every referenced output declared.

    Inputs are read at launch. Inside a library step, ${{ inputs.<name> }} in its image, command, env, when: and the with: of its own invokes reads the value its caller bound, so in the example above plan runs plan us-east-1. Inside a library, inputs never means the Run’s launch parameters, and reading an input the library does not declare is a compile error. A literal with: value is checked against the input’s type when the pipeline compiles. A with: value that holds a template, such as the caller’s ${{ outputs.<step>.<name> }}, is rendered in the caller’s scope when the library step launches, then checked against the input’s type and validate:. The inputs also reach each inlined step as SCARAB_PARAM_<NAME>.

    What the invoke step carries. An invoke step may set needs, with, matrix, when, deploy, timeout, resources and placement_profiles. Its timeout, resources and placement_profiles apply to each inlined step that leaves them unset (the library’s own value wins), and never to a gate. placement_profiles never applies to a step with forge_token. placement_profiles may be a list, which applies to every inlined step, or a map from a step id of the library to a list, which applies to that step only (placement_profiles: { image: [arm64], push: [ecr-push] }). A map key that is not a step of the library, or names a step with forge_token or with its own placement_profiles, is a compile error; a key naming a nested invoke applies to every step it inlines. Its when is ANDed with the when of every inlined step and gate. Any other field, env included, is a compile error on an invoke step.

    Installed libraries are closed. A lib: library may invoke only lib: and plugin: targets, never file:, so a repository cannot change the steps of a library its org installed.

    Every inlined step records where it came from in origin: the chain of libraries that produced it, outermost first, each with its kind, name and content hash (and, for lib:, the source it was installed from). Policies read it, so a library can be allowed or blocked through any depth of nesting. A library should pin its images by digest; scarab lint warns about a library image pinned only by tag.

    Results & interpolation

    Section titled “Results & interpolation”

    A step publishes named, typed results that a downstream step reads at launch via ${{ outputs.<step-id>.<name> }}; launch parameters are read the same way as ${{ inputs.<name> }}. Interpolation is resolved at launch time against the upstream step’s captured results, so a consumer must needs: the producer.

    Results are not artifacts. A result is a small typed value the DAG interpolates into a later step’s environment; an artifact is a file published from /scarab/artifacts/ that you download after the run.

    Publishing a result

    Section titled “Publishing a result”

    A step publishes result <name> by writing the file /scarab/results/<name>.json. The result’s name is the filename minus .json, and the file must hold valid JSON: "abc123" (quotes included) for a string, 42 for a number, never bare text.

    A step can also list the results it writes, with results: [tag, build]. The list is a declaration, not a filter: a step that declares nothing still publishes every file it writes.

    Beyond writing the file, capture needs no setup in the pipeline: on Kubernetes a trusted per-Pod egress sidecar drains the step’s results back to the control plane. The build library’s step publishes an image result (BuildKit writes --metadata-file /scarab/results/image.json); its caller writes nothing.

    The trap: a bare filename publishes nothing, and the step still goes green

    Section titled “The trap: a bare filename publishes nothing, and the step still goes green”

    The sidecar drains *.json files only. Writing a bare /scarab/results/tag, the obvious guess, publishes nothing: the glob matches no file, the sidecar logs only no results to drain, and the step still exits 0. The run goes green while ${{ outputs.version.tag }} silently resolves to empty downstream. Nothing tells the author they produced no result.

    So make the consumer check that its interpolation resolved. That turns the silent no-op into a failure where the value is used. The value goes in through env:, not into the script (see Values in commands and scripts):

    Values in commands and scripts

    Section titled “Values in commands and scripts”

    Scarab never puts a value from outside the pipeline into a step’s command, except a choice value the pipeline listed, true/false, a non-negative decimal number, a hex commit SHA, or the trigger kind; every other outside value reaches the step only as the value of an environment variable the pipeline named, passed byte for byte.

    A value is from outside the pipeline when it comes from a launch parameter (inputs in a pipeline file), a step’s results (outputs), a trigger event’s fields, or a library input whose caller’s with: reads one of these, through any number of callers. Literals, matrix values, a literal with: value and an input’s default are the pipeline’s own, and may go anywhere.

    To use a free-text value (a branch, a ref, a URL, a result) in a command, name an environment variable in env: and read it from the environment. In a shell, quote it:

    The fixed shapes may be written into a command, whole or inside an argument:

    Value Where it comes from What Scarab checks when the step launches
    a choice value an input declared type: choice the value is one of its options
    true or false an input declared type: boolean, or an expression over fixed values (${{ inputs.replicas > 3 }}) it is a boolean
    a number an input declared type: number, or an expression over fixed values (${{ inputs.replicas + 1 }}) it matches ^[0-9]+(\.[0-9]+)?$: no sign, no exponent
    a commit SHA ${{ event.sha }} it matches ^[0-9a-f]{40}([0-9a-f]{24})?$: 40 or 64 lower-case hex characters
    a pull request or issue number ${{ event.number }}, ${{ event.issue }} it matches ^[0-9]+$
    true or false ${{ event.fork }} it is a boolean
    the trigger kind ${{ event.kind }} it is one of push, pull_request, tag, release, comment, cron, manual, api, upstream

    The other event fields (ref, branch, tag, repo.owner, repo.name, repo.clone_url and run) are free text and reach a step only through env:.

    A library input counts by the type the library declares, so a library that takes a string input can use it in a command only through env:. A free-text value in a command is a compile error that names the step and the argument; for a library step it also names the library and the caller’s with: that binds the input. The step launch checks the same rule again, so a pipeline posted to the API without compiling cannot skip it. A value that does not fit its shape when the step launches (a number that turns negative, a choice value the pipeline did not list) fails the step before it starts.

    Why so strict: many programs read some of their arguments as code or as instructions. An argument that starts with - is an option (git fetch origin --upload-pack=… runs a command), @file reads a file, +ref force-pushes, and ssh, su -c and env -S join their arguments back into a shell command. A -- in front does not help either: it ends the options of one program, and the value can reach another one (sh -c '…' -- "$1", npm run lint -- …). No list of such programs can be complete, so Scarab does not keep one. The fixed shapes contain none of these forms. An environment variable’s value is not parsed by anything until your step reads it.

    In a script, any ${{ … }} becomes part of the code. This covers the script of sh -c (and bash, dash, zsh, ash, ksh), python -c, node -e, perl -e and ruby -e, also behind env, busybox, timeout, nice, nohup, stdbuf, setsid, sudo and exec. A value from outside the pipeline in a script is a compile error, fixed shapes included; a value written in the pipeline is a lint warning. Pass the value in env: and read it as "$VALUE".

    What stays your responsibility: once a step reads an environment variable, Scarab no longer sees it. An unquoted $REF, eval "$REF" or ssh host "git checkout $REF" turns it back into code. Quote it, and pass it to programs as one argument.

    Trigger values: event

    Section titled “Trigger values: event”

    A template can read the trigger’s values through ${{ event.<field> }}, in a pipeline file and in a library. Only fields whose values Scarab can check are readable:

    Field Value In a command
    kind the trigger kind yes
    sha the commit, 40 or 64 hex characters, where the trigger has one yes, lower-case hex only
    number, issue a pull request or issue number yes
    fork true for a pull request from a fork yes
    run the upstream Run’s id no, env: only
    repo.clone_url the repository’s clone URL, from its forge connection no, env: only
    repo.owner, repo.name letters, digits, ., _ and -; no leading -, not . or ..; at most 100 bytes no, env: only
    ref, branch, tag letters, digits, ., _, /, @ and -; no leading -, no .. or //; at most 255 bytes no, env: only

    The last column is the command rule: a field marked yes may be written into a command and is checked against its shape again when the step launches.

    repo.clone_url is at most 2048 bytes, run 64 and kind 32.

    actor, a comment’s body, schedule and changed_paths are not readable, and neither is ${{ event }} as a whole: each is a compile error. The same holds for a concurrency.group, which renders against the same checked values. A group reads only inputs and event: it is fixed when the Run is created, before any step has run, so reading outputs is a compile error. A when: still sees the whole event.

    The values are checked and stored when the Run is created, so a rerun reads the same ones. A pipeline that reads a field the trigger does not have, or one whose value fails its check, is refused: a push to fix;rm refuses a pipeline that reads ${{ event.branch }} (“branch name contains ;”), and runs every pipeline that does not.

    Environments & gates

    Section titled “Environments & gates”

    This section covers only the YAML you author. For the concepts behind them (how secrets are stored and scoped, and what an environment governs), see Secrets and Environments.

    A top-level environment: puts the pipeline’s runs under that environment’s governance: they are checked against its protection rules at admission, get its scoped secrets, and are never cancelled by newest-wins. It does not mark them as deploys; for that, see Deploys: deploy: true. Secrets a step needs are named with secrets: [KEY, ...]; each key is resolved against the run’s scope (a run from a fork’s pull request is locked out and receives none).

    Each secret is a file, /scarab/secrets/KEY, on a read-only in-memory volume in the step’s container; $SCARAB_SECRETS names the directory. The values come from a Kubernetes Secret for the step’s Pod, deleted when the step’s attempt ends. The local executor has no container: it writes the files to disk, in a directory under the step’s working directory that only its own user can read, sets $SCARAB_SECRETS to that directory, and removes it when the step’s process ends.

    A secret is not an environment variable unless its entry says so: write { name: KEY, env: true } in the same list, and the step also gets the environment variable KEY. Kubernetes fills that variable from the Pod’s own Secret, so the value is never written into the Pod spec. Prefer the file: every process the step starts inherits its environment, and many tools print their environment when they fail.

    A secret’s name is its file name: letters, digits, -, _ and ., not starting with .. forge-token and forge-username are taken by the forge credential. A name with env: true must also be an environment variable name, and not one the step’s env: or Scarab already sets. scarab validate warns when a step’s command reads $KEY or ${KEY} for a secret listed without env: true, since that variable is empty when the step runs. It reads only the step’s command: a script file the command runs is not checked.

    Gates are durable suspend points with no image: gate: manual is an approval, gate: timer waits gate_after seconds, gate: external releases via API/webhook. Placed before a deploy step, a manual gate is the approval mechanism for a governed environment:

    Any gate can fail with a reason: by expiry, by a human reject, or by an external gate released with {"passed": false, "reason": "..."}. A waiting gate holds only the steps that depend on it, and each gate has its own clock, measured from when its needs finished.

    Plugin gates

    Section titled “Plugin gates”

    A plugin installed in your org with the resolve_gates capability declares gates in its manifest. A pipeline waits on one with invoke: plugin:<installation>/<gate>:

    This inlines one gate, gate: plugin, with the invoke step’s id. Only the installation it names can release it. with: is checked against the gate’s declared inputs when the pipeline compiles, and a value that reads an upstream output is rendered once, when the gate is reached. A value that does not render fails the gate with the reason. The inputs are sent to the plugin, so with: cannot read secrets or env, and an upstream output it reads must be one that step declares; each is a compile error. gate_expires_after is required, at most 2592000 seconds (30 days): a gate the plugin never answers fails when it expires. Anyone with write access to the project can reject it sooner.

    The plugin releases the gate with the outputs it declares, each of its declared type, and a later step reads them as ${{ outputs.<gate>.<name> }}. They are values from outside the pipeline, like a step’s results: the same command and script rules apply to them. A plugin never approves a gate: manual, and it cannot see or release a gate in another org or one another installation releases.

    No plugin’s gates run until an org admin lists the installation in the plugins_allowed setting.

    Deploys: deploy: true

    Section titled “Deploys: deploy: true”

    deploy: true marks the runs that deploy. Set it on the pipeline, and every run of it is a deploy run:

    Or set it on the one step that deploys. The step is marked on the run page, and its run is a deploy run:

    The mark is separate from environment:. A deploy needs no environment, and a run in an environment need not deploy. A gate cannot be marked.

    A deploy run differs from other runs in two ways:

    • It is never cancelled by newest-wins. A newer push to the same branch does not cancel it half-way, and its concurrency group queues even if the pipeline declares concurrency: { group: ..., policy: cancel-in-progress }. A run that names an environment behaves the same way.
    • You can filter for it. The Runs tab has a deploys toggle and an Environment filter, and the API takes the same filters: GET /v1/repos/{org}/{repo}/runs?deploy=true&environment=production. Both are applied in the database query, so a page holds the newest matching runs, not the matches among the newest page.

    A deploy run’s green means only that its steps succeeded. With GitOps, the deploy step’s success means its change merged into the gitops repository; the CD tool applies it later, and the rollout can still fail. To keep the run open until the change is live, add a step after the deploy step that waits for it. Deploying with Argo CD has a recipe. Scarab keeps no record of the deploy after the run ends; the CD tool’s UI is where you see what is live.

    To keep two runs from deploying one service at the same time, give the pipeline a concurrency group, for example concurrency: { group: deploy-prod-payments-api }. A group holds the whole run, and it is scoped to the repository, so two repositories that deploy one service do not wait for each other.

    deployment_requests and gate: deployment are gone

    Scarab 0.2 had a Deployment record: a step field deployment_requests and a gate: deployment that waited for a CD tool to report the change live. Both were removed (ADR-0074). A pipeline that still uses them fails the pipeline check; replace the gate with a wait step as shown on Deploying with Argo CD.

    Placement & resources

    Section titled “Placement & resources”

    By default steps land on the operator’s default placement profile. An author targets scheduling by naming profiles (never raw Kubernetes) via placement_profiles, and requests exact compute with resources:

    For a rare dynamic per-job Kubernetes need there is a governed k8s_overlay escape hatch: a raw pod-spec fragment merged last onto the Pod. Writing one grants nothing by itself: it is admitted only if the run’s target environment permits raw overlays; otherwise the run is rejected (fail-closed). Prefer a named profile for anything static. Even where raw overlays are permitted, an overlay cannot set or delete the Pod’s metadata.name, generateName, namespace, ownerReferences or finalizers, or labels and annotations under app.kubernetes.io/, scarab.io/ or scarab.dev/: Scarab uses them to find, route to and clean up the Pod. Apart from Scarab’s own containers, volumes, mounts and env (below), the rest of the Pod spec is not checked. An overlay can ask for privileged containers, host mounts, the host network, or a ServiceAccount token. Step Pods run in Scarab’s own namespace by default, so that can be Scarab’s ServiceAccount. Permit raw overlays only on an Environment whose pipeline authors you trust with that.

    The operator’s baseline, each named profile in the order you list them, and then the k8s_overlay are merged onto the Pod one after another, with a Kubernetes strategic merge:

    • Objects merge key by key, and a null deletes a key.
    • Lists Kubernetes merges by a key are merged item by item: containers, initContainers and ephemeralContainers by name; in a container, env by name, volumeMounts by mountPath, ports by containerPort and volumeDevices by devicePath; volumes and imagePullSecrets by name; hostAliases by ip; topologySpreadConstraints by topologyKey and whenUnsatisfiable. An item with a new key is appended.
    • tolerations add up: a profile’s tolerations are appended to the baseline’s, and a toleration already on the Pod is not added twice. Kubernetes replaces this list; Scarab does not, so a profile cannot drop the baseline’s tolerations.
    • Every other list replaces, as in Kubernetes. Node affinity terms are one of them.

    So an overlay can change one field of the step container and keep the rest:

    The step container is the only container Scarab adds that a profile or overlay may name. The results sidecar (scarab-results-egress), the workspace containers (scarab-workspace-init, scarab-workspace-egress) and service sidecars (service-0, service-1, …) carry Scarab’s own wiring. If the baseline, a profile or an overlay names or removes one, Scarab does not create the Pod, and the launch error names the container and the layer. A container with a new name, such as an extra init container, is allowed.

    Scarab’s volumes, mounts and env are guarded the same way. A layer may not:

    • name, remove or replace a volume Scarab created (results, workspace, forge token, registry auth, OIDC token, secrets), or mount one in a container it adds or at a new path on the step container;
    • change a mount Scarab set on the step container, such as /workspace (/workspace/ and //workspace count as the same path);
    • set or remove an env variable the step container was built with, such as SCARAB_ATTEMPT or one from the step’s own env:.

    A volume with a new name, a mount at a new path and an env variable with a new name are allowed. Kubernetes’ patch directives ($patch, $retainKeys and other keys starting with $) are not supported: a layer that uses one is refused.

    Step Pods, service Pods and debug Pods do not mount a Kubernetes ServiceAccount token (automountServiceAccountToken: false), so code in a step cannot call the Kubernetes API with the namespace’s default ServiceAccount. A step that needs the API names a placement profile that sets both serviceAccountName and automountServiceAccountToken: true.

    An operator marks a profile registry_auth_only: true when it grants push access to a registry (a ServiceAccount with a push role, an init container that logs in). Scarab applies such a profile only to a step with registry_auth that the launch found eligible for a registry credential: a step from a library your org trusts with the registry credential, in a Run that is not a fork pull request or locked out of its Environment’s secrets. It applies whether or not a credential resolves, so a profile that logs in itself works with no REGISTRY_AUTH secret (Pushing images to Amazon ECR). Named on any other step it fails that step’s launch; on a registry_auth step the launch did not find eligible it is left out. A marked profile cannot be the default (Building an image shows the map form that routes one to the push step).

    Retries, timeouts & reruns

    Section titled “Retries, timeouts & reruns”

    A step may set a timeout: (seconds) and an opt-in retry: policy. Retry is at-least-once: by declaring it, you assert that the step is idempotent or fenced; a side effect that is neither will fire twice.

    The timeout counts from when the step’s process starts running. Waiting for a node, pulling the image and fetching the workspace do not count against it. They have their own limit of 30 minutes: a step that has not started running by then fails as never started, with a message saying so, and is retried automatically.

    Re-execution that a person starts is modelled as Takes: a rerun re-executes a run from the top, a retry resumes from a failed step, and an earlier attempt becomes superseded or shadowed by the newer one. The UI shows these in a run’s history. You don’t write anything for them.

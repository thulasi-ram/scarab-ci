Design artifact · run detail

Blueprint-first layout

The DAG is Scarab's differentiator, but today it's boxed into a third of the run-detail width and a fixed height — a real 10-step pipeline with a services lane can't be seen at once. This proposes making the blueprint the primary, pannable canvas with evidence in an on-demand drawer. Recommendation A — with B rendered below for a side-by-side comparison.

1 The problem

The run detail crams three things across one row — the versions rail, the blueprint, and the evidence pane. The blueprint, the one view that's inherently 2-D and unbounded, loses: ~⅓ width and a capped height, so fans scroll sideways and the services lane sits off the top.

Today cramped

rail │ dag (½) │ logs — the graph shows ~2 nodes before it scrolls; the postgres node is unreachable without fighting the scroll.

Goal

The blueprint reads at a glance (services + fans + gates), and evidence gets a wide, focused column exactly when you want it.

2 Proposal A — full-width canvas + evidence drawer recommended

The blueprint takes the full content width and becomes a proper graph canvas (pan / zoom / fit-to-view / minimap). Click a step and a resizable drawer slides in from the right with its evidence; dismiss it and the whole graph is back.

3 Proposal B — stack (blueprint on top, evidence pinned below)

Both surfaces get the full width and stay visible — no drawer to toggle (the GitHub-Actions shape). It only pays off if the blueprint is re-oriented left→right so depth runs along the wide axis and the fan stacks within the band's height. That re-orientation — flipping the flow + the edge routing — is the real cost, and it's bigger than A's additive drawer.

4 A vs B — the call

A · canvas + drawer recommended

Blueprint is the hero (full canvas + pan/zoom); evidence on demand in a wide drawer. Additive change. Cost: logs aren't pinned — mitigated by auto-opening for the running step.

B · stack

Both pinned, full-width, no toggle. Cost: only worth it with the DAG re-oriented left→right (flow + edge-routing rework).

  • I still lean A. The blueprint is Scarab's differentiator — it earns the hero surface, and pan / zoom / fit future-proofs any pipeline size.
  • A is the smaller, additive change (a drawer + canvas controls) vs B's flow re-orientation.
  • Reach for B only if pinned-always logs during live runs matter more to you than a big, uncluttered graph.

Rejected — modal / Miller columns

A modal fully occludes the graph (the point of a blueprint is keeping the shape in view). Miller columns model hierarchies (folder→file); a DAG isn't one, so column-1 would flatten the graph into a step list and throw away the 2-D layout.

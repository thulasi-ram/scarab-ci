Scarab — Context & Ubiquitous Language

The thesis, the durability contract, and the ubiquitous language.

Scarab is a forge-native CI engine for Kubernetes, built on a durable core — written in Rust. The field splits in two: durable workflow engines (Argo, Tekton, Temporal) that aren’t CI, and forge-native CIs (GitHub Actions, Woodpecker) whose orchestrator is a job runner. Scarab is designed to be both — a cohesive forge-native CI on a crash-safe state machine (Postgres; the DBOS/Temporal pattern).

Thesis: A run is durable state, not a fire-and-forget process.

Architectural wedge vs public headline: durable execution is the architectural wedge — the hard core every ADR is judged against (ADR-0001). It is not the public headline: it’s table stakes against Argo/Tekton/Temporal, so we sell cohesion (forge-native product on a durable engine), not the bare word “durable”. Taglines, the AI-era angle, the Woodpecker lineage, and the honest red lines live in docs/positioning.md. This doc is the internal anchor.

This document is the anchor for the codebase: the ubiquitous language every crate, API, ADR, and UI view must use, plus the system overview and non-goals. If a term here conflicts with a name in code, the code is wrong. Decisions are recorded as ADRs in docs/adr/.

The name: the working directory is historically scrarab-ci, but the product, crates, CLI, and env prefix are all scarab (SCARAB_*, scarab, scarab-*). The scarab is the Egyptian symbol of resurrection and of rolling the ball uphill — apt for a CI whose wedge is resurrecting crashed runs and rolling builds durably forward.

1. The wedge (why Scarab exists)

Section titled “1. The wedge (why Scarab exists)”

Durability is the differentiator. Everything else — forge integration, k8s-native execution — is a means, not the point. Because the orchestrator is a crash-safe, resumable state machine, the following are derived properties rather than bolted-on features:

  • Resume a pipeline after a control-plane crash/failover — from the last durable state.
  • Rerun a single step — it is a re-creatable, individually-addressable object.
  • Time-travel — inspect the DAG/logs as they were at any point.
  • Suspend indefinitely on a gate (human approval, timer, external event) — for seconds or for weeks — at nearly zero cost, because state lives in Postgres.

2. The durability contract (read this twice)

Section titled “2. The durability contract (read this twice)”

Durable execution here means a durable orchestrator, not replayable step interiors.

  • Durable & exactly-once: the DAG state machine — which steps ran, their exit codes, their output manifests — and the append-only event log.
  • Not replayable: the interior of a step. A step is an opaque black box (docker push, terraform apply) that is re-executed wholesale on restart.
  • Execution guarantee: at-least-once per step. Idempotency of external effects is a step-author contract, for which Scarab provides tooling (content-addressed skip, fencing tokens), not a magic promise. See ADR-0021.

3. Non-goals (what Scarab deliberately is NOT)

Section titled “3. Non-goals (what Scarab deliberately is NOT)”
  • Not multi-backend. Kubernetes is the only execution substrate. No Docker-socket, local, or SSH backends. (This — not “does many things” — is the “Woodpecker baggage” we shed.)
  • Not a hostile-tenant public SaaS (v1). Soft multi-tenancy (orgs/repos/teams under RBAC, namespace-per-run) only. gVisor/Kata hostile isolation is deferred.
  • Not a general durable-execution engine. We own a bounded CI state machine on Postgres (the “DBOS pattern, in Rust”), not a Temporal/Restate-style generic engine.
  • Not forge-coupled for identity. IAM is forge-agnostic (OAuth/OIDC + Scarab-native RBAC).
  • Not a replay-of-step-logic system. No deterministic replay of user shell.

4. Ubiquitous language

Section titled “4. Ubiquitous language”

4.1 Definition plane (authored, in-repo, declarative)

Section titled “4.1 Definition plane (authored, in-repo, declarative)”
Term Meaning
Pipeline Top-level authored unit: a flat recursive DAG of Steps. Lives in-repo (.scarab/), read at the triggering ref, compiled to IR.
Step The atomic unit and the Pod boundary. An OCI image + command + I/O convention. The unit of re-execution.
needs A dependency edge between Steps. Parallelism is emergent from the DAG (anything not transitively dependent runs concurrently).
invoke A built-in Step kind that references another Pipeline in the same Run. Compile-time inlining, not a runtime object (ADR-0025): the referenced Pipeline’s Steps are flattened into the caller’s DAG, id-namespaced by the invoke-step id (deploy/build). Composition = recursion; replaces “reusable workflows” and “composite actions”. A “job” is a named subgraph — sugar, not structure.
Library pipeline A Pipeline authored under .scarab/lib/ that exists to be invoked, not triggered. Referenced by repo-relative path, read at the caller’s ref (atomic git versioning; no registry, no semver). Out of trigger discovery by convention (subdir) and by carrying no matching on:.
Matrix An orthogonal modifier on a Step: expands to N instances (cartesian product) at submit time (static in v1). Applied to an invoke step, it fans out N copies of the whole referenced subgraph — “run this reusable subgraph once per coordinate”.
Trigger (on:) What starts a Pipeline: push, pull_request, tag, release, comment-command, cron, manual, api, upstream. Matched against the normalized Event via CEL.
Gate A built-in Step kind: a durable wait point awaiting human approval, a timer, an external event, or a Deployment (DeploymentGate). Resolves passed or failed with a reason — a failed Gate skips its dependents and fails the Run (failure class gate, never auto-retried). Any kind can fail: by expiry, by a human reject with a reason (POST /v1/runs/{id}/gates/{step}/reject), by an external gate’s token /release with passed: false, or, for a DeploymentGate, by core. A waiting Gate holds only the Steps that depend on it; the Run suspends only when nothing else can run (so waiting bills no Run budget). Each wait is an Attempt: once every need has succeeded, core opens a running Attempt while the Gate Step itself stays Pending. Each Gate has its own wait clock — the latest finish of its needs (or its own latest re-arm, if later), frozen on that Attempt’s start, evaluated whether the Run is running or suspended — never a Run-level clock; timer and expiry both measure from it. A Gate is approved, released or rejected only once reached, and approvals count per wait. A verdict is final per Attempt — journaled once, as GateResolved, when first reached: a Retry of a failed Gate is a new Attempt that waits afresh (a rejected approval asks again).
Service A Scarab-provisioned backing container (db/redis/etc.) a Pipeline needs at runtime, in one of two forms — Sidecar service or Shared service (ADR-0058). Never a needs-able DAG node: a Service is infrastructure for Steps, not a Step (it has no id to depend on, no exit code, no Attempt/evidence of its own).
Sidecar service The default form: a throwaway container co-located inside the declaring Step’s Pod, reachable at localhost:<port>, alive only for that one Step’s execution. Fenced by inheritance — shares the Step’s Attempt identity and teardown, no cross-Pod networking, no k8s Service object. The common case: one test Step + a throwaway DB. Two Steps that each declare Postgres each get their own.
Shared service The opt-in form: a Run-scoped standalone Pod with a cluster DNS name, reachable by the Steps that opt in, torn down when the Run (that Take) ends — riding namespace-per-run teardown, not a refcount. A fresh instance per Take: a Rerun’s Take gets a new instance keyed by {run, take} and never sees the prior Take’s writes (Takes are independent — ADR-0056). Unfenced external mutable state: intra-Take idempotency across auto-retries and parallel writers is a step-author contract (ADR-0021), exactly as for any other external effect — Scarab does not fence it.
clone A built-in Step kind: forge-aware checkout (ADR-0008, 0045). Runs git in a restricted Pod, pinned to the resolved commit SHA, producing the Run’s workspace root that downstream Steps inherit via needs. Zero-config — repo/ref/SHA/token are implicit from the Run’s trigger context; depth/submodules/lfs/ref are optional. Authored explicitly (no implicit checkout); a push/pull_request Pipeline with no clone step is a lint warning, not an error.
Environment An org-level place deployments land in (staging/prod), with protection rules — its baseline: approvers, wait timer (carried and merged but not enforced — git-bug 2b94989), allowed refs, require_reason, the EnvironmentDeploymentDeadline, and concurrency (per DeploymentTarget, deployment_concurrency: at most N Runs in flight requesting one target — a Run counts from its deploy Step’s promotion to Ready until that request’s DeploymentGate has a verdict, or until the Step finishes if no DeploymentGate waits on it; a DeploymentGate not yet reached stops counting once the Environment deadline has elapsed since the requesting Step’s latest Attempt started (the one that succeeded, where the gate’s first wait opens — not the request’s earlier effective time), so opposite-order holds cannot deadlock; the hold is decided per Step at Pending → Ready; it counts Runs, not Deployments, since two Runs requesting one version join one Deployment. A deploy Step at the limit is held Pending at the point of use, never rejected, and its Run may suspend; a count that cannot be decided holds it (fail closed). Never an org-wide serialisation; unset = no limit). The OIDC subject is not the Environment’s: it is still minted per repo from the Run’s coordinates. Owns the DeploymentTargets in it and the Deployments to them, so “what’s live in prod” is one org-wide answer. Which Projects may deploy into it is its EnvironmentProjectEligibility; which sources may report into it, its EnvironmentDeploymentSources. Administered by org admins today — RBAC has no scope finer than Project. An unknown name is refused (fail-closed) — a pipeline’s environment: must name an existing org Environment that admits the Project. Administer on that Environment, an RBAC scope of its own so prod can be delegated (e.g. to a platform team) without org admin, is MLP, not built. (Was per-Project under ADR-0037; the migration keeps what every visible Run does — each old per-repo rule set, require_reason included, becomes that Project’s EnvironmentProjectOverlay over an initially permissive baseline; a name only ever referenced, never defined, gets eligibility all projects; concurrency migrates unset, since the stored 1 was a UI default nothing read. The migration sees only the database — legacy rows and the Runs that happened, never pipeline YAML — so two never-seen cases are now refused where they were admitted: a name no Project defined and no Run used (unknown Environment — an org admin must create it), and a Project that names an Environment another Project defined but never ran a deploy into it (not eligible — an org admin must add it). ADR-0071 §10.)
EnvironmentProjectEligibility The set of Projects an Environment admits Deploy Runs from: all projects, or an explicit list (project-name globs allowed). Owned by the Environment, never the Project — the YAML environment: is the request, eligibility is the authority. A new Environment starts with no eligible Projects (fail-closed). Checked at Run creation, before any Pod or secret — and again at the point of use: a manual or external gate does not release (409) for a Project no longer eligible, and every launch of a Deploy Run’s step is re-admitted — refused, the step fails Config with the reason, before any secret, OIDC token or privilege grant is used (timer gates are covered by this launch check). A refused webhook deploy is named in the delivery body. Avoid: bare “eligibility”, opt-in.
EnvironmentProjectPrivilegeGrant The privilege whitelist (which image digests may use which governed Grants, ADR-0039) and the raw k8s_overlay permission (ADR-0055), granted to one Project within one Environment by the Environment’s admin — never to the Environment as a whole, so one team’s privileged image never becomes another’s. Today that admin is an org admin: a Project’s own admins can no longer grant privileges (they could under ADR-0037).
EnvironmentSecretScope / EnvironmentProjectSecretScope The two Environment secret scopes: org-wide for an Environment (shared by every eligible Project’s Deploy Runs), and one Project within an Environment. Resolution, most specific first: EnvironmentProjectSecretScope → EnvironmentSecretScope → Project → Org — an Environment-specific value always beats a generic one.
EnvironmentProjectOverlay A Project’s tighten-only layer over an org Environment’s protection rules — approvers accumulate; a ref must match the baseline and match the overlay (empty list = any ref; never a list intersection, which fails open); require_reason holds if either sets it; the stricter timer/concurrency wins; a tighter deadline applies only to that Project’s DeploymentGates (a Deployment’s status uses the baseline deadline). A Project can make its deploys stricter than the org’s baseline, never looser. Absent = the baseline applies as-is. Written by that Project’s admins (or an org admin), only for an Environment the Project is eligible for or already holds an overlay in; it pins the Environment against deletion.
Grant A named, closed-vocabulary escalation above the hardened “restricted” step baseline (ADR-0039). run-as-root (self-service — does not escape the sandbox); add-capabilities and privileged (governed — require an EnvironmentProjectPrivilegeGrant keyed on the image digest, Administer-only). Requested by the pipeline author, granted by the Environment admin, admitted fail-closed. A grant is a ceiling, not a default.
placement_profiles A Step field (ADR-0055): a list of PlacementProfile names. Their admin-defined k8s overlays are merged (in listed order) onto the Step’s Pod; empty → the default profile. The author names profiles, never raw k8s → no topology/k8s leak. Sibling of resources (exact cpu/memory — no size tiers, ADR-0055).
PlacementProfile An operator-owned, cluster-scoped named bundle (ADR-0055) mapping a name → concrete k8s Placement (nodeSelector/tolerations/runtimeClass/annotations — an opaque overlay, not a fixed schema). Lives in Scarab operator config (gitops), not per-Project. One may be default. It is where a Step lands — not an Environment (deploy governance), not settings of a Run (a Pipeline instance). Composed atop the control-plane placement baseline (default tolerations/nodeSelector/resources stamped on every step Pod).
RetentionProfile An operator-owned, cluster-scoped named bundle (ADR-0065) mapping a name → a retention policy: the Data Depot’s space budget, per-class TTLs, which directories are Cache-eligible, and the thresholds at which a Snapshot is dropped in favour of re-deriving it. Lives in Scarab operator config (gitops), not per-Project. A Pipeline may name one; it never defines the values — so no byte cost enters authored YAML. Deliberate sibling of PlacementProfile: same pattern, different axis (how long things are kept vs where a Step lands). Composed with ADR-0061’s manual pin (“keep this Run’s workspaces”), which is the per-Run escape hatch for investigations.
k8s_overlay A Step’s governed escape hatch (ADR-0055): a raw pod-spec fragment merged last onto the Pod. Carries no authority — like a governed Grant, it takes effect only if the Run’s Environment permits raw overlays, else the Run is rejected fail-closed. The k8s_ prefix marks the backend-coupling (won’t run on the local executor). For the rare dynamic per-job k8s need; static placement belongs in a PlacementProfile.

4.2 Data plane (nine distinct concepts — never conflate)

Section titled “4.2 Data plane (nine distinct concepts — never conflate)”
Term Scope Lifetime Purpose
Parameter launch-time input, supplied from outside the run resolved once at launch, then persisted for the run’s life a typed value a launcher supplies to start a Pipeline. Declared in the Pipeline’s interface.inputs; each is required (static bool) with an optional default and optional validate: CEL predicate. Supplied by a human/API on a manual/api launch and by an invoke: caller’s with: — one declaration, one env rail (SCARAB_PARAM_<NAME>), one launch-time CEL binding ${{ inputs.<name> }}. Not the per-Step workspace inputs: (ADR-0007), which is a different concept sharing the word.
Workspace one Step’s execution ephemeral (dies with the Attempt) the mutable filesystem a Step executes in. A Step may write anywhere in it; nothing outside the Step reads it directly. Where its bytes live is not part of the concept — they may sit on the Pod’s node, on the workspace service, or be split across both (ADR-0061), and a Step cannot tell which. The Workspace is the view a Step executes against; it never outlives the Attempt.
Workspace Snapshot intra-run, flows along DAG edges retained per policy, then archived, then gone (ADR-0061) the immutable, content-addressed tree (per-file merkle CAS) that crosses a DAG edge and that an Attempt owns as evidence. Implicit-by-default (inherit needs), explicit-on-demand (inputs:/outputs:). Two coordinates, never conflated: the snapshot root is where the bytes are — the address a Step materialises, GC marks from, and an Attempt records; the content identity is what the bytes are — the same merkle fold with mtimes dropped, which is what restart invalidation compares (ADR-0027, 0061 s8). A root moves when a file’s mtime moves and an identity does not, so only the root is an address: nothing is stored under an identity and nothing can be fetched by one.
Workspace Export one Attempt dies with the Attempt; reaped, never archived the delivered form of a Workspace: a per-Attempt, writable, network-mounted view of one Workspace Snapshot that a Step Pod receives as its Workspace (ADR-0062). Distinct from the Snapshot it is a view of, and the distinction has consequences: losing an Export fails that Attempt, which retries; losing a Snapshot widens a rerun’s scope (ADR-0061 retention). Its address is a capability — unguessable, TTL’d to the Step deadline, client-pinned — not a name, because the mount protocol cannot carry a per-Step identity.
Change set one Attempt derived; folded into a Snapshot, then discarded the set of paths an Attempt wrote — what the drain hashes, and the reason it need not re-read an unchanged tree. Known where the Attempt had a Workspace Export: the overlayfs upper layer is the kernel’s own record of what was touched (ADR-0062), so it is exact and rests on nothing. Derived where there was none (the local executor): each file’s (size, mtime, ctime) compared against the input manifest. The derived form is sound but conditionally — it assumes ctime cannot be forged (no syscall sets it), a capture stamped after materialisation completed, a filesystem whose ctime is not coarse, and a Step that cannot move the clock back. (size, mtime) alone is not sound: cp -p, touch -r and tar -xp defeat it deterministically, not as a race.
Result intra-run, flows along DAG edges ephemeral small typed values (a version, a bool) for params/conditionals. No bytes anywhere — the value is JSONB in Postgres (attempts.results); nothing is stored in the CAS or the object store. Interpolated as ${{ results.<id>.<name> }} (ADR-0041, renamed from outputs. — see outputs: below).
Artifact output of record retained (TTL), downloadable, UI-visible binaries, reports, coverage, images. Bytes in the object store; Postgres holds only metadata. Immutable per Attempt — a retry never overwrites a prior Attempt’s version; the name-addressed record resolves to the latest successful Attempt’s version.
Cache cross-run best-effort, evictable ~/.cargo, node_modules — author-declared directories under a key (e.g. a lockfile hash), restored at Step start and saved at Step end (ADR-0065). Stored as a content-addressed tree, so it rides the same Farm/Export machinery as a Snapshot and materialises lazily. Not correctness-critical and never evidence — which is what puts it outside the durability rules. A keyed directory cache, never a shared mutable mount: two concurrent Runs writing one node_modules is corruption.
outputs: a Step field — the workspace-relative paths a Step publishes downstream (ADR-0007) — bytes on a filesystem, narrowing what flows along an edge. A precision tool for cache keys, safe fan-out and remapping; never something an author declares for speed (ADR-0007 amendment, ADR-0065). Not a Result: until 2026-07-28 the Result interpolation namespace was also spelled outputs.<id>.<name>, so one word named both a list of file paths and a namespace of typed scalars. The namespace is now results. and this term means paths only.
Step logs one Attempt own retention class, long TTL an Attempt’s stdout/stderr. Bytes in the object store, keyed {run, step, attempt} and not in the CAS — content addressing buys nothing for an append-only stream (ADR-0063, amended 2026-08-23). Postgres holds byte offsets only, never bodies. The Data Depot may cache log chunks for a fast live tail, but its copy is never authoritative — logs are the one class that cannot be re-derived, so the Depot, being definitionally a cache, may not be their home. The one class that cannot be re-derived: re-running a Step yields different logs, so eviction here is real loss, not a latency event — hence pinned until a durable sink acknowledges them, and when the bytes are gone for any reason at all, said so out loud — absence is authoritative and the eviction record only explains it, because a lost volume was evicted by nobody. External log systems (Loki, VictoriaLogs) are additional sinks, never the system of record.

4.3 Run-time / instance plane (what the durable engine tracks)

Section titled “4.3 Run-time / instance plane (what the durable engine tracks)”
Term Meaning
Run A durable instance of a Pipeline for a specific Event/commit. Stores the compiled IR + {ir_version, event_schema_version} (self-describing).
StepRun A durable instance of a Step within a Run.
Attempt A single execution of a StepRun. A Rerun or Retry creates a new Attempt. Each Attempt owns its evidence — logs, Results, Artifacts, workspace snapshot — keyed by {run, step, attempt}, and records which upstream Attempts it consumed.
Superseded Intrinsic terminal outcome of an Attempt cut short while running because a human reran or retried an ancestor (the cascade re-armed this step): its live Pod is torn down (SIGTERM + grace) and any late verdict is rejected by the fence, so it could not honestly finish and a fresh Attempt takes its place. It is the Attempt’s own fate — shown as superseded in every view, never repainted as the transient “running” it passed through nor as a later Attempt’s success (ADR-0056). Distinct from Cancelled — a deliberate stop with no replacement (cancel_run_request) — from Failed (ran and errored), and from Not-run (never started, no Pod). Evidence retained like any other.
Not-run Terminal display state of a step that never started in a version superseded before its turn (an ancestor was rerun while this step was still upstream-blocked). Distinct from Skipped (a when: was false or a dependency died), Pending (implies a future that will happen — it will not, in this version), and Superseded (had a live Pod and may have partially side-effected — a not-run step did nothing). Per-version, derived from the event log (ADR-0056).
Auto-retry The engine re-executing a not-yet-succeeded StepRun within its retry budget (ADR-0047). Machine-initiated, never on a succeeded or in-progress step; adds an Attempt but does not fork the Run (stays within the current Take). Its human counterpart — same version, no fork, on a Failed step — is a manual Retry (one concept, two triggers).
Retry (manual) The human trigger of a Retry: re-executing a Failed step as another Attempt in the current version (Take) — no fork: it reopens the settled Run (Failed → Running) and re-arms the target plus its dependent cascade (ADR-0027). Backend retry_step; event StepRetryRequested. The human counterpart of Auto-retry — one concept, two triggers (manual vs auto); the authored retry: policy governs the auto side. Contrast Rerun (forks a new version). Offered on Failed steps only.
Rerun The human action of re-executing a step as a new Run version — forks a new Take (a new history row) and cascades to descendants (ADR-0027). Offered on any target, terminal or not; an in-flight member of the invalidation set is voided (torn down, marked Superseded; ADR-0056). Backend rerun_step; event RunRerunRequested. Contrast Retry (another Attempt in the same version, Failed-only). Avoid: “restart” (user-facing).
Cascade The downstream half of a Rerun: descendants dragged into re-execution because an ancestor was rerun (per smart invalidation, ADR-0027) — not individually chosen by the human. A cascade Attempt’s cause points back at the rerun that triggered it (“⟵ b was rerun”).
Shadowed A finished-successful Attempt whose result is retained and readable but is no longer the “of-record” latest — a newer Attempt (from a Rerun/cascade) replaced its role. Distinct from Superseded (never finished — cut short while running). ADR-0056’s word for non-latest Artifact versions; generalized here to any evidence.
Take The span of a Run between two Reruns. A Rerun closes the current Take and opens the next (a new history row); auto-retries, crash re-adoptions, and dead-letters happen within a Take. The run-level version unit (“Take 2 of 3”) — a bookmark over a frontier of Attempts, not a copy of anything. Internal term — the end-user run-history language is still being designed (does not surface “Take”/“Attempt” verbatim; the surfaced form is a row per Rerun).
Event log Append-only, versioned, immutable record of state transitions. Drives SSE, timeline, audit, time-travel. State tables are the source of truth; the event log is derived-but-durable (via the outbox).
Admission Scarab’s scheduling decision — which Runs/Steps are allowed to run (concurrency groups, fairness, priority, backpressure). Distinct from k8s Placement (node fit).
Fence A monotonic {run, step, attempt} token handed to each Attempt and to cooperating external systems (idempotency keys, digest/generation checks) to neutralize the double-effect hazard.
Provisioning deadline The bound on how long an Attempt may spend getting ready to run — scheduling, image pull, workspace feed — as opposed to running (ADR-0066). A separate clock from the Step’s authored timeout:, which measures execution only, from the moment the step container starts. The principle: waiting for infrastructure must not bill the Step’s execution budget — before the split, queueing delay ate the author’s timeout and a Step that never ran could fail as Timeout. Overrunning it is its own failure class, never Timeout, so the two causes are distinguishable in the record. Distinct again from the Run budget, which is a wall-clock spend limit over a whole Run and is not split.

4.4 Structural / architectural

Section titled “4.4 Structural / architectural”
Term Meaning
Port A domain-owned trait describing an external capability in domain language (ForgePort, SecretProvider, ObjectStore, Cas, Executor, Db, Clock, OidcIssuer).
Adapter A concrete implementation of a Port, in a separate vendor crate (scarab-forge-github, scarab-db-postgres, …), holding all infra deps.
IR The typed, versioned Pipeline Intermediate Representation — the real DSL. YAML is one frontend; the API schema is the IR.
Forge The domain concept of a source-of-repos/sink-of-status (GitHub, GitLab, Forgejo). Vendors are adapters, never their own domain.
Data Depot The long-lived Scarab-operated service that holds the data plane near where Steps run: the warm CAS, Snapshot Farms, live Workspace Exports, the Step log namespace, and Cache (ADR-0061, 0062, 0063, 0065). Same binary as the control plane, different role (--role depot) and no durable core. It connects to the control plane’s Postgres but owns no schema and never migrates (2026-08-23): the boundary being protected is not a system of record, not never uses a database — a Depot rolled ahead of the control plane must not be able to half-migrate anything, and everything it reads there is derived and rebuildable from the object store. Was “the workspace service” until 2026-07-28; renamed because that named it after one of its tenants and broke as soon as a second kind of data arrived. warm store was rejected for naming it after one of its properties, which encodes a tiering decision and dates the same way. Not a Workspace, a Workspace Snapshot or a Workspace Export — those are data it holds, and they keep their names. Definitionally a cache (ADR-0066): it holds nothing that cannot be recreated, which is what makes running more replicas a sufficient HA story, eviction safe by construction, and a lost replica a latency event. Anything that makes it a system of record is a defect.
Warm-only Retired as a deployment mode (2026-08-23). Postgres and an object store are both hard requirements; Scarab is not expected to function without either. Warm-only survives only as a runtime degradation — the cold tier is configured but momentarily unreachable — never as a supported way to deploy. What follows is the superseded definition, kept because the disclosure vocabulary it introduced is still the right shape for that degradation. The named deployment mode in which no independent cold tier is configured (ADR-0064’s st_dev test) — object storage is a soft, recommended requirement, not a hard one (ADR-0066). Supported, with a smaller, true guarantee rather than a silent downgrade: the Data Depot offers a bounded recent window, every Attempt is stamped warm-only in attempts.output_durability, and warm eviction is genuine loss rather than a latency event. It does not mean the Depot becomes the system of record — it means there is no system of record for Workspace Snapshots in that deployment, which is disclosable because they are reproducible from the forge. Depot HA requires object storage — a documented consequence, not a gap.

4.5 Tenancy & forge binding

Section titled “4.5 Tenancy & forge binding”
Term Meaning
Org A top-level tenant. Owns Projects. The Scarab tenancy boundary — not the forge’s owner namespace (one Org may span a GitHub org and a Forgejo instance).
Project Scarab’s governed unit of CI and the aggregate root beneath an Org: it binds a source (a RepoRef on a forge, via a ForgeConnection) to its governance (Environments + ProtectionRules, privilege whitelist, secret scope, OIDC subject) and owns the Pipelines and Runs produced from that source. RBAC is enforced at the Project scope. 1:1 with a repo in v1 (monorepo per-subdir governance deferred to an optional path scope). There is no separate governed “Repo” entity — a Project is the governed repo.
RepoRef A forge coordinate — {owner, name} as the forge addresses a repository, plus the forge it lives on. External and mutable (a forge rename/transfer changes it). Carried by Event/Status. Lives in scarab-forge; it is the only concept named “Repo”. Resolved to a Project via a ForgeConnection.
Actor The identity that caused an Event — the forge principal who pushed, opened the PR, cut the tag, or dispatched a manual/api run (a vendor login, normalized). Carried on every Event variant (not just dispatch), stamped onto the Run at creation as a discrete fact (beside the trigger kind, ref, and commit SHA — not bundled), and surfaced in the UI (labelled “author”). A forge-originated fact, not a Scarab RBAC principal — do not conflate with the authenticated caller in an authorization check.
Headline (trigger title) The one normalized human line that says what a Run is about, disambiguated by trigger kind: a push’s commit subject, a pull request’s title, or a manual/api dispatch reason (a cron schedule / upstream run id for those). A forge-originated, display/audit-only provenance fact — a sibling of Actor, stamped on the Run at creation, never load-bearing and never entering trigger-matching or ${{ }} interpolation. Surfaced as the secondary line of the Trigger cell (ADR-0057).
ForgeConnection A configured link between Scarab and a forge account (a GitHub App installation, a Forgejo connection): {forge_kind, base_url, credential_ref} owning a set of RepoRefs. The seam that resolves RepoRef → Project and supplies credentials. The type is pure (scarab-forge, holds a credential reference, not secret bytes); persistence is a store port + adapter; credentials live in SecretProvider.

4.6 Deployments

Section titled “4.6 Deployments”

Scarab’s deployment language is vendor-neutral: no CD tool’s nouns (Argo’s Application/sync, Kargo’s Freight/Promotion) enter it. A CD tool is a source of observations and a provider of actions, never the shape of the model.

Term Meaning
Deploy Run A Run that names an Environment — today once for the whole Run (pipeline-level environment:); in the target state also per invoke segment, each segment governed by its own Environment (approval, secrets, eligibility checked at Run creation for every Environment named, concurrency per segment, never per Run). Promotion until then is chained Deploy Runs. It is the request to deploy plus its governance (admission against protection rules, env-scoped secrets, exemption from newest-wins cancel). Its success means only that its Steps succeeded — e.g. “the gitops change merged” — not that anything is live.
Deployment A specific DeploymentVersion made (or asked to be made) live on a specific DeploymentTarget within an Environment, together with what was subsequently reported about it. A Deployment is an occurrence with its own identity; (Environment, DeploymentTarget, DeploymentVersion) is only its correlation key — a source report attaches to the newest Deployment with that key, and a new request joins that Deployment unless it is final (so a retried deploy step or two concurrent requesters make one Deployment, while a rollback makes a new one). Outlives the Deploy Run that requested it, and may exist with no Deploy Run at all (a change observed but never requested through Scarab). Approval is evidence attached to a Deployment, never the Deployment itself. Rollback is a new Deployment of an older DeploymentVersion, never an edit to an old one. Avoid: release (a forge noun), sync (an Argo noun), promotion.
DeploymentTarget The smallest unit a Deployment can independently succeed or fail on — one Argo Application, one Helm release, one ECS service. Belongs to exactly one Environment. Its identity is opaque and source-supplied — (source, id), understood only by the source that named it — and it comes into existence the first time it is named (by a Deploy Run’s request or a source’s report), never by prior registration. A source rename is a new DeploymentTarget, and so is a re-home — the source reporting a known target under a grouping that maps to another Environment (an Argo Application moved to another Argo project) records a new DeploymentTarget in the new Environment and ends the old one — shown Moved on the old Environment’s board, never a status; never moved, never a standing conflict. Fan-out (one Environment across regions/clusters) is several DeploymentTargets, not a grouping concept. Avoid: bare “target”, app, application (Argo’s nouns), service (collides with Sidecar service / Shared service).
DeploymentTargetProjectOwnership The set of Projects that may request Deployments on, and invoke actions against, a DeploymentTarget. Reported by the source (derived from the vendor’s own metadata, e.g. an annotation the plugin installation is configured to read), never assigned in Scarab: Scarab mirrors the source’s authority, never invents a parallel one — so ownership is, in effect, write access to the gitops source (in a shared gitops repo, whoever can merge there; a deploy Step can write an owner annotation into its own commit). May name several Projects. Reading and watching a DeploymentTarget need only EnvironmentProjectEligibility. A request may name a DeploymentTarget no one owns yet (a new service whose source object is created by the very change being deployed) — recorded unconfirmed, and flagged if the source later reports owners that exclude the requester; it is rejected only when other Projects own it (that rejection and the flag are not built — git-bug 9c1173a). A request explains a Deployment a report created only if its Step started at or before core first received that Deployment; one that started later is recorded as a claim (kept among the requesters, its gate still resolves) and the Deployment stays Unexplained, so no request can launder a hand-applied hotfix. PluginActions always need ownership; no PluginAction is offered on a DeploymentTarget with no owners — the fix is for the source to report one, not a side door around Runs. Avoid: bare “owner”, first-claim.
DeploymentVersion PROVISIONAL (owner decision; revisit after real use). The opaque label identifying what a Deployment deploys. Compared only for equality; never parsed. Its scheme is declared by the source, per DeploymentTarget, published as a scheme id; requesters must use it, and a request whose version does not fit is to be rejected when recorded (not built — git-bug 5fc1860; today any non-empty string is recorded). The Argo plugin’s default is the set of image references in the pod templates of the Application’s target manifests (what Argo rendered — not status.summary.images, which reads live Pods: the rollout union, injected sidecars, hook Pods, empty at scale-to-zero); optionally the last gitops commit touching the target’s path (misses bases outside the path, multi-source apps, remote charts). Blind spots, stated plainly: references are usually tags, not digests; a config-only change is invisible (it joins the live Deployment, and a DeploymentGate on it passes at once); the requester must predict the whole rendered set. The known weakness is that equality-only correlation makes the requester predict the source’s rendering; the leading alternative to evaluate with real data is source acknowledgement (the source maps a request/commit to the version it rendered, GitHub-Deployments style). Artifact digests attach to a Deployment as evidence (zero or more), never identity. Avoid: bare “version” (collides with a Run version / Take).
EnvironmentDeploymentSource A source an Environment admits reports from — a PluginInstallation (whose name is the source name, assigned by Scarab, never chosen by the Plugin) plus the vendor grouping that maps into this Environment (e.g. Argo project prod). Owned by the Environment, like EnvironmentProjectEligibility: reports from any other source into it are dropped and the drop recorded. Core sets a report’s source from the identity that pushed it (a projected ServiceAccount token mapped to its installation), never from the report body. The consent unit is the installation: the vendor grouping is plugin-asserted, so one installation per Environment is recommended. Avoid: bare “source” as a modelled name.
DeploymentRequest A Step’s declaration, in a Deploy Run, that its success asks for a DeploymentVersion on a DeploymentTarget — the Step field deployment_requests: [{ target: {source, id}, version, evidence? }], where version and evidence name results the Step declares in its results: list. Recorded only when that Step succeeds, in the same transaction as the success transition (its DeploymentVersion — a non-empty string, in the target’s declared scheme — and any evidence digests come from the Step’s own results, e.g. the image set its gitops change renders; on Kubernetes those arrive through the results-egress sidecar, and success waits for its drain); a Step that changed the world and then failed records nothing, and the change surfaces as Unexplained. The DeploymentTarget must be static (a literal or exactly ${{ inputs.<name> }}), resolved at Run creation, so the Environment check happens before any Pod (the ownership check is not built — git-bug 9c1173a). The Pipeline check refuses a request without environment:, on a matrixed Step, reading an undeclared result, or naming one target twice; Run creation refuses two requests resolving to one target, and inline POST /v1/runs refuses any. Carries an effective time — when the Step’s first Attempt in its current Take started (automatic retries and an operator Retry share it; a Rerun of the Step starts a new Take and a later effective time — git-bug 2b5d9d9), control-plane time clamped to no later than the request’s receipt — so a request recorded after the source already saw the change joins that Deployment as history rather than looking like a rollback. The same time decides whether it explains a Deployment a report created: only if its Step started at or before core first received that Deployment; otherwise it is a claim (see Unexplained). If the Step exits 0 but its DeploymentRequest cannot be completed (a referenced result missing or mistyped — including a failed results drain on Kubernetes), the Step fails as DeploymentRequest incomplete (deployment-request-incomplete) — never auto-retried, since its change has probably landed. When the results sidecar terminated non-zero the reason says so — the delivery failed, the Step’s own output may be fine, retry the Step — rather than asking the author for /scarab/results/<name>.json (git-bug 0cb5895); when the backend cannot say (an API error, the Pod gone) the reason says delivery could not be checked; every wording names the missing results. A DeploymentTarget already known in another Environment — by its source’s routing, else its newest recorded input — is rejected at Run creation (two Runs first naming one target from two Environments are both admitted — git-bug 9e66f2c); one the source later reports under another Environment is re-homed (see DeploymentTarget), never moved. A field on any Step, not a step kind.
DeploymentGate A Gate (gate: deployment, deployment: { step, target? }) that waits on a DeploymentRequest made by an upstream Step of the same Run that it needs, and looks only forward from its window start. Attribution and the gate window are split (owner decision 2026-10-24): the request’s effective time (the deploy Step’s first Attempt in its Take) only decides what the request explains; the gate’s first wait opens at the start of the deploy Step’s Attempt that succeeded and recorded the request — the same instant when the Step was not retried, a later floor when it was, so a report received while an earlier, failed Attempt ran never decides the gate and the stall clock starts at the succeeding Attempt, not at the first or at an operator’s late Retry; only a wait that waits afresh (an earlier wait of the gate already reached a verdict on this same request: a Retry, or a Rerun of the gate alone — judged by journal position) opens at the later of that and its Attempt’s start: passed if the Deployment was already live then or is reported live after; failed on a failed report after it, on superseded, or once the deadline (the Project’s effective one) has elapsed since it — carrying the source’s label as the reason. A failed (or live) received while the succeeding deploy Attempt was still running therefore decides the first wait at once, with that label (owner decision 2026-10-24, git-bug fce05da); the deadline runs from the window start too, so a deploy Attempt that ran past it fails its gate stalled when the gate is reached, the reason naming what it ran from — but no verdict is reached before the gate’s own Attempt exists. A Rerun of the deploy Step makes a new request, and the gate’s next wait is a first wait on it, opening at that request’s succeeding deploy Attempt. For a wait that waits afresh, an input received in the Attempt’s starting millisecond counts as before the window, and the window opens only once that millisecond has ended. Humans cannot approve or release it; they can reject it. A record that cannot be read means no decision until the deadline (from the gate Attempt’s start), then stalled with the read error. “Before”/“after” mean received before/after: core stamps every input with its receipt time on one clock (the store stamps it), monotone per Org; a gate decides only below the store’s horizon, so every input it has not seen is stamped after the instant it decided for; a source’s timestamp is display only. A failure received before the window (e.g. a re-deploy after fixing a missing secret) never fails it. It proves “V is live”, not “my change took effect” — under the default version scheme a config-only request passes at once. Resolved by core from status reports — a plugin reports facts, never resolves a Gate. A Retry’s window starts at the later of its request’s effective time and its Attempt’s start, so Retry after a recovery (fix the secret, Resync, Retry the gate) waits afresh on the same Deployment without re-running the deploy. Its verdict is journaled per Attempt when first reached, never re-derived from the log; the Deployment’s status may move on (a Run red on stalled stays red even if the Deployment later goes live).
DeploymentStatus The fixed, vendor-neutral state of a Deployment — the only status core understands, and the only thing gates, governance and red/green read. Source-asserted: in_progress, live, failed (with a reason). Core-derived (a source can never assert them): requested (asked, no source report yet), stalled (not converged within the EnvironmentDeploymentDeadline; can still recover), superseded (a newer Deployment took its place on the same DeploymentTarget — whether it was ever live is read from its reports, not a separate status). At most one live Deployment per DeploymentTarget. failed → live is allowed while the Deployment is still the newest on its DeploymentTarget; only superseded is final. A status earns its place only if a gate, governance rule or view branches on it; anything else is a label or a fact read from history. New vendor states become labels, never new statuses. Shares the word superseded with an Attempt in the same sense — “a newer one took its place”; Attempts additionally split off Shadowed because evidence retention cares, Deployments do not. Avoid: overtaken, retired, inactive.
DeploymentStatusReport One report from a source about a Deployment: a DeploymentStatus, a free-form label (“canary 2/4 at 25%”, “hook migrate: secret missing”), an optional link, the source’s time (display only — core orders by receipt time), an idempotency key and a source sequence per (installation, DeploymentTarget). Pushed to a reserved broker path under a projected ServiceAccount token (ADR-0072 §11). The ordered reports are the Deployment’s stages as shown to QA; core displays the label without interpreting it.
DeploymentReporterContract What every report_deployments Plugin promises, published by core so behaviour is consistent across CD tools: report failed only when the source has given up (won’t progress without intervention — e.g. Argo’s retries exhausted), in_progress with the reason until then; live only when the requested DeploymentVersion is actually serving (applied and healthy at that version, where the source can tell); live → failed allowed; a re-apply of the same DeploymentVersion is a report, not a new Deployment; report transitions only (never every reconcile), in source order, never replaying older history (core orders by receipt, so a stale report delivered late reads as new); each report idempotency-keyed and sequenced so an at-least-once retry cannot flip live back to failed; and, the one exception to “transitions only”, re-send a target’s current state when core flags it resend (its grouping was just mapped or moved, so its last status never reached where it routes now — core never fabricates one). The first-party Argo Plugin is its reference implementation.
EnvironmentDeploymentDeadline How long a Deployment in an Environment may stay requested/in_progress before core marks it stalled — measured from creation, restarted by every request that joins it. Set on the Environment, and that baseline deadline alone drives a Deployment’s status; a tighter deadline in a Project’s EnvironmentProjectOverlay applies only to that Project’s DeploymentGates.
Unexplained / Unconfirmed / Moved Display terms, not statuses. Unexplained — a Deployment a source report created rather than a Deploy Run’s request (a change made outside Scarab), and that no request explains. A request that joins it explains it only if its Step started at or before core first received the Deployment (the source got there before the Step finished); one whose Step started later is a claim — listed, never “made live by”, and the Deployment stays Unexplained. Once explained, always explained (a rerun cannot undo it). A retried Step is judged by its first Attempt in the current Take, so an Attempt that pushed the change and then died still explains it (git-bug 2b5d9d9); a Rerun’s request is judged by its own Take’s first Attempt. Known limit: a long Step, its retries included, that spans a hand-applied change of the same version explains it (inherent). Unconfirmed — requested on a DeploymentTarget its source has not reported yet. Moved — a DeploymentTarget whose source now routes it to another Environment (or to none: unmapped), shown on the old Environment’s board with where it went (“now: prod”); its history there is untouched, nothing is appended, and a request for it there stalls. The re-home’s “the old one ends” (see DeploymentTarget).

4.7 Plugins

Section titled “4.7 Plugins”

A Plugin extends Scarab with concepts it is not aware of or should not own — vendor knowledge (how to observe and act on Argo CD, Flux, Slack…). It is a second extension point beside Steps, not a replacement: a Step is still any container (ADR-0008). Core owns the vendor-neutral nouns; a Plugin owns only vendor knowledge. First-party Plugins use exactly the contract third parties do — if one needs more, core changes.

Term Meaning
Plugin A digest-pinned OCI image + PluginManifest, run as a long-lived workload Scarab manages, outside any Run. Depends only on core, never on another Plugin. Never resolves a Gate (it reports facts; core decides) unless an Environment admin has named its PluginPrincipal as an approver, never holds a long-lived credential, never reads secrets/workspaces/artifacts/logs unless a future capability says so.
PluginInstallation An org’s approval to run one pinned digest of a Plugin with its PluginManifest. Nothing changes without an admin action: no auto-apply, ever (a new digest is new code). Same-or-narrower manifest → one-click upgrade by one org admin; wider → review of only the new capabilities; elevated tiers → dual approval on every digest. Subject to the operator’s ceiling (which publishers may be trusted, whether elevated tiers exist at all) and to a kill switch. Runs as one instance per org.
PluginPublisher A signing identity (Sigstore identity or key) an org trusts to publish Plugins. Unsigned or untrusted-publisher images cannot be installed. Scarab’s own release identity is trusted by default (first-party); “which plugins do we trust” is answered as “which publishers”.
PluginPrincipal A Plugin installation’s own identity — not tied to any human — under which it reports, calls the broker, and (if named) approves. Proven by a projected ServiceAccount token (audience scarab-broker, short TTL, automount off), verified by TokenReview or JWKS and mapped to the installation; the kill switch revokes at that mapping. Appears in audit and the UI as plugin:<name> (“approved by plugin:servicenow (CHG0012345)”). It can be listed among an Environment’s approvers, in addition to humans by default; a DeploymentGate is never resolved by one.
PluginManifest The Plugin’s declaration of every PluginCapability it wants, with scopes. What an org admin approves is exactly (image digest, manifest).
PluginCapability One entry of a closed vocabulary (grows only with a Scarab release) of what a Plugin may do, each scoped: report_deployments (DeploymentStatusReports + DeploymentTargetProjectOwnership for named sources), subscribe_events (read-only Run/Deployment events), offer_actions (declare actions humans or Runs may invoke), use_connection (reach a named external system without holding its credential), contribute_ui (a PluginUiContribution), approve_gates (approve/reject approval Gates — effective only where an Environment admin names the Plugin as an approver; two keys, two roles).
PluginAction A typed operation a Plugin declares (resync, promote, abort, post-to-Slack), with typed inputs. Every invocation is a plugin_action Step in a Run — written in a Pipeline, or created as a single-step Run by a UI button in the DeploymentTarget’s owning Project and Environment — so audit, Environment governance, durability and fencing apply unchanged. Its one-shot authority is bound to that Step’s Attempt and dies when the Take is superseded. Each PluginAction declares whether it needs the Environment’s approval; the admin sees this at install and may only tighten it (force approval), never loosen. What a PluginAction means is the Plugin’s business — a mislabelled one is caught by install review, the broker’s rules and the vendor’s own RBAC, and anything it makes live without a request surfaces as Unexplained. A Plugin never invokes its own PluginActions. Dispatch is at-least-once: core passes the Attempt’s fence as an idempotency key and the Plugin must accept a repeat (ADR-0021). A UI-started plugin_action Run runs no project code, so it is exempt from allowed_refs (only) — Eligibility, ownership, the approval flag and require_reason still apply. Surfaced to broad audiences only by its plugin-declared label (“Resync”).
plugin_action A built-in Step kind that invokes a PluginAction. Launches no Pod of its own; core dispatches to the Plugin and records its response as the Step’s results.
PluginConnection An org-admin-configured binding of a credential to the one destination it may be used against (base URL + credential reference + auth scheme) — the destination is part of the authority, so the two are never separated. The secret bytes live in the SecretProvider. May be scoped to an Environment (e.g. argocd-prod with a token limited to Argo’s prod project), so the vendor’s own RBAC tells prod from staging; the broker uses the connection matching the invoked DeploymentTarget’s Environment. Avoid: bare “credential”, PluginCredential.
PluginConnectionCredentialMode How a Plugin uses a PluginConnection. brokered (default) — the Plugin never holds the credential: the CredentialBroker adds it to requests the Plugin sends to a stable in-cluster address, and the Plugin keeps its own client (native SDK, retries, streaming). delivered (escape hatch, for protocols the broker cannot proxy) — the credential is mounted into the Plugin, egress tunnelled through the broker and pinned to the destination’s address and TLS name (SNI), dual org-admin approval, re-approved on every digest; everything the Plugin emits (labels, links, action results) is scrubbed by the secret redactor. Honest limit: behind a shared ingress it may reach other sites on that ingress — meant for destinations with their own address (databases, SSH, dedicated endpoints).
CredentialBroker Core’s authenticating reverse proxy between Plugins and PluginConnections: checks each request against the manifest’s PluginConnectionRequestRules, adds the credential, forwards, journals. Supports streaming. A Plugin’s network reaches only the broker, so DeploymentStatusReports are pushed to a reserved path on it (core sets the report’s source from the caller’s verified identity).
PluginConnectionRequestRule A manifest-declared allowed request shape on a PluginConnection — method + path pattern + the query keys it may carry (any other key, or one twice, is refused, not dropped) (+ body schema). Read rules apply any time. Write rules are declared per PluginAction and open only while that action is being invoked; they may bind {target.id} in the path, a query parameter (Argo’s appNamespace) and a body field, which the broker fills from the invoked DeploymentTarget — percent-encoded as one path segment (ids are plugin-supplied) — rejecting a request whose bound value differs; each invocation gets its own fenced broker credential, so concurrent invocations cannot be confused — the Plugin cannot aim a write at another target. A second line of defence; vendor-side least privilege (e.g. an Argo role that can sync but not override) is the first.
PluginUiContribution UI a Plugin adds, at a declared PluginUiTrustTier.
PluginUiTrustTier framed (default) — the Plugin’s UI runs in a sandboxed, opaque-origin iframe at a UiExtensionPoint: it owns its own DOM inside the frame (any UI library), gets core’s design tokens to look native, and talks to core only through a narrow bridge (context + proposals of its declared PluginActions — the bridge only proposes; core renders the confirmation outside the frame, so frame code cannot fire an action without a real click); it cannot act as the viewer or read Scarab. One org admin approves. trusted_dom — same-origin code that can change any page and can do anything any viewer of that page can do: equivalent to adding code to Scarab itself. Allowed only for publishers the operator names, dual org-admin approval, re-approved on every digest, served pinned (SRI). Its guardrails ensure you chose to trust it; they do not contain it — no exfiltration or page-boundary guarantee is claimed.
UiExtensionPoint A named place in core’s UI where a framed contribution is mounted (a Deployment row’s expansion, a Run panel, an Environment board column, an org tab, a Step panel).
StepUpConfirmation A fresh, script-unforgeable confirmation by a human in an interactive session — a Scarab-registered passkey (WebAuthn), or (not built yet) a forced re-login only where the identity provider proves the authentication is fresh (a login through a provider that cannot prove it, such as GitHub or Forgejo OAuth, never counts: those users confirm with a passkey, enrolling one the first time they attempt a crown-jewel operation) — required for crown-jewel operations: Plugin install/upgrade, PluginConnection create/edit (above all its destination), the operator ceiling, ForgeConnection edits, identity links, secret writes, role changes, API token creation, anything that loosens an Environment (protection rules — including removing an approver or widening an allowed ref —, EnvironmentProjectEligibility, EnvironmentDeploymentSources, privilege whitelist), approvals on Gates of Environments with approvers, adding or removing a passkey after the first, and irreversible destruction (deleting an Org, Project, Environment or secret; shortening retention). Every mutating route carries one classification in a single route table, so a new route cannot skip the guard; an operation with no route yet (Plugin upgrade, the operator ceiling, shortening retention, deleting an Org) is covered the day its route appears. Environment loosening and Gate approval are conditional: the handler judges the change against the stored state (fail-closed; a concurrent change answers 409), and an approval needs a step-up when the Environment has approvers or its governance cannot be resolved. An API token never satisfies a step-up; it reaches a crown-jewel operation only through a StepUpConfirmationRequest. The one pre-authorised machine exception: a PluginPrincipal named as an approver may approve. Naming it is a tightening (approvers are ALL-of) and needs no step-up; what was stepped up is the install that approved approve_gates. A confirmation covers the cookie session that made it for 5 minutes from the moment of confirming — activity never extends it, and the same session presented as Bearer never uses it — except the operations that mint a new credential or outbound channel (API token creation, Plugin install/upgrade, every PluginConnection write, adding/removing/resetting passkeys), which confirm every time with a challenge committed to that exact action. Tightening needs no step-up. Defends against stolen tokens, CSRF and unattended sessions — not against trusted_dom code, which can swap what is being confirmed.
StepUpConfirmationRequest A crown-jewel operation a non-interactive caller (an API token, or a CLI presenting a human’s session as Bearer) asked for and cannot perform itself: it is held as a pending request naming exactly the operation, its target and what changes, and runs once only when a human confirms that exact request with a StepUpConfirmation. It is held as the sealed request itself and, once confirmed, replayed through the real route, pinned to the confirmed operation and request digest and to the loosenings the human saw. It expires after 5 minutes, cannot be reused or widened, and is recorded as requested-by the caller and confirmed-by the human. At most 10 wait per requester. The confirm page shows the method, path, query and every value in full (a URL’s parsed host included). The caller never satisfies step-up; the human does, per request. Only the human the caller acts for (the token’s owner, the CLI session’s human, or a Principal that human was merged into) may confirm it — never another admin, who gets a 404 — and it runs with the narrower of the caller’s scope and that human’s live role; a PluginPrincipal has no human and cannot raise one.
OrgSecurityEventLog The Org’s append-only record of step-up activity: every StepUpConfirmation (who, when, which passkey, which session), every crown-jewel operation and the confirmation or StepUpConfirmationRequest that authorised it, every refusal (a caller that attempted a crown-jewel operation without step-up), and every passkey enrollment, removal and reset (the server break-glass included). Postgres refuses every update and delete, and retention never touches it. Confirmations, enrollments, authorised operations and resets are fail-closed: an action whose record cannot be written does not happen. Org admins see the Org’s log: its own events plus the Org-less confirmations and passkey events of its members, with no detail of another Org’s operation. Each user sees their own; global admins see the whole install. Forwarding it elsewhere is a Plugin’s job (subscribe_events), not core’s.

5. System overview

Section titled “5. System overview”

Which edge carries bulk is the whole point of ADR-0061, so the four labels are load-bearing. control plane ↔ Step Pod carries root hashes only — that property belongs to this edge and no other. Step Pod ↔ workspace service is the bulk edge by design; its feed half is real, its drain half is s3-drain and is not built. control plane → object store is bulk today, for the drain, and a diagram without that edge asserts part 3 is finished. control plane ↔ workspace service is small and off the critical path: Browse reads snapshots through the service (falling through to the object store when it cannot answer), and the drain seeds it as a warm tier.

  • One binary, many roles (scarab-server --role converged|api|scheduler|executor|webhook|workspace). Postgres (outbox) is the coordination bus; no service-to-service RPC required internally. workspace is the one data-plane role: it never connects to Postgres and never runs a migration (ADR-0061), so it keeps serving a Step its inputs through a database outage.
  • Control-plane / data-plane split: the durable brain records intent (“Step S should run”); the executor observes it, creates the Pod, watches it, writes back terminal state. The intent is that bulk data does not cross the brain — the control plane exchanges root hashes and Step Pods talk to the workspace service. Half true today: ADR-0061 supersedes the kubectl exec tar tunnel on the feed side, where a Scarab-owned fetcher has replaced it. The drain still tars every byte out through the Kubernetes API server, and artifact harvest is a third exec tar; both go with s3-drain. Do not read this bullet as a description of the running system’s write path.
  • Three stateful components — and the third is deliberate. Postgres (state + event log), an object store (blobs), and the workspace service’s persistent volume. ADR-0004 called object storage “the second (and last)”; ADR-0061 knowingly adds a third, because one standard path beats a fast path plus a fallback path, and because binding volumes to a long-lived service removes every cost PVCs have when bound to short-lived Step Pods. The two storage tiers carry different promises, and that asymmetry is load-bearing: the workspace service’s volume is bounded by space and promises nothing (a miss is slower, never wrong), while the object store is bounded by time (a retention TTL) and is the guarantee users are given. Nothing else is stateful.

7. Key invariants (must hold from commit one)

Section titled “7. Key invariants (must hold from commit one)”
  1. Forward progress or explicit dead-letter. A Run never loops forever; poison steps hit max-attempts and dead-letter with diagnostics.
  2. Exactly-once admission, at-least-once step. Enforced by outbox + idempotency keys; proven by crash-interleaving tests on the pure scarab-engine.
  3. Version tolerance from day one. Event log + IR carry version stamps; migrations are expand-contract; Runs are self-describing. Gates make Runs outlive deploys, so resume-across-upgrades is the normal case, not an edge case.
  4. Pure domain crates import no infra. If scarab-engine’s Cargo.toml ever lists sqlx/kube/reqwest, that is a bug.
  5. The UI eats the same API as everyone else. No private UI backchannel.
  6. The Data Depot is a cache. Nothing on its volume may be irreplaceable; anything that makes it a system of record is a defect (ADR-0066). Guarantee what cannot be recreated, degrade what can.

8. Testing philosophy (see ADR-0017)

Section titled “8. Testing philosophy (see ADR-0017)”

Classical (Detroit-school): real collaborators in-process, mock only true externals at the adapter boundary. Minimal in v1 — enough integration tests to catch glaring bugs; grow the suite from real bugs (each fix leaves a regression test). E2e per layer, a few genuine cross-layer e2e. Exception: 2–3 targeted crash/resume tests guard the durability wedge. Don’t fight test infra; keep velocity.

Canonical tier names (rules in ADR-0017’s addendum): unit, functional (real router + engine in-process, fakes at ports), kind (executor layer against a real apiserver), stack e2e (cross-layer, nightly); UI pyramid: no-DOM ≫ DOM ≫ browser.

9. Roadmap (tracer-bullet vertical slices)

Section titled “9. Roadmap (tracer-bullet vertical slices)”
  1. Durable core skeleton — POST /runs (inline 1-step) → admit → k8s Pod → logs (SSE + object store) → terminal → kill control-plane mid-run, resume exactly-once.
  2. IR + YAML + CEL; multi-step DAG; content-addressed workspace; restart-a-step.
  3. GitHub adapter + identity: webhook → in-repo .scarab → run → checks back; OAuth login.
  4. Scheduler richness + gates: concurrency groups, auto-cancel, fairness, priority; Environments/approvals.
  5. Secrets + OIDC issuer + BuildKit: encrypted secrets, keyless federation, fork-PR lockout, image builds.
  6. UI (SolidJS): live DAG, logs, rerun/resume, time-travel timeline.
  7. Local exec + CLI polish + provenance/signing fast-follow.

An org admin installs a library once, and every Pipeline in the org can use it:

```yaml
steps:
  - id: ship
    invoke: lib:acme::scarab-libs::deploy-helm
    with: { release: web }
```

A library is a YAML file with `kind: library` (see [Reuse: `invoke`](/scarab-ci/usage/pipeline-syntax/#reuse-invoke)).
Scarab stores the file it installed and compiles Pipelines against that copy, so a Pipeline never
fetches anything, and the org decides when a library changes.

## Install a library

Settings › Libraries › **Install library**, or the API. **Install library** asks for a **file**
in a git repository, a **ref** (a branch, tag or commit) and a **name**, and **Fetch and review**
opens the review page (`/orgs/<org>/settings/libraries/review`), which every library goes
through, Scarab's own included.

```
File  github.com/acme/scarab-libs//deploy-helm.yaml
Ref   v1.4.0
Name  acme::scarab-libs::deploy-helm
```

The part before `//` is the repository and the part after it is the file. Scarab reads a branch or
tag at the commit it points to when you fetch, and the review page shows that commit. The
installation is pinned to that commit and to the content you reviewed: a branch that moves later
changes nothing until you upgrade. The API takes the same two fields, `source` and `ref`, or a
`source` that ends in `@<full commit id>`.

### The ref and the commit

Scarab keeps the ref you asked for and the commit it read the file at. The library list, the
library's page and the review page show them as `v1.4.0 → 8c2f4e1`: the ref, then the first 7
characters of the commit. Hover the commit to see all of it, or click it to copy it. A library
fetched with a source that ends in `@<commit>` has no ref, and shows the commit alone.

The installation records the ref and commit of the fetch you installed, and its `source` names
that commit. Fetching the same file again under another ref, or at another commit that holds the
same content, does not change what an installed library says until you install that fetch
([Upgrade](#upgrade)). The API answers both, in the fetch answer (and its `current`) and in each
installation:

```json
{"requested_ref": "v1.4.0", "resolved_commit": "8c2f4e1a9d7b3c5e0f6a2b8d4c1e7f9a3b5d2c6e"}
```

`requested_ref` is `null` when the source named the commit, and for libraries installed before
Scarab kept it; `resolved_commit` is always the full commit.

The install can name the fetch you reviewed, as the review page does: send the fetch answer's
`requested_ref` and `resolved_commit` with the install. When someone fetched the same content again
in between, under another ref or at another commit, the install fails with a 409 that names both,
and nothing is installed; fetch again and review it. Without them, the install records the most
recent fetch of the version.

```sh
curl -X POST "$SCARAB/v1/orgs/acme/library-installations" \
  -d '{"name": "acme::scarab-libs::deploy-helm", "content_hash": "5d1e…",
       "requested_ref": "v1.4.0", "resolved_commit": "8c2f4e1a9d7b3c5e0f6a2b8d4c1e7f9a3b5d2c6e"}'
```

Installing takes two steps:

1. **Fetch and review.** Scarab reads the file, checks that it is a library, that it invokes only
   `lib:` and `plugin:` targets (never `file:`), and that every library it invokes is installed in
   the org. It stores the file as a version, keyed by its SHA-256, and shows you the content.
   Nothing is installed yet. An org keeps its 50 most recent fetches that were never installed;
   an older one is deleted and has to be fetched again before you install it.
2. **Install.** Scarab installs the version you reviewed, by its hash. This asks you to confirm
   with your passkey.

```sh
curl -X POST "$SCARAB/v1/orgs/acme/libraries/fetch" \
  -d '{"source": "github.com/acme/scarab-libs//deploy-helm.yaml@8c2f…"}'
# → {"name": "acme::scarab-libs::deploy-helm", "content_hash": "5d1e…", "requested_ref": null,
#    "resolved_commit": "8c2f…", "content": "…"}

curl -X POST "$SCARAB/v1/orgs/acme/library-installations" \
  -d '{"name": "acme::scarab-libs::deploy-helm", "content_hash": "5d1e…"}'
```

**The name.** Pipelines name a library `lib:<name>`. The name defaults to
`<owner>::<repo>::<file>`, the file name without `.yaml` or `.yml`: the file above installs as
`acme::scarab-libs::deploy-helm`. You can type another name at install, such as `deploy-helm` or
`platform/helm`. A name is parts of letters, digits, `.`, `_` and `-`, joined by `::` or `/`, each
part starting with a letter, digit or `_`, at most 255 bytes; it is case-sensitive. When the
default does not fit that rule (a file name starting with `.` or `-`), the fetch asks you for a
name. Each name names one installation in the org. A name says nothing about where the library
came from: the installation records its source, and Policies match on the source. The
libraries allowed and blocked lists, under **Libraries** › **Library policies**, are such rules:
see [Library and plugin policies](/scarab-ci/usage/policies/#library-and-plugin-policies).

**Where Scarab reads from.** A public repository on github.com, or on the host of a Forgejo
connection, is read without credentials, over https only, from public addresses only, with no
redirects and a 1 MiB limit. Any other host is refused. For a private repository, pick a
connection of the installing org, and Scarab reads the file through it. A connection of another
org, or one with no org yet, is refused, and through a GitHub App connection Scarab reads only
repositories your org owns. When the connection cannot reach the repository (a GitHub App that is
not installed on it, for example), Scarab reads the file without credentials instead, which works
for a public repository; for a private one, give the connection access to it. See [Forge connections](/scarab-ci/get-started/deploy-helm/#forge-connections).

## Upgrade

Each installed library has its own page, reached from its row under Settings › Libraries
(`/orgs/<org>/settings/libraries/<id>/manage`, where the id is the installation's and stays the
same across upgrades). Its **Upgrade** asks for the newer
commit of the same file, and starts from the branch or tag the installed version was fetched at,
so fetching again reads where that ref points now. Scarab shows the diff from the installed
version, and the ref and commit before and after (`from v1.1.0 → 9f8e7d6 to v1.2.0 → 1a2b3c4`),
and **Upgrade** on the review page installs it. The passkey confirmation and the org's security
log name both. The upgrade names the version it replaces, so if someone else changed the
installation after you fetched, it fails and you fetch again to see the current diff.

**A new commit with the same file.** When the ref points to a new commit and the file did not
change there, there is no diff. The review page says so ("The file is the same at this commit;
installing moves `lib:…` from `v1.1.0 → 9f8e7d6` to `v1.2.0 → 1a2b3c4`") and **Move to this
commit** moves the installation to the new ref and commit, with the same passkey confirmation and
the same trust boxes as an upgrade. The fetch answer has `"content_unchanged": true`, and the
install names the installed hash as both `content_hash` and `replaces`. Pipelines run the same
content, and Runs created after the move name the new commit in their Steps' `origin`. Fetching
the ref and commit already installed shows nothing to do, and the API refuses that install with a
409.

**Trust carries over.** Trust is kept for a source, not a commit
([below](#trusting-a-library-with-forge-credentials)), so a new commit from a trusted source gets
the same grants as the installed one. When the org trusts the source with forge credentials, the
registry credential or the build sandbox, the review page lists them under **Trust**, one box
each, and **Upgrade** stays off until you tick every box. The fetch answer names them in
`carried_grants`, and the install must name the same grants in `carry_grants`:

```sh
curl -X POST "$SCARAB/v1/orgs/acme/library-installations" \
  -d '{"name": "acme::scarab-libs::deploy-helm", "content_hash": "9b2a…", "replaces": "5d1e…",
       "carry_grants": ["build_sandbox", "forge_credentials", "registry_credential"]}'
```

Leaving one out, or naming one the source does not hold, fails with a 400 that names the grants
the source holds. Trust given between your fetch and your install fails the same way: fetch again
to see it. The same rule applies to a first install from a trusted source, so removing a library
and installing a new commit does not skip it. With step-up on, the confirmation your passkey
signs and the org's security log name the grants carried.

A Run keeps the version it was created with. Its inlined Steps record the version's hash in
`origin`, and a Rerun or Retry uses the stored Steps, so upgrading changes only Runs created after
it.

## Remove

**Remove** deletes the installation. It needs no passkey. Pipelines that invoke it then fail to
compile with "`lib:acme::scarab-libs::deploy-helm` is not installed in this org"; Runs already created keep their
Steps. The stored version stays, so those Runs still show what they ran.

## Yank a version

Yank a version when it must stop running, for example because an image it pins has a known
vulnerability. Give a reason; every refusal shows it. Once a version is yanked in your org, Scarab
refuses:

- a new Run whose Steps or gates come from it, at Run creation;
- each launch of a Step that comes from it, including Reruns and Retries of Runs created before the
  yank (the Step fails with a configuration error naming the version and the reason);
- approving or releasing a gate that comes from it; a timer gate from it fails with the reason
  when its timer runs out;
- a debug Pod of a Step that comes from it.

A Policy cannot allow a yanked version, in `audit` mode or with `except_projects`. A yank applies
to one org. Yanking needs no passkey; lifting a yank does.

The usual fix is an upgrade to a version that pins the patched image, then a yank of the old one.

```sh
curl -X POST "$SCARAB/v1/orgs/acme/library-yanks" \
  -d '{"content_hash": "5d1e…", "reason": "pins helm with CVE-2026-1234; upgrade to 9b2a…"}'
```

## Install Scarab's clone library

`lib:thulasi-ram::scarab-ci::clone` checks out the Run's repository
([Checking out the repository](/scarab-ci/usage/pipeline-syntax/#checking-out-the-repository)).
It is the file `libs/clone.yaml` in Scarab's repository, and an org admin installs it like any
other library. Scarab installs no library into an org by itself, a new org included, and gives
no library more trust because Scarab published it.

1. Settings › Libraries › **Install library**, with the file
   `github.com/thulasi-ram/scarab-ci//libs/clone.yaml` and a Scarab release tag as the ref, such
   as `v0.4.0`. Use a release tag: each Scarab release checks that the file at its tag pins a
   published scarab-clone image by digest. Scarab reads it from github.com without credentials.
2. Keep the default name, `thulasi-ram::scarab-ci::clone` (the repository's owner and name and
   the file name), which is the name Scarab's docs and errors use. Review the file and install
   it. Confirm with your passkey.
3. On a Forgejo or GitHub token connection, also trust its source with forge credentials
   ([below](#trusting-a-library-with-forge-credentials)). Without that, a Run that invokes it is
   refused with the reason. On a GitHub App connection this step is not needed.

The library pins the scarab-clone image by digest. To run checkouts from a mirror's image, install
a copy of `libs/clone.yaml` that pins the mirror's image, and trust the mirror's source instead.
Its default name names the mirror's repository; type `thulasi-ram::scarab-ci::clone` as the name
to keep Pipelines unchanged.

## Install Scarab's build library

`lib:thulasi-ram::scarab-ci::build` builds an image with rootless BuildKit and pushes it with crane
([Building an image](/scarab-ci/usage/pipeline-syntax/#building-an-image)). It is the file
`libs/build.yaml` in Scarab's repository. It has two steps: `image` builds in the build sandbox
and holds no registry credential, and `push` pushes and holds it. Install it the same way as the
clone library, then give its source the trust its steps need:

1. Settings › Libraries › **Install library**, with the file
   `github.com/thulasi-ram/scarab-ci//libs/build.yaml` and a Scarab release tag as the ref.
2. Keep the default name, `thulasi-ram::scarab-ci::build`. Review the file and install it.
   Confirm with your passkey.
3. Trust its source for the build sandbox
   ([below](#trusting-a-library-for-the-build-sandbox)). Without that, a Run that invokes it is
   refused with the reason.
4. To push, trust its source with the registry credential
   ([below](#trusting-a-library-with-the-registry-credential)), so its push step receives the
   `REGISTRY_AUTH` secret. Without that the push runs anonymously and fails at a registry that
   needs a login. To push to the forge's own registry (GHCR, the Forgejo package registry) with
   no `REGISTRY_AUTH` secret, also trust its source with forge credentials
   ([below](#trusting-a-library-with-forge-credentials)). The build step never receives a
   credential, so it pulls only public base images, unless a placement profile logs its Pod in
   to ECR ([Private base images in ECR](/scarab-ci/usage/pushing-to-ecr/#private-base-images-in-ecr)).
5. If a placement profile grants push access (a ServiceAccount with a push role, say), the
   operator marks it `registry_auth_only: true`, and Pipelines route it to the push step with
   `placement_profiles: { push: [<profile>] }`. Scarab applies a marked profile only to that step,
   and only when the launch found that step eligible for a registry credential (step 4, in a Run
   that is not a fork pull request), whether or not a `REGISTRY_AUTH` secret exists
   ([Placement & resources](/scarab-ci/usage/pipeline-syntax/#placement--resources)).

The push step runs as uid 1000 (`security: { run_as_user: 1000 }`), not as root, so an org
Policy that denies run-as-root does not refuse it.

`push: true` needs the server to collect step results: the push step checks the layout against
the build step's `image` result, and refuses (exit 2) when there is none. Set the chart value
`secrets.resultsTokenSecret`. An earlier version of the library pushed without the check, with a
warning; upgrading it on a server with no results token secret makes every push fail
([`push: true` needs step results](/scarab-ci/usage/pipeline-syntax/#building-an-image)).

The library pins the rootless BuildKit image and the crane image by digest. A newer BuildKit or
crane is a new version of the file: upgrade the installation, and trust carries over because the
source is the same. To run a different builder, or BuildKit with other flags, install your own
library and trust its source instead. It gets the sandbox on the same terms as Scarab's.

**Upgrading from the `build` step kind.** The release that ships this library removes the
`build:` step kind, with no release in between that accepts both. A Pipeline with a `build:` step
fails to compile until you rewrite the step. The error for each such step holds its replacement,
written from the step's own `build:`, `needs`, `when`, `timeout`, `resources` and
`placement_profiles`, ready to paste:

```yaml
# before
- id: image
  build: { context: ., dockerfile: Dockerfile, image: ghcr.io/acme/app:1.2.0, push: true }

# after
- id: image
  invoke: lib:thulasi-ram::scarab-ci::build
  with: { context: ., dockerfile: Dockerfile, image: ghcr.io/acme/app:1.2.0, push: true }
```

`${{ outputs.image.image }}` reads the same result as before: BuildKit's metadata, whose
`containerimage.digest` is the digest of the image built. `${{ outputs.image.push }}` is new: the
pushed reference and digest, set only when the image was pushed; deploy by
`outputs.image.push.digest`. A step that reads `outputs.image.image` also receives the build
step's workspace, image layout included. `cache: registry` is gone, because
writing a registry cache needs the push credential in the build step; use `cache: s3` or no
cache. A step of a Run created before the upgrade that has not launched yet fails when it would
launch, and again on each retry or rerun, with the same replacement; start a new Run once the
Pipeline is changed. A Pipeline that fails its check creates no Run and posts no commit status
yet; the error shows in the repository's Runs list in Scarab.

## Install Scarab's image index library

`lib:thulasi-ram::scarab-ci::image-index` joins images built for different architectures into one
multi-architecture image with crane
([Joining images into one multi-architecture image](/scarab-ci/usage/pipeline-syntax/#joining-images-into-one-multi-architecture-image)).
It is the file `libs/image-index.yaml` in Scarab's repository. Its one step, `index`, pushes the
images that build layout steps left in the workspace (`layouts`) and the index, so it holds the
registry credential. It needs no build sandbox.

1. Settings › Libraries › **Install library**, with the file
   `github.com/thulasi-ram/scarab-ci//libs/image-index.yaml` and a Scarab release tag as the ref.
2. Keep the default name, `thulasi-ram::scarab-ci::image-index`. Review the file and install it.
   Confirm with your passkey.
3. Trust its source with the registry credential
   ([below](#trusting-a-library-with-the-registry-credential)). Without that the step runs
   anonymously, and the push fails at a registry that needs a login. To push to the forge's own
   registry with no `REGISTRY_AUTH` secret, also trust its source with forge credentials. Trust
   given to the build library's source does not reach this one: each source is trusted on its
   own.
4. A placement profile marked `registry_auth_only` (an ECR push role, say) reaches the step from
   a plain list, `placement_profiles: [<profile>]`, since the library has no other step.

The step runs as uid 1000 and pins the same crane image as the build library, by digest.

**Upgrading from a version without `layouts`.** Earlier versions read only images already in a
registry (`images`), and their header said the step reads nothing from the workspace. Many orgs
trusted the source with the registry credential on that basis. Trust is kept per source, so it
carries over to the upgrade, and with `layouts` the upgraded step reads image layouts from the
workspace and uploads them to the registry under that trust. It still runs no code from your
repository, and it checks each layout before it uploads anything (only directories and regular
files, no symlink, the manifest and every blob it names hash to their names, the manifest is the
digest its `layouts` line gives). The image index library pushes whatever layout its `layouts`
lines name: any step of the Pipeline, a plain `run:` step included, can write a layout under
`/workspace/.scarab-build/` and name its digest, so the digest check shows the layout was not
changed after it was named, not that a build step made it. The upgrade's review page lists the registry credential under **Trust**, and you
tick it to carry it over. A Pipeline that passes only `image` and `images` gets the same registry
calls as before and no workspace read.

## Install Scarab's build layout library

`lib:thulasi-ram::scarab-ci::build-layout` is the build library's build step without its push
step: it builds an image with rootless BuildKit and leaves it in the workspace as an OCI image
layout for the image index library to push
([Joining images into one multi-architecture image](/scarab-ci/usage/pipeline-syntax/#joining-images-into-one-multi-architecture-image)).
It is the file `libs/build-layout.yaml` in Scarab's repository. Its one step holds no credential
and pushes nothing.

1. Settings › Libraries › **Install library**, with the file
   `github.com/thulasi-ram/scarab-ci//libs/build-layout.yaml` and a Scarab release tag as the ref.
2. Keep the default name, `thulasi-ram::scarab-ci::build-layout`. Review the file and install it.
   Confirm with your passkey.
3. Trust its source for the build sandbox
   ([below](#trusting-a-library-for-the-build-sandbox)). It needs no registry credential trust,
   and should not be given one.

Never route a profile that grants push access to its step: the step runs your Dockerfile.

## Install Scarab's multi-architecture build library

`lib:thulasi-ram::scarab-ci::build-multiarch` builds an image once per platform its `platforms`
input names (`linux/amd64` and `linux/arm64` by default), each on a node of that architecture,
and pushes every image, their tags and the index from one step
([Building a multi-architecture image](/scarab-ci/usage/pipeline-syntax/#building-a-multi-architecture-image)).
It is the file `libs/build-multiarch.yaml` in Scarab's repository. Its matrix step `build` (one
instance per platform) builds in the build sandbox and holds no credential; its step `push` holds
the registry credential.
It holds its own copy of the build and index scripts and invokes no other library, so you review
the whole of it at install.

1. Settings › Libraries › **Install library**, with the file
   `github.com/thulasi-ram/scarab-ci//libs/build-multiarch.yaml` and a Scarab release tag as the
   ref.
2. Keep the default name, `thulasi-ram::scarab-ci::build-multiarch`. Review the file and install
   it. Confirm with your passkey.
3. Trust its source for the build sandbox
   ([below](#trusting-a-library-for-the-build-sandbox)). Without that, a Run that invokes it is
   refused with the reason.
4. Trust its source with the registry credential
   ([below](#trusting-a-library-with-the-registry-credential)). To push to the forge's own
   registry with no `REGISTRY_AUTH` secret, also trust it with forge credentials. Trust given to
   the build or image index library's source does not reach this one.
5. A profile marked `registry_auth_only` goes to the push step with the map form, beside a
   coordinate key for each build instance:
   `placement_profiles: { "build[arch=linux/amd64]": [...], "build[arch=linux/arm64]": [...], push: [<profile>] }`.
   Named on a build instance it fails that instance's launch.

**Upgrading from the version with fixed `amd64` and `arm64` steps.** Those steps are now
instances of `build`. After the upgrade, a Pipeline whose invoke names `amd64:` or `arm64:` in its
placement map fails to compile, and the error names the coordinate key to write
(`"build[arch=linux/amd64]"`). Change the Pipelines that invoke it in the same change as the
upgrade, or upgrade first and fix each Pipeline the error names. Upgrade every server replica
before you upgrade the library: an older server cannot parse its matrix and refuses each Run
that invokes it ([below](#a-matrix-from-an-input)). To roll the server back, first put the
library back to its earlier version.

The push step runs as uid 1000. The library pins the same BuildKit and crane images as the build
library, by digest.

## Trusting a library with forge credentials

A step with `forge_token` receives a forge credential ([Pipeline syntax](/scarab-ci/usage/pipeline-syntax/#forge-credentials-forge_token)).
On a Forgejo or GitHub token connection that credential is one long-lived token, so only a step
from a library installed from a source your org trusts receives it. No source is trusted by
default, Scarab's clone library included. An org admin trusts a source on the library's page under
Settings › Libraries (**Trust source**), or with the API:

```sh
curl -X POST "$SCARAB/v1/orgs/acme/library-trust" \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $SCARAB_TOKEN" \
  -d '{"source": "github.com/thulasi-ram/scarab-ci//libs/clone.yaml", "grant": "forge_credentials"}'
```

`grant` is `forge_credentials` when you leave it out.

Trust is for the source without a commit, so it holds when you upgrade the library from the same
source, and each upgrade still shows you its diff and asks you to confirm the grants it carries
([Upgrade](#upgrade)). Trusting needs a step-up; removing trust
(`DELETE …/library-trust?source=<source>&grant=forge_credentials`) does not. Each row under
Settings › Libraries says whether its source is trusted, and a trusted source no installed library
comes from is listed below them.

On a GitHub App connection Scarab mints a token for one repository each time a step launches, so
any step may ask for one and no trust is needed.

**After an upgrade.** Scarab 0.3.0 trusted its clone library without a trusted-source entry.
Migration 0090 adds that entry for every org that had the clone library from 0.3.0's release
manifest, for the source it was fetched from, listed as trusted by `scarab:migration-0090`. Those
orgs keep cloning after the upgrade, and an admin can remove the entry like any other.

## Trusting a library for the build sandbox

A step with `security: { sandbox: rootless-buildkit }` runs as uid 1000, not privileged, with
seccomp and AppArmor unconfined, which rootless BuildKit needs. Only a step from a library installed
from a source your org trusts for the build sandbox gets it. A step written in a Pipeline file, or
reached through `invoke: file:`, never does, and a library that a trusted library invokes needs its
own trust. No source is trusted by default, Scarab's build library included. An org admin trusts
a source on the library's page under Settings › Libraries (**Build sandbox › Trust source**), or
with the API:

```sh
curl -X POST "$SCARAB/v1/orgs/acme/library-trust" \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $SCARAB_TOKEN" \
  -d '{"source": "github.com/thulasi-ram/scarab-ci//libs/build.yaml", "grant": "build_sandbox"}'
```

Each grant is separate: trusting a source with forge credentials or the registry credential does
not trust it for the build sandbox, and the reverse. Trust is checked when a Run is created and
again each time the step launches, so removing it
(`DELETE …/library-trust?source=<source>&grant=build_sandbox`) stops retries and reruns too. A
`DELETE` that names no `grant` removes every grant of the source. Trusting needs a step-up;
removing trust does not.

## Trusting a library with the registry credential

A step with `registry_auth: true` may receive the Run's registry credential: the `REGISTRY_AUTH`
secret, or the credential the forge derives for its own registry. For the secret, a Step that the
Environment admits (approved, or no approvers) uses the Run's Environment chain; any other Step
uses the repository default, then the org default. Only a step from a library installed from a
source your org trusts with the registry credential receives one; a step written in a Pipeline
file, or reached through `invoke: file:`, runs your repository's own command and never does. The
forge-derived credential can write packages, so it needs the source trusted with forge
credentials as well. No source is trusted by default:

```sh
curl -X POST "$SCARAB/v1/orgs/acme/library-trust" \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $SCARAB_TOKEN" \
  -d '{"source": "github.com/thulasi-ram/scarab-ci//libs/build.yaml", "grant": "registry_credential"}'
```

A step that may not have the credential is not refused: it runs without one, and a push fails at
the registry. Each launch checks the trust again. A fork pull request never receives a registry
credential. Settings › Libraries shows this trust on the library's page under **Registry
credential**.

## A matrix from an input

For library authors. A library step's matrix dimension may be one input instead of a literal
list, so the caller chooses how many instances the step has. `build-multiarch` uses it:

```yaml
kind: library
interface:
  inputs:
    - name: platforms
      type: string
      required: false
      default: "linux/amd64,linux/arm64"
      validate: 'value.matches("^[ ,]*linux/[a-z0-9]+(/v[0-9])?([ ,]+linux/[a-z0-9]+(/v[0-9])?)*[ ,]*$")'
  outputs: [push]
steps:
  - id: build
    matrix:
      dimensions:
        arch: "${{ inputs.platforms }}"
    image: …
    env: [[PLATFORM, "${{ matrix.arch }}"]]
  - id: push
    needs: [build]
    image: …
    env:
      - [LAYOUTS, '${{ outputs.build.map(b, has(b.results.image) ? b.results.image.layout : "").join("\n") }}']
      - [COUNT, "${{ size(outputs.build) }}"]
```

- **The dimension is exactly `${{ inputs.<name> }}`**, as a quoted string. The input must be a
  declared `string` with a `default:`. An installed library is checked when it is installed,
  with no caller, and the default gives the matrix real values to expand and check against
  `validate:`; an input a matrix reads with no default is a compile error. A default that holds
  `${{` is refused too. Its value is split on commas and whitespace, with empty pieces dropped and
  the order kept, so `"linux/amd64, linux/arm64"` gives two instances,
  `build[arch=linux/amd64]` and `build[arch=linux/arm64]`. `${{ matrix.arch }}` in the step reads
  one value.
- **The value is known when the Pipeline compiles.** It is the caller's `with:` value or the
  input's default. A `with:` value that holds `${{ }}` has a value only when a step launches, after
  the matrix is expanded, so it is a compile error. A library that invokes this one cannot pass
  its own input through.
- **Values become step ids**, so a value may not hold `[`, `]`, `,`, `=`, `::service-` or a
  control character, and may not appear twice. `/` is allowed. `exclude:` and the matrix limits
  apply to the values as listed.
- **Guarded steps need `validate:`.** An input that feeds the matrix of a step with the build
  sandbox, `registry_auth` or `forge_token` counts as a read by that step, so it needs a
  `validate:` rule, like any string input such a step reads.
- **Only in a library.** A Pipeline file's own matrix is a literal list.

**Reading every instance.** In a library, a step that needs a matrix step of the same library
and reads `outputs.<step>` gets a list, one entry per instance, in expansion order (dimensions
sorted by name, the last changing fastest, `exclude` applied):

```
[ { "matrix": { "arch": "linux/amd64" }, "results": { "image": { … } } },
  { "matrix": { "arch": "linux/arm64" }, "results": {} } ]
```

`results` is `{}` for an instance that published nothing. Read fields with
`outputs.build.map(b, …)`; `outputs.build.image` is a compile error that shows the `map` form.
One instance stays readable by its id, `outputs["build[arch=linux/amd64]"]`. A Pipeline file's
own steps see no change. Results are text a step wrote, so they
reach a step only through `env:`, as every result does.

**`join`.** `<list>.join()` and `<list>.join(<separator>)` join a list of strings; any other
element is an error when the step launches. It works in every Pipeline and library expression:
`${{ }}`, `when:`, `validate:` and a matrix `exclude`. Policies do not have it. In a YAML single-quoted
string, write the separator as `"\n"` so CEL reads a line break. `size`, `map` and `has` are
standard CEL.

**IR version 4.** A Pipeline whose steps read a list of instances, or that calls `join` in a
template, a `when:` or a `validate:`, compiles to IR version 4. A server that knows only versions
up to 3 refuses to launch a step of such a Run ("this Run was compiled for IR version 4; this
server understands versions up to 3"). Not everything is covered by the version: a 0.7.7 server
fails a trigger `when:` or a matrix `exclude` that calls `join` before any Run exists, and cannot
parse a matrix dimension written as an input. So upgrade every server replica first, then
upgrade libraries that use these features and start calling `join`. Redeliver the webhook, or
rerun, for anything that failed in between.

**Placement per instance.** A caller places each instance with a coordinate key in the
invoke's `placement_profiles` map, `"build[arch=linux/arm64]": [arm64-builders]`
([Reuse: `invoke`](/scarab-ci/usage/pipeline-syntax/#reuse-invoke)), so which nodes each
instance runs on stays the caller's choice, among the profiles the operator defined.

## Check a Pipeline before you push

`scarab validate` without `--server` reports each `lib:` target as unresolved and checks the rest
of the Pipeline. With `--server`, the server compiles it against your org's installed libraries:

```sh
scarab validate .scarab/ci.yaml --server "$SCARAB" --org acme --project web
```

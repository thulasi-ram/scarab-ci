An org admin installs a library once, and every Pipeline in the org can use it:

```yaml
steps:
  - id: ship
    invoke: lib:acme/deploy-helm
    with: { release: web }
```

A library is a YAML file with `kind: library` (see [Reuse: `invoke`](/scarab-ci/usage/pipeline-syntax/#reuse-invoke)).
Scarab stores the file it installed and compiles Pipelines against that copy, so a Pipeline never
fetches anything, and the org decides when a library changes.

## Install a library

Settings › Libraries › **Install library**, or the API. **Install library** asks for a **source**,
a file in a git repository at a full commit id, and **Fetch and review** opens the review page
(`/orgs/<org>/settings/libraries/review`), which every library goes through, Scarab's own
included.

```
github.com/acme/scarab-libs//deploy-helm.yaml@8c2f4e1a9d7b3c5e0f6a2b8d4c1e7f9a3b5d2c6e
```

The part before `//` is the repository and the part after it is the file. A branch or tag is
refused, because it can point somewhere else after you review it.

Installing takes two steps:

1. **Fetch and review.** Scarab reads the file, checks that it is a library, that it invokes only
   `lib:` and `plugin:` targets (never `file:`), and that every library it invokes is installed in
   the org. It stores the file as a version, keyed by its SHA-256, and shows you the content.
   Nothing is installed yet. An org keeps its 50 most recent fetches that were never installed;
   an older one is deleted and has to be fetched again before you install it.
2. **Install.** Scarab installs the version you reviewed, by its hash. This asks you to confirm
   with your passkey.

```sh
curl -X POST "$SCARAB/v1/orgs/acme/libraries/fetch" \
  -d '{"source": "github.com/acme/scarab-libs//deploy-helm.yaml@8c2f…"}'
# → {"publisher": "acme", "name": "deploy-helm", "content_hash": "5d1e…", "content": "…"}

curl -X PUT "$SCARAB/v1/orgs/acme/libraries/acme/deploy-helm" \
  -d '{"content_hash": "5d1e…"}'
```

**The name.** Pipelines name a library `lib:<publisher>/<name>`. The publisher defaults to the
repository's owner and the name to the file name, and you can change both at install. Each
publisher and name names one installation in the org. A name says nothing about where the library
came from: the installation records its source, and Policies match on the source. The
libraries allowed and blocked lists, under **Libraries** › **Library policies**, are such rules:
see [Library and plugin policies](/scarab-ci/usage/policies/#library-and-plugin-policies).

**Where Scarab reads from.** A public repository on github.com, or on the host of a Forgejo
connection, is read without credentials, over https only, from public addresses only, with no
redirects and a 1 MiB limit. Any other host is refused. For a private repository, pick a
connection of the installing org, and Scarab reads the file through it. A connection of another
org, or one with no org yet, is refused, and through a GitHub App connection Scarab reads only
repositories your org owns. See [Forge connections](/scarab-ci/get-started/deploy-helm/#forge-connections).

## Upgrade

Each installed library has its own page, reached from its row under Settings › Libraries
(`/orgs/<org>/settings/libraries/<publisher>~<name>/manage`). Its **Upgrade** asks for the newer
commit of the same file. Scarab shows the diff from the installed version, and **Upgrade** on the
review page installs it. The upgrade names the version it replaces, so if someone else changed the
installation after you fetched, it fails and you fetch again to see the current diff.

A Run keeps the version it was created with. Its inlined Steps record the version's hash in
`origin`, and a Rerun or Retry uses the stored Steps, so upgrading changes only Runs created after
it.

## Remove

**Remove** deletes the installation. It needs no passkey. Pipelines that invoke it then fail to
compile with "`lib:acme/deploy-helm` is not installed in this org"; Runs already created keep their
Steps. The stored version stays, so those Runs still show what they ran.

## Yank a version

Yank a version when it must stop running, for example because an image it pins has a known
vulnerability. Give a reason; every refusal shows it. Once a version is yanked in your org, Scarab
refuses:

- a new Run whose Steps or gates come from it, at Run creation;
- each launch of a Step that comes from it, including Reruns and Retries of Runs created before the
  yank (the Step fails with a configuration error naming the version and the reason);
- approving or releasing a gate that comes from it; a timer gate from it fails with the reason
  when its timer runs out;
- a debug Pod of a Step that comes from it.

A Policy cannot allow a yanked version, in `audit` mode or with `except_projects`. A yank applies
to one org. Yanking needs no passkey; lifting a yank does.

The usual fix is an upgrade to a version that pins the patched image, then a yank of the old one.

```sh
curl -X POST "$SCARAB/v1/orgs/acme/library-yanks" \
  -d '{"content_hash": "5d1e…", "reason": "pins helm with CVE-2026-1234; upgrade to 9b2a…"}'
```

## Install Scarab's clone library

`lib:thulasi-ram/clone` checks out the Run's repository
([Checking out the repository](/scarab-ci/usage/pipeline-syntax/#checking-out-the-repository)).
It is the file `libs/clone.yaml` in Scarab's repository, and an org admin installs it like any
other library. Scarab installs no library into an org by itself, a new org included, and gives
no library more trust because Scarab published it.

1. Find the commit of a Scarab release tag. The source needs the full 40-character commit id;
   a tag name is refused:

   ```sh
   git ls-remote https://github.com/thulasi-ram/scarab-ci 'refs/tags/v0.3.0^{}'
   # 630461e6457dc4ec9dfcda164e791d424fc416ab	refs/tags/v0.3.0^{}
   ```

   Use a release tag's commit: each Scarab release checks that the file at its tag pins a
   published scarab-clone image by digest.
2. Settings › Libraries › **Install library**, with the source
   `github.com/thulasi-ram/scarab-ci//libs/clone.yaml@<commit>`. Scarab reads it from github.com
   without credentials.
3. Review the file and install it as `lib:thulasi-ram/clone` (the defaults: the publisher is the
   repository's owner, the name is the file name). Confirm with your passkey.
4. On a Forgejo or GitHub token connection, also trust its source with forge credentials
   ([below](#trusting-a-library-with-forge-credentials)). Without that, a Run that invokes it is
   refused with the reason. On a GitHub App connection this step is not needed.

The library pins the scarab-clone image by digest. To run checkouts from a mirror's image, install
a copy of `libs/clone.yaml` that pins the mirror's image, under the same name, and trust the
mirror's source instead.

## Trusting a library with forge credentials

A step with `forge_token` receives a forge credential ([Pipeline syntax](/scarab-ci/usage/pipeline-syntax/#forge-credentials-forge_token)).
On a Forgejo or GitHub token connection that credential is one long-lived token, so only a step
from a library installed from a source your org trusts receives it. No source is trusted by
default, Scarab's clone library included. An org admin trusts a source on the library's page under
Settings › Libraries (**Trust source**), or with the API:

```sh
curl -X POST "$SCARAB/v1/orgs/acme/library-trust" \
  -d '{"source": "github.com/thulasi-ram/scarab-ci//libs/clone.yaml"}'
```

Trust is for the source without a commit, so it holds when you upgrade the library from the same
source, and each upgrade still shows you its diff. Trusting needs a step-up; removing trust
(`DELETE …/library-trust?source=<source>`) does not. Each row under Settings › Libraries says whether
its source is trusted, and a trusted source no installed library comes from is listed below them.

On a GitHub App connection Scarab mints a token for one repository each time a step launches, so
any step may ask for one and no trust is needed.

**After an upgrade.** Scarab 0.3.0 trusted its clone library without a trusted-source entry.
Migration 0090 adds that entry for every org that had the clone library from 0.3.0's release
manifest, for the source it was fetched from, listed as trusted by `scarab:migration-0090`. Those
orgs keep cloning after the upgrade, and an admin can remove the entry like any other.

## Check a Pipeline before you push

`scarab validate` without `--server` reports each `lib:` target as unresolved and checks the rest
of the Pipeline. With `--server`, the server compiles it against your org's installed libraries:

```sh
scarab validate .scarab/ci.yaml --server "$SCARAB" --org acme --project web
```

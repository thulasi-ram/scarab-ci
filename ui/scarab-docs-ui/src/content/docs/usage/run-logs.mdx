---

Scarab stores each step's output in chunks while the step runs. You can read it on the Run page,
with `scarab logs`, or through the API.

## On the Run page

Open a Run and pick a step. The Logs tab shows the try in view and follows it while it runs.

A try that failed opens on its **Error** tab, before Logs. It says how the try failed and why, how
long it waited for a node before it ran, when it started and what started it, and shows the last
lines of its log. **Open in Logs** goes to the whole log. A try that did not fail has no Error tab.

- The pane loads at least the last 2 MiB of the try's log, from the start of the stored chunk
  that holds the cut, so up to about 256 KiB more. When the log is longer, a notice above it says
  how much shows, for example "Showing the last 2.1 MiB of 14.3 MiB. Line numbers start here." The
  sizes are in KiB, MiB and GiB, powers of 1024. The whole size is the stored size when the pane
  opened the log, and grows as more is stored; while the try runs the notice says "so far". Line
  numbers count from the first line loaded, not from the start of the log.
- **Load full log** reads the log again, up to 8 MiB. It shows only when the whole log is 8 MiB or
  less.
- **Download** saves the whole log of the try as a text file, with the bytes the step wrote and a
  `[scarab] …` line for each note the server stored with the log (see
  [Notes in a log](#notes-in-a-log)). It is in the log toolbar for every try.
- A note the server stored with the log (the log source restarted, part of the log was not
  stored, the end could not be read) shows as a row of its own, set apart from the step's output.
- The pane keeps at most 8 MiB. Past that, it drops lines from the top as new output arrives. The
  notice counts those too, and the lines that stay keep their numbers. A log with no line breaks
  has no line to drop: once its last line is over 16 MiB, the pane cuts its start down to 8 MiB, at
  a character boundary.
- The server can still be storing a log after its try ended: it reads the container's log behind
  the step, and a step that prints fast can end before all of it is stored. Until it is, the pane
  says "The log is still being stored." and shows the rest as it is stored. It says "No log output
  was captured for this try." only once the server says the log is whole. When the server stops
  waiting for it (after 10 minutes), the pane says "The log is still being stored; reload to check
  again." and stops following.
- If the connection drops while the try runs, the pane connects again after 1 s, then 2 s, 4 s and
  so on up to 30 s, and continues after the last part it received. A connection that stayed open
  longer than the last wait starts the waits over at 1 s. After three reopens in a row that fail
  before the stream opens, the pane asks the server about its position. Only when the server
  answers 400 does it clear the pane and load the end of the log again, as much as it showed
  (2 MiB, or 8 MiB after Load full log). While the server cannot be reached, it keeps its position
  and keeps trying.

A shared service's pane works the same way. Its **Download** is in the pane's header and in the
notice above a longer log, and saves the whole log of the service in the Take in view.

A `\r\n` line end shows as one line break. A lone `\r`, which a progress bar writes to redraw its
line, also shows as a line break, so each redraw is a line of its own. Download keeps both as the
step wrote them.

## With `scarab logs`

```sh
scarab logs <run-id>
```

This prints the log of every try of every step of the Run, in step order, and follows the Run until
it finishes. It prints the whole log, with no 2 MiB cut. It prints each note the server stored with
the log on stderr, as `[scarab] <text>`, so stdout holds the step output only. It exits 1 when a stored part of the log
cannot be read. When the reader of its output goes away, as with `scarab logs <run-id> | head`, it
stops and exits 0. It reads `SCARAB_SERVER` and `SCARAB_TOKEN` (see [API tokens](/scarab-ci/usage/api-tokens/)).

## Through the API

`{step}` is the Step's key, listed as `steps[].key` by `GET /v1/runs/{id}`, or its id
percent-encoded (see [Step keys](/scarab-ci/get-started/deploy-helm/#step-keys)).

| Call | What it returns |
|------|-----------------|
| `GET /v1/runs/{id}/steps/{step}/logs` | one step's log as Server-Sent Events. `?attempt=` picks one try, `?tail=<bytes>` asks for the end of the log only (at most 64 MiB), `?from=<event id>` resumes |
| `GET /v1/runs/{id}/steps/{step}/logs/raw?attempt=<id>` | one try's whole log as `text/plain`, sent as an attachment, each note written as a line `[scarab] <text>`. `?markers=none` returns the stored output bytes only. `?sidecar=<index>` reads a sidecar's log for the same try. `attempt` is an attempt id such as `a1` (listed as `steps[].attempt_list[].id` by `GET /v1/runs/{id}`), not a number; without it, the Step's latest attempt. An unknown id answers 404 and lists the Step's attempt ids |
| `GET /v1/runs/{id}/services/{service}/logs` | one shared service's log, with the same `?tail=` and `?from=` |
| `GET /v1/runs/{id}/services/{service}/logs/raw?take=<n>` | one shared service's whole log in Take `n` as `text/plain`, sent as an attachment named `scarab-<run>-<service>-take<n>.log` (a character outside `A-Z`, `a-z`, `0-9`, `_` and `-` becomes `_`). Without `?take=`, the current Take. `?markers=none` as above |
| `GET /v1/runs/{id}/logs` | every step's log, as `scarab logs` reads it. Event ids, no `?tail=` |

Each `data` event carries about 256 KiB of one try's log (at most 256 KiB plus two stored chunks)
and has an id `<attempt_id>:<next_seq>`, the position after it. Send it back as `?from=` or in the
`Last-Event-ID` header to continue after that event. The server answers 400 to an id it cannot
read and to one that names a try outside the log you asked for. An id with a position past the
end of a try's log is not refused: the stream sends nothing for that try until the log passes that
position.

A UTF-8 character that a stored chunk cuts in two is sent whole when the next chunk arrives. On a
running try the server waits at most two polls for it, then sends the cut bytes as U+FFFD; on a
try that has ended it sends U+FFFD at once.

The stream ends one poll after the Run finishes, or when the Run no longer exists. A try that has ended and sent its whole log, with no new part for 30 s, is no longer
read on each poll.

A try that has ended and whose log a server replica is still storing (it holds the try's log
lease) is read like a running try, also after the Run finished: the stream does not end while one
is, for at most 10 minutes. The stream sends `event: storing` with `{"storing":true}` when that
starts and `{"storing":false}` when it stops, and `{"storing":true,"wait_over":true}` when it ends
after the 10 minutes with the log still being stored. A running try never counts.

With `?tail=`, when the log is longer than the tail, the stream starts at the stored chunk that
holds the byte `tail` bytes before the end, so it sends at least `tail` bytes and less than one
chunk more. It first sends `event: truncated` with `{"skipped_bytes":N,"total_bytes":M}`, where
`M` is the stored length when the stream opened. `event: error` means a
stored part of the log could not be read, and the stream ends after it.

Each note the server stored with the log is sent as `event: marker`, with an id like a `data`
event's (the position after it) and data `{"kind":"…","reason":"…","text":"…"}` (`reason` only on
`not_stored`). A `data` event never spans a note. Clients built before Scarab 0.7 ignore the event.

The stream sends each `\r\n` as `\n`. The raw download returns the stored bytes unchanged, with
a line `\n[scarab] <text>\n` where each note is; `?markers=none` leaves the notes out. Either way,
the `X-Scarab-Log-Markers` header says how many notes the log has. A plain text file cannot prove
that a line is a note: a step can print `[scarab] …` itself. The stream's `marker` events and the
header can.

## How the server stores a log

A server replica reads each step's container log while the step runs and stores it in chunks of
about 256 KiB at most: it stores what it has read once that reaches 256 KiB, 250 ms after the
first byte of it, and when the read ends. The raw download and the stream fetch up to 16 chunks
ahead. One replica at a time reads a log: it holds the log's lease, and the database refuses a
chunk from a replica whose lease another replica took over.

### Secret values

Before it stores anything, the server replaces each value the step can read with `***`: the
step's secrets, its registry credential, its forge token and its OIDC token. It redacts the log as
one stream, so a value split between two chunks of output is still replaced. A step's values
redact only that step's log (and its sidecars' logs), never another step's.

The values come from the step's value ledger. Each time Scarab launches a step, before it creates
the Pod or any Secret, it stores the values that launch hands the step as a new generation of the
ledger, encrypted with the server's master key, in Postgres. Every replica reads the ledger, so
the replica that reads a log does not have to be the one that launched the step, and a step
launched again with a new token is redacted with both tokens. A replica loads every generation or
none: one that cannot decrypt the ledger (it has a different master key) reads none of that log
and leaves it to a replica that can. Scarab never reads a value back from a Kubernetes Secret.

A failure cause or infra message about a step (what the Run page shows when a step fails) is
redacted with the same values. The server reads the ledger from Postgres each time it stores a
cause, so a token another replica added after this one last loaded the ledger is redacted too. A
cause about a step with no ledger, or with values over 256 KiB in all (see
[Edges of a value](#edges-of-a-value)), is replaced by "the cause was not stored: it may quote
secret values that could not be checked". A cause that ends in the first bytes of a value has
them replaced by `***`, as a log's confirmed end does. The server keeps at most 1,024 bytes of an
API server message in a cause and ends a cut message with `…`; the bytes before the `…` count as
the end.

A Pod that a Scarab server keeps a ledger for carries the label `scarab.io/value-ledger: "1"`, and
Scarab's per-Pod Secrets for it are named `<pod>-v-secrets`, `<pod>-v-registry`, `<pod>-v-token`
and `<pod>-v-oidc`. An earlier version writes other names, which such a Pod does not mount. The server reads the log of a labelled Pod only. A Pod without the label was
started by an earlier Scarab version, and its log gets one note in place of the rest:

```text
[scarab] the rest of this log was not stored: this step was started by an earlier Scarab version, so its secret values are not known
```

Someone who can create Pods in the step namespace can create a labelled Pod themselves. Scarab
does not defend against that: that person can already read the step's Secrets.

### Forge tokens and when a ledger is deleted

Each ledger generation that holds a minted forge token records when that token was revoked, so
each token is revoked once:

- A launch that replaces an earlier one (a re-drive) revokes the tokens of older generations,
  never the one it mounted, so a launch that returns late does not revoke a newer launch's token.
- When the try ends, the server that sees the end revokes the tokens not revoked yet.
- A launch whose minted token is in no generation of the ledger revokes that token and fails, so a
  token is never left live with nothing to revoke it.

The ledger is deleted:

- once every log of the try (the step's and each sidecar's) is stored to its end or closed with a
  note, and its tokens are revoked;
- otherwise an hour after the try ends or its Run ends, once its tokens are revoked;
- at the latest 24.5 hours after its first generation (the longest step timeout, the 30-minute
  provisioning deadline and an hour), once the try is not running, even while a revocation still
  fails. Those tokens then expire on their own: a GitHub App token lasts an hour.

One replica retries failed revocations and deletes ledgers: the one that holds the lease
`ledger-sweep`. It runs every 30 seconds in a task of its own, so a forge that does not answer
delays no scheduling. It waits at most 20 seconds for one try's revocations, and a revocation that
fails or times out is tried again after 1 minute, then 2, 4 and so on up to an hour. A log whose
end was not read when its ledger was deleted gets the `ledger_purged` note.

### Edges of a value

Where values overlap in a log, the run of bytes they cover is one `***`. With the values
`user:hunter2pw` and `hunter2pw-and-more-secret`, the line `dsn=user:hunter2pw-and-more-secret`
is stored as `dsn=***`. A value that repeats a word counts too: `abab` printed twice in a row is
one `***`. Two values that only touch (one ends where the next starts) stay two: `abc` then `def`
is `******`, and so is a value printed twice in a row when its end does not begin it again.

Edges of a log can cut a value:

- When the server has confirmed that the container ended and the log ends in the first bytes of a
  value, it stores `***` for them.
- When a log, or its part after a `source_restarted` note (below), starts inside a value, the
  server stores `***` for the value's last bytes if there are 8 or more of them. Fewer than 8
  bytes of a value's end can be stored there.
- When a log or a part lies wholly inside a value (it starts after the value's first byte and
  the container ended before the value's last byte), the server stores `***` for it if it is 8
  bytes or longer. A shorter one is stored.

A log starts inside a value when the kubelet rotates the log file between two lines of a
multi-line value (a PEM key, a kubeconfig), or between the two halves of a line over 16 KiB.
Value bytes that start a log and stop before the value's end, with other output after them, are
stored.

The rule for the start applies to every log. So when a step's output begins with 8 or more bytes
that end a secret value, the log shows `***` there, even when the step printed those bytes for
another reason. Up to one value's length of a log's first bytes can show a moment later than the
rest, until the server reads enough to tell whether a value starts there.

A step's values can add up to at most 256 KiB (every value the step can read, each counted once).
The server keeps up to 52 bytes of lookup tables per value byte while it reads a log, so the cap
holds that at 13 MiB per step. It keeps at most 128 MiB of these tables in all by default and builds them
for 2 steps at a time; a log read that does not fit waits until another read ends, so with many
steps near the cap at once, some logs show later. A PEM key is about 3 KiB and a kubeconfig is
under 10 KiB. A step
over the cap gets one note in place of its log, and the server reads none of it:

```text
[scarab] the rest of this log was not stored: this step's secret values add up to more than 256 KiB, more than a log is checked against
```

### When a read ends

A followed read can end while the container still runs (a kubelet restart, a dropped connection
between the API server and the kubelet). So when a read ends, the server asks Kubernetes about the
container for up to 10 seconds. The log is complete only once the container has ended at about the
time the read ended. Otherwise the server keeps what it stored, drops the bytes it held back, and
reads again.

A followed read that gets no byte for 5 minutes fails and is opened again. A node or a load
balancer can drop a connection without telling either end, and the Kubernetes client Scarab uses
(kube 4.0) has no TCP keepalive setting, so without this read timeout the live log would stop until
the step ended. A step that prints nothing for 5 minutes is read again from the start each time;
when the log begins with the stored part, nothing new is stored and no note is added.

A sidecar or shared service whose container ended and waits to restart (for example in
`CrashLoopBackOff`) is read again after 3 seconds, then 6, 12 and so on up to 60 seconds. A new
container that already runs is read at once.

A read that breaks part way, or a later read, reads the container's log again from the start and
compares it with the part already stored, by a SHA-256 digest of each stored chunk:

- When the log begins with the stored part, the server stores only what follows it.
- When it does not, because the kubelet rotated the log file, a sidecar or service container
  restarted, or the step was launched again with a new secret value, the server stores a note and
  then the whole log it read. Lines stored before the note may show again after it.

### Notes in a log

A note is a row of the log's index, written by the server; a step cannot write one by printing
text. These are the notes:

| Note (`kind`) | Text |
|---|---|
| `source_restarted` | the log source restarted; lines before this point may be missing or repeat |
| `not_stored` (`no_ledger`) | the rest of this log was not stored: this step was started by an earlier Scarab version, so its secret values are not known |
| `not_stored` (`ledger_purged`) | the rest of this log was not stored: its secret values were removed before it could be read |
| `not_stored` (`values_too_large`) | the rest of this log was not stored: this step's secret values add up to more than 256 KiB, more than a log is checked against |
| `incomplete` | the end of this log could not be read |

`not_stored` covers the rest of the log, and the server stores none of the step's output after it:

- `no_ledger`: the step has no value ledger, or its Pod has no `scarab.io/value-ledger` label. An
  earlier Scarab version started it, for example a step that ran across the upgrade to 0.7. A step
  of an earlier version whose Pod is gone when the server reads its end gets this note if it
  started, and no note if it never started.
- `ledger_purged`: the step's ledger was deleted before its log was read to the end (see
  [above](#forge-tokens-and-when-a-ledger-is-deleted)).
- `values_too_large`: the step's secret values add up to more than 256 KiB (see
  [Edges of a value](#edges-of-a-value)). A step launched again with more values can pass the
  cap part way through its log; the note then follows the part already stored.

`incomplete` is written when the step's Pod is gone before the end of its log was read, or when
the server could not read the end of the log within 30 minutes after the step ended. A step
cancelled before it started gets no note. Output the kubelet rotated away before the server read
it is gone, and no note marks the gap: the kubelet's log API does not say that an earlier file was
deleted. When that happens before the server's first read of the log, the log starts at the oldest
byte the kubelet kept.

Scarab stores a step's log so you can read it with the Run; it is not a log store. A step that
writes more than the kubelet keeps for one container (`containerLogMaxSize`, 10 MiB by default)
between two reads can lose lines. To keep all of a large log, send the container output to a log
store with a node log agent, such as Vector or Fluent Bit.

Logs stored by Scarab 0.6 and earlier keep their notes as they were stored, as output lines that
start with `scarab:`.

## Upgrading from Scarab 0.6

Read [Upgrading to Scarab 0.7](/scarab-ci/get-started/deploy-helm/#upgrading-to-scarab-07) first.
For logs, the upgrade means:

- Let running Runs finish before you upgrade. A step or shared service that runs across the
  upgrade was started without a value ledger, so the new server stores none of its output after
  the upgrade: its log gets the `no_ledger` note after the part the old server stored, and a
  failure cause about it reads "the cause was not stored".
- Once migration 0099 has run, the database refuses log chunks from a 0.6 server. With the chart's
  default `strategy.type: Recreate` no 0.6 server runs by then. With `RollingUpdate`, the 0.6
  servers still running store no log, and a step one of them launches gets the `no_ledger` note and
  nothing else.
- Never drop the `log_chunks_fenced` check on `log_chunks`. It is what stops a 0.6 server that is
  still running during a rolling update from storing output it cannot redact.
- Forge tokens minted by 0.6 are in no ledger, so 0.7 does not revoke them; they expire on their
  own.
- A 0.6 server does not start on the migrated database. To go back, see
  [Rolling back to Scarab 0.6](/scarab-ci/get-started/deploy-helm/#rolling-back-to-scarab-06): the
  revert deletes the notes of logs stored by 0.7 and every value ledger, and the output stays
  readable.
- Every replica must use the same master keys (see
  [Master keys and value ledgers](/scarab-ci/get-started/deploy-helm/#master-keys-and-value-ledgers)).

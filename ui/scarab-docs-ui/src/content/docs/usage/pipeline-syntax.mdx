## The model, in brief

A **step** is the basic unit of work: an OCI **image** plus a **command** (the step contract),
which Scarab runs as a single Kubernetes **Pod**. A **pipeline** is a group of steps, plus how they
are triggered and wired together. Structurally a pipeline is a **flat recursive DAG**
(`Pipeline → Step`).

You write YAML, with **CEL** for expressions. Scarab compiles it to a **typed IR**, and the IR
(not the YAML) defines what a valid pipeline is.
`invoke` reuses a library by inlining it into the caller's DAG at compile time.
`matrix` is a modifier that fans a step out over a set of inputs.

Compilation is **static**: the whole DAG (every matrix combination, every inlined library step) is
materialised and validated at submit time, so a cycle, a dangling `needs`, or an empty matrix
dimension is rejected up front, never discovered mid-run.

Keys are **strict** at every level of that schema. A key Scarab does not know (a misspelling,
a field borrowed from another CI system, a knob from a newer version) is a compile error that names
the key and the ones that were expected. It is never silently ignored:

```
unknown field `cpu_milis`, expected `cpu_millis` or `memory_mib`
```

Ignoring unknown keys would be worse: `resources: { cpu_milis: 500 }` would parse cleanly, report
`ok`, and then run the step with no CPU request at all, with nothing to show the setting was
dropped.

A repo's CI lives in `.scarab/`. A triggered pipeline is a YAML file such as `.scarab/ci.yaml`;
its file name is the default display name (`ci.yaml` reads as `ci`, overridable with a top-level
`name:`). Reusable **libraries** (files marked `kind: library`) live under `.scarab/lib/` by
convention and are pulled in with [`invoke`](#reuse-invoke). Start from
[Run locally](/scarab-ci/get-started/run-locally/) to submit your first pipeline.

:::caution[Commit `.scarab/`, and never blanket-ignore it]
`.scarab/` is **tracked source**: it is read from the triggering commit, so an ignored pipeline file
is a pipeline that does not exist. The catch is that a local `scarab-server` also writes its
development object store *inside* that directory (`SCARAB_OBJECT_DIR` defaults to
`./.scarab/objects`). That tempts a blanket `/.scarab` ignore rule, which then silently swallows
`git add .scarab/ci.yaml`. Ignore only the runtime path instead:

```gitignore
# runtime state only — the pipeline configs beside it are tracked source
/.scarab/objects/
```
:::

A minimal pipeline is an `on:` block and a list of `steps`:

```yaml
on:
  push: {}
  pull_request: {}

steps:
  - id: checkout
    invoke: lib:thulasi-ram::scarab-ci::clone

  - id: check
    image: rust:1-bookworm
    needs: [checkout]
    command: ["cargo", "check"]
```

The rest of this page goes through each part: triggers and inputs, the step shape, wiring and
reuse, deploys, and the operational settings.

## Triggers: `on:`

`on:` maps a trigger kind to a filter. The kinds Scarab understands are `push`, `pull_request`,
`tag`, `release`, `comment`, `cron`, `manual`, `api`, and `upstream`. An empty `on:` means the
pipeline has no automatic triggers: it runs only when launched explicitly.

A `pull_request` trigger fires when a pull request is opened or reopened, when new commits reach
it, and when it is edited to target another base branch. Closing or merging it, a label, an
assignee, a review request, marking it ready for review, or an edit of its title or description
starts no Run and posts no status; the webhook answers 200 with `{"ignored": "<reason>"}`. This
holds on GitHub and Forgejo.

```yaml
on:
  push: {}
  pull_request: {}
```

Each kind takes an optional `when:` CEL guard over the event context, so a trigger can fire
selectively:

```yaml
on:
  push:
    when: "event.branch == 'main'"
```

### Changed files: `event.changed_paths`

A `when:` can read the files a push or pull request changed, as `event.changed_paths`: a sorted
list of repository paths. This Pipeline builds an image only when something under
`docker/ci-tools/` changed:

```yaml
on:
  push:
    when: event.changed_paths.exists(p, p.startsWith("docker/ci-tools/"))
  pull_request:
    when: event.changed_paths.exists(p, p.startsWith("docker/ci-tools/"))
```

Where the list comes from:

- **push**: the forge's compare API, from the branch's head before the push to its head after
  it, asked once per delivery and only when a Pipeline whose `push` trigger matches reads
  `event.changed_paths`. The list is every file that differs between the two commits, including
  a file changed only in a merge's conflict resolution. A renamed file is listed under both
  names.
- **pull_request**: the forge's pull request files API, asked the same way. The list is the pull
  request's files when Scarab handles the webhook, which can differ from the event's head commit
  if the pull request moved since.
- Every other trigger (`tag`, `release`, `comment`, `cron`, `manual`, `api`, `upstream`) has no
  list.

A repository whose Pipelines do not read `event.changed_paths` makes no extra API calls. Each
request may take at most 5 seconds; past that the list is unknown.

Sometimes the list is **unknown**. Unknown is not the same as an empty list. While the list is
unknown, a `when:` that needs it counts as true, so the Run starts, and the Run's activity log
says why:

```text
changed paths unknown: forced push; the path filter in `when:` was not applied (on.push)
```

The reasons:

| Reason in the activity log | When |
|---|---|
| this trigger does not say which files changed | a trigger with no list |
| new branch | the push created the branch, so there is no earlier commit to compare with |
| the push deleted the branch | the push deleted the branch |
| forced push | the earlier head is not an ancestor of the new one, on GitHub and on Forgejo |
| the branch's earlier head is not on the new head's first-parent line | Forgejo only: a merge whose first parent is not the branch, such as a `git pull` merge pushed back. Forgejo lists each commit's files against its first parent only, so the list could miss a change |
| 300 or more files changed | a GitHub push: its compare API lists at most 300 files |
| 3000 or more files changed | a pull request, or a Forgejo push |
| more than 1000 commits were pushed, so the changed files were not asked for | a Forgejo push of more than 1,000 commits |
| the forge's changed files answer was over 16 MiB | the answer was too large to read |
| the forge's answer did not list every pushed commit or file | the forge sent an answer that is not whole |
| the forge answered 404 | the forge no longer has the earlier head (removed after a forced push), or Scarab can no longer read the repository |
| the push payload's commit ids are not commit ids | the webhook's `before` or `after` is not a full commit id |
| the forge did not answer the changed files request | an API error, or a rate limit that outlasted the retries |
| the forge did not list the changed files within 5 seconds | the forge was slow |

The push list needs Forgejo 16.0.1 or later. We tested the changed files behaviour against
Forgejo 16.0.1: the Forgejo adapter's test fixtures are compare answers recorded from the
Forgejo 16.0.1 that the local kind stack runs. Scarab does not check the Forgejo version. An
older Forgejo, or a Gitea whose compare answer has no per-commit files, gives an unknown list on
every push, so its path-filtered Pipelines always run.

To a `when:`, the field is always there and only its value is unknown, so
`has(event.changed_paths)` is true either way and cannot test for an unknown list. Read
`event.changed_paths_known` for that: `true` when Scarab has the complete list (an empty list
included), `false` when the list is unknown and on every trigger that has no list (`tag`,
`release`, `comment`, `cron`, `manual`, `api`, `upstream`). This trigger runs only when the list
is known and something under `infra/` changed, and skips on an unknown list:

```yaml
on:
  push:
    when: event.changed_paths_known && event.changed_paths.exists(p, p.startsWith("infra/"))
```

A trigger that skips this way starts no Run, so no activity log line says why. Reading
`event.changed_paths_known` asks the forge for the list the same way reading
`event.changed_paths` does. Only a push and a pull request have a list, so in a step's `when:`
in a Pipeline that a manual dispatch, a cron fire or another trigger also starts,
`event.changed_paths_known && …` skips that step on every one of those Runs. To run the step on
them, write `!(event.kind in ["push", "pull_request"]) || (event.changed_paths_known && …)`.

The rest of the expression still decides when it can: `event.branch == 'main' &&
event.changed_paths.exists(…)` is false on another branch whether or not the list is known. A
`when:` that does not read `event.changed_paths` is unaffected. The same rule applies to a step's
`when:`: a step that needs an unknown list runs.

A `changed_paths` filter is not a deploy guard: it decides when a Pipeline may skip work. An
unknown list runs the Pipeline, and a list is unknown during a forge outage, when the forge is
slow or rate-limits Scarab, and on every GitHub push of 300 or more files. A Pipeline that runs
`terraform apply` when `infra/` changed also runs on each of those. Guard a deploy with an
[Environment](#environments--gates)'s protection and approvals.

The list is not stored with the Run, and a template cannot read it: `${{ event.changed_paths }}`
is a compile error, because anyone who can push chooses the paths. `${{
event.changed_paths_known }}` is a compile error too: it is decided while the trigger is matched
and is not stored with the Run.

**Manual dispatch is opt-in**: a pipeline is dispatchable from the UI/API only if it declares
`on: manual`. The trigger context also feeds each run's provenance and **Headline** (the trigger
title shown against the run).

```yaml
on:
  manual: {}
  push: {}
```

### Scheduled Runs: `on: cron`

`on: cron` starts a Run on a schedule. `schedule:` takes one cron expression or a list:

```yaml
on:
  cron:
    schedule: "0 2 * * *"          # 02:00 UTC every day
  # or: schedule: ["0 2 * * *", "30 14 * * mon-fri"]
```

A schedule has five fields, `minute hour day-of-month month day-of-week`, read in UTC. A field is
`*`, a number, a range `a-b`, any of those with a step `/n`, or a comma-separated list. Months may
be written `jan`-`dec` and days `sun`-`sat`; day-of-week `0` and `7` are both Sunday. When both
day fields are set (neither starts with `*`), a day matches if either matches. The macros
`@hourly`, `@daily`, `@weekly`, `@monthly` and `@yearly` are accepted too.

The Pipeline check refuses a schedule that does not parse, that never fires (`0 0 30 2 *`), or
that can fire less than 5 minutes apart (`*/2 * * * *`).

A cron Run builds the head of the repository's **default branch**. Its ref is
`refs/heads/<default branch>`, so an Environment's `allowed_refs` treats it as it treats a push
to that branch, and its Headline is the schedule. `when:` applies, and the event context has
`event.schedule`, `event.branch`, `event.ref` and `event.sha`. A cron Run has no launch inputs:
every input the Pipeline declares needs a default, or the Run is refused.

How a schedule is found and fired:

- A push to the default branch records the schedules of every Pipeline file in it.
- At each slot Scarab reads the default branch from the forge again, then its head, then the
  Pipeline at that head. The Run starts only if the Pipeline there still declares the schedule. A
  schedule removed, a Pipeline file deleted, or a default branch renamed takes effect at the next
  slot, even when the webhook for that change was lost.
- A schedule added in a push whose webhook was lost is not seen until the next push to the default
  branch, or the next slot of another schedule in the same repository.
- Each Pipeline gets at most one Run per minute, however many server replicas run and however many
  of its schedules name that minute. After the server was down, a missed slot fires once, not once
  for each slot it missed.
- When the forge cannot be read within a minute after the slot (it is down, or it rate-limited
  Scarab), the slot is skipped. It is listed with the repository's refused runs, as is a slot
  whose Pipeline no longer compiles.

A repository's **Schedules** tab lists each schedule with its next slot and the last one that
fired, and links to the runs it started. On the **Runs** tab, the **scheduled** filter shows only
those runs.

### After another pipeline: `on: upstream`

`on: upstream` starts a Run when a Run of another pipeline in the same repository finishes.
`pipeline:` names that pipeline: its `name:`, or its file name without `.scarab/` and the
extension. `status:` says which endings start it: `succeeded` (the default), `failed`, or a list
of both.

```yaml
# .scarab/deploy.yaml
on:
  upstream:
    pipeline: ci
    when: "event.branch == 'main'"
```

Use it to split a build from its deploy. In one pipeline, a deploy step makes the whole Run a
Deploy Run, so a newer push no longer cancels its build ([Deploys](#deploys-deploy-true)), and a
rejected or expired deploy gate fails the Run the build is in. With `ci` on `push` and `deploy`
on `upstream`, newest-wins still cancels stale `ci` Runs, and only the `deploy` Run waits for
approval.

The follow-up Run:

- builds the commit the upstream Run built, and runs on its ref, so an Environment's
  `allowed_refs` applies to it as it applied to the upstream. A follow-up of a pull request Run
  has the ref `refs/pull/<n>/head`; the `when:` above keeps `deploy` to the `main` branch.
- has the upstream Run's actor, and the Headline `<pipeline> <status>`, such as `ci succeeded`.
- sees `event.pipeline`, `event.status`, `event.run`, `event.ref`, `event.branch`, `event.sha`
  and `event.chain` (the pipeline names that led to it) in `when:`. A template may read
  `event.run`, `event.ref`, `event.branch` and `event.sha` ([Trigger values](#trigger-values-event)).
- is cancelled by newest-wins as a push is: a newer follow-up of the same pipeline on the same
  branch or pull request cancels an older one still running, unless it is a Deploy Run or names
  an Environment.

These start no follow-up:

- a Run of a pull request from a fork;
- a cancelled Run;
- an ending of a Run that was rerun since. When the Rerun finishes, it starts the follow-up again.

A pipeline already in the chain of Runs that led to it (`a` follows `b` and `b` follows `a`) is
refused, and so is a follow-up of a chain 8 pipelines long. Both are listed with the repository's
refused runs. Only pipelines in the same repository can be followed.

### Commit statuses

Each pipeline posts its own commit status to the forge, named `scarab/<pipeline>` (its `name:`,
or its file name), so two pipelines on one commit do not overwrite each other. Two pipelines with
the same `name:` share one status. A branch protection rule requires `scarab/<pipeline>` for each
pipeline it waits for. A deploy pipeline whose Environment does not exist or does not admit the
Project starts no Run, and its status is a `failure` that says why (see
[Environments](/scarab-ci/usage/environments/#who-may-run-in-it)).

A Pipeline that a push or pull request does not start because it was refused also posts a
`failure` under its usual status name, with the reason as the description and a link to the
repository page, where the refused Run is listed. That covers a Policy deny, a sandbox or library
rule (a yanked library, for example), an `event` field or `forge_token` rule, a missing approval
gate, a `when:` that could not be decided (only that Pipeline is refused; the other files still
start their Runs), and a follow-up refused for a loop or a chain 8 Pipelines long. A branch-scoped
Environment that does not deploy from the pushed branch posts nothing.

Each refused event posts again, also on a commit where a later Run of the Pipeline has posted its
own status since, so the check shows the latest refusal. The same delivery sent twice posts once.

#### When a Pipeline file does not compile

A push or pull request in which any Pipeline file does not compile starts no Run, from any file:
Scarab compiles every file before it creates a Run. So that no required check waits for a Run that
will not come:

- each file that does not compile is listed with the repository's refused runs and posts `failure`
  with its first compile error, when its `on:` names the event or cannot be read. A broken file
  that only runs on `manual` posts nothing on a push;
- each other Pipeline whose trigger matches the event, its `when:` included, posts `failure` with
  `not run: <file> failed to compile`, naming the first file that did not compile;
- a Pipeline whose trigger `when:` cannot be decided posts the same `failure`, since it may have
  run;
- a Pipeline whose trigger does not match posts nothing. A Pipeline kept to `main` by its `when:`
  gets no red check on a feature branch because another file is broken.

The status name of a broken file is its `name:`, read without compiling the file, or its file
name.

## Interface: `interface.inputs` (and `outputs`)

A pipeline declares its typed launch parameters under `interface.inputs`. An `invoke` caller
fills in the same interface with `with:`, so launching and reuse share one contract. A
bare string is shorthand for a required string; the map form sets the type, whether it is required, a default and a description:

```yaml
on:
  manual: {}

interface:
  inputs:
    - { name: region, type: choice, options: [us-east-1, eu-west-1], description: "target region" }
    - { name: replicas, type: number, required: false, default: 2 }
    - { name: force, type: boolean, required: false, default: false }

steps:
  - id: ship
    image: busybox
    command: ["deploy", "${{ inputs.region }}", "n=${{ inputs.replicas }}"]
```

- `type` is one of `string` (default), `boolean`, `number`, `choice`. A `choice` needs a non-empty
  `options` list.
- `required` defaults to `true`. An optional parameter (`required: false`) **must** carry a
  `default`, so every parameter always has a resolved value.
- An optional `validate:` CEL predicate over the resolved value (bound as `value`) rejects a launch
  with a bad value (fail-closed).

Resolved parameters are read in steps as `${{ inputs.<name> }}` and are also injected into the
step environment as `SCARAB_PARAM_<NAME>`. A `choice`, `boolean` or `number` parameter may be
written into a `command`, as above; a `string` parameter reaches a step only through `env:` (see
[Values in commands and scripts](#values-in-commands-and-scripts)). A **library** additionally declares the `outputs` it
exposes to its caller, and inside a library `${{ inputs.<name> }}` reads the caller's `with:`, not
the Run's launch parameters (see [Reuse: `invoke`](#reuse-invoke)).

## Steps: the step shape

The step contract is an OCI `image` plus a `command`; everything else is a modifier. `env` is a list
of `[NAME, VALUE]` pairs; `artifacts` publishes globs of files the step wrote to `/scarab/artifacts/`.
A step names the secrets it needs with `secrets: [KEY, ...]`; each one is a file,
`/scarab/secrets/KEY` (resolution, scoping and the env form are covered under
[Environments & gates](#environments--gates)).

```yaml
- id: check
  image: rust:1-bookworm
  needs: [checkout]
  env:
    - [CARGO_TARGET_DIR, /tmp/scarab-target]
  command:
    - bash
    - -c
    - |
      set -euxo pipefail
      cargo check
      mkdir -p /scarab/artifacts
      rustc --version > /scarab/artifacts/toolchain.txt
  artifacts:
    - "*.txt"
```

A step asks for privilege above the hardened baseline under `security:`. `run_as_root` is
self-service (root inside the unprivileged sandbox, with its capabilities already dropped, does not escape it);
`add_capabilities` and `privileged` are governed and take effect only if the environment whitelists
the image digest.

```yaml
- id: check
  image: rust:1-bookworm      # its USER is root
  security:
    run_as_root: true
```

Without `run_as_root`, a step runs with `runAsNonRoot` and no user id of its own, so the image's
`USER` must be a non-zero number (`USER 65532`). The kubelet cannot check that a user name is not
root, so an image whose `USER` is a name, such as `curlimages/curl`, fails to start with
`CreateContainerConfigError`. The step fails as a configuration error whose message says to use a
numeric user. Scarab does not override the image's user unless the step names one: rebuild the
image with a numeric `USER`, use an image that has one, set `run_as_user`, or ask for
`run_as_root`.

`run_as_user` runs the step as that uid, for an image whose `USER` is root or a name but whose
program runs as any user. A non-zero uid is self-service and is not a grant: the step still runs
with `runAsNonRoot`, and it reads and writes `/workspace` through the workspace group, as every
step does.

```yaml
- id: push
  image: gcr.io/go-containerregistry/crane:debug@sha256:…   # its USER is root
  security:
    run_as_user: 1000
```

`run_as_user: 0` is root: it is the same request as `run_as_root: true`, and a Policy sees it in
the step's `grants` as `run-as-root`. `run_as_root: true` beside `run_as_user: 0` is the same
request and compiles; `run_as_root: true` beside a non-zero `run_as_user` contradicts itself and
does not compile. The same rule holds for a service's `run_as_user` and `run_as_root`, and a
Policy sees a root service too (see
[Policies: rules over services](/scarab-ci/usage/policies/#rules-over-services)). A uid is
not allowed beside `sandbox`, which sets the uid itself.

Some steps are **kinds** with no image that the engine runs on your behalf (you set no `image`/`command`):

- **`gate: manual`**: a durable approval/wait point (see [Environments & gates](#environments--gates)).
- **`invoke: file:.scarab/lib/...`**: reuse at compile time (see [Reuse: `invoke`](#reuse-invoke)).

### Checking out the repository

Scarab's clone library, `lib:thulasi-ram::scarab-ci::clone`, checks out the Run's repository at the commit
the Run is pinned to. An org admin installs it like any other library; no org has it until then
([Install Scarab's clone library](/scarab-ci/usage/libraries/#install-scarabs-clone-library)).
On a Forgejo or GitHub token connection its source must also be trusted with forge credentials
(see [`forge_token`](#forge-credentials-forge_token)).

```yaml
- id: checkout
  invoke: lib:thulasi-ram::scarab-ci::clone   # depth 1, the Run's commit

- id: full
  invoke: lib:thulasi-ram::scarab-ci::clone
  with: { depth: full, submodules: true, lfs: true }
  timeout: 1800                               # carried onto the library's step
```

`depth` is `"1"`, a number of commits, or `full`. The library's one step is `checkout/git`, and
`needs: [checkout]` reaches it, so later steps inherit the checked-out workspace as usual. It works
the same on GitHub and Forgejo.

The `clone` step kind is gone. A `clone:` step fails the pipeline check with a message that names
`invoke: lib:thulasi-ram::scarab-ci::clone`.

### Building an image

Scarab's build library, `lib:thulasi-ram::scarab-ci::build`, builds an image from the Run's workspace with
rootless BuildKit and pushes it when you ask. An org admin installs it and trusts its source for the
build sandbox; no org has it until then
([Install Scarab's build library](/scarab-ci/usage/libraries/#install-scarabs-build-library)).

```yaml
- id: checkout
  invoke: lib:thulasi-ram::scarab-ci::clone

- id: image
  invoke: lib:thulasi-ram::scarab-ci::build
  needs: [checkout]
  with:
    image: 123456789012.dkr.ecr.ap-south-1.amazonaws.com/app:${{ event.sha }}
    context: services/api
    push: true
    build_args: |
      VERSION=${{ event.sha }}
    cache: s3
    cache_bucket: acme-buildkit-cache
    cache_region: ap-south-1

- id: deploy
  image: alpine:3.20
  needs: [image]
  env: [[PUSHED, "${{ outputs.image.push }}"]]
  command: [sh, -c, 'echo "pushed: $PUSHED"']
```

The library has two steps, and `needs: [image]` reaches the second:

- `image/image` builds. It runs BuildKit in the build sandbox and holds no registry credential.
  When the image is to be pushed, it writes the image as an OCI image layout to
  `/workspace/.scarab-build/<key>/oci`, after removing anything an earlier step left under
  `.scarab-build`. The key is the first 32 hex characters of the SHA-256 of the build step's id
  (`image/image` here), so two builds whose workspaces a later step receives write different
  paths. An image that is not pushed stays in BuildKit.
- `image/push` needs `image/image` and pushes the layout with
  [crane](https://github.com/google/go-containerregistry/tree/main/cmd/crane). It receives only
  the build step's workspace (`inputs: [image]`), not those of the steps the invoke needs. It
  holds the registry credential, runs no code from your repository, and removes the layout from its own
  workspace when it is done, so a step that needs only `image` does not receive it. With
  `push: false` it exits without pushing.

A step that reads `outputs.image.image` needs the build step too, and so receives the layout
through the build step's workspace. To deploy, read `outputs.image.push.digest`, which needs only
the push step, or limit what the step receives with `inputs:`.

The image travels from the build step to the push step through the workspace, so pushing a large
image costs a transfer through the Data Depot. A build that does not push writes no layout.

Its inputs:

| Input | Default | What it is |
|---|---|---|
| `image` | (required) | The image reference to build, such as `ghcr.io/acme/app:1.2.0`. No `,`. |
| `context` | `.` | The build context, relative to the workspace. No absolute path, no `..`, no `,`. |
| `dockerfile` | `Dockerfile` | The Dockerfile, relative to the context, with the same rules. |
| `push` | `false` | Push the image after building it. Needs the server to collect step results ([below](#building-an-image)). |
| `build_args` | empty | Build arguments, one `KEY=VALUE` per line. No `,` in a value, and no name that starts with `BUILDKIT_`. |
| `cache` | `none` | Where BuildKit imports and exports its layer cache: `none` or `s3`. |
| `cache_bucket` | empty | For `cache: s3`, the bucket. |
| `cache_region` | empty | For `cache: s3`, the bucket's region. |
| `cache_name` | empty | For `cache: s3`, the cache's name in the bucket; BuildKit's default when empty. |
| `insecure_push` | `false` | Push over plain HTTP. For a test or development registry with no TLS only. crane then also skips TLS verification, so the push Step refuses it (exit 2) when it holds a registry login. |

`build_args` refuses a name that starts with `BUILDKIT_`, in any case: BuildKit reads those
arguments as settings, and `BUILDKIT_SYNTAX` names a frontend image that BuildKit pulls and runs.
Don't build `build_args` from text that someone else writes, such as a step result that holds a
commit message or a pull request title. Each line of that text becomes a build argument, which
your Dockerfile can read and which BuildKit may act on.

Its outputs:

- `outputs.image.push` is set only when the image was pushed: `{"ref": "<repository>@sha256:…",
  "digest": "sha256:…"}`, as crane reported the push. Deploy by this digest. When nothing was
  pushed (`push: false`, a fork pull request, or a Run locked out of its Environment's secrets)
  there is no such result, and a step that reads it fails before it launches, so read it only
  where the image is pushed.
- `outputs.image.image` is what BuildKit wrote with `--metadata-file`: a JSON object whose
  `containerimage.digest` is the digest of the image it built. The build step adds two keys to
  it: `digest`, the same digest under a key with no `.` (`outputs.image.image.digest`), and,
  when it wrote a layout, `layout`, the layout's path. The push step reads the path from
  `layout`. Before it pushes, the push step
  checks that the layout's `index.json` names one manifest, that the manifest's file hashes to
  that digest, and that the digest is the build step's `containerimage.digest`. It refuses
  (exit 2) a layout that fails any of these: a stale, half-written or swapped layout. It also
  refuses an `index.json` that holds a backslash, a byte that is not printable ASCII, or the word
  `digest` (in any case) other than once, since crane's JSON decoder would read it differently.
  crane then pushes from an `index.json` the step writes, naming only the checked manifest. The
  step fails if crane reports another digest, so this digest and `outputs.image.push.digest` are
  the same. The check does not cover a build that rewrites its own `image` result as well as the
  layout. In `env:` this output becomes that object's compact JSON text.

**`push: true` needs step results.** The push step compares the layout with the build step's
`image` result, so when the server collects no step results it pushes nothing and fails (exit 2):

```
scarab: push refused: results are not collected, so the image's digest cannot be checked against the build step's; set the server's results token secret (SCARAB_RESULTS_TOKEN_SECRET, the chart value secrets.resultsTokenSecret)
```

The server collects results when it has a results token secret: the chart value
`secrets.resultsTokenSecret`, or a `SCARAB_RESULTS_TOKEN_SECRET` key in `secrets.existingSecret`
([Environment variables](/scarab-ci/usage/environment-variables/#server-configuration)). A build with `push: false` and a fork pull
request's push step exit 0 before this check. The multi-architecture build library and the image
index library's `layouts` need results too: without them the push step fails with
`scarab: index refused: results are not collected, so the layouts' digests cannot be checked
against the builds'; …`, which names the same secret.

- **The registry credential.** Only the push step asks for `registry_auth: true`. It receives a
  credential only when the org trusts the library's source with the registry credential
  ([Libraries](/scarab-ci/usage/libraries/#trusting-a-library-with-the-registry-credential)); a
  step written in your Pipeline file never receives one. Each time it launches, Scarab resolves
  the `REGISTRY_AUTH` secret: a Step that the Environment admits (approved, or no approvers) uses
  the Run's Environment chain
  ([Secrets](/scarab-ci/usage/secrets/#scoping-and-inheritance)); any other Step uses the
  repository default, then the org default. Scarab mounts it as
  `/scarab/registry/config.json`, with `DOCKER_CONFIG` pointing at that directory. It is never an
  environment variable, and Scarab replaces it with `***` in the step's log. With no
  `REGISTRY_AUTH` secret, the step gets the credential the forge derives for its own registry
  (GHCR, the Forgejo package registry), and only when the org also trusts the library's source
  with forge credentials. With neither, the build still runs and pulls public base images, and
  the push fails at the registry. The build step never receives a credential: BuildKit runs
  without its process sandbox, so a `RUN` in your Dockerfile could read anything the build step
  holds. For the same reason Scarab gives the build step no login to pull private base images;
  for ECR, a placement profile can
  ([Private base images in ECR](/scarab-ci/usage/pushing-to-ecr/#private-base-images-in-ecr)).
- **No registry cache.** The library offers no `cache: registry`: writing a cache to a registry
  needs the push credential in the build step. The S3 cache is reached with the build Pod's own
  identity, such as a ServiceAccount a placement profile sets; Scarab passes no credential.
- **A fork pull request**, or a Run locked out of its Environment's secrets, gets no registry
  credential, and Scarab sets `SCARAB_FORK_PR=true` on both steps, so the build exports no layer
  cache and writes no layout, and the push step pushes nothing, whatever `push` says. The build still imports the cache. No Pipeline or library may
  set `SCARAB_FORK_PR`.
- **Paths stay in the workspace.** The inputs are checked against their rules when the Pipeline
  compiles and again when each step launches. The build step resolves the context and the
  Dockerfile and stops before BuildKit runs if either leads outside `/workspace`, through a
  symlink committed in the repository for example. The push step stops before crane runs if the
  layout leads outside `/workspace` or holds a symlink, or anything that is not a regular file
  or a directory: a step before it could plant a symlink to `/scarab/registry/config.json`,
  which crane would upload.
- **The sandbox.** The build step runs as uid 1000, not privileged, with seccomp and AppArmor
  unconfined, which rootless BuildKit needs. Only a step from an installed library whose source
  the org trusts for the build sandbox gets it; a step written in your Pipeline file never does.
  A sandboxed step may not have `secrets:`. The push step runs in the default restricted Pod
  shape as uid 1000, so an org Policy that denies run-as-root does not refuse it.
- **Placement per step.** A list in the invoke step's `placement_profiles` reaches both steps. A
  map from the library's step id to a list routes each list to its own step, so build-node
  placement and the S3 cache identity reach only the build step. An operator marks a profile
  that grants push access (a ServiceAccount with a push role, an init container that logs in)
  `registry_auth_only`. Scarab applies a marked profile only to a step with `registry_auth` that
  the launch found eligible for a credential, which here is the push step of a Run that is not a
  fork. Named on any other step it fails that step's launch, so a list that holds one fails the
  build step: route it with the map form. On a fork's push step it is left out, and the step
  pushes nothing.

  ```yaml
  - id: image
    invoke: lib:thulasi-ram::scarab-ci::build
    placement_profiles:
      image: [arm64-builders, build-cache]
      push: [ecr-push]
    with: { image: "123456789012.dkr.ecr.ap-south-1.amazonaws.com/app:${{ event.sha }}", push: true }
  ```

- **Other architectures.** BuildKit builds for the architecture of the node it runs on, so the
  build step's placement decides the image's architecture. To publish one image for amd64 and
  arm64, use the multi-architecture build library
  ([below](#building-a-multi-architecture-image)): it builds on both node pools and pushes
  both images, their tags and the index from one step.

The `build` step kind is gone. A `build:` step fails the pipeline check with one error that holds
its replacement, an `invoke: lib:thulasi-ram::scarab-ci::build` step written from the old step's fields. The local executor refuses the build library's build step; it
needs the Kubernetes executor.

### Building a multi-architecture image

Scarab's multi-architecture build library, `lib:thulasi-ram::scarab-ci::build-multiarch`, builds
an image once per platform, each build on a node of that architecture, then pushes every image,
their tags and the image index that joins them from one step. A client that pulls the tag gets
the image for its own platform. An org admin installs it and trusts its source for the build
sandbox and with the registry credential; no org has it until then
([Install Scarab's multi-architecture build library](/scarab-ci/usage/libraries/#install-scarabs-multi-architecture-build-library)).

```yaml
- id: checkout
  invoke: lib:thulasi-ram::scarab-ci::clone

- id: app
  invoke: lib:thulasi-ram::scarab-ci::build-multiarch
  needs: [checkout]
  placement_profiles:
    "build[arch=linux/amd64]": [amd64-builders]
    "build[arch=linux/arm64]": [arm64-builders]
  with:
    image: "ghcr.io/acme/app:${{ event.sha }}"
    platforms: "linux/amd64,linux/arm64"
    extra_tags: latest
    context: .
    dockerfile: Dockerfile

- id: deploy
  image: alpine:3.20
  needs: [app]
  when: "event.kind == 'push'"
  env: [[DIGEST, "${{ outputs.app.push.digest }}"]]
  command: [sh, -c, 'echo "deploy ghcr.io/acme/app@$DIGEST"']
```

The library has two steps, and `needs: [app]` reaches the second:

- `build` is a matrix step with one instance per platform in `platforms`: here
  `app/build[arch=linux/amd64]` and `app/build[arch=linux/arm64]`. Each builds with the same
  BuildKit script as the build library's build step, in the build sandbox and with no registry
  credential. Each writes its image as an OCI image layout at `/workspace/.scarab-build/<key>/oci`
  (the key comes from the instance's id, so the layouts do not collide) and names the layout's
  path and the image's digest in its `image` result.
- `app/push` needs every build instance and receives only their workspaces (`inputs: [build]`).
  It is the only step that holds the registry credential. It runs as uid 1000, runs no code from
  your repository, and runs the image index library's script
  ([below](#joining-images-into-one-multi-architecture-image)) on the layouts: it checks all of
  them, then pushes each image by digest, pushes the index under `image`'s tag, tags each image
  `<tag>-<architecture>`, and tags the index with each extra tag, in that order.

**Route each instance to its nodes.** BuildKit builds only for the architecture of the node it
runs on. Name each instance in the map form of `placement_profiles` by its coordinate,
`"build[arch=<platform>]"`, with the platform written in full (`linux/arm64`, not `arm64`) and
the key quoted, as above. A plain `build:` key reaches every instance that no coordinate key names,
and `push:` reaches the push step. A plain list reaches every step. A build instance whose node
has another architecture fails (exit 2) before BuildKit starts:

```
scarab: build refused: this step builds linux/arm64, but its node's architecture is amd64 (uname -m: x86_64); the placement map routes this instance to the wrong nodes
```

Every check the push step makes itself runs before the first registry write, so a step it refuses
writes nothing. A failure crane or the registry reports after that can leave images pushed by
digest with no tag, and a retry pushes them again. A push step that fails part way through the
tags leaves the tags it wrote until it is retried.

Its inputs:

| Input | Default | What it is |
|---|---|---|
| `image` | (required) | The tag to push the index to, such as `ghcr.io/acme/app:1.2.0`. It must name a tag, and no digest. |
| `platforms` | `linux/amd64,linux/arm64` | The platforms to build, separated by commas or spaces: `linux/amd64`, `linux/amd64/v2` to `v4`, `linux/arm/v5` to `v8`, `linux/arm64`, `linux/loong64`, `linux/ppc64`, `linux/ppc64le`, `linux/riscv64` or `linux/s390x`. 32-bit arm is written with its variant (`linux/arm/v7`). `linux/386` and the mips platforms are not offered: the check that a build runs on a node of its architecture cannot tell them apart. Write it as text: the build steps are made when the Pipeline compiles, before any `${{ }}` has a value, so a template here is a compile error. |
| `extra_tags` | empty | More tags for the index, in `image`'s repository: tag names such as `latest`, not references, separated by spaces or line breaks. A tag named twice, or the same as `image`'s, is written once. |
| `arch_tags` | `true` | Also tag each platform's image: `<tag>-amd64`, `<tag>-arm64`. |
| `context`, `dockerfile`, `build_args`, `cache`, `cache_bucket`, `cache_region`, `cache_name` | as in the build library | The build library's inputs, with the same rules ([Building an image](#building-an-image)). Every build uses them, except that each build keeps its own layer cache: `<cache_name>-amd64`, `<cache_name>-arm64`, `<cache_name>-arm-v7` (`buildkit-amd64` and so on when `cache_name` is empty). |
| `insecure_push` | `false` | Reach the registry over plain HTTP. For a test or development registry with no TLS only. crane then also skips TLS verification, so the push step refuses it (exit 2) when it holds a registry login. |

Its output: `outputs.app.push` is `{"ref": "<repository>@sha256:…", "digest": "sha256:…"}` for
the index, as crane reported the push. Deploy by `outputs.app.push.digest`.

- **One node pool per architecture.** Each platform needs nodes of its architecture that the
  instance's profile reaches. QEMU emulation is not used: a rootless, unprivileged step cannot
  register it.
- **Arch tags are on by default.** Without a tag, a platform's image is reachable only through
  the index, and a registry rule that expires untagged images (an ECR lifecycle policy can) could
  delete it and break the index. We have not confirmed how ECR treats untagged images that a
  tagged index names. arm64 is tagged `<tag>-arm64` whether or not its config names `v8`; a
  32-bit arm image is tagged with its variant, `<tag>-arm-v7`. The push step's log names each tag
  it wrote (`scarab: tagged <repository>@sha256:… as <tag>`). With `arch_tags: false` the step
  writes `image`'s tag and the extra tags only.
- **A retry pushes every platform again.** The push is one step, so retrying it repeats every
  write: every image, the index, the arch tags and the extra tags. Each write puts the same
  content under the same name, and a registry skips blobs it already has. A failed build is its
  own step and retries on its own. A repository with immutable tags refuses a tag that moves,
  such as `latest`, with or without this library.
- **The push step needs disk for every layout.** Its Pod receives every build's workspace: the
  checkout they received and every image layout. Size its node's ephemeral storage for all of
  it.
- **It needs step results.** The push step reads each build's layout from its `image` result. With
  no results collected it refuses (exit 2) with `scarab: index refused: results are not collected,
  …`, which names the results token secret ([`push: true` needs step
  results](#building-an-image)).
- **A fork pull request**, or a Run locked out of its Environment's secrets, gets no registry
  credential, and Scarab sets `SCARAB_FORK_PR=true` on every step. The builds run, export no
  layer cache and write no layout; the push step pushes nothing, exits 0 and publishes no `push`
  result. A step that reads `outputs.app.push` needs `when: "event.kind == 'push'"`, or another
  condition that keeps it off a fork's Run. On any other Run, a build that published no layout
  fails the push step (exit 2) with `layouts line (linux/amd64 wrote no layout) does not name a
  path …`, so an index never leaves a platform out.

**Upgrading from the fixed amd64 and arm64 version.** The library's build steps were `amd64` and
`arm64`; they are now the instances of `build`. A Pipeline whose invoke names `amd64:` or
`arm64:` in its placement map fails to compile, and the error names the key to write instead:

```
step `app`: `placement_profiles` names step `amd64`, which library `lib:thulasi-ram::scarab-ci::build-multiarch` does not have; to place one instance of a matrix Step, write its coordinate: `build[arch=linux/amd64]`
```

Step ids change with it (`app/amd64` becomes `app/build[arch=linux/amd64]`), so a Policy or a
step that names the old ids needs the new ones. `outputs.app.push` is unchanged.

### Joining images into one multi-architecture image

Scarab's image index library, `lib:thulasi-ram::scarab-ci::image-index`, joins images built for
different architectures into one image index and pushes it under one tag. An org admin installs it
and trusts its source with the registry credential; no org has it until then
([Install Scarab's image index library](/scarab-ci/usage/libraries/#install-scarabs-image-index-library)).
It takes images two ways:

- `layouts`: OCI image layouts that Scarab's build layout library,
  `lib:thulasi-ram::scarab-ci::build-layout`, left in the workspace. The index step pushes them
  itself, so no build step holds a credential. This is what the multi-architecture build library
  does in one invoke; compose the two libraries when you need another shape, such as builds
  with different inputs per architecture, or another step between the builds and the push.
- `images`: images already in a registry, named by digest, such as the build library's pushed
  references.

The build layout library has one step, the build library's build step without a push step. It
takes the build library's inputs except `image`, `push` and `insecure_push`, needs only the build
sandbox trust, and publishes `digest` and `layout` in its `image` result
([Install Scarab's build layout library](/scarab-ci/usage/libraries/#install-scarabs-build-layout-library)).
Each `layouts` line is one build's `layout` and `digest`, read with `has(...)` so that a build
that wrote no layout renders an empty line:

```yaml
- id: amd64
  invoke: lib:thulasi-ram::scarab-ci::build-layout
  needs: [checkout]
  placement_profiles: [amd64-builders]

- id: arm64
  invoke: lib:thulasi-ram::scarab-ci::build-layout
  needs: [checkout]
  placement_profiles: [arm64-builders]

- id: app
  invoke: lib:thulasi-ram::scarab-ci::image-index
  needs: [amd64, arm64]
  with:
    image: "ghcr.io/acme/app:${{ event.sha }}"
    extra_tags: latest
    layouts: |
      ${{ has(outputs.amd64.image) && has(outputs.amd64.image.layout) ? outputs.amd64.image.layout + ' ' + outputs.amd64.image.digest : '' }}
      ${{ has(outputs.arm64.image) && has(outputs.arm64.image.layout) ? outputs.arm64.image.layout + ' ' + outputs.arm64.image.digest : '' }}
```

A build layout step keeps its layout in its workspace, so every step that needs it receives the
layout (a large image costs a transfer through the Data Depot); limit what a step receives with
`inputs:`. The index step removes `.scarab-build` from its own workspace after it pushes.

With `images`, this Pipeline builds the image on amd64 and arm64 nodes with the build library,
each build pushing its own tag, joins the two, and deploys the index by digest. Each build's
push step holds the credential too, so prefer `layouts` when the builds run in the same Run:

```yaml
on:
  push:
    when: "event.branch == 'main'"
steps:
  - id: checkout
    invoke: lib:thulasi-ram::scarab-ci::clone

  - id: amd64
    invoke: lib:thulasi-ram::scarab-ci::build
    needs: [checkout]
    placement_profiles: [amd64]
    with: { image: "ghcr.io/acme/app:${{ event.sha }}-amd64", push: true }

  - id: arm64
    invoke: lib:thulasi-ram::scarab-ci::build
    needs: [checkout]
    placement_profiles: [arm64]
    with: { image: "ghcr.io/acme/app:${{ event.sha }}-arm64", push: true }

  - id: app
    invoke: lib:thulasi-ram::scarab-ci::image-index
    needs: [amd64, arm64]
    with:
      image: "ghcr.io/acme/app:${{ event.sha }}"
      images: |
        ${{ has(outputs.amd64.push) ? outputs.amd64.push.ref : '' }}
        ${{ has(outputs.arm64.push) ? outputs.arm64.push.ref : '' }}

  - id: deploy
    image: alpine:3.20
    needs: [app]
    env: [[DIGEST, "${{ outputs.app.index.digest }}"]]
    command: [sh, -c, 'echo "deploy ghcr.io/acme/app@$DIGEST"']
```

The library has one step, `app/index`, and `needs: [app]` reaches it. `needs: [amd64, arm64]`
reaches each build's push step, whose `push` result holds the pushed `<repository>@sha256:…`.
The step runs [crane](https://github.com/google/go-containerregistry/tree/main/cmd/crane) with
the crane image the build library pins. It holds the registry credential, runs as uid 1000 and
runs no code from your repository. With `images` alone it reads nothing from the workspace. With
`layouts` it reads each layout from the workspace and uploads it.

Its inputs:

| Input | Default | What it is |
|---|---|---|
| `image` | (required) | The tag to push the index to, such as `ghcr.io/acme/app:1.2.0`. It must name a tag, and no digest. |
| `layouts` | empty | The image layouts to push and join, one `<path> sha256:<digest>` per line, the path `/workspace/.scarab-build/<key>/oci` as a build layout step reports it. |
| `images` | empty | The images to join, one `<repository>@sha256:<digest>` per line. Each image is named by digest, never by tag: a tag can be moved, so a retry could join other images. |
| `extra_tags` | empty | More tags for the index, in `image`'s repository: tag names such as `latest`, not references, separated by spaces or line breaks. A tag named twice, or the same as `image`'s, is written once. |
| `arch_tags` | `true` | Also tag each image from `layouts` `<tag>-<architecture>`, or `<tag>-<architecture>-<variant>` for a variant other than arm64's `v8` and amd64's `v1` (`<tag>-arm-v7`). It does not apply to `images`. |
| `insecure` | `false` | Reach the registry over plain HTTP. For a test or development registry with no TLS only. crane then also skips TLS verification, so the step refuses it (exit 2) when it holds a registry login. |

`layouts` and `images` may both be given, and between them must name at least one image.

Every check the step makes itself runs before the first registry write, so a step it refuses
writes nothing and leaves the workspace as it found it. A failure crane or the registry reports
after that can leave images pushed by digest with no tag, and a retry pushes them again. For each
layout, the step refuses (exit 2):

- a path that is not `/workspace/.scarab-build/<key>/oci` (the key 32 hex characters), that
  holds a symlink at any level or anything other than directories and regular files, or that
  resolves outside the workspace. A step before this one, or a Dockerfile `RUN`, could plant a
  symlink to `/scarab/registry/config.json`, which crane would upload;
- an `index.json` that does not name one manifest, a manifest that does not hash to its name or
  is not the digest the line gives, a blob the manifest names (the config or a layer) that is not
  `sha256:<64 hex>`, is missing from the layout or does not hash to its name, and a manifest
  that names a `subject` (a referrer). The platform is read from the layout's config;
- an architecture or variant the step does not tag: the architecture must be one of `386`,
  `amd64`, `arm`, `arm64`, `loong64`, `mips`, `mipsle`, `mips64`, `mips64le`, `ppc64`,
  `ppc64le`, `riscv64` and `s390x`, with no variant, or `v5` to `v8` for `arm`, or `v2` to `v4`
  for `amd64`, whatever `arch_tags` says.

The digest check shows a layout was not changed after its `layouts` line named it, not that a
build step made it: any step of the Pipeline, a plain `run:` step included, can write a layout
under `/workspace/.scarab-build/` and name its digest.

For each image in `images`, it reads the manifest and config from the registry, by digest. For
every source, it refuses:

- an image that is itself an index (a multi-architecture image, or one with attestations): name
  each architecture's image by its own digest;
- a manifest or config that is not one JSON object (one that starts with a byte-order mark, for
  example), or that names `config`, `os`, `architecture`, `variant` or `os.version` anywhere but
  as a key of its top-level object, which is the only place crane reads them;
- an image whose config names no `os` or `architecture`, or names one of them twice (a label
  called `os`, for example);
- two images of the same platform: `os/architecture`, then the `variant` (`arm/v7`) and the
  `os.version` a Windows image names. `arm64/v8` counts as `arm64` and `amd64/v1` as `amd64`, so
  an arm64 image with `v8` and one without are one platform. An index holds one image per
  platform;
- a manifest or config that writes a letter, digit, `.`, `_` or `-` with a `\u` escape, or names
  `manifests`, `os`, `architecture`, `variant` or `os.version` more than once in any case (`os`
  and `OS`). crane's JSON decoder reads both forms, so the step would otherwise check another
  field than the one crane reads;
- a tag over 128 characters, and an arch tag that two images, or an image and an extra tag, would
  share.

Then it writes, in this order: each layout's image by digest into the index's repository, the
index under `image`'s tag, the arch tags, and each extra tag on the index. Until the index is
pushed only untagged images exist; crane reads every config again when it pushes the index, and
after that each write moves a tag to a digest already in the registry. It removes
`.scarab-build` from its workspace after it pushes. A retried step writes all of them again; each
write puts the same content under the same name. With `layouts`, the step's Pod receives every
layout through the workspace, so it needs disk for all of them. Arch tags are on by default for
the reason given under [Building a multi-architecture image](#building-a-multi-architecture-image).

The images in `images` may live in other repositories, or other registries, than the index.
crane copies each into the index's repository when it is not already there, so the step's
credential must be able to read each image and push to the index's repository.

Its output: `outputs.app.index` is `{"ref": "<repository>@sha256:…", "digest": "sha256:…"}`,
as crane reported the push. Deploy by this digest.

A fork pull request, or a Run locked out of its Environment's secrets, pushes nothing: the build
library's push step writes no `push` result, and a build layout step builds but writes no layout
and publishes no `layout` key. Each line reads the result only when it is there, so on a fork the
lines are empty, and the index step pushes nothing and exits 0 before it reads any input.
Anywhere else, `images` and `layouts` both empty fail the step, and so does a mix of references
or layouts and empty lines. A line written as `${{ outputs.amd64.push.ref }}` does not render
when the build pushed nothing, and the index step fails before it launches. The steps that read
`outputs.app.index` need `when: "event.kind == 'push'"`, or another condition that keeps them off
a fork's Run.

`layouts` needs the server to collect step results, since each line's digest comes from a build's
result. With `layouts` set and no results collected, the step fails (exit 2) with `scarab: index
refused: results are not collected, …`, which names the results token secret ([`push: true` needs
step results](#building-an-image)). `images` alone does not need results.

The step asks for `registry_auth: true` and is the library's only step, so a profile marked
`registry_auth_only` (an ECR push role, say) can be named in a plain list:
`placement_profiles: [ecr-push]`.

### Forge credentials: `forge_token`

A step that needs to talk to the Run's repository asks for a forge credential:

```yaml
- id: tag
  image: alpine/git@sha256:…
  forge_token: write        # or read
```

Scarab mints the credential each time the step's attempt launches, a rerun or retry included, and
mounts it as two files: `/scarab/secrets/forge-token` and `/scarab/secrets/forge-username`. It is
never an environment variable. When the attempt ends, the Kubernetes Secret that holds it is
deleted, even if the Pod is kept, and a token GitHub minted is revoked, by whichever Scarab server
sees the end. Each minted token is revoked once, from the step's value ledger. A failed revocation
is tried again until the ledger is deleted, at the latest 24.5 hours after the attempt first
launched; a token still live then expires on its own (see
[Run logs](/scarab-ci/usage/run-logs/#forge-tokens-and-when-a-ledger-is-deleted)).

Whether a step may have one is decided when the Run is created; a Run that asks for more is
refused with the reason. Each launch checks again, from the connection and the org's trust as
they are then: a step that may no longer have the token fails with the reason, and nothing is
minted.

- **On a GitHub App connection**, which mints a short-lived token for one repository, any step may
  ask. **On a Forgejo or GitHub token connection**, which hands out one long-lived token, only a
  step from a library installed from a source an org admin trusted receives it, and no source is
  trusted by default, Scarab's clone library included
  ([Libraries](/scarab-ci/usage/libraries/#trusting-a-library-with-forge-credentials)).
  A repository's own steps never read that token. Such a step also starts with an empty
  workspace: no file another step wrote is present while the token is mounted.
- **The forge connection** must be served over `https://`. A Run with a step that asks for
  `forge_token` on a connection whose base URL is `http://` is refused: the token is never sent
  over plain HTTP.
- **A fork pull request** always gets `read`, whatever the step asks for.
- **`write`** needs a GitHub App connection, and a Run governed by an environment that restricts
  the refs it deploys from. Where that environment has approvers, put a `gate: manual` in the
  step's `needs`.
- **The `image` and `command`** of a step with `forge_token` are written out in full: a
  `${{ … }}` in either is a compile error. An input, a result or an `event` value reaches the step
  only through `env:`, and only under a name of the form `SCARAB_<NAME>` (upper-case letters,
  digits and `_`) that Scarab does not set itself. Other names can make the value run as code:
  git runs `GIT_SSH_COMMAND`, and the loader reads `LD_PRELOAD`. A literal value may use any name.
- **A library input** that reaches a step with `forge_token` must be a `boolean`, a `number`, a
  `choice`, or a `string` with a `validate:` rule.
- A step with `forge_token` may not have a `cache`.
- An invoke step's `placement_profiles` is never carried onto a step with `forge_token`.

The local executor refuses a step with `forge_token`; it needs the Kubernetes executor.

The clone uses the forge connection's token only for the repository being cloned, and
only over https. Submodules are fetched without it, so a private submodule fails the
step; make it public or vendor it. LFS objects come from the repository's own LFS
endpoint, and an `lfs.url` in `.lfsconfig` is ignored.

## Ordering: `needs`

`needs:` declares the DAG edges. A step runs once all of its needs succeed and inherits their
workspaces:

```yaml
- id: deploy
  image: deployer
  needs: [build]
```

## Fan-out: `matrix`

**`matrix`** fans one authored step into the cartesian product of its dimensions, expanded
statically at submit time. An `exclude` list of
CEL predicates (evaluated against each combination's own coordinate) drops combinations:

```yaml
- id: test
  image: rust:1-bookworm
  matrix:
    dimensions:
      os: [linux, windows]
      arch: [amd64, arm64]
    exclude:
      - "os == 'windows' && arch == 'arm64'"
```

Each instance gets a deterministic id like `test[arch=amd64,os=linux]`, and a downstream
`needs: [test]` fans in over every surviving instance.

The values are a literal list. In a library, a dimension may instead be exactly one input,
`arch: "${{ inputs.platforms }}"`, whose values the caller writes in `with:`, and another step
of the library reads every instance's results as a list
([Libraries: a matrix from an input](/scarab-ci/usage/libraries/#a-matrix-from-an-input)).

A step id may not contain `::service-`, whether it is written that way or built from a matrix
value: Scarab names a step's sidecar logs `<step>::service-<i>`, and a step `t[v=1]::service-0]`
would read as a sidecar of `t[v=1]`. The compiler refuses it with one error that names the matrix
value.

A matrix can have at most 65,536 combinations before `exclude`, and 256 `exclude` predicates. All
the matrices of one pipeline, counting a library's matrix each time the library is inlined, can
have at most 1,048,576 combinations, and at most 262,144 `exclude` checks (combinations times
predicates).

## Conditions: `when`

A `when:` CEL guard skips a step whose predicate is false; expressions read the run's context
(e.g. `event`, including [`event.changed_paths`](#changed-files-eventchanged_paths), and any
`matrix` coordinate):

```yaml
- id: deploy
  image: deployer
  needs: [build]
  when: "event.branch == 'main'"
```

### Expression limits

Each CEL expression in a pipeline (a `when:` guard, a matrix `exclude` predicate, an input's
`validate:` predicate, or the inside of one `${{ … }}`) can be at most **4096 bytes** long, with
brackets (`(`, `[` and `{` together) nested at most **64** deep. Brackets inside string literals
and `//` comments don't count. A pipeline over either limit is rejected at submit time, and the
error names the step, the field and the limit (the expression is cut short here):

```
step `build`: when cel error: `1+1+1+…`: expression is 5000 bytes; the limit is 4096 bytes
```

The CEL parser recurses once per nesting level and once per operator in a chain such as
`a + b + c`, so these limits bound how much stack one expression can use on the server.

### Size limits

A pipeline or library file can be at most **1 MiB**, and the libraries one pipeline invokes can
hold at most **16 MiB** in all, each counted once however often it is invoked. The compiled
pipeline can be at most **16 MiB** of JSON: each step a library inlines stores the library's
inputs, and each matrix leg stores a copy of its step, so a small file can compile to a large
pipeline. A pipeline over any of these limits is rejected at submit time, and the error names the
file or step and the limit. The server also stops a compile that takes longer than 10 seconds,
and the trigger fails with that reason.

## Reuse: `invoke`

`invoke` inlines a **library** into the caller's DAG at compile time; it is not a runtime call.
The invoked steps are namespaced by the invoke step's id (`deploy/plan`, `deploy/url`), and
`matrix` on an invoke step fans out the whole subgraph.

The target always has a prefix that says where it comes from:

| `invoke:` | Target |
|---|---|
| `file:<path>` | a library file in the repository, read at the caller's ref |
| `lib:<name>` | a library installed in your org, such as `lib:acme::scarab-libs::deploy-helm` |
| `plugin:<installation>/<gate>` | a gate a plugin installed in your org resolves ([Plugin gates](#plugin-gates)) |

A `file:` path is repo-relative: no leading `/`, no `..`, and no remote or cross-repo forms
(a library from elsewhere is installed in the org and invoked as `lib:`). A bare path is a compile error that tells you to add
`file:`, and `url:` is refused: Scarab does not invoke from a URL. A `lib:` target resolves to the
version your org installed ([Libraries](/scarab-ci/usage/libraries/)); a name the org has not
installed fails with "`lib:<name>` is not installed in this org". The name is parts of letters,
digits, `.`, `_` and `-`, joined by `::` or `/`, and is case-sensitive.

A library is a YAML file marked `kind: library`. It has no `on:` triggers and never runs on its
own: Scarab does not trigger it or list it for dispatch, even directly under `.scarab/`. It
declares its contract with `interface` (the `inputs` it takes and the `outputs` it exposes) and the
caller supplies inputs with `with:`:

```yaml
# .scarab/lib/deploy.yaml
kind: library
interface:
  inputs:
    - { name: region, type: choice, options: [us-east-1, eu-west-1] }
    - { name: replicas, type: number, required: false, default: 2 }
  outputs: [url]
steps:
  - { id: plan, image: tf@sha256:…, command: ["plan", "${{ inputs.region }}"] }
  - { id: url,  image: tf@sha256:…, command: ["apply"], needs: [plan] }
```

```yaml
# .scarab/ci.yaml
steps:
  - id: deploy
    invoke: file:.scarab/lib/deploy.yaml
    with: { region: us-east-1, replicas: "3" }
    timeout: 1800

  - id: notify
    image: busybox
    needs: [deploy]
    env: [[URL, "${{ outputs.deploy.url }}"]]
    command: ["sh", "-c", 'echo "$URL"']
```

The interface is checked at compile time: every required input present, no unknown extras, each
value of its declared type, and every referenced output declared.

**Inputs are read at launch.** Inside a library step, `${{ inputs.<name> }}` in its `image`,
`command`, `env`, `when:` and the `with:` of its own invokes reads the value its caller bound, so
in the example above `plan` runs `plan us-east-1`. Inside a library, `inputs` never means the
Run's launch parameters, and reading an input the library does not declare is a compile error. A
literal `with:` value is checked against the input's type when the pipeline compiles. A `with:`
value that holds a template, such as the caller's `${{ outputs.<step>.<name> }}`, is rendered in
the caller's scope when the library step launches, then checked against the input's type and
`validate:`. The inputs also reach each inlined step as `SCARAB_PARAM_<NAME>`.

**What the invoke step carries.** An invoke step may set `needs`, `with`, `matrix`, `when`,
`deploy`, `timeout`, `resources` and `placement_profiles`. Its `timeout`, `resources` and
`placement_profiles` apply to each inlined step that leaves them unset (the library's own value
wins), and never to a gate. `placement_profiles` never applies to a step with `forge_token`.
`placement_profiles` may be a list, which applies to every inlined step, or a map from a step id
of the library to a list, which applies to that step only
(`placement_profiles: { image: [arm64], push: [ecr-push] }`). A map key that is not a step of the
library, or names a step with `forge_token` or with its own `placement_profiles`, is a compile
error; a key naming a nested invoke applies to every step it inlines. Its `when` is ANDed with the `when` of every inlined step and gate.
Any other field, `env` included, is a compile error on an invoke step.

For a matrix step the library writes itself, a key may name a coordinate,
`"<step>[<dimension>=<value>]"` (several pairs separated by `,`), and places each instance whose
coordinate matches every pair. The value is written as the matrix holds it
(`"build[arch=linux/arm64]"`). Each instance takes the coordinate key that names it, else the
plain key for its step, else the list an outer invoke gives when the library is itself invoked
from another library. The compiler checks each key against the library's matrix when it inlines
the invoke, and refuses a dimension or value the matrix does not have, two keys that could name
one instance, and a key whose instances `exclude` removes. Each compiled step still holds a
plain list of profiles, so Policies and admission see what they saw before.

**Step ids beside an invoke.** An invoke's steps are named `<invoke id>/<step>`, so no other step
at the same level may have an id that starts with `<invoke id>/`, or the invoke's own id. A
step `app/build` written beside `invoke` `app` is a compile error: it would read as one of the
library's steps, and the library would take its results as its own. A `[` or `]` in a step id
must pair, since Scarab reads `[…]` as a matrix coordinate when it splits an inlined step's
name.

**Installed libraries are closed.** A `lib:` library may invoke only `lib:` and `plugin:`
targets, never `file:`, so a repository cannot change the steps of a library its org installed.

**Every inlined step records where it came from** in `origin`: the chain of libraries that
produced it, outermost first, each with its kind, name and content hash (and, for `lib:`, the
source it was installed from). Policies read it, so a library can be allowed or blocked through
any depth of nesting. A library should pin its images by digest; `scarab lint` warns about a
library image pinned only by tag.

## Results & interpolation

A step publishes **named, typed results** that a downstream step reads at launch via
`${{ outputs.<step-id>.<name> }}`; launch parameters are read the same way as `${{ inputs.<name> }}`.
Interpolation is resolved at launch time against the upstream step's captured results, so a
consumer must `needs:` the producer.

**Results are not artifacts.** A result is a small typed value the DAG interpolates into a later
step's environment; an [artifact](#steps-the-step-shape) is a file published from
`/scarab/artifacts/` that you download after the run.

### Publishing a result

A step publishes result `<name>` by writing the file **`/scarab/results/<name>.json`**. The
result's name is the filename minus `.json`, and the file must hold **valid JSON**: `"abc123"`
(quotes included) for a string, `42` for a number, never bare text.

```yaml
- id: version
  image: busybox
  command:
    - sh
    - -c
    - |
      set -eu
      mkdir -p /scarab/results
      printf '"%s"' "1.4.2" > /scarab/results/tag.json     # string result "tag"
      printf '%s' 42 > /scarab/results/build.json          # number result "build"

- id: notify
  image: busybox
  needs: [version]
  env: [[TAG, "${{ outputs.version.tag }}"]]
  command: ["sh", "-c", 'echo "release $TAG"']
```

A step can also list the results it writes, with `results: [tag, build]`. The list is a
declaration, not a filter: a step that declares nothing still publishes every file it writes.

Beyond writing the file, capture needs no setup in the pipeline: on Kubernetes a trusted per-Pod egress sidecar
drains the step's results back to the control plane. The build library's step
publishes an `image` result (BuildKit writes `--metadata-file /scarab/results/image.json`);
its caller writes nothing.

### The trap: a bare filename publishes nothing, and the step still goes green

The sidecar drains **`*.json` files only**. Writing a bare `/scarab/results/tag`, the obvious
guess, publishes **nothing**: the glob matches no file, the sidecar logs only
`no results to drain`, and the step still **exits 0**. The run goes green while
`${{ outputs.version.tag }}` silently resolves to empty downstream. Nothing tells the author
they produced no result.

So make the consumer check that its interpolation resolved. That turns the silent no-op into a
failure where the value is used. The value goes in through `env:`, not into the script (see
[Values in commands and scripts](#values-in-commands-and-scripts)):

```yaml
- id: notify
  image: busybox
  needs: [version]
  env:
    - [TAG, "${{ outputs.version.tag }}"]
  command:
    - sh
    - -c
    - |
      test -n "$TAG"    # a producer-side typo fails HERE instead of shipping ""
      echo "release $TAG"
```

### Values in commands and scripts

Scarab never puts a value from outside the pipeline into a step's command, except a `choice`
value the pipeline listed, `true`/`false`, a non-negative decimal number, a hex commit SHA, or the
trigger kind; every other outside value reaches the step only as the value of an environment
variable the pipeline named, passed byte for byte.

A value is **from outside the pipeline** when it comes from a launch parameter (`inputs` in a
pipeline file), a step's results (`outputs`), a trigger event's fields, or a library input whose
caller's `with:` reads one of these, through any number of callers. Literals, `matrix` values, a
literal `with:` value and an input's `default` are the pipeline's own, and may go anywhere.

To use a free-text value (a branch, a ref, a URL, a result) in a command, name an environment
variable in `env:` and read it from the environment. In a shell, quote it:

```yaml
- id: checkout
  image: alpine/git
  env: [[REF, "${{ inputs.ref }}"]]
  command: ["sh", "-c", 'git checkout -- "$REF"']
```

The fixed shapes may be written into a command, whole or inside an argument:

| Value | Where it comes from | What Scarab checks when the step launches |
|---|---|---|
| a `choice` value | an input declared `type: choice` | the value is one of its `options` |
| `true` or `false` | an input declared `type: boolean`, or an expression over fixed values (`${{ inputs.replicas > 3 }}`) | it is a boolean |
| a number | an input declared `type: number`, or an expression over fixed values (`${{ inputs.replicas + 1 }}`) | it matches `^[0-9]+(\.[0-9]+)?$`: no sign, no exponent |
| a commit SHA | `${{ event.sha }}` | it matches `^[0-9a-f]{40}([0-9a-f]{24})?$`: 40 or 64 lower-case hex characters |
| a pull request or issue number | `${{ event.number }}`, `${{ event.issue }}` | it matches `^[0-9]+$` |
| `true` or `false` | `${{ event.fork }}` | it is a boolean |
| the trigger kind | `${{ event.kind }}` | it is one of `push`, `pull_request`, `tag`, `release`, `comment`, `cron`, `manual`, `api`, `upstream` |

The other event fields (`ref`, `branch`, `tag`, `repo.owner`, `repo.name`, `repo.clone_url` and
`run`) are free text and reach a step only through `env:`.

```yaml
- id: ship
  image: deployer
  command: ["deploy", "${{ inputs.region }}", "n=${{ inputs.replicas }}"]

- id: checkout
  image: alpine/git
  command: ["git", "checkout", "${{ event.sha }}"]
```

A library input counts by the type the library declares, so a library that takes a `string`
input can use it in a command only through `env:`. A free-text value in a command is a compile
error that names the step and the argument; for a library step it also names the library and the
caller's `with:` that binds the input. The step launch checks the same rule again, so a pipeline
posted to the API without compiling cannot skip it. A value that does not fit its shape when the
step launches (a number that turns negative, a choice value the pipeline did not list) fails the
step before it starts.

Why so strict: many programs read some of their arguments as code or as instructions. An argument
that starts with `-` is an option (`git fetch origin --upload-pack=…` runs a command), `@file`
reads a file, `+ref` force-pushes, and `ssh`, `su -c` and `env -S` join their arguments back into
a shell command. A `--` in front does not help either: it ends the options of one program, and the
value can reach another one (`sh -c '…' -- "$1"`, `npm run lint -- …`). No list of such programs
can be complete, so Scarab does not keep one. The fixed shapes contain none of these forms. An
environment variable's value is not parsed by anything until your step reads it.

**In a script**, any `${{ … }}` becomes part of the code. This covers the script of `sh -c` (and
`bash`, `dash`, `zsh`, `ash`, `ksh`), `python -c`, `node -e`, `perl -e` and `ruby -e`, also behind
`env`, `busybox`, `timeout`, `nice`, `nohup`, `stdbuf`, `setsid`, `sudo` and `exec`. A value from
outside the pipeline in a script is a compile error, fixed shapes included; a value written in the
pipeline is a lint warning. Pass the value in `env:` and read it as `"$VALUE"`.

What stays your responsibility: once a step reads an environment variable, Scarab no longer sees
it. An unquoted `$REF`, `eval "$REF"` or `ssh host "git checkout $REF"` turns it back into code.
Quote it, and pass it to programs as one argument.

### Trigger values: `event`

A template can read the trigger's values through `${{ event.<field> }}`, in a pipeline file and in
a library. Only fields whose values Scarab can check are readable:

| Field | Value | In a `command` |
|---|---|---|
| `kind` | the trigger kind | yes |
| `sha` | the commit, 40 or 64 hex characters, where the trigger has one | yes, lower-case hex only |
| `number`, `issue` | a pull request or issue number | yes |
| `fork` | `true` for a pull request from a fork | yes |
| `run` | the upstream Run's id | no, `env:` only |
| `repo.clone_url` | the repository's clone URL, from its forge connection | no, `env:` only |
| `repo.owner`, `repo.name` | letters, digits, `.`, `_` and `-`; no leading `-`, not `.` or `..`; at most 100 bytes | no, `env:` only |
| `ref`, `branch`, `tag` | letters, digits, `.`, `_`, `/`, `@` and `-`; no leading `-`, no `..` or `//`; at most 255 bytes | no, `env:` only |

The last column is the [command rule](#values-in-commands-and-scripts): a field marked yes may be
written into a command and is checked against its shape again when the step launches.

`repo.clone_url` is at most 2048 bytes, `run` 64 and `kind` 32.

`actor`, a comment's `body`, `schedule`, `changed_paths` and `changed_paths_known` are not readable, and neither is `${{ event }}` as a
whole: each is a compile error. The same holds for a `concurrency.group`, which renders against the
same checked values. A group reads only `inputs` and `event`: it is fixed when the Run is created,
before any step has run, so reading `outputs` is a compile error. A `when:` still sees the whole
event.

The values are checked and stored when the Run is created, so a rerun reads the same ones. A
pipeline that reads a field the trigger does not have, or one whose value fails its check, is
refused: a push to `fix;rm` refuses a pipeline that reads `${{ event.branch }}` ("branch name
contains `;`"), and runs every pipeline that does not.

## Environments & gates

This section covers only the YAML you author. For the concepts behind them (how secrets are
stored and scoped, and what an environment governs), see
[Secrets](/scarab-ci/usage/secrets/) and [Environments](/scarab-ci/usage/environments/).

A top-level `environment:` puts the pipeline's runs under that environment's governance: they are
checked against its protection rules at admission, get its scoped secrets, and are never cancelled
by newest-wins. It does not mark them as deploys; for that, see
[Deploys: `deploy: true`](#deploys-deploy-true). **Secrets** a step needs are named with
`secrets: [KEY, ...]`; each key is resolved against the run's scope (a run from a fork's pull
request is locked out and receives none).

Each secret is a file, `/scarab/secrets/KEY`, on a read-only in-memory volume in the step's
container; `$SCARAB_SECRETS` names the directory. The values come from a Kubernetes Secret for the
step's Pod, deleted when the step's attempt ends. The local executor has no container: it writes
the files to disk, in a directory under the step's working directory that only its own user can
read, sets `$SCARAB_SECRETS` to that directory, and removes it when the step's process ends.

A secret is not an environment variable unless its entry says so: write
`{ name: KEY, env: true }` in the same list, and the step also gets the environment variable `KEY`.
Kubernetes fills that variable from the Pod's own Secret, so the value is never written into the
Pod spec. Prefer the file: every process the step starts inherits its environment, and many tools
print their environment when they fail.

```yaml
environment: prod

steps:
  - id: ship
    image: deployer
    secrets:
      - DEPLOY_KEY                       # only the file /scarab/secrets/DEPLOY_KEY
      - { name: DEPLOY_TOKEN, env: true } # the file, and $DEPLOY_TOKEN
    command: ["sh", "-c", "./deploy.sh --key-file /scarab/secrets/DEPLOY_KEY"]
```

A secret's name is its file name: letters, digits, `-`, `_` and `.`, not starting with `.`.
`forge-token` and `forge-username` are taken by the [forge credential](#forge-credentials-forge_token).
A name with `env: true` must also be an environment variable name, and not one the step's `env:`
or Scarab already sets. `scarab validate` warns when a step's command reads `$KEY` or `${KEY}`
for a secret listed without `env: true`, since that variable is empty when the step runs. It reads
only the step's `command`: a script file the command runs is not checked.

**Gates** are durable suspend points with no image: `gate: manual` is an approval, `gate: timer` waits
`gate_after` seconds, `gate: external` releases via API/webhook. Placed before a deploy step, a
manual gate is the approval mechanism for a governed environment:

```yaml
- id: approve
  gate: manual
  needs: [build]

- id: release
  image: deployer
  needs: [approve]
```

Any gate can fail with a reason: by expiry, by a human reject, or by an external gate released
with `{"passed": false, "reason": "..."}`. A waiting gate holds only the steps that depend on it,
and each gate has its own clock, measured from when its `needs` finished.

### Plugin gates

A plugin installed in your org with the `resolve_gates` capability declares gates in its manifest.
A pipeline waits on one with `invoke: plugin:<installation>/<gate>`:

```yaml
- id: live
  needs: [bump]
  invoke: plugin:argocd-prod/wait-live
  with:
    app: payments-api
    image: ${{ outputs.bump.image }}
  gate_expires_after: 1800

- id: smoke
  image: cgr.dev/chainguard/busybox@sha256:…
  needs: [live]
  env: [[REVISION, "${{ outputs.live.revision }}"]]
```

This inlines one gate, `gate: plugin`, with the invoke step's id. Only the installation it names
can release it. `with:` is checked against the gate's declared inputs when the pipeline compiles,
and a value that reads an upstream output is rendered once, when the gate is reached. A value that
does not render fails the gate with the reason. The inputs are sent to the plugin, so `with:`
cannot read `secrets` or `env`, and an upstream output it reads must be one that step declares;
each is a compile error. `gate_expires_after` is required, at most 2592000 seconds (30 days): a
gate the plugin never answers fails when it expires. Anyone with write access to the project can
reject it sooner.

The plugin releases the gate with the outputs it declares, each of its declared type, and a later
step reads them as `${{ outputs.<gate>.<name> }}`. They are values from outside the pipeline, like
a step's results: the same `command` and script rules apply to them. A plugin never approves a
`gate: manual`, and it cannot see or release a gate in another org or one another installation
releases.

No plugin's gates run until an org admin lists the installation in the `plugins_allowed` setting.

## Deploys: `deploy: true`

`deploy: true` marks the runs that deploy. Set it on the pipeline, and every run of it is a
**deploy run**:

```yaml
environment: production
deploy: true
```

Or set it on the one step that deploys. The step is marked on the run page, and its run is a
deploy run:

```yaml
steps:
  - id: test
    image: tester
  - id: bump
    image: deployer
    needs: [test]
    deploy: true
```

The mark is separate from `environment:`. A deploy needs no environment, and a run in an
environment need not deploy. A gate cannot be marked.

A deploy run differs from other runs in two ways:

- **It is never cancelled by newest-wins.** A newer push to the same branch does not cancel it
  half-way, and its concurrency group queues even if the pipeline declares
  `concurrency: { group: ..., policy: cancel-in-progress }`. A run that names an environment
  behaves the same way.
- **You can filter for it.** The Runs tab has a **deploys** toggle and an Environment filter, and
  the API takes the same filters:
  `GET /v1/repos/{org}/{repo}/runs?deploy=true&environment=production`. Both are applied in the
  database query, so a page holds the newest matching runs, not the matches among the newest
  page.

A deploy run's green means only that its steps succeeded. With GitOps, the deploy step's success
means its change merged into the gitops repository; the CD tool applies it later, and the rollout
can still fail. To keep the run open until the change is live, add a step after the deploy step
that waits for it. [Deploying with Argo CD](/scarab-ci/usage/deploying-with-argo-cd/) has a
recipe. Scarab keeps no record of the deploy after the run ends; the CD tool's UI is where you see
what is live.

To keep two runs from deploying one service at the same time, give the pipeline a concurrency
group, for example `concurrency: { group: deploy-prod-payments-api }`. A group holds the whole run,
and it is scoped to the repository, so two repositories that deploy one service do not wait for
each other.

:::note[`deployment_requests` and `gate: deployment` are gone]
Scarab 0.2 had a Deployment record: a step field `deployment_requests` and a `gate: deployment`
that waited for a CD tool to report the change live. Both were removed (ADR-0074). A pipeline that
still uses them fails the pipeline check; replace the gate with a wait step as shown on
[Deploying with Argo CD](/scarab-ci/usage/deploying-with-argo-cd/).
:::

## Placement & resources

By default steps land on the operator's `default` placement profile. An author targets scheduling by
**naming profiles** (never raw Kubernetes) via `placement_profiles`, and requests exact compute
with `resources`:

```yaml
- id: heavy
  image: builder
  placement_profiles: [arm64, critical]
  resources: { cpu_millis: 8000, memory_mib: 16384 }
```

With the k8s executor, Scarab checks each name against the operator's profile registry when the
Run is created. A name the registry does not hold refuses the Run, and the error names the step
and the profile. It does not list the profiles the registry holds; ask the operator for those.
`scarab validate --server` and the policy test
report the same refusal. If the operator removes a profile after a Run was created, that Run's
step fails to launch and is retried as a launch error.

For a rare dynamic per-job Kubernetes need there is a governed `k8s_overlay` escape hatch: a raw
pod-spec fragment merged last onto the Pod. Writing one grants nothing by itself: it is admitted only
if the run's target environment permits raw overlays; otherwise the run is rejected (fail-closed). Prefer a named
profile for anything static.

```yaml
- id: heavy
  image: builder
  k8s_overlay:
    spec:
      nodeSelector:
        gpu: a100
```

Whoever edits the Pipeline file writes the overlay, so even where raw overlays are permitted it may
set only these fields. Scarab refuses any other field when the Run is created, and the error names
its path. `scarab validate --server` and the policy test report the same refusals. The executor
checks the same list again before it creates the Pod; an overlay refused there (after the
operator changed the lists, for example) fails the step as a configuration error with the reason.

An overlay that keeps to these fields can still make a Pod Kubernetes refuses, such as a
`nodeSelector` value that is not a valid label value, a memory request above the limit, or a field
that Pod Security, a LimitRange, an admission policy or a webhook in the step namespace denies.
When Kubernetes refuses the Pod as invalid (400, 422) or forbidden (403), Scarab asks it twice
more with dry runs, which create nothing: once for the same Pod, and, if that is refused again,
once for the Pod without the overlay. The step fails as a configuration error only when the same
Pod is refused again and the Pod without the overlay passes. Otherwise the launch is retried as a
launch error:

- the same Pod passes its dry run: the first refusal was of the moment, such as a ServiceAccount
  created a moment later or a webhook that answers each request on its own;
- the Pod fails without the overlay too: the operator's baseline, a profile or the server's
  permissions (RBAC) are at fault;
- the refusal is a ResourceQuota denial, which Kubernetes writes as
  `pods "<name>" is forbidden: exceeded quota: <quota>, ...`: it can pass once other Pods finish.
  A policy or webhook message that only contains the words "exceeded quota" is not this shape,
  and is checked like any other refusal.

The step's failure carries Kubernetes' message, cut to its first 1,024 bytes. The Run's author
reads it, so an admission policy's or webhook's denial message should hold nothing the author may
not read. The message of a refusal by the chart's step Pod admission policy is cut the same way.

One case is blamed on the overlay wrongly: a webhook that refuses for a reason of the moment (a
budget that frees up once a Pod finishes, for example) on both the create and the dry run, and
admits the Pod without the overlay, fails the step. Rerun the step once the reason has passed.

The dry runs go through the same admission webhooks as a real create. A webhook that does not
declare `sideEffects: None` or `NoneOnDryRun` refuses every dry run, so on a cluster with such a
webhook on Pods the Pod without the overlay never passes: a refusal the overlay caused stays a
launch error, and the launch is retried until it dead-letters. To get the configuration error
instead, make every validating and mutating webhook that matches Pods in the step namespace
support dry run.

| Field | Why it is allowed |
|-------|-------------------|
| `metadata.labels` | Only keys the operator lists in the placement config's `author_overlay.label_keys`. |
| `metadata.annotations` | Only keys the operator lists in `author_overlay.annotation_keys`. |
| `spec.nodeSelector` | Picks nodes by label. It can only narrow where the Pod runs. |
| `spec.affinity.nodeAffinity` | Picks nodes for placement. Pod affinity and anti-affinity are refused: a required anti-affinity keeps other Pods off the nodes the step Pod runs on. |
| `spec.tolerations` | Lets the Pod onto a tainted node pool, for taint keys the operator lists in `author_overlay.toleration_keys`. |
| `spec.topologySpreadConstraints` | Spreads step Pods over zones or nodes. |
| `spec.volumes[]` with `name` and `emptyDir` only | Scratch space that starts empty and holds no credential. The name must be new to the Pod and appear once in the overlay. |
| `spec.containers[]` entry `step`: `resources.requests`, `resources.limits` | CPU, memory or an extended resource such as a GPU. |
| `spec.containers[]` entry `step`: `env[]` with `name` and `value` | A literal value. `valueFrom` and `envFrom` can read a Secret. |
| `spec.containers[]` entry `step`: `volumeMounts[]` with `name`, `mountPath`, `readOnly` | Mounts an emptyDir volume the same overlay adds. |

Labels, annotations and tolerations are refused unless the operator lists their key. A label can
make the Pod match a NetworkPolicy or a Service, and an annotation can ask an admission webhook
for an IAM role, a Vault or mesh sidecar, or a network attachment, so the operator chooses which
keys authors may set. Nothing is listed by default. The operator lists keys in the server's
placement config (the chart value `scarab.placement.author_overlay`):

```yaml
author_overlay:
  label_keys: [team, cost-center]
  annotation_keys: ["karpenter.sh/do-not-disrupt", "prometheus.io/*"]
  toleration_keys: [nvidia.com/gpu]
```

Each entry is an exact key, `prefix/*` for every key under that prefix, or `*` for every key with
no prefix. An exact key matches only itself: `team` does not cover `team-admin`. A prefix holds no
`/` of its own (`example.com/*`, not `example.com/x/*`), since a key has one `/` at most; the
server refuses such an entry when it loads the config. Some keys stay refused even when listed: labels and annotations under `scarab.io/`,
`scarab.dev/` and `app.kubernetes.io/`, the AppArmor and seccomp annotations, and tolerations of a
`node-role.kubernetes.io/` taint or with an empty or missing `key`, which would let the Pod onto
the control-plane nodes.

Everything else is refused. That includes any Secret reference (a `secret` or `projected` volume,
`secretKeyRef`, `envFrom`, `imagePullSecrets`), `serviceAccountName`, `serviceAccount` and
`automountServiceAccountToken`, `hostNetwork`, `hostPID`, `hostIPC`, `hostPath` volumes,
`hostAliases` and `dnsConfig`, `nodeName`, `priorityClassName` (a high class preempts other
workloads), `schedulerName` (a custom scheduler can ignore the operator's taints and affinity), any
`securityContext`, the step container's `image` and `command`, and containers of its own
(`initContainers`, `ephemeralContainers`, or a `containers` entry other than `step`).

The overlay may add to the Pod, but it may not change or remove anything Scarab, the placement
baseline or a placement profile put there. It can add a toleration or a `nodeSelector` key; it
cannot remove the baseline's toleration, change a profile's `HTTP_PROXY`, override the baseline's
`nodeSelector` value, add a second node affinity term, or declare a volume with a name the Pod
already has. Set the step container's CPU and memory with
`resources:`; when that or the operator's default already set `requests.cpu`, the overlay cannot
change it.

To use a field the list does not allow, ask the operator to put it in a placement profile and name
that profile in `placement_profiles`. The baseline and profiles are written by the operator and are
not limited by this list.

The operator's baseline, each named profile in the order you list them, and then the
`k8s_overlay` are merged onto the Pod one after another, with a Kubernetes strategic merge:

- Objects merge key by key, and a `null` deletes a key.
- Lists Kubernetes merges by a key are merged item by item: `containers`, `initContainers` and
  `ephemeralContainers` by `name`; in a container, `env` by `name`, `volumeMounts` by `mountPath`,
  `ports` by `containerPort` and `volumeDevices` by `devicePath`; `volumes` and
  `imagePullSecrets` by `name`; `hostAliases` by `ip`; `topologySpreadConstraints` by
  `topologyKey` and `whenUnsatisfiable`. An item with a new key is appended.
- `tolerations` add up: a profile's tolerations are appended to the baseline's, and a toleration
  already on the Pod is not added twice. Kubernetes replaces this list; Scarab does not, so a
  profile cannot drop the baseline's tolerations.
- Every other list replaces, as in Kubernetes. Node affinity terms are one of them.

So a profile can change one field of the step container and keep the rest:

```yaml
k8s:
  spec:
    containers:
      - name: step
        securityContext:
          seccompProfile: { type: Unconfined }
```

The step container is the only container Scarab adds that a profile or overlay may name. The
results sidecar (`scarab-results-egress`), the workspace containers (`scarab-workspace-init`,
`scarab-workspace-egress`) and service sidecars (`service-0`, `service-1`, ...) carry Scarab's own
wiring. If the baseline, a profile or an overlay names or removes one, Scarab does not create
the Pod, and the launch error names the container and the layer. In the baseline or a profile, a
container with a new name, such as an extra init container, is allowed.

Scarab's volumes, mounts and env are guarded the same way. A layer may not:

- name, remove or replace a volume Scarab created (results, workspace, forge token, registry auth,
  OIDC token, secrets), or mount one in a container it adds or at a new path on the step container;
- change a mount Scarab set on the step container, such as `/workspace` (`/workspace/` and
  `//workspace` count as the same path);
- set or remove an env variable the step container was built with, such as `SCARAB_ATTEMPT` or
  one from the step's own `env:`.

A volume with a new name, a mount at a new path and an env variable with a new name are allowed.
Kubernetes' patch directives (`$patch`, `$retainKeys` and other keys starting with `$`) are not
supported: a layer that uses one is refused.

Step Pods, service Pods and debug Pods do not mount a Kubernetes ServiceAccount token
(`automountServiceAccountToken: false`), so code in a step cannot call the Kubernetes API with the
namespace's default ServiceAccount. A step that needs the API names a placement profile that sets
both `serviceAccountName` and `automountServiceAccountToken: true`.

An operator marks a profile `registry_auth_only: true` when it grants push access to a registry
(a ServiceAccount with a push role, an init container that logs in). Scarab applies such a profile
only to a step with `registry_auth` that the launch found eligible for a registry credential: a
step from a library your org trusts with the registry credential, in a Run that is not a fork pull
request or locked out of its Environment's secrets. It applies whether or not a credential
resolves, so a profile that logs in itself works with no `REGISTRY_AUTH` secret
([Pushing images to Amazon ECR](/scarab-ci/usage/pushing-to-ecr/)). Named on a step without
`registry_auth`, it refuses the Run when it is created (with the k8s executor), and the step fails
as a configuration error if such a Run reaches launch; on a `registry_auth` step the launch did
not find eligible it is left out. A marked profile cannot be the
`default` ([Building an image](#building-an-image) shows the map form that routes one to the push
step).

## Retries, timeouts & reruns

A step may set a `timeout:` (seconds) and an opt-in `retry:` policy. Retry is
**at-least-once**: by declaring it, you assert that the step is idempotent or fenced; a
side effect that is neither will fire twice.

```yaml
- id: flaky
  image: tester
  timeout: 600
  retry: { on: failure, max: 3 }
```

The timeout counts from when the step's process starts running. Waiting for a node, pulling
the image and fetching the workspace do not count against it. They have their own limit of
30 minutes: a step that has not started running by then fails as never started, with a message
saying so, and is retried automatically.

Re-execution that a person starts is modelled as **Takes**: a *rerun* re-executes a run from
the top, a *retry* resumes from a failed step, and an earlier attempt becomes *superseded* or
*shadowed* by the newer one. The UI shows these in a run's history. You don't write anything
for them.

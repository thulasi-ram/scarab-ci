## The model, in brief

A **step** is the basic unit of work: an OCI **image** plus a **command** (the step contract),
which Scarab runs as a single Kubernetes **Pod**. A **pipeline** is a group of steps, plus how they
are triggered and wired together. Structurally a pipeline is a **flat recursive DAG**
(`Pipeline → Step`).

You write YAML, with **CEL** for expressions. Scarab compiles it to a **typed IR**, and the IR
(not the YAML) defines what a valid pipeline is.
`invoke` reuses a library by inlining it into the caller's DAG at compile time.
`matrix` is a modifier that fans a step out over a set of inputs.

Compilation is **static**: the whole DAG (every matrix combination, every inlined library step) is
materialised and validated at submit time, so a cycle, a dangling `needs`, or an empty matrix
dimension is rejected up front, never discovered mid-run.

Keys are **strict** at every level of that schema. A key Scarab does not know (a misspelling,
a field borrowed from another CI system, a knob from a newer version) is a compile error that names
the key and the ones that were expected. It is never silently ignored:

```
unknown field `cpu_milis`, expected `cpu_millis` or `memory_mib`
```

Ignoring unknown keys would be worse: `resources: { cpu_milis: 500 }` would parse cleanly, report
`ok`, and then run the step with no CPU request at all, with nothing to show the setting was
dropped.

A repo's CI lives in `.scarab/`. A triggered pipeline is a YAML file such as `.scarab/ci.yaml`;
its file name is the default display name (`ci.yaml` reads as `ci`, overridable with a top-level
`name:`). Reusable **libraries** (files marked `kind: library`) live under `.scarab/lib/` by
convention and are pulled in with [`invoke`](#reuse-invoke). Start from
[Run locally](/scarab-ci/get-started/run-locally/) to submit your first pipeline.

:::caution[Commit `.scarab/`, and never blanket-ignore it]
`.scarab/` is **tracked source**: it is read from the triggering commit, so an ignored pipeline file
is a pipeline that does not exist. The catch is that a local `scarab-server` also writes its
development object store *inside* that directory (`SCARAB_OBJECT_DIR` defaults to
`./.scarab/objects`). That tempts a blanket `/.scarab` ignore rule, which then silently swallows
`git add .scarab/ci.yaml`. Ignore only the runtime path instead:

```gitignore
# runtime state only — the pipeline configs beside it are tracked source
/.scarab/objects/
```
:::

A minimal pipeline is an `on:` block and a list of `steps`:

```yaml
on:
  push: {}
  pull_request: {}

steps:
  - id: checkout
    invoke: lib:thulasi-ram/clone

  - id: check
    image: rust:1-bookworm
    needs: [checkout]
    command: ["cargo", "check"]
```

The rest of this page goes through each part: triggers and inputs, the step shape, wiring and
reuse, deploys, and the operational settings.

## Triggers: `on:`

`on:` maps a trigger kind to a filter. The kinds Scarab understands are `push`, `pull_request`,
`tag`, `release`, `comment`, `cron`, `manual`, `api`, and `upstream`. An empty `on:` means the
pipeline has no automatic triggers: it runs only when launched explicitly. `cron` and `upstream`
parse, but nothing produces those events yet, so those two triggers never fire.

```yaml
on:
  push: {}
  pull_request: {}
```

Each kind takes an optional `when:` CEL guard over the event context, so a trigger can fire
selectively:

```yaml
on:
  push:
    when: "event.branch == 'main'"
```

**Manual dispatch is opt-in**: a pipeline is dispatchable from the UI/API only if it declares
`on: manual`. The trigger context also feeds each run's provenance and **Headline** (the trigger
title shown against the run).

```yaml
on:
  manual: {}
  push: {}
```

## Interface: `interface.inputs` (and `outputs`)

A pipeline declares its typed launch parameters under `interface.inputs`. An `invoke` caller
fills in the same interface with `with:`, so launching and reuse share one contract. A
bare string is shorthand for a required string; the map form sets the type, whether it is required, a default and a description:

```yaml
on:
  manual: {}

interface:
  inputs:
    - { name: region, type: choice, options: [us-east-1, eu-west-1], description: "target region" }
    - { name: replicas, type: number, required: false, default: 2 }
    - { name: force, type: boolean, required: false, default: false }

steps:
  - id: ship
    image: busybox
    command: ["deploy", "${{ inputs.region }}", "n=${{ inputs.replicas }}"]
```

- `type` is one of `string` (default), `boolean`, `number`, `choice`. A `choice` needs a non-empty
  `options` list.
- `required` defaults to `true`. An optional parameter (`required: false`) **must** carry a
  `default`, so every parameter always has a resolved value.
- An optional `validate:` CEL predicate over the resolved value (bound as `value`) rejects a launch
  with a bad value (fail-closed).

Resolved parameters are read in steps as `${{ inputs.<name> }}` and are also injected into the
step environment as `SCARAB_PARAM_<NAME>`. A **library** additionally declares the `outputs` it
exposes to its caller, and inside a library `${{ inputs.<name> }}` reads the caller's `with:`, not
the Run's launch parameters (see [Reuse: `invoke`](#reuse-invoke)).

## Steps: the step shape

The step contract is an OCI `image` plus a `command`; everything else is a modifier. `env` is a list
of `[NAME, VALUE]` pairs; `artifacts` publishes globs of files the step wrote to `/scarab/artifacts/`.
A step names the secrets it needs with `secrets: [KEY, ...]` (resolution and scoping is covered under
[Environments & gates](#environments--gates)).

```yaml
- id: check
  image: rust:1-bookworm
  needs: [checkout]
  env:
    - [CARGO_TARGET_DIR, /tmp/scarab-target]
  command:
    - bash
    - -c
    - |
      set -euxo pipefail
      cargo check
      mkdir -p /scarab/artifacts
      rustc --version > /scarab/artifacts/toolchain.txt
  artifacts:
    - "*.txt"
```

A step asks for privilege above the hardened baseline under `security:`. `run_as_root` is
self-service (root inside the unprivileged sandbox, with its capabilities already dropped, does not escape it);
`add_capabilities` and `privileged` are governed and take effect only if the environment whitelists
the image digest.

```yaml
- id: check
  image: rust:1-bookworm      # its USER is root
  security:
    run_as_root: true
```

Some steps are **kinds** with no image that the engine runs on your behalf (you set no `image`/`command`):

- **`build: { image: ..., push: true }`**: a rootless BuildKit image build.
- **`gate: manual`**: a durable approval/wait point (see [Environments & gates](#environments--gates)).
- **`invoke: file:.scarab/lib/...`**: reuse at compile time (see [Reuse: `invoke`](#reuse-invoke)).

### Checking out the repository

The first-party clone library, `lib:thulasi-ram/clone`, checks out the Run's repository at the
commit the Run is pinned to. Your org installs it like any other library
([Libraries](/scarab-ci/usage/libraries/)); a new org gets it when its first repository is bound.

```yaml
- id: checkout
  invoke: lib:thulasi-ram/clone          # depth 1, the Run's commit

- id: full
  invoke: lib:thulasi-ram/clone
  with: { depth: full, submodules: true, lfs: true }
  timeout: 1800                          # carried onto the library's step
```

`depth` is `"1"`, a number of commits, or `full`. The library's one step is `checkout/git`, and
`needs: [checkout]` reaches it, so later steps inherit the checked-out workspace as usual. It works
the same on GitHub and Forgejo.

The `clone` step kind is gone. A `clone:` step fails the pipeline check with a message that names
`invoke: lib:thulasi-ram/clone`.

### Forge credentials: `forge_token`

A step that needs to talk to the Run's repository asks for a forge credential:

```yaml
- id: tag
  image: alpine/git@sha256:…
  forge_token: write        # or read
```

Scarab mints the credential each time the step's attempt launches, a rerun or retry included, and
mounts it as two files: `/scarab/secrets/forge-token` and `/scarab/secrets/forge-username`. It is
never an environment variable. When the attempt ends, the Kubernetes Secret that holds it is
deleted, even if the Pod is kept, and a token GitHub minted is revoked, by whichever Scarab server
sees the end.

Whether a step may have one is decided when the Run is created; a Run that asks for more is
refused with the reason. Each launch checks again, from the connection and the org's trust as
they are then: a step that may no longer have the token fails with the reason, and nothing is
minted.

- **On a GitHub App connection**, which mints a short-lived token for one repository, any step may
  ask. **On a Forgejo or GitHub token connection**, which hands out one long-lived token, only a
  step from a library your org trusts receives it: the first-party clone library, or a source an
  org admin trusted ([Libraries](/scarab-ci/usage/libraries/#trusting-a-library-with-forge-credentials)).
  A repository's own steps never read that token. Such a step also starts with an empty
  workspace: no file another step wrote is present while the token is mounted.
- **The forge connection** must be served over `https://`. A Run with a step that asks for
  `forge_token` on a connection whose base URL is `http://` is refused: the token is never sent
  over plain HTTP.
- **A fork pull request** always gets `read`, whatever the step asks for.
- **`write`** needs a GitHub App connection, and a Run governed by an environment that restricts
  the refs it deploys from. Where that environment has approvers, put a `gate: manual` in the
  step's `needs`.
- **The `image` and `command`** of a step with `forge_token` are written out in full: a
  `${{ … }}` in either is a compile error. An input, a result or an `event` value reaches the step
  only through `env:`, and only under a name of the form `SCARAB_<NAME>` (upper-case letters,
  digits and `_`) that Scarab does not set itself. Other names can make the value run as code:
  git runs `GIT_SSH_COMMAND`, and the loader reads `LD_PRELOAD`. A literal value may use any name.
- **A library input** that reaches a step with `forge_token` must be a `boolean`, a `number`, a
  `choice`, or a `string` with a `validate:` rule.
- A step with `forge_token` may not have a `cache`.
- An invoke step's `placement_profiles` is never carried onto a step with `forge_token`.

The local executor refuses a step with `forge_token`; it needs the Kubernetes executor.

## Ordering: `needs`

`needs:` declares the DAG edges. A step runs once all of its needs succeed and inherits their
workspaces:

```yaml
- id: deploy
  image: deployer
  needs: [build]
```

## Fan-out: `matrix`

**`matrix`** fans one authored step into the cartesian product of its dimensions, expanded
statically at submit time. An `exclude` list of
CEL predicates (evaluated against each combination's own coordinate) drops combinations:

```yaml
- id: test
  image: rust:1-bookworm
  matrix:
    dimensions:
      os: [linux, windows]
      arch: [amd64, arm64]
    exclude:
      - "os == 'windows' && arch == 'arm64'"
```

Each instance gets a deterministic id like `test[arch=amd64,os=linux]`, and a downstream
`needs: [test]` fans in over every surviving instance.

A matrix can have at most 65,536 combinations before `exclude`, and 256 `exclude` predicates. All
the matrices of one pipeline, counting a library's matrix each time the library is inlined, can
have at most 1,048,576 combinations, and at most 262,144 `exclude` checks (combinations times
predicates).

## Conditions: `when`

A `when:` CEL guard skips a step whose predicate is false; expressions read the run's context
(e.g. `event`, and any `matrix` coordinate):

```yaml
- id: deploy
  image: deployer
  needs: [build]
  when: "event.branch == 'main'"
```

### Expression limits

Each CEL expression in a pipeline (a `when:` guard, a matrix `exclude` predicate, an input's
`validate:` predicate, or the inside of one `${{ … }}`) can be at most **4096 bytes** long, with
brackets (`(`, `[` and `{` together) nested at most **64** deep. Brackets inside string literals
and `//` comments don't count. A pipeline over either limit is rejected at submit time, and the
error names the step, the field and the limit (the expression is cut short here):

```
step `build`: when cel error: `1+1+1+…`: expression is 5000 bytes; the limit is 4096 bytes
```

The CEL parser recurses once per nesting level and once per operator in a chain such as
`a + b + c`, so these limits bound how much stack one expression can use on the server.

### Size limits

A pipeline or library file can be at most **1 MiB**, and the libraries one pipeline invokes can
hold at most **16 MiB** in all, each counted once however often it is invoked. The compiled
pipeline can be at most **16 MiB** of JSON: each step a library inlines stores the library's
inputs, and each matrix leg stores a copy of its step, so a small file can compile to a large
pipeline. A pipeline over any of these limits is rejected at submit time, and the error names the
file or step and the limit. The server also stops a compile that takes longer than 10 seconds,
and the trigger fails with that reason.

## Reuse: `invoke`

`invoke` inlines a **library** into the caller's DAG at compile time; it is not a runtime call.
The invoked steps are namespaced by the invoke step's id (`deploy/plan`, `deploy/url`), and
`matrix` on an invoke step fans out the whole subgraph.

The target always has a prefix that says where it comes from:

| `invoke:` | Target |
|---|---|
| `file:<path>` | a library file in the repository, read at the caller's ref |
| `lib:<publisher>/<name>` | a library installed in your org |
| `plugin:<installation>/<gate>` | a gate a plugin installed in your org resolves ([Plugin gates](#plugin-gates)) |

A `file:` path is repo-relative: no leading `/`, no `..`, and no remote or cross-repo forms
(cross-repo causation is `on: upstream`). A bare path is a compile error that tells you to add
`file:`, and `url:` is refused: Scarab does not invoke from a URL. A `lib:` target resolves to the
version your org installed ([Libraries](/scarab-ci/usage/libraries/)); a name the org has not
installed fails with "`lib:<publisher>/<name>` is not installed in this org".

A library is a YAML file marked `kind: library`. It has no `on:` triggers and never runs on its
own: Scarab does not trigger it or list it for dispatch, even directly under `.scarab/`. It
declares its contract with `interface` (the `inputs` it takes and the `outputs` it exposes) and the
caller supplies inputs with `with:`:

```yaml
# .scarab/lib/deploy.yaml
kind: library
interface:
  inputs:
    - { name: region, type: string }
    - { name: replicas, type: number, required: false, default: 2 }
  outputs: [url]
steps:
  - { id: plan, image: tf@sha256:…, command: ["plan", "${{ inputs.region }}"] }
  - { id: url,  image: tf@sha256:…, command: ["apply"], needs: [plan] }
```

```yaml
# .scarab/ci.yaml
steps:
  - id: deploy
    invoke: file:.scarab/lib/deploy.yaml
    with: { region: us-east-1, replicas: "3" }
    timeout: 1800

  - id: notify
    image: busybox
    needs: [deploy]
    command: ["echo", "${{ outputs.deploy.url }}"]
```

The interface is checked at compile time: every required input present, no unknown extras, each
value of its declared type, and every referenced output declared.

**Inputs are read at launch.** Inside a library step, `${{ inputs.<name> }}` in its `image`,
`command`, `env`, `when:` and the `with:` of its own invokes reads the value its caller bound, so
in the example above `plan` runs `plan us-east-1`. Inside a library, `inputs` never means the
Run's launch parameters, and reading an input the library does not declare is a compile error. A
literal `with:` value is checked against the input's type when the pipeline compiles. A `with:`
value that holds a template, such as the caller's `${{ outputs.<step>.<name> }}`, is rendered in
the caller's scope when the library step launches, then checked against the input's type and
`validate:`. The inputs also reach each inlined step as `SCARAB_PARAM_<NAME>`.

**What the invoke step carries.** An invoke step may set `needs`, `with`, `matrix`, `when`,
`deploy`, `timeout`, `resources` and `placement_profiles`. Its `timeout`, `resources` and
`placement_profiles` apply to each inlined step that leaves them unset (the library's own value
wins), and never to a gate. `placement_profiles` never applies to a step with `forge_token`. Its `when` is ANDed with the `when` of every inlined step and gate.
Any other field, `env` included, is a compile error on an invoke step.

**Installed libraries are closed.** A `lib:` library may invoke only `lib:` and `plugin:`
targets, never `file:`, so a repository cannot change the steps of a library its org installed.

**Every inlined step records where it came from** in `origin`: the chain of libraries that
produced it, outermost first, each with its kind, name and content hash (and, for `lib:`, the
source it was installed from). Policies read it, so a library can be allowed or blocked through
any depth of nesting. A library should pin its images by digest; `scarab lint` warns about a
library image pinned only by tag.

## Results & interpolation

A step publishes **named, typed results** that a downstream step reads at launch via
`${{ outputs.<step-id>.<name> }}`; launch parameters are read the same way as `${{ inputs.<name> }}`.
Interpolation is resolved at launch time against the upstream step's captured results, so a
consumer must `needs:` the producer.

**Results are not artifacts.** A result is a small typed value the DAG interpolates into a later
step's command or environment; an [artifact](#steps-the-step-shape) is a file published from
`/scarab/artifacts/` that you download after the run.

### Publishing a result

A step publishes result `<name>` by writing the file **`/scarab/results/<name>.json`**. The
result's name is the filename minus `.json`, and the file must hold **valid JSON**: `"abc123"`
(quotes included) for a string, `42` for a number, never bare text.

```yaml
- id: version
  image: busybox
  command:
    - sh
    - -c
    - |
      set -eu
      mkdir -p /scarab/results
      printf '"%s"' "1.4.2" > /scarab/results/tag.json     # string result "tag"
      printf '%s' 42 > /scarab/results/build.json          # number result "build"

- id: notify
  image: busybox
  needs: [version]
  command: ["echo", "release ${{ outputs.version.tag }}"]
```

A step can also list the results it writes, with `results: [tag, build]`. The list is a
declaration, not a filter: a step that declares nothing still publishes every file it writes.

Beyond writing the file, capture needs no setup in the pipeline: on Kubernetes a trusted per-Pod egress sidecar
drains the step's results back to the control plane. A `build:` step
emits an `image` result natively (BuildKit writes `--metadata-file /scarab/results/image.json`);
its author writes nothing.

### The trap: a bare filename publishes nothing, and the step still goes green

The sidecar drains **`*.json` files only**. Writing a bare `/scarab/results/tag`, the obvious
guess, publishes **nothing**: the glob matches no file, the sidecar logs only
`no results to drain`, and the step still **exits 0**. The run goes green while
`${{ outputs.version.tag }}` silently resolves to empty downstream. Nothing tells the author
they produced no result.

So make the consumer check that its interpolation resolved. That turns the silent no-op into a
failure where the value is used. The value goes in through `env:`, not into the script (see
[Values in commands and scripts](#values-in-commands-and-scripts)):

```yaml
- id: notify
  image: busybox
  needs: [version]
  env:
    - [TAG, "${{ outputs.version.tag }}"]
  command:
    - sh
    - -c
    - |
      test -n "$TAG"    # a producer-side typo fails HERE instead of shipping ""
      echo "release $TAG"
```

### Values in commands and scripts

Each `${{ … }}` is rendered once, when the step launches, and its value is data: Scarab never
reads a `${{` inside a value again. Where you put a value decides what it can do.

**In a `command` argument or an `env` value**, the value is passed as it is, with no quoting
needed. A value from outside the pipeline has two exceptions, and a step that breaks either fails
before it starts, with an error that names the template:

- It may not start an argument with `-`. A program reads such an argument as an option, so
  `git fetch origin ${{ inputs.ref }}` with the value `--upload-pack=touch /tmp/x` would run a
  command. A `--` argument in front does not help: it ends the options of one program, and the
  value can still reach another one (`sh -c 'git fetch "$1"' -- …`, `npm run lint -- …`). Write
  the option in front of the value, or pass the value in `env:`.
- It may not name the program. That is the first thing in `command[0]`, and the program that
  `env`, `sudo`, `timeout`, `nice`, `nohup`, `stdbuf`, `setsid`, `exec`, `busybox` or `xargs`
  runs when one of them comes first, including the command line of `env -S`. Write the program
  in the pipeline and pass the value to it.

```yaml
- { id: ship, image: deployer, command: ["deploy", "--ref=${{ inputs.ref }}"] }
- id: fetch
  image: alpine/git
  env: [[REF, "${{ inputs.ref }}"]]
  command: ["sh", "-c", 'git fetch origin "refs/heads/$REF"']
```

**In a script**, the value becomes part of the code. This covers the script of `sh -c` (and
`bash`, `dash`, `zsh`, `ash`, `ksh`), `python -c`, `node -e`, `perl -e` and `ruby -e`, also behind
`env`, `busybox`, `timeout`, `nice`, `nohup`, `stdbuf`, `setsid`, `sudo` and `exec`. A value from
outside the pipeline in a script is a compile error; a value written in the pipeline is a lint
warning. Pass the value in `env:` and read it from the environment, as in the `notify` example
above.

A value is **from outside the pipeline** when it comes from a launch parameter (`inputs` in a
pipeline file), a step's results (`outputs`), an `event` field, or a library input whose caller's
`with:` reads one of these, through any number of callers. Literals, `matrix` values, a literal `with:` value and an
input's `default` are the pipeline's own.

### Trigger values: `event`

A template can read the trigger's values through `${{ event.<field> }}`, in a pipeline file and in
a library. Only fields whose values Scarab can check are readable:

| Field | Value |
|---|---|
| `kind` | the trigger kind |
| `sha` | the commit, 40 or 64 hex characters, where the trigger has one |
| `number`, `issue` | a pull request or issue number |
| `fork` | `true` for a pull request from a fork |
| `run` | the upstream Run's id |
| `repo.clone_url` | the repository's clone URL, from its forge connection |
| `repo.owner`, `repo.name` | letters, digits, `.`, `_` and `-`; no leading `-`, not `.` or `..`; at most 100 bytes |
| `ref`, `branch`, `tag` | letters, digits, `.`, `_`, `/`, `@` and `-`; no leading `-`, no `..` or `//`; at most 255 bytes |

`repo.clone_url` is at most 2048 bytes, `run` 64 and `kind` 32.

`actor`, a comment's `body` and `schedule` are not readable, and neither is `${{ event }}` as a
whole: each is a compile error. The same holds for a `concurrency.group`, which renders against the
same checked values. A `when:` still sees the whole event.

The values are checked and stored when the Run is created, so a rerun reads the same ones. A
pipeline that reads a field the trigger does not have, or one whose value fails its check, is
refused: a push to `fix;rm` refuses a pipeline that reads `${{ event.branch }}` ("branch name
contains `;`"), and runs every pipeline that does not.

## Environments & gates

This section covers only the YAML you author. For the concepts behind them (how secrets are
stored and scoped, and what an environment governs), see
[Secrets](/scarab-ci/usage/secrets/) and [Environments](/scarab-ci/usage/environments/).

A top-level `environment:` puts the pipeline's runs under that environment's governance: they are
checked against its protection rules at admission, get its scoped secrets, and are never cancelled
by newest-wins. It does not mark them as deploys; for that, see
[Deploys: `deploy: true`](#deploys-deploy-true). **Secrets** a step needs are named with
`secrets: [KEY, ...]`; each key is resolved against the run's scope and made available to the step
under the same name (a run from a fork's pull request is locked out and receives none).

```yaml
environment: prod

steps:
  - id: ship
    image: deployer
    secrets: [DEPLOY_TOKEN]
    command: ["./deploy.sh"]
```

**Gates** are durable suspend points with no image: `gate: manual` is an approval, `gate: timer` waits
`gate_after` seconds, `gate: external` releases via API/webhook. Placed before a deploy step, a
manual gate is the approval mechanism for a governed environment:

```yaml
- id: approve
  gate: manual
  needs: [build]

- id: release
  image: deployer
  needs: [approve]
```

Any gate can fail with a reason: by expiry, by a human reject, or by an external gate released
with `{"passed": false, "reason": "..."}`. A waiting gate holds only the steps that depend on it,
and each gate has its own clock, measured from when its `needs` finished.

### Plugin gates

A plugin installed in your org with the `resolve_gates` capability declares gates in its manifest.
A pipeline waits on one with `invoke: plugin:<installation>/<gate>`:

```yaml
- id: live
  needs: [bump]
  invoke: plugin:argocd-prod/wait-live
  with:
    app: payments-api
    image: ${{ outputs.bump.image }}
  gate_expires_after: 1800

- id: smoke
  image: curlimages/curl
  needs: [live]
  env: [[REVISION, "${{ outputs.live.revision }}"]]
```

This inlines one gate, `gate: plugin`, with the invoke step's id. Only the installation it names
can release it. `with:` is checked against the gate's declared inputs when the pipeline compiles,
and a value that reads an upstream output is rendered once, when the gate is reached. A value that
does not render fails the gate with the reason. `gate_expires_after` is required: a gate the plugin
never answers fails when it expires. Anyone with write access to the project can reject it sooner.

The plugin releases the gate with the outputs it declares, each of its declared type, and a later
step reads them as `${{ outputs.<gate>.<name> }}`. They are values from outside the pipeline, like
a step's results: the same `command` and script rules apply to them. A plugin never approves a
`gate: manual`, and it cannot see or release a gate in another org or one another installation
releases.

No plugin's gates run until an org admin lists the installation in the `plugins_allowed` setting.

## Deploys: `deploy: true`

`deploy: true` marks the runs that deploy. Set it on the pipeline, and every run of it is a
**deploy run**:

```yaml
environment: production
deploy: true
```

Or set it on the one step that deploys. The step is marked on the run page, and its run is a
deploy run:

```yaml
steps:
  - id: test
    image: tester
  - id: bump
    image: deployer
    needs: [test]
    deploy: true
```

The mark is separate from `environment:`. A deploy needs no environment, and a run in an
environment need not deploy. A gate cannot be marked.

A deploy run differs from other runs in two ways:

- **It is never cancelled by newest-wins.** A newer push to the same branch does not cancel it
  half-way, and its concurrency group queues even if the pipeline declares
  `concurrency: { group: ..., policy: cancel-in-progress }`. A run that names an environment
  behaves the same way.
- **You can filter for it.** The Runs tab has a **deploys** toggle and an Environment filter, and
  the API takes the same filters:
  `GET /v1/repos/{org}/{repo}/runs?deploy=true&environment=production`. Both are applied in the
  database query, so a page holds the newest matching runs, not the matches among the newest
  page.

A deploy run's green means only that its steps succeeded. With GitOps, the deploy step's success
means its change merged into the gitops repository; the CD tool applies it later, and the rollout
can still fail. To keep the run open until the change is live, add a step after the deploy step
that waits for it. [Deploying with Argo CD](/scarab-ci/usage/deploying-with-argo-cd/) has a
recipe. Scarab keeps no record of the deploy after the run ends; the CD tool's UI is where you see
what is live.

To keep two runs from deploying one service at the same time, give the pipeline a concurrency
group, for example `concurrency: { group: deploy-prod-payments-api }`. A group holds the whole run,
and it is scoped to the repository, so two repositories that deploy one service do not wait for
each other.

:::note[`deployment_requests` and `gate: deployment` are gone]
Scarab 0.2 had a Deployment record: a step field `deployment_requests` and a `gate: deployment`
that waited for a CD tool to report the change live. Both were removed (ADR-0074). A pipeline that
still uses them fails the pipeline check; replace the gate with a wait step as shown on
[Deploying with Argo CD](/scarab-ci/usage/deploying-with-argo-cd/).
:::

## Placement & resources

By default steps land on the operator's `default` placement profile. An author targets scheduling by
**naming profiles** (never raw Kubernetes) via `placement_profiles`, and requests exact compute
with `resources`:

```yaml
- id: heavy
  image: builder
  placement_profiles: [arm64, critical]
  resources: { cpu_millis: 8000, memory_mib: 16384 }
```

For a rare dynamic per-job Kubernetes need there is a governed `k8s_overlay` escape hatch: a raw
pod-spec fragment merged last onto the Pod. Writing one grants nothing by itself: it is admitted only
if the run's target environment permits raw overlays; otherwise the run is rejected (fail-closed). Prefer a named
profile for anything static.

```yaml
- id: heavy
  image: builder
  k8s_overlay:
    spec:
      schedulerName: my-scheduler
```

## Retries, timeouts & reruns

A step may set a `timeout:` (seconds) and an opt-in `retry:` policy. Retry is
**at-least-once**: by declaring it, you assert that the step is idempotent or fenced; a
side effect that is neither will fire twice.

```yaml
- id: flaky
  image: tester
  timeout: 600
  retry: { on: failure, max: 3 }
```

Re-execution that a person starts is modelled as **Takes**: a *rerun* re-executes a run from
the top, a *retry* resumes from a failed step, and an earlier attempt becomes *superseded* or
*shadowed* by the newer one. The UI shows these in a run's history. You don't write anything
for them.

---
title: Fork Run approval
description: An org setting that holds every Run of fork code at an approval gate until someone with write on the repository approves it. Approving it starts the Run and unlocks nothing else.
---

Fork Run approval is an org setting. While it is on, a Run of **fork code** waits at an approval
gate before any of its steps or shared services start. Someone with write on the repository
approves it from the Run page, and the Run continues. It is off until an org admin turns it on.

A Run is fork code when it builds a pull request from another repository, or a commit that no
branch or tag of the repository points at (see [Runs](/scarab-ci/usage/runs/#starting-a-run-by-hand)).
Fork code gets no secrets whether or not this setting is on. The setting adds a person who
decides whether the code runs at all.

## Turning it on

In **Org settings › Security**, tick **Hold Runs of fork code for approval**. Only an org admin can
change it, and only from a signed-in browser: an API token, a session sent as `Bearer`, or an app
acting for you cannot. Turning it off asks you to confirm with your passkey; turning it on does
not. Each change is recorded in the org's security events as `fork_run_approval.changed`, with the
old and new value.

The API is `GET` and `PUT /v1/orgs/{org}/security/fork-run-approval`:

```bash
curl -s "$SCARAB_ADDR/v1/orgs/acme/security/fork-run-approval" \
  -H "Authorization: Bearer $SCARAB_TOKEN"
# {"enabled":true,"can_change":false}
```

Reading it needs the `settings.read` operation. The `PUT` body is `{"enabled": true}` or
`{"enabled": false}`.

The setting applies to Runs created after the change. A Run created before it keeps its gate, or
runs without one.

## The gate

Scarab adds one `manual` gate, `fork-run-approval`, with no `needs`, and puts it in the `needs`
of every step that had none. Nothing in the Run starts before it is approved, and the Run's shared
services wait too. The Run page labels the gate "added by Fork Run approval". A step whose
`when:` is false at creation is left out, and a Run with no step that would start gets no gate.

In the stored Run the gate looks like this:

```yaml
- id: fork-run-approval
  gate: manual
  gate_expires_after: 259200
  origin: [{ kind: fork_run_approval_gate, name: fork_run_approval, content_hash: "" }]
```

A gate that nobody approves fails the Run after 72 hours. Rejecting it fails the Run.

## Who can approve it

| Who | What happens |
|-----|--------------|
| A person with write on the repository, in a browser | approved at once, like any plain `manual` gate |
| An API token whose owner has write on the repository | refused with `403 step_up_required`; the approval counts once the owner confirms it with a passkey |
| An app connected to Scarab for you (an `oauth` token) | refused; an app never approves a gate |

The Run's events record who approved it, and the token when one was used.

## It is not an Environment approval

The gate never counts as an Environment's approval gate. A pipeline that deploys to an
Environment with approvers still gets that Environment's own gate, behind this one, and the
Environment's approvers still decide. Approving the Fork Run approval gate does not approve a
deploy, and an Environment's gate does not stand in for this one.

## What approving does not unlock

An approved Run is still fork code. It still gets no Environment secrets, no registry credentials,
the `env=none` OIDC subject, a read-only clone token and no image push. Approving the gate lets the
code run; it does not give the code anything a Run of fork code would not get.

## Reruns and retries

An approval covers the version of the Run it was given in. A **Rerun** opens a new version, so in
a Run of fork code it puts the gate back: the gate waits for approval again, and the steps between
the gate and the step you reran wait behind it. Those steps are skipped when their inputs did not
change. The rerun's confirm box lists them under "Waits for Fork Run approval again".

A **Retry** of a failed step stays in the current version and does not ask again.

## Rolling back

The setting is stored in migration 0114. 0.8.4 is the release to roll back to: it reads Runs that
have the gate and holds them at it, and an earlier server cannot load such a Run. Before you roll
back, turn the setting off in every org and approve or reject the gates still waiting. See the
chart README, "Upgrading from 0.8.4", for the revert script.

## What an Environment is

An Environment (for example `staging` or `prod`) is a **deploy destination whose rules and
scoped secrets an admin owns** (ADR-0037).
The useful part is the bundle. One reference (`environment: prod` in a pipeline) pulls in
approval, secrets, allowed refs and OIDC subject, which an admin defines **once** and any
pipeline can reuse. Because the rules live in the environment, which an admin owns, and not in the
pipeline YAML, you get separation of duties: a pipeline author *requests* a deploy, and the
environment *decides* whether it goes ahead, whatever the YAML says. Editing an environment needs
the **Administer** capability on the repo.

Protection is **optional per environment**. An environment with no rules (typically `staging`) is
only a label that scopes secrets. Add reviewers and it becomes gated. Rules are opt-in, so
low-risk targets carry no overhead.

## The rules it bundles

An environment's `ProtectionRules` carry:

- **`approvers`**: principals whose approval is required. Approvals are recorded on a gate, not in
  a separate table: a `manual` gate in the run accumulates distinct approver identities on the run's
  durable event log (`GateApproved { step, by }`), and the run stays suspended until every named
  approver has approved. This survives restarts, and approvals cannot be forged.
- **`wait_timer`**: a mandatory wait (seconds) before a run may proceed.
- **`allowed_refs`**: glob patterns for the git refs allowed to deploy here; checked at **run
  creation** so a disallowed ref is rejected before any pod launches (blank = any ref).
- **`require_reason`**: a human dispatch (`manual`/`api`) into this environment must carry a
  reason (ADR-0057); push/PR/tag/release/cron are exempt.
- **`concurrency`**: the maximum concurrent deployments into this environment.

Two more governed settings need Administer and fail closed: `privileged_images` (the
ADR-0039 privilege whitelist keyed by digest) and `permit_k8s_overlay` (the ADR-0055 raw pod-spec escape
hatch).

## Scoped secrets with inheritance

An environment defines a **secret scope**. Steps in a run targeting it resolve keys through the
chain **`env → repo → org`, where the most specific scope wins**, so a value shared across environments lives once
at repo/org scope and only values that differ are stored per-environment. The server sets the
scope from the environment's `(org, repo, name)` coordinate, so prod credentials exist **only**
under the gated environment and cannot be moved by editing pipeline YAML. See [Secrets](/scarab-ci/usage/secrets/).

## Admission at the point of use

The engine enforces admission itself; a caller can't satisfy it with a request body.
`allowed_refs` is checked at run creation, `approvers` is satisfied by the gate approvals the run
has collected, and `require_reason` is checked at the admission gate. There is no `approvals` list
for the caller to supply: the old standalone `POST …/deploy` admission path is retired, and
deployment history is read-only.

## API endpoints

Environments are managed under `/v1/repos/{org}/{repo}/environments...` (writes require
**Administer**):

| Method | Path | Purpose |
|---|---|---|
| `PUT` | `/v1/repos/{org}/{repo}/environments/{name}` | Create or replace an environment + rules |
| `GET` | `/v1/repos/{org}/{repo}/environments` | List a repo's environments |
| `GET` | `/v1/repos/{org}/{repo}/environments/{name}` | One environment's protection rules |
| `DELETE` | `/v1/repos/{org}/{repo}/environments/{name}` | Delete (idempotent) |
| `GET` | `/v1/repos/{org}/{repo}/environments/{name}/deployments` | Deployment history (read-only) |

These endpoints are **behind a feature gate**: if the environment store is not configured, they
return **404**.

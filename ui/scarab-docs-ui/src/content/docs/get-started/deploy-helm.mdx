You install Scarab on a cluster with its Helm chart; Scarab is Kubernetes-only by design. The
chart deploys `scarab-server` (one binary, selectable roles) with the RBAC it needs to launch one
Pod per step in its namespace.

The **same chart** targets any Kubernetes: a local kind cluster or a real, live cluster.
`just stack up` (below) installs this chart on a local kind cluster; a live cluster uses the same
`helm upgrade --install` with your own Postgres, object store, and credentials. The chart is
new and will get more production hardening as people use it, but nothing in it is local-only.

## The chart

The chart lives at `deploy/helm/scarab/` (`Chart.yaml`, `values.yaml`, `templates/`). It expects:

- **Postgres**: the durable store that all run state and coordination go through; without it the server serves the API only.
- **An S3-compatible object store** (AWS S3 or in-cluster MinIO) for logs, artifacts, and the
  content-addressed workspace snapshots reruns restore; a fallback to a local directory exists for development.
- **The published image** `ghcr.io/thulasi-ram/scarab-server`, built by
  `.github/workflows/image.yml`. Use the mutable `edge` tag or a pinned `sha-<gitsha>`.

A direct install:

```sh
helm upgrade --install scarab deploy/helm/scarab \
  --namespace scarab --create-namespace \
  --set image.tag=edge \
  --set secrets.databaseUrl='postgres://scarab:scarab@postgres.scarab.svc:5432/scarab' \
  --set scarab.s3.bucket=scarab-logs \
  --set scarab.s3.endpoint=http://minio.scarab.svc:9000 \
  --set secrets.s3AccessKey=scarab --set secrets.s3SecretKey=scarabsecret
```

For production, keep credentials out of `--set`: create a Secret whose keys are the `SCARAB_*`
environment-variable names and reference it with `secrets.existingSecret`.

The GitHub App private key is the one credential with a bootstrap problem: storing it through the
API needs a server that is already running, and a stored key is lost if the database is recreated.
So the chart can instead mount it from a Secret you manage out-of-band, and the server reads it at
boot:

```sh
kubectl -n scarab create secret generic scarab-github-app \
  --from-file=github-app.pem=./my-app.private-key.pem
# then: --set scarab.githubAppId=123456 \
#       --set secrets.githubAppPemSecret.name=scarab-github-app
```

A boot-supplied key overrides any stored `_forge` credential and survives a database recreate. The
*installations* it authenticates as are separate durable state, registered from the App's
`installation` webhook deliveries.

:::caution[Two App settings that fail silently]
A correct webhook URL and secret are not enough. Both of these produce a loop that *looks* healthy
and has no error anywhere:

- **Subscribe to events** (App → *Permissions & events → Subscribe to events*): check **Push** and
  **Pull request**. With the list empty, `push`/`pull_request` are never delivered, so nothing ever
  runs. But `installation` and `installation_repositories` still arrive (App-management events are
  independent of the subscription list), so the connection registers and `GET /v1/repos` looks
  fine. The symptom: *"the repo is registered but no run ever starts."*
- **Commit statuses: read & write** (App → *Permissions → Repository*): without `statuses:write`
  every status post is rejected `403 Resource not accessible by integration`. The run itself still
  succeeds, so the only visible effect is a pull request that never shows a Scarab status. Add
  **Checks: read & write** only if you use checks; **Contents: read** is what a checkout needs (add **Contents: write** only for a step with
  `forge_token: write`).

You do not have to verify these by eye: the org's **Settings › Connections** runs a preflight against the
App and names whatever is missing (`GET /v1/connections/{id}/preflight`), so a misconfigured App
shows as *unhealthy* instead of failing silently. A permission change is not live until an
installation owner **approves the new access** (GitHub emails them). Until they do, the preflight
keeps reporting the gap.
:::

## Forge connections

A forge connection (a GitHub App installation, or a Forgejo or GitHub token) serves one org, and
every repository bound through it must be owned by that org. An org's admins manage its
connections under **Settings › Connections** (`/orgs/<org>/settings/connections`); they do not
see another org's connections, and `GET /v1/connections` lists only the connections of orgs you
administer (`?org=<org>` narrows it to one).

- **An org's first connection** is created by a global admin, under **Settings › Server
  administration › Connect a forge** (`/settings/server/connect-forge`), or with
  `POST /v1/connections` and an `org` field. After that, the org's own admins can add more.
- **An org name** is not empty, is at most 100 characters, and has no `/`, spaces or control
  characters. It is not `.` or `..`, does not start with `_` (those names are Scarab's own), and
  is not one of `settings`, `orgs`, `account` or `security`: a project's page is
  `/<org>/<repository>`, and those are the first part of other web UI addresses. The server
  answers 400 otherwise, and a `connections:` entry with such an `org:` fails the boot.
- **A GitHub App installation** registers itself from its `installation` webhook, which also
  records the account's GitHub id. It is assigned the org named like the account the App is
  installed on when two things hold: every repository already bound through it is owned by that
  account, and the org either does not exist yet or is already served by a GitHub connection to
  the same host with the same account id. A login can be renamed and then registered by another
  account, so a login alone does not join an org. An org exists once anything is kept for it:
  members, an API token, a secret, an Environment, a Policy, a Plugin or a library, as well as a
  connection or a repository. Otherwise the connection stays unassigned and binds none of the
  delivery's repositories. Once it serves an org, it mints tokens only from its own
  installation, and only for repositories that org owns.
- **A connection declared in `scarab.connections`** names its org with `org:`. Without `org:`,
  the org is the one owner of its `repos:`. A repository of another owner, repositories of
  several owners without `org:`, no repositories and no `org:`, or a repository already bound
  through another connection that serves an org fail the boot. So does an `org:` that differs
  from the org the connection already serves, a change of case included; to move a connection
  to another org, remove it from the config, unbind its repositories, and add it again. In
  GitHub App mode a `kind: github` entry needs `installation_id:` (the installation it is),
  unless its id is `github-install-<id>`; the boot is refused without it, because the
  connection would otherwise list the repositories of every installation of the App:

  ```yaml
  scarab:
    connections:
      - id: forgejo-main
        kind: forgejo
        org: acme
        base_url: https://git.example.com
        credential: { env: FORGEJO_CI_TOKEN }
        repos: [acme/widgets]
      - id: github-acme
        kind: github
        org: acme
        installation_id: 12345678
        base_url: https://api.github.com
        credential: { secret_ref: github-app }
  ```

A connection with no org is shown only to global admins, and its repositories keep working.
After an upgrade from a release before connections had an org, these are the connections whose
repositories have several owners or none, and **every GitHub App installation connection**: the
database does not hold an installation's account, and an earlier re-sync could bind another
installation's repositories to it. An unassigned installation connection keeps looking up each
repository's installation, so its repositories keep getting tokens. Its next `installation`
delivery assigns it when the rules above allow it; for an org that existed before the upgrade
they do not (no connection has an account id yet), so a global admin assigns it. Nothing assigns it an org as a side effect: opening Add repository, a re-sync or a bind
leaves it unassigned. A re-sync through it binds nothing and lists every repository the forge
reports in `skipped`, so the UI does not offer Re-sync on it.

A global admin assigns it with **Assign to org** (`PUT /v1/connections/{id}/org` with
`{ "org": "<name>" }`). It asks for step-up confirmation and is recorded in the org's event log.
The server answers 409 with the reason when a repository bound through the connection is owned
by another account, when the org is served by another forge or host, when the org exists with no
connection, or when the connection is managed by configuration. Anyone other than a global admin,
an API token included, gets 403.

To split a connection whose repositories have several owners, add a connection for each org and
bind or re-sync the repositories through it. A repository moves only off a connection that does
not serve its owner (one with no org, or one of another org); one bound through a connection of
its own org stays there, even when you bind it through another connection of the same org (409
on Add repository, `skipped` on re-sync). Unbind it from the connection that holds it first.
When every repository has moved, remove the old connection. Removing a connection that still
holds a repository of another org is refused (409, naming it): that org re-syncs or adds it on
its own connection first.

## Settings

The web UI's settings page has a sidebar with up to three groups, and each section has its own
address:

- **Your account**, for everyone, under `/settings/<section>`: Profile (your sign-in accounts),
  Security (your passkeys and security events), [API tokens](/scarab-ci/usage/api-tokens/)
  (your own tokens) and Appearance.
- **Organization settings**, for the admins of an org, under `/orgs/<org>/settings/<section>`:
  Connections, Members, Environments, Plugins, Libraries, Secrets, API tokens (every token issued
  in the org), Security and Event log. `/orgs/<org>/settings` opens Connections. An admin of several orgs switches org at the top
  of the group.
- **Server administration**, for global admins, under `/settings/server/<section>`: Connect a
  forge.

`/settings` opens the first org you administer, or your profile. The old addresses (`/account`,
`/account/security`, `/settings/libraries/review`) redirect to the new ones. The UI shows only
the groups you may use; the server checks every request.

### Appearance

Settings › Appearance picks the palette, **Emerald** or **Mono** (greys), and light or dark mode.
Both choices are kept in your browser, so they apply to you on that browser only.

## Key values

Every key in this table exists in `values.yaml`:

| Key | Default | Notes |
|-----|---------|-------|
| `image.repository` / `image.tag` | `ghcr.io/thulasi-ram/scarab-server` / appVersion | container image |
| `scarab.role` | `converged` | `api` / `scheduler` / `executor` / `webhook` / `converged` |
| `scarab.executor` | `k8s` | `k8s` (prod) or `local` (dev only) |
| `scarab.namespace` | release ns | namespace step Pods launch into (RBAC granted there) |
| `scarab.publicUrl` | `http://localhost:8080` | where forges reach Scarab: webhook URLs and the run link in commit statuses |
| `scarab.uiUrl` | `scarab.publicUrl` | where people open the web UI, when that differs from `publicUrl`; see [The UI URL](#the-ui-url) |
| `scarab.s3.*` | — | object store; set `bucket` to enable S3/MinIO |
| `secrets.*` / `secrets.existingSecret` | — | sensitive `SCARAB_*` env (DB URL, S3 keys, master key, webhook secrets) |
| `secrets.githubAppPemSecret.name` / `.key` | — / `github-app.pem` | mount the GitHub App private key from your own Secret |
| `rbac.create` | `true` | Role/RoleBinding for Pod execution |
| `ingress.enabled` | `false` | expose the HTTP API |

See `deploy/helm/scarab/README.md` and `values.yaml` for every value.

### Plugins

`plugins.enabled` (default `false`) turns on the plugin runtime: a shared plugin namespace, the
CredentialBroker and the RBAC they need. No built plugin capability acts on Scarab yet (ADR-0074),
so you don't need it to run pipelines or deploys; leave it off unless you are working on a plugin.
A plugin that needs storage brings its own: you create a PersistentVolumeClaim in the plugin
namespace and the plugin runtime mounts it. Scarab doesn't provision, back up or read that
volume, and its data is outside what Scarab keeps.

#### Plugin storage

Create the claim in the plugin namespace (`plugins.namespace`, default `scarab-plugins`) and
annotate it with the installation it is for, as `<org>/<installation name>`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: argocd-state
  namespace: scarab-plugins
  annotations:
    scarab.io/plugin-installation: acme/argocd-prod
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 1Gi
```

Then name it on the installation, under Settings › Plugins › storage, or with
`PUT /v1/orgs/{org}/plugins/{name}/storage` and a body of
`{"claim": "argocd-state", "mount_path": "/data"}`. `mount_path` defaults to `/data`; it
can't be `/`, and it can't overlap `/tmp`, `/var/run/secrets` or the other paths the runtime
or the kubelet mounts.

The plugin namespace is shared by every org, so the runtime mounts a claim only when its
annotation names that installation. Until it does, or while the claim is missing, the plugin is
held at zero replicas and its status names the claim. A claim that hasn't bound yet shows as
waiting. The plugin runs as uid and gid 65532 with `fsGroup: 65532`; a volume type that ignores
`fsGroup` (hostPath, some local provisioners) needs to be writable by that uid.

Adding storage to an installation that has none, or removing it, needs no step-up. Moving it
to another claim or mount path asks for a passkey step-up. Removing it leaves the claim and its
data in place.

## A minimal `values.yaml`

An example override for a real cluster, where Postgres and S3 credentials come from a Secret you
manage out-of-band (`secrets.existingSecret`), not inline:

```yaml
image:
  tag: sha-<gitsha>        # pin an immutable published tag; `edge` tracks main

scarab:
  role: converged          # or split: api / scheduler / executor / webhook
  executor: k8s
  publicUrl: https://scarab.example.com   # run deep-link in commit statuses
  s3:
    bucket: scarab-artifacts
    endpoint: ""           # empty => AWS S3; set for in-cluster MinIO
    region: us-east-1

secrets:
  # Keys in this Secret must match the SCARAB_* env-var names
  # (e.g. SCARAB_DATABASE_URL, SCARAB_S3_ACCESS_KEY, SCARAB_MASTER_KEY,
  #  SCARAB_GITHUB_WEBHOOK_SECRET).
  existingSecret: scarab-env

ingress:
  enabled: true
  className: nginx
  hosts:
    - host: scarab.example.com
      paths:
        - path: /
          pathType: Prefix
```

Every key above exists in the chart's `values.yaml`; see it (and `README.md`) for the full
reference.

### The UI URL

`scarab.uiUrl` (`SCARAB_UI_URL`) is the address people open the web UI at. Leave it empty when
that is `scarab.publicUrl`. Set it when forges and people reach Scarab at different addresses,
for example a staging install whose public hostname routes only `/webhooks/` while people use
`http://localhost:8080` through a port-forward. Three things use it:

- the login callback, `{uiUrl}/v1/auth/callback`, which is the callback URL to register with the
  login provider;
- the passkey origin: a passkey works only on that origin, and one enrolled on another address
  does not work here;
- the confirmation link a step-up request answers with.

Webhook URLs and the run links in commit statuses stay on `scarab.publicUrl`. The server refuses
to boot when `uiUrl` is not an `http` or `https` URL, has a query or fragment, or, with step-up
on, is plain `http` on a host other than `localhost`, `127.0.0.1` or `::1`. Browsers refuse
passkeys on an IP address, so a local `uiUrl` is `http://localhost:<port>`. A sign-in started
on `127.0.0.1` is sent to the `localhost` address first, so the sign-in keeps its cookie.

Session cookies are marked `Secure`. Chrome and Firefox accept them on `http://localhost`;
Safari may not, so sign in to a plain-`http` local install with Chrome or Firefox.

### Grant the first roles

The people in `scarab.oauth.owners` are Owners each time they sign in. To give anyone a role
before an Owner can do it in the UI, or to have an install's first members listed on the org's
Members page, run the server binary with the database URL:

```sh
scarab-server admin grant --org acme --subject github:alice --role member --reason "first members"
```

`--role` is `viewer`, `member`, `admin` or `owner`. The person must have signed in once; until
then the command exits 3 and says so. The command sets the role exactly: it lowers a higher
role, restores a revoked one, and turns a role a forge import gave into one the forge sync
does not change. When the person already holds that role, nothing is written. Each grant is
recorded in the org's event log as `binding.operator_grant`, with the host, OS user and
reason, in the same transaction as the role. The command needs only `--database-url` or
`SCARAB_DATABASE_URL` and never migrates the database.

A script that runs on every deploy should pass `--if-absent`. The command then writes nothing
when the person has any role binding in the org, at the org or at a project, or one that was
revoked, and prints what is there. A role an Owner changed in the UI stays as the Owner set it.

In a cluster, run it in the server Pod, which has the database URL:

```sh
kubectl exec -n scarab deploy/scarab -c scarab-server -- \
  scarab-server admin grant --org acme --subject github:alice --role member
```

## The chart on a local kind cluster

`just stack up` installs the same chart on a local kind cluster, `scarab-dev`, with Postgres and
MinIO running in the cluster beside it. What differs from a live install is where the
binaries come from: the server and the workspace service run a `scarab-server` built from your
working tree and mounted into a small runtime image, and the step helper images are built
locally and loaded into the node. A code change needs a rebuild and a Pod restart
(`just stack reload`), not an image build.

```sh
just stack up          # build the server, create the kind cluster, install the chart
just stack reload      # rebuild and roll the server and workspace Pods onto the new binary
just stack up dogfood  # the same release in GitHub App mode, behind a Cloudflare tunnel
just stack down        # delete the cluster and its data
```

Every kubectl and helm call uses the cluster's own kubeconfig (`deploy/kind/.kubeconfig`),
checked against the cluster before each call. See
[Run locally](/scarab-ci/get-started/run-locally/) for a first run and `deploy/kind/README.md`
for the details.

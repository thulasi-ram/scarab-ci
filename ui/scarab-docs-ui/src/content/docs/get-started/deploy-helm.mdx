You install Scarab on a cluster with its Helm chart; Scarab is Kubernetes-only by design. The
chart deploys `scarab-server` (one binary, selectable roles) with the RBAC it needs to launch one
Pod per step in its namespace.

The **same chart** targets any Kubernetes: a local kind cluster or a real, live cluster.
`just stack up` (below) installs this chart on a local kind cluster; a live cluster uses the same
`helm upgrade --install` with your own Postgres, object store, and credentials. The chart is
new and will get more production hardening as people use it, but nothing in it is local-only.

## The chart

The chart lives at `deploy/helm/scarab/` (`Chart.yaml`, `values.yaml`, `templates/`). It expects:

- **Postgres**: the durable store that all run state and coordination go through; without it the server serves the API only.
- **An S3-compatible object store** (AWS S3 or in-cluster MinIO) for logs, artifacts, and the
  content-addressed workspace snapshots reruns restore; a fallback to a local directory exists for development.
- **The published image** `ghcr.io/thulasi-ram/scarab-server`, built by
  `.github/workflows/image.yml`. Use the mutable `edge` tag or a pinned `sha-<gitsha>`.

A direct install:

```sh
helm upgrade --install scarab deploy/helm/scarab \
  --namespace scarab --create-namespace \
  --set image.tag=edge \
  --set secrets.databaseUrl='postgres://scarab:scarab@postgres.scarab.svc:5432/scarab' \
  --set scarab.s3.bucket=scarab-logs \
  --set scarab.s3.endpoint=http://minio.scarab.svc:9000 \
  --set secrets.s3AccessKey=scarab --set secrets.s3SecretKey=scarabsecret
```

For production, keep credentials out of `--set`: create a Secret whose keys are the `SCARAB_*`
environment-variable names and reference it with `secrets.existingSecret`.

The GitHub App private key is the one credential with a bootstrap problem: storing it through the
API needs a server that is already running, and a stored key is lost if the database is recreated.
So the chart can instead mount it from a Secret you manage out-of-band, and the server reads it at
boot:

```sh
kubectl -n scarab create secret generic scarab-github-app \
  --from-file=github-app.pem=./my-app.private-key.pem
# then: --set scarab.githubAppId=123456 \
#       --set secrets.githubAppPemSecret.name=scarab-github-app
```

A boot-supplied key overrides any stored `_forge` credential and survives a database recreate. The
*installations* it authenticates as are separate durable state, registered from the App's
`installation` webhook deliveries.

:::caution[Two App settings that fail silently]
A correct webhook URL and secret are not enough. Both of these produce a loop that *looks* healthy
and has no error anywhere:

- **Subscribe to events** (App → *Permissions & events → Subscribe to events*): check **Push** and
  **Pull request**. With the list empty, `push`/`pull_request` are never delivered, so nothing ever
  runs. But `installation` and `installation_repositories` still arrive (App-management events are
  independent of the subscription list), so the connection registers and its repositories are
  listed on the org page. The symptom: *"the repo is enabled but no run ever starts."*
- **Commit statuses: read & write** (App → *Permissions → Repository*): without `statuses:write`
  every status post is rejected `403 Resource not accessible by integration`. The run itself still
  succeeds, so the only visible effect is a pull request that never shows a Scarab status. Add
  **Checks: read & write** only if you use checks; **Contents: read** is what a checkout needs (add **Contents: write** only for a step with
  `forge_token: write`).

You do not have to verify these by eye: the org's **Settings › Connections** runs a preflight against the
App and names whatever is missing (`GET /v1/connections/{id}/preflight`), so a misconfigured App
shows as *unhealthy* instead of failing silently. A permission change is not live until an
installation owner **approves the new access** (GitHub emails them). Until they do, the preflight
keeps reporting the gap.
:::

## Forge connections

A forge connection (a GitHub App installation, or a Forgejo or GitHub token) serves one org, and
every repository bound through it must be owned by that org. An org's admins manage its
connections under **Settings › Connections** (`/orgs/<org>/settings/connections`); they do not
see another org's connections, and `GET /v1/connections` lists only the connections of orgs you
administer (`?org=<org>` narrows it to one).

- **An org's first connection** is created by a global admin: in Organization settings, pick
  **New organization…** at the bottom of the org dropdown (`/orgs/_new`), name the org and add its
  Forgejo connection, or call `POST /v1/connections` with an `org` field. After that, the org's
  own admins add more under its **Settings › Connections**. For GitHub, install the App on the
  account instead: the installation registers the connection and the org. The page asks which
  forge, and for GitHub lists the install steps with a link to the App's install page; **Check
  for the organization** opens the org the installation created.
- **An org name** is not empty, is at most 100 characters, and has no `/`, spaces or control
  characters. It is not `.` or `..`, does not start with `_` (those names are Scarab's own), and
  is not one of `settings`, `orgs`, `account` or `security`: a project's page is
  `/<org>/<repository>`, and those are the first part of other web UI addresses. The server
  answers 400 otherwise, and a `connections:` entry with such an `org:` fails the boot.
- **A GitHub App installation** registers itself from its `installation` webhook, which also
  records the account's GitHub id. It is assigned the org named like the account the App is
  installed on when two things hold: every repository already bound through it is owned by that
  account, and the org either does not exist yet or is already served by a GitHub connection to
  the same host with the same account id. A login can be renamed and then registered by another
  account, so a login alone does not join an org. An org exists once anything is kept for it:
  members, an API token, a secret, an Environment, a Policy, a Plugin or a library, as well as a
  connection or a repository. Otherwise the connection stays unassigned until a global admin
  assigns it. Either way the delivery binds no repository: see
  [Enabling repositories](#enabling-repositories). Once it serves an org, it mints tokens only
  from its own installation, and only for repositories that org owns.
- **A connection declared in `scarab.connections`** names its org with `org:`. Without `org:`,
  the org is the one owner of its `repos:`. A repository of another owner, repositories of
  several owners without `org:`, no repositories and no `org:`, or a repository already bound
  through another connection that serves an org fail the boot. So does an `org:` that differs
  from the org the connection already serves, a change of case included; to move a connection
  to another org, remove it from the config, unbind its repositories, and add it again. In
  GitHub App mode a `kind: github` entry needs `installation_id:` (the installation it is),
  unless its id is `github-install-<id>`; the boot is refused without it, because the
  connection would otherwise list the repositories of every installation of the App:

  ```yaml
  scarab:
    connections:
      - id: forgejo-main
        kind: forgejo
        org: acme
        base_url: https://git.example.com
        credential: { env: FORGEJO_CI_TOKEN }
        repos: [acme/widgets]
      - id: github-acme
        kind: github
        org: acme
        installation_id: 12345678
        base_url: https://api.github.com
        credential: { secret_ref: github-app }
  ```

### Enabling repositories

A repository becomes a project, with its own runs, Environments and secrets, only when an org
admin enables it. Installing the GitHub App, adding repositories to the installation, adding a
Forgejo connection and a re-sync all make repositories *available*; none of them enables one.

The org page, `/orgs/<org>` (click the org name before a repository's name), lists every
repository the org's connections reach, 25 to a page, each marked **Enabled** or **Not enabled**,
with a few counts for the org above it: enabled repositories, runs in the last 24 hours, failed
runs in the last 24 hours, and runs waiting on a gate. An org admin sees:

- **Enable**, which binds the repository through the connection that reaches it
  (`POST /v1/connections/{id}/repos`). For Forgejo it also registers the repository's webhook.
  Pushes start runs from then on.
- **Disable**, which unbinds it (`DELETE /v1/connections/{id}/repos/{owner}/{name}`) after you
  type `<org>/<repository>` to confirm. The project goes with its Environment overlays, secrets and
  access grants. Disabling sticks: no later installation event or re-sync enables the repository
  again. Enabling it again creates a new project without the old one's settings.

Anyone who can read the org sees the same list without the buttons. The list comes from
`GET /v1/orgs/{org}/repos?page=&per_page=&q=&connection=`, which asks each connection's forge on
every request (with `connection`, only that connection's); a connection the forge would not
answer for is named in `unlisted`, and its enabled repositories are still listed. The org page is
where repositories are enabled. **Settings › Connections** shows how many repositories each
connection has enabled (`enabled_repos` on `GET /v1/connections`), and each connection's page
links to the org page narrowed to that connection (**Manage repositories**). An enabled repository's **Settings** tab
has the same **Disable** for org admins, and goes to the org page once it is done; both ask for
the same typed name. For a Forgejo repository, the tab also has **Register webhook**
(`POST /v1/connections/{id}/repos/{owner}/{name}/webhook`), for when enabling could not register
it.

Events of a repository that is not enabled (a push to a repository the App covers, for example)
are acknowledged with `200 {"ignored": "repository not enabled"}` and start nothing, so the forge
does not retry them. A **Re-sync** (`POST /v1/connections/{id}/resync`) lists the repositories the
forge reaches that are not enabled in `available` and binds none of them.

Repositories that an earlier release bound when the App was installed stay enabled after an
upgrade; nothing is unbound.

Nothing the forge sends deletes a project either. When you remove an enabled repository from the
App's installation on GitHub, or uninstall or suspend the App, its repositories stay enabled and
are marked **unreachable** (`unreachable_since`, unix ms, on `GET /v1/repos` and the org page
rows). The repository's page and the org page say so. While a repository
is unreachable, its events are ignored like those of a repository that is not enabled, a manual
run answers 409, and any other forge call for it (a status post, a clone) fails with an error that
names the reason. The mark clears when GitHub covers the repository again (an
`installation_repositories` delivery that adds it, or an `unsuspend`), or when a re-sync lists it.
To remove the project, disable the repository, on the org page or on its Settings tab.

### Connections without an org

A connection with no org is shown only to global admins, under **Waiting for an organization**
on the New organization page (`/orgs/_new`), and its repositories keep working. An org's
Connections does not list it. The org dropdown's last entry counts these connections, for
example **New organization… (1 waiting)**, and so does the command palette.
After an upgrade from a release before connections had an org, these are the connections whose
repositories have several owners or none, and **every GitHub App installation connection**: the
database does not hold an installation's account, and an earlier re-sync could bind another
installation's repositories to it. An unassigned installation connection keeps looking up each
repository's installation, so its repositories keep getting tokens. Its next `installation`
delivery assigns it when the rules above allow it; for an org that existed before the upgrade
they do not (no connection has an account id yet), so a global admin assigns it. Nothing assigns it an org as a side effect: listing what it reaches, a re-sync or a bind
leaves it unassigned. A re-sync through it binds nothing and lists every repository the forge
reports in `skipped`, so the UI does not offer Re-sync on it.

Each row names the forge account: its login and immutable id, and for GitHub the installation
id, as the last `installation` delivery recorded them (the login follows a rename on the next
delivery; a row no delivery has reached since the upgrade shows neither). A global admin assigns
it there with **Assign to an organization**, or makes a new org from it with **Create a new
organization from it**, whose name starts as the account's login. Both call `PUT /v1/connections/{id}/org` with
`{ "org": "<name>" }`; a name no org has yet creates the org. It asks for step-up confirmation and
is recorded in the org's event log.
The server answers 409 with the reason when a repository bound through the connection is owned
by another account, when the org is served by another forge or host, when the org exists with no
connection, or when the connection is managed by configuration. Anyone other than a global admin,
an API token included, gets 403.

To split a connection whose repositories have several owners, add a connection for each org and
enable or re-sync the repositories through it: a re-sync moves the org's projects off a
connection that does not serve it (`moved`). A repository moves only off a connection that does
not serve its owner (one with no org, or one of another org); one bound through a connection of
its own org stays there, even when you bind it through another connection of the same org (409
on the bind, `skipped` on re-sync). Unbind it from the connection that holds it first.
When every repository has moved, remove the old connection. Removing a connection that still
holds a repository of another org is refused (409, naming it): that org re-syncs or adds it on
its own connection first.

### Webhook deliveries

The forge posts each event to `/webhooks/github` or `/webhooks/forgejo`. Scarab keeps the
delivery's id (`X-GitHub-Delivery`, `X-Forgejo-Delivery` or `X-Gitea-Delivery`) and, for each
Pipeline file, what that delivery decided: a Run, a refusal, not run, or no match. A redelivery
with the same id decides only the files no earlier try decided, so it creates the Runs the
delivery is missing and no Run twice. The forge's delivery log shows the answer:

| Answer | What happened | What to do |
|---|---|---|
| 202 | Runs were created; the body lists their ids. `earlier` lists what an earlier try of the same delivery decided | Nothing |
| 200 | Nothing started: `{"ignored": "<reason>"}` (for example `no matching pipeline`, or `duplicate delivery` when every Pipeline is already decided), or `refused` lists the Pipelines that were refused | Nothing |
| 400 | A Pipeline file does not compile (the text says why; its check is posted as failed), the body is not an event Scarab reads, or the delivery has no id header (with forge connections configured) | Fix the Pipeline and push again; a hand-made request needs the forge's delivery id header |
| 401 | The signature does not match the webhook secret | Check the secret on both sides |
| 409 | Another try of this delivery is running, on this server replica or another, or a Run of it is still being created. The lease of a try lasts 10 minutes | Redeliver it later |
| 502 | The forge could not be read (three tries, 0.5 and 2 seconds apart), or a Pipeline was left undecided: its file could not be read, or its Run could not be created. The body lists `run_ids`, `refused`, `earlier` and `undecided` | Redeliver it from the forge's webhook page |
| 503 | 64 deliveries were already running and none ended within 10 seconds. Nothing was recorded | Redeliver it later |

On a redelivery:

- `.scarab/` is read at the commit the first try read it at. For a comment that is `HEAD`
  then, and for a tag or release the tag's commit then. When that commit cannot be looked up,
  the try reads at `HEAD` or the tag, as before, and the next try looks it up again.
- A push, a pull request or a comment on a pull request creates no Run when a newer delivery
  of the same ref or pull request arrived at another commit, whatever that delivery started.
  The Pipeline is recorded as not run, and its check fails with "no longer the head of" the ref
  or pull request. Tags, releases and comments that are not on a pull request always run, and
  so does a comment whose pull request's head could not be read on the first try. Scarab
  orders deliveries by when they arrived: a forge that delivers two pushes out of order makes
  the newer one look old.
- A Run whose creation stopped part way (the server stopped, a write failed) is replaced: after
  10 minutes, or at once when it already ended `Failed`. The old Run stays `Failed`, names its
  replacement, and rerun, retry and gate actions on it answer 409.

GitHub's Redeliver sends the same id, so it repairs the delivery. A Forgejo Replay sends a new
id: Scarab treats it as a new delivery and starts its Runs again. Neither forge redelivers on
its own, so a delivery answered 502 or 409 waits until someone redelivers it (GitHub keeps
deliveries for 3 days).

Scarab keeps deliveries for `retention.webhookDeliveryDays` (`SCARAB_RETENTION_WEBHOOK_DELIVERY_DAYS`,
default 30) and refuses to start with fewer than 7: a redelivery of a delivery already pruned
would create its Runs again.

A delivery's work runs in a task of its own. When the forge stops waiting (GitHub after 10
seconds, Forgejo after its `DELIVER_TIMEOUT`), the delivery still creates its Runs; only the
answer is lost. When the server shuts down, it waits up to 20 seconds for running deliveries to
finish, then logs how many it left. A try the shutdown cuts short leaves its delivery for a
redelivery once its lease lapses. The chart sets no `terminationGracePeriodSeconds`, so a Pod
has Kubernetes' default 30 seconds to stop.

## Settings

The web UI has two settings pages, each with its own sidebar, and each section has its own
address. The user menu links the pages you may use:

- **Account settings**, for everyone, under `/settings/<section>`: Profile (your sign-in accounts),
  Security (your passkeys and security events), [API tokens](/scarab-ci/usage/api-tokens/)
  (your own tokens) and Appearance.
- **Organization settings**, for the admins of an org, under `/orgs/<org>/settings/<section>`:
  Connections, Members, Environments, Plugins, Libraries, Secrets, API tokens (every token issued
  in the org) and Security (the step-up settings, then the org's security event log with its
  filters; **Refusals, last 24h** filters it to recent refusals). `/orgs/<org>/settings` opens
  Connections. The old address `/orgs/<org>/settings/events` opens Security. The org
  dropdown at the top of the sidebar switches org and keeps the section. For a global admin its
  last entry is **New organization…** (`/orgs/_new`), where a new org is created with its first
  Forgejo connection, and where the connections that serve no org wait for one.

Connections is the one place a forge connection is added: **Add forge connection**, top right
of an org's Connections, or New organization… for an org Scarab does not have yet. The dialog asks
which forge. For GitHub it lists the steps to install the App on the org's account and links to
the App's install page, which the server reads from GitHub (`GET /v1/forges/github/app`); a
server without a GitHub App says so. For Forgejo or Codeberg it asks for the instance URL and an
access token. Connections
lists one row per connection: its forge and host, tags such as **credential missing**, **no
deliveries yet** or **managed by configuration**, how many repositories it has enabled and its
last webhook delivery. The forge and host link to the connection's page
(`/orgs/<org>/settings/connections/<id>`), which shows its id, whether its credential resolves,
its last delivery and, for GitHub, the App's configuration check, and has **Manage
repositories**, **Re-sync**, **Manage on GitHub** and **Remove**. Removing asks you to type the
connection's id. A connection managed by configuration has no Re-sync or Remove there.

On Security, an owner resets the passkeys of a member who lost theirs with **Reset passkeys**, at
the top right: pick the member (the admins without a passkey are marked), then type their name.
Clicking an admin in **Admins without a passkey** opens the same dialog with that admin picked.
The reset asks you to confirm with your own passkey, and the page says how many passkeys and
confirmations it removed.

Members lists one row per person: their org role, which applies to every repository in the org,
and how many repositories they hold a role in. Someone who holds roles on single repositories only
is listed with no org role. **Grant role**, at the right of the list's header, grants an org role
in a dialog. **Manage** on a row opens the person's page
(`/orgs/<org>/settings/members/<subject>/manage`), where you change or revoke their org role
(revoking asks you to type the subject) and see their repository roles, each linking to that
repository's Access. A role on one repository
is managed on that repository's **Settings** tab, under **Access** (org admins only). It lists who
holds a role on the repository and whether it was granted in Scarab or came from the forge's
collaborators, then, greyed, the people whose org role reaches it. **Re-sync collaborators**
reads the repository's collaborators from the forge and gives each a role from their permission
there: admin → admin, write → member, read → viewer. Someone the forge no longer lists loses the
role it gave them; roles granted or revoked in Scarab are never changed. The dialog lists who was
added, changed and removed.

`/settings` opens the first org you administer; a global admin with no org yet gets New
organization…, and anyone else their profile. The old addresses (`/account`, `/account/security`,
`/settings/libraries/review`, and `/settings/server/connect-forge` from the former Server
administration page) redirect to the new ones. The UI shows only the pages you may use; the
server checks every request.

### Appearance

Settings › Appearance picks the palette, **Emerald** or **Mono** (greys), and light or dark mode.
Both choices are kept in your browser, so they apply to you on that browser only.

### About Scarab

**About Scarab** in the user menu opens `/about`: the server's version, the git commit it was
built from (with a link to it on GitHub), when the server started, its role, where steps run, and
whether sign-in, the GitHub App and plugins are on. It links the release notes for that version,
the docs, the API description (`/openapi.json`) and the source code. Copy the version and commit
from it when you report a problem. The page reads `GET /v1/about`, which any signed-in user may
call. A server built outside the release workflow, such as a local build, has no commit to show.

### Where step Pods run

Step Pods run pipeline code, so by default they run in a namespace of their own,
`<release namespace>-steps`, which the chart creates. The server's Secret, its ServiceAccount and
the Data Depot stay in the release namespace. The chart gives the server's ServiceAccount a Role in
the step namespace for what it does to step Pods: create, watch and delete them, read their logs and
events, exec into them, and manage the Secrets, Services and NetworkPolicies it creates for them.
Step Pods reach the Data Depot and the server through Services.

- To run step Pods in a namespace you name, set `scarab.namespace` and create the namespace before
  the install: the chart renders the Role into it.
- To keep the default name and create the namespace yourself (to add a LimitRange, say), set
  `scarab.namespace: <release namespace>-steps` and create it before the install.
- To keep step Pods beside the server, as up to 0.4.4, set `scarab.namespace` to the release
  namespace.
- Creating a Namespace needs cluster-wide rights. An installer with rights only in the release
  namespace sets `scarab.createNamespace: false`, and step Pods run in the release namespace; or
  it names a namespace that already exists in `scarab.namespace`.
- With `rbac.create: false` the chart renders no Role, and an empty `scarab.namespace` means the
  release namespace, where you grant the server's ServiceAccount its rights.
- With `scarab.executor: local` the chart renders no Namespace.

A release namespace longer than 57 characters makes `<release namespace>-steps` longer than a
namespace name may be; the render fails and asks you to set `scarab.namespace`.

What you set up for step Pods goes in the step namespace: a LimitRange or ResourceQuota,
`imagePullSecrets` on its `default` ServiceAccount, and every ServiceAccount a placement profile
names, such as the one in [Pushing images to Amazon ECR](/scarab-ci/usage/pushing-to-ecr/).
`helm uninstall` leaves the namespace and any step Pods in it.

**Upgrading from 0.4.4 or earlier.** Up to 0.4.4 an empty `scarab.namespace` meant the release
namespace. With the default values it now means `<release namespace>-steps`, so the upgrade creates
that Namespace and moves the executor's Role there. Step Pods running in the release namespace
during the upgrade stay there, and the new server does not see them: for a step that was still
running it finds no Pod and marks the Attempt lost, and the step's retry policy decides whether a
new Attempt runs in the new namespace. It does not delete the old Pods. Let running Runs finish
before the upgrade (`kubectl -n <release namespace> get pods -l scarab.io/run` lists none), or set
`scarab.namespace` to the release namespace to keep step Pods where they are. Recreate what you set
up for step Pods in the new namespace first. If the account that runs `helm upgrade` cannot create
a Namespace, the upgrade fails: set `scarab.createNamespace: false`, or name an existing namespace
in `scarab.namespace`. Installs that already set `scarab.namespace`, set `rbac.create: false`, or
run the local executor see no change.

### The step Pod admission policy

Any Pod can mount any Secret and run as any ServiceAccount in its own namespace: the kubelet
resolves those references without asking the Pod's ServiceAccount, and RBAC cannot limit `create
pods` by what the Pod refers to. Scarab's Pod builder keeps step Pods off the server's Secret and
ServiceAccount. The chart also installs a ValidatingAdmissionPolicy, so the cluster refuses such a
Pod if Scarab has a bug.

The policy holds every Pod the server's ServiceAccount creates in the step namespace, in both
namespace modes: `<release namespace>-steps`, and `scarab.namespace` set to the release namespace.
It refuses a Pod that:

- names a Secret in a Secret volume, a projected volume, an env `secretKeyRef` or an `envFrom`
  `secretRef`, other than the Pod's own per-Pod Secrets (`<pod>-v-secrets`, `<pod>-v-token`,
  `<pod>-v-registry`, `<pod>-v-oidc`, `<pod>-workspace`, and the names a server before 0.7
  wrote: `<pod>-secrets`, `<pod>-token`, `<pod>-registry`, `<pod>-oidc`), the Secrets your
  `scarab.placement` baseline and profiles name, and `scarab.admissionPolicy.allowSecrets`;
- runs as a ServiceAccount other than `default`, the ServiceAccounts your placement baseline and
  profiles name, and `scarab.admissionPolicy.allowServiceAccounts`;
- has a `hostPath` volume, `hostNetwork`, `hostPID` or `hostIPC`.

The old names are allowed so that Pods a 0.6 server made still pass during an upgrade. Upgrade the
chart with the server image: under a 0.6 chart's policy, which lists only the old names, every step
Pod a 0.7 server makes with one of the `-v-` Secrets is refused, and its step fails.

The policy cannot tell which profile a Pod was placed with, so a Secret or ServiceAccount any
profile names is allowed on every step Pod. It does not check `privileged` or added capabilities:
Scarab allows those per step by grant, which the policy cannot see. Use Pod Security on the step
namespace for those. It does not check `imagePullSecrets`. Nor does it check CSI
`nodePublishSecretRef`, the Secret references of the older in-tree volume types, or ConfigMap
references: when step Pods share the release namespace, the server's ConfigMaps sit beside them.

The server's own Pods are not held by it when they share the namespace: the ReplicaSet and
StatefulSet controllers create the server's and the Data Depot's Pods, not the server's
ServiceAccount. Plugin Pods and the plugin isolation probe run in `plugins.namespace`, which the
chart keeps apart from the step namespace and labels Pod Security `restricted`.

The two allow lists are for names the chart cannot see, such as the profiles of a placement file
you mount through `extraVolumes` instead of `scarab.placement`.

A step whose Pod the policy refuses fails with the policy's reason, for example `Scarab step Pod
policy: a Secret volume names a Secret that is not the Pod's own`; the Run does not retry the
launch.

The policy and its binding are cluster-scoped: the account that runs `helm install` or `helm
upgrade` needs rights to create `validatingadmissionpolicies` and
`validatingadmissionpolicybindings` (`admissionregistration.k8s.io`). With `scarab.createNamespace:
false`, the setting for an installer with rights in the release namespace only, the chart leaves
the policy out and the install notes say so; set `scarab.admissionPolicy.enabled: true` to install
it anyway. `enabled: auto` (the default) means on unless `scarab.createNamespace` is false.

The policy needs Kubernetes 1.30 or later (`admissionregistration.k8s.io/v1`). On an older cluster
the chart installs no policy and the install notes say so. `helm template` without a cluster
cannot see the API: pass `--api-versions
admissionregistration.k8s.io/v1/ValidatingAdmissionPolicy` or set `scarab.admissionPolicy.force:
true`.

To try it before it refuses anything, run it in Audit mode: the API server creates the Pod and records what it
would have refused in its audit log (when the API server has audit logging on).

```yaml
scarab:
  admissionPolicy:
    validationActions: [Audit]
```

When the audit log shows no `scarab-step-pods.*` refusals for your pipelines, set it back to
`[Deny]`.

With the policy on, the render fails when:

- your placement baseline or a profile sets a `hostPath` volume, `hostNetwork`, `hostPID` or
  `hostIPC`: every step Pod placed with it would be refused. The error names the baseline or the
  profile. Remove the field, or set `scarab.admissionPolicy.enabled: false`.
- step Pods share the release namespace and the server's ServiceAccount is one the policy allows:
  `default` (with `serviceAccount.create: false` and no `serviceAccount.name`), or a name in a
  profile or `allowServiceAccounts`. A step Pod could then run as the server. Give the server its
  own ServiceAccount, run step Pods in another namespace, or turn the policy off.

| Key | Default | Notes |
|-----|---------|-------|
| `scarab.admissionPolicy.enabled` | `auto` | `auto`: on unless `scarab.createNamespace` is false; `true`; `false` |
| `scarab.admissionPolicy.force` | `false` | install it even when Helm cannot see the API |
| `scarab.admissionPolicy.validationActions` | `[Deny]` | `[Audit]` for a trial, `[Warn]` to warn the server only |
| `scarab.admissionPolicy.failurePolicy` | `Fail` | `Fail` refuses a Pod when the policy cannot be evaluated |
| `scarab.admissionPolicy.allowSecrets` | `[]` | Secrets a step Pod may name besides its own and the placement config's |
| `scarab.admissionPolicy.allowServiceAccounts` | `[]` | ServiceAccounts a step Pod may run as besides `default` and the placement config's |

### Hardening the nodes that run step Pods

We recommend `kernel.yama.ptrace_scope` set to 1 or more on the nodes that run step Pods. Scarab
does not check it, and runs at any value.

At 1, a process can attach to (`ptrace`, `/proc/<pid>/mem`) only its own descendants unless it
holds `CAP_SYS_PTRACE`. It is hardening, not a boundary Scarab relies on: Yama checks attach-mode
access only, not reads of `/proc/<pid>/root` or `/proc/<pid>/environ`. What keeps a Dockerfile
`RUN` in the build library away from buildkitd and buildctl is the kernel's capability rule, which
holds at any `ptrace_scope` (measured on 2026-11-12 in Docker with the executor's settings).
Amazon Linux 2023, the EKS default, ships with 0; Ubuntu ships with 1.

The cost at 1: `strace -p`, `gdb -p` and `py-spy --pid` against a process that is not a child need
`CAP_SYS_PTRACE`. `strace <command>` and `gdb ./<program>` still work.

The setting is the node's, not the Pod's, so any Pod on a node shows it:

```bash
kubectl -n <step namespace> exec <pod> -- cat /proc/sys/kernel/yama/ptrace_scope
```

On Amazon Linux 2023 nodes, add a sysctl drop-in through the node's user data. With Karpenter, in
the `EC2NodeClass` of the pool that runs step Pods (a launch template's user data takes the same
part):

```yaml
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: steps
spec:
  amiSelectorTerms:
    - alias: al2023@latest
  userData: |
    MIME-Version: 1.0
    Content-Type: multipart/mixed; boundary="BOUNDARY"

    --BOUNDARY
    Content-Type: text/x-shellscript; charset="us-ascii"

    #!/bin/bash
    echo 'kernel.yama.ptrace_scope = 1' > /etc/sysctl.d/90-ptrace-scope.conf
    sysctl --system
    --BOUNDARY--
  # role, subnetSelectorTerms, securityGroupSelectorTerms as for your other pools
```

New nodes pick it up; replace the existing nodes of the pool to apply it there.

### Health checks

The server answers three health endpoints. The chart's probes use `/livez` and `/readyz`.

| Endpoint | Answers 200 when | Probe |
|----------|------------------|-------|
| `/livez` | the process is up, and its scheduler is still making progress | liveness |
| `/readyz` | the database and the object store answer | readiness |
| `/healthz` | the process is up | none |

The scheduler runs in a loop on each replica, and the replica that holds the scheduler lease
starts Runs; the others wait to take over if it stops. A pass of the loop that makes no progress
for 60 seconds is stopped, with a warning that names the part it was in, and the next pass starts;
a pass over many Runs that keeps making progress runs as long as it needs. When a replica's loop
has made no progress for 90 seconds, `/livez` answers 503 with the reason, and Kubernetes restarts
the Pod. This holds for every replica, not only the lease holder: a stuck replica could not take
over the lease. Without this, Runs stayed pending with nothing logged until someone restarted the
Pod. `/livez` does not call the database: a database that answers with errors does not fail it,
but one that stops answering stops the scheduler on every replica, and they are all restarted. If
the loop stops for another reason (a panic), the server shuts down as it does on SIGTERM and exits
with status 1.

The two limits are settings, `scarab.driverStallCutoffSecs` (default 60, from 30 to 3600) and
`scarab.driverStalledAfterSecs` (default 90, at least the cutoff plus 30). Raise them if one call
on your install, such as a slow Kubernetes API or a large batch of forge statuses, takes longer
than a minute: the warning names the part that was stopped.

Calls to the Kubernetes API wait at most 30 seconds for a response before they fail, and calls to
a forge (GitHub, Forgejo) at most 30 seconds in all. A followed log read fails after 5 minutes
with no byte and is opened again ([Run logs](/scarab-ci/usage/run-logs/#when-a-read-ends));
`exec` sessions have no limit.

A `values.yaml` that sets the whole `livenessProbe.httpGet` keeps its own path; point it at
`/livez` to get this check. When it is `/healthz`, `helm install` and `helm upgrade` print a
warning.

### Master keys and value ledgers

Every replica must use the same master keys. `SCARAB_MASTER_KEYS` is a comma-separated list of
base64 32-byte keys: the first encrypts, the rest only decrypt (`SCARAB_MASTER_KEY` sets one key).
Scarab encrypts stored secrets with them, and each step's value ledger: the secret values a launch
hands the step, which the server redacts the step's log with
([Run logs](/scarab-ci/usage/run-logs/#secret-values)). A replica that cannot decrypt a step's
ledger stores none of that step's log and leaves it to a replica that can.

To redact a log, the server builds lookup tables from the step's values, up to 52 bytes per value
byte (at most 13 MiB for a step at the 256 KiB cap), and frees them when the step's last log read
ends. `scarab.logAutomataBudgetMib` (`SCARAB_LOG_AUTOMATA_BUDGET_MIB`, default 128, from 16 to
65536) is the most MiB of these tables a replica keeps at once; a log read that does not fit waits
until another ends, and a read that loses its tail lease while it waits stops. It builds them for
2 steps at a time, about 36 MiB each at the cap. Count the budget and 72 MiB in the server Pod's
memory limit: the default 128 fits the chart's default limit of 512Mi, and a larger budget needs a
larger `resources.limits.memory`.

To rotate a key:

1. Add the new key after the active one on every replica, and roll them out.
2. Move the new key to the front on every replica, and roll them out. At boot each replica
   rewraps the stored secrets under the active key. A ledger generation cannot be rewrapped (its
   encryption is bound to its step and generation), so it stays under the key it was sealed with
   until the ledger is deleted.
3. Remove the old key only when `scarab_secrets_rows_under_nonactive_key` reads 0 on every
   replica. The metric counts the stored secrets and the ledger generations still under a key
   that is not the active one, as of the replica's boot, so restart the replicas to read it again.
   It reaches 0 at most 24.5 hours after the key stopped being active, the longest a ledger lives.
   Removing the key earlier stops the logs of running steps from being stored, and a re-drive of
   such a step fails.

One replica revokes forge tokens and deletes ledgers: the one that holds the lease
`ledger-sweep`, every 30 seconds, in a task of its own beside the scheduler. It waits at most 20
seconds for one step's revocations; a failed revocation is tried again after 1 minute, doubling to
an hour, and a ledger is deleted anyway 24.5 hours after its first generation once its step is not
running. A forge that does not answer delays no scheduling.

### Plugins

`plugins.enabled` (default `false`) turns on the plugin runtime: a shared plugin namespace, the
CredentialBroker and the RBAC they need. No built plugin capability acts on Scarab yet (ADR-0074),
so you don't need it to run pipelines or deploys; leave it off unless you are working on a plugin.
The chart creates the plugin namespace (`plugins.createNamespace`) and labels it with the release
it belongs to. If you create the namespace yourself, give it the labels
`pod-security.kubernetes.io/enforce=restricted` and
`scarab.io/plugin-runtime-owner=<release namespace>.<release name>`. Scarab runs no plugin in a
namespace labelled for another release, so two releases can't share one plugin namespace.
Each installation runs as one Deployment named after it, with the vowels dropped and its id
added: `argocd-staging` runs as `scarab-plugin-rgcd-stgng-<id>`. Its ServiceAccount is
`plugin-<id>`. The isolation probe's Pods are named `scarab-probe-<role>-<id>`.

If every node in your cluster is tainted, set `plugins.tolerations` and `plugins.nodeSelector`.
Scarab puts them on every plugin Pod and on the isolation probe's Pods, so the probe checks the
nodes plugins run on. Without a matching toleration the probe's Pods stay Pending and no plugin
starts. These settings don't place the server, the Data Depot or step Pods. A toleration field
Scarab doesn't know (a misspelling such as `efect`) stops the server from starting, with the
field named in the error.
A plugin that needs storage brings its own: you create a PersistentVolumeClaim in the plugin
namespace and the plugin runtime mounts it. Scarab doesn't provision, back up or read that
volume, and its data is outside what Scarab keeps.

#### Install a plugin

Every plugin installs the same way, Scarab's own Argo CD plugin included: no plugin is installed
or trusted by default. An org admin installs one under Organization settings › Plugins ›
**Install plugin**, or with the API, in two steps:

1. **Fetch and review.** Give the plugin's manifest as a source,
   `<host>/<owner>/<repo>//<path>@<commit>`, where the path ends in `.json`, `.yaml` or `.yml` and
   the commit is a full commit id. Scarab reads it the way it reads a
   [library source](/scarab-ci/usage/libraries/#install-a-library): without credentials from
   github.com or a Forgejo connection's host, or through a connection of your org for a private
   repository. It checks the manifest and shows what the plugin asks for: its capabilities, its
   connection slots and the requests each slot allows, its config keys and its gates. Nothing is
   installed yet.
2. **Install.** Name the installation and give the plugin's image pinned by digest,
   `<repository>@sha256:<digest>`, from any registry your cluster pulls from. Scarab reads the
   source again and refuses the install (409) if the manifest is no longer the one you reviewed.
   This asks you to confirm with your passkey.

```sh
curl -X POST "$SCARAB/v1/orgs/acme/plugin-fetch" \
  -d '{"source": "github.com/acme/scarab-plugins//notify/manifest.json@8c2f…"}'
# → {"source": "…", "manifest": {…}, "manifest_sha256": "a41c…", "content": "…", "installed": []}

curl -X POST "$SCARAB/v1/orgs/acme/plugins" \
  -d '{"name": "notify", "image": "ghcr.io/acme/notify@sha256:…",
       "source": "github.com/acme/scarab-plugins//notify/manifest.json@8c2f…",
       "manifest_sha256": "a41c…"}'
```

The install body also takes `connection` (the connection the fetch read through), `config`
(values for the manifest's config keys) and `storage` (below). After the install, bind each
connection slot under the installation, or with `PUT /v1/orgs/{org}/plugins/{name}/connections/{slot}`.

The installation records the source it was read from and the connection it was read through.
An installation made before Scarab recorded sources shows "source not recorded".

A manifest can name the image repository the plugin ships as, in its `image` field
(`"image": "ghcr.io/thulasi-ram/scarab-plugin-argocd"`, no tag or digest). Scarab then refuses an
install or upgrade with an image of any other repository (400), so the manifest cannot be paired
with someone else's build. A manifest without `image` installs with any repository, and the review
says that it names none.

#### Upgrade a plugin

Open the installation's page and choose **Upgrade**, or use the API, in two steps:

1. **Fetch and compare.** Give the new commit, and Scarab reads the recorded source's file at that
   commit; or give a whole source to read another file. Scarab has no branch lookup, so you give
   the commit. It shows what the new manifest adds, removes and keeps against the installed one:
   capabilities, connection slots, auth schemes, read rules, config keys, gates and the named
   image.
2. **Upgrade.** Give the image pinned by digest: a new one, or the installed one to change only
   the manifest. Scarab reads the source again and refuses the upgrade (409) if the manifest is
   not the one you compared, if the installation changed since you compared it, or while plugins
   are off.

A new image digest is new code, so an upgrade to one asks you to confirm with your passkey, as an
install does, even when the manifest is the same or narrower. So does a manifest that adds a
capability, a connection slot, an auth scheme, a read rule or a gate, or that stops naming its
image or names another. The one upgrade that needs no passkey keeps the installed image and
removes from the manifest or keeps it as it is. Scarab decides this from the installation and the
manifest it reads; the request cannot say it. Give the image to the fetch too, and its answer
(`needs_step_up`, with `step_up_reasons`) says which applies.

```sh
curl -X POST "$SCARAB/v1/orgs/acme/plugins/notify/upgrade-fetch" \
  -d '{"commit": "4b1e…", "image": "ghcr.io/acme/notify@sha256:…"}'
# → {"source": "…@4b1e…", "manifest_sha256": "77d0…", "current_manifest_sha256": "a41c…",
#    "diff": {"read_rules": {"added": [], "removed": ["api: GET /v1/legacy"], …}, …},
#    "step_up_reasons": ["runs new code: image `…` instead of `…`"], "needs_step_up": true, …}

curl -X POST "$SCARAB/v1/orgs/acme/plugins/notify/upgrade" \
  -d '{"image": "ghcr.io/acme/notify@sha256:…",
       "source": "github.com/acme/scarab-plugins//notify/manifest.json@4b1e…",
       "manifest_sha256": "77d0…", "expected_current_sha256": "a41c…"}'
```

The installation keeps its name, id, config, storage, state and connection bindings. A config key
or connection slot the new manifest no longer declares is dropped, and a dropped binding's
credential is deleted. Scarab keeps the version the upgrade replaced (image, manifest, source and
who approved it) and restarts the plugin with the new image after the isolation probe passes
again.

#### Plugin storage

Create the claim in the plugin namespace (`plugins.namespace`, default `scarab-plugins`) and
annotate it with the installation it is for, as `<org>/<installation name>`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: argocd-state
  namespace: scarab-plugins
  annotations:
    scarab.io/plugin-installation: acme/argocd-prod
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 1Gi
```

Then name it on the installation's page (Settings › Plugins, then the installation's row), under
**Storage**, or with
`PUT /v1/orgs/{org}/plugins/{name}/storage` and a body of
`{"claim": "argocd-state", "mount_path": "/data"}`. `mount_path` defaults to `/data`; it
can't be `/`, and it can't overlap `/tmp`, `/var/run/secrets` or the other paths the runtime
or the kubelet mounts.

The plugin namespace is shared by every org, so the runtime mounts a claim only when its
annotation names that installation. Until it does, or while the claim is missing, the plugin is
held at zero replicas and its status names the claim. A claim that hasn't bound yet shows as
waiting. The plugin runs as uid and gid 65532 with `fsGroup: 65532`; a volume type that ignores
`fsGroup` (hostPath, some local provisioners) needs to be writable by that uid.

Adding storage to an installation that has none, or removing it, needs no step-up. Moving it
to another claim or mount path asks for a passkey step-up. Removing it leaves the claim and its
data in place.

## A minimal `values.yaml`

An example override for a real cluster, where Postgres and S3 credentials come from a Secret you
manage out-of-band (`secrets.existingSecret`), not inline:

```yaml
image:
  tag: sha-<gitsha>        # pin an immutable published tag; `edge` tracks main

scarab:
  role: converged          # or split: api / scheduler / executor / webhook
  executor: k8s
  publicUrl: https://scarab.example.com   # run deep-link in commit statuses
  s3:
    bucket: scarab-artifacts
    endpoint: ""           # empty => AWS S3; set for in-cluster MinIO
    region: us-east-1

secrets:
  # Keys in this Secret must match the SCARAB_* env-var names
  # (e.g. SCARAB_DATABASE_URL, SCARAB_S3_ACCESS_KEY, SCARAB_MASTER_KEY,
  #  SCARAB_GITHUB_WEBHOOK_SECRET).
```

reference.

### The UI URL

`scarab.uiUrl` (`SCARAB_UI_URL`) is the address people open the web UI at. Leave it empty when
that is `scarab.publicUrl`. Set it when forges and people reach Scarab at different addresses,
for example a staging install whose public hostname routes only `/webhooks/` while people use
`http://localhost:8080` through a port-forward. Three things use it:

- the login callback, `{uiUrl}/v1/auth/callback`, which is the callback URL to register with the
  login provider;
- the passkey origin: a passkey works only on that origin, and one enrolled on another address
  does not work here;
- the confirmation link a step-up request answers with.

Webhook URLs and the run links in commit statuses stay on `scarab.publicUrl`. The server refuses
to boot when `uiUrl` is not an `http` or `https` URL, has a query or fragment, or, with step-up
on, is plain `http` on a host other than `localhost`, `127.0.0.1` or `::1`. Browsers refuse
passkeys on an IP address, so a local `uiUrl` is `http://localhost:<port>`. A sign-in started
on `127.0.0.1` is sent to the `localhost` address first, so the sign-in keeps its cookie.

Session cookies are marked `Secure`. Chrome and Firefox accept them on `http://localhost`;
Safari may not, so sign in to a plain-`http` local install with Chrome or Firefox.

### A proxy in front of Scarab

The Steps of an invoked library and matrix Steps have ids that hold `/` (`amd64/image`) or `[`,
`,` and `=` (`test[os=linux]`). Scarab's own clients (the web UI, `scarab rerun` and the results
sidecar) do not put such an id in a URL: they name a Step by its key, so they need nothing from a
proxy, ingress controller or gateway in front of Scarab.

#### Step keys

Each Step of a Run has a key: 12 characters of `a` to `z` and `2` to `7`, random, unique within
the Run, and fixed for the Run's life (a retry, a rerun or a new Take keeps it). `GET
/v1/runs/{id}` lists it as `key` on each entry of `steps`, and a waiting gate in a run list has
one too. Every Step route takes it as `{step}`:

```
GET /v1/runs/{id}                                → steps[].key, e.g. "q4mmz2c7eh5a"
GET /v1/runs/{id}/steps/q4mmz2c7eh5a/logs/raw?attempt=a1
```

A Step route also takes the Step's id, percent-encoded as one path segment
(`/v1/runs/{id}/steps/amd64%2Fimage/results`). A `{step}` that is neither a key nor an id of a
Step of that Run gets a 404 from a read.

#### Keeping `%2F` for API callers that send a Step id

An API caller that puts a Step id holding `/` in a path sends it as `%2F`, and the proxy must
pass `%2F` on unchanged. One that decodes it, or redirects to the decoded path, sends the request
to a path no route matches, and Scarab answers 404. Send the key instead and the proxy does not
matter.

Envoy Gateway redirects to the decoded path by default (`UnescapeAndRedirect`). To keep `%2F`, set
`escapedSlashesAction: KeepUnchanged` in a `ClientTrafficPolicy` on the Gateway that routes to
Scarab:

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: ClientTrafficPolicy
metadata:
  name: scarab-keep-escaped-slashes
  namespace: <gateway namespace>
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: Gateway
      name: <gateway name>
  path:
    escapedSlashesAction: KeepUnchanged
```

With an nginx you configure yourself, write `proxy_pass` with no URI part
(`proxy_pass http://scarab;`), so nginx passes the path as the client sent it.

#### Where step Pods post results

Step Pods post their results to `scarab.resultsApiUrl`. Leave it empty: the chart then points it
at the release's in-cluster Service, `http://<release fullname>.<release namespace>.svc`, so the
results do not go through the proxy at all. If you set it, point it at that Service too. The
results sidecar counts only the server's `202` as delivered; a gateway that redirects or rewrites
the path makes every try fail, and the Step fails after the sixth.

### Grant the first roles

The people in `scarab.oauth.owners` are Owners each time they sign in. To give anyone a role
before an Owner can do it in the UI, or to have an install's first members listed on the org's
Members page, run the server binary with the database URL:

```sh
scarab-server admin grant --org acme --subject github:alice --role member --reason "first members"
```

`--subject` is the person's handle, the name they signed in under (`github:alice`); their
Scarab id (`p_` and 32 hex characters) works too. `--role` is `viewer`, `member`, `admin` or
`owner`. The person must have signed in once; until then the command exits 3 and says so. The command sets the role exactly: it lowers a higher
role, restores a revoked one, and turns a role a forge import gave into one the forge sync
does not change. When the person already holds that role, nothing is written. Each grant is
recorded in the org's event log as `binding.operator_grant`, with the host, OS user and
reason, in the same transaction as the role. The command needs only `--database-url` or
`SCARAB_DATABASE_URL` and never migrates the database.

A script that runs on every deploy should pass `--if-absent`. The command then writes nothing
when the person has any role binding in the org, at the org or at a project, or one that was
revoked, and prints what is there. A role an Owner changed in the UI stays as the Owner set it.

In a cluster, run it in the server Pod, which has the database URL:

```sh
kubectl exec -n scarab deploy/scarab -c scarab-server -- \
  scarab-server admin grant --org acme --subject github:alice --role member
```

## Upgrading to Scarab 0.7

0.7 changes how the server stores logs and keeps the secret values it redacts them with
([Run logs](/scarab-ci/usage/run-logs/#how-the-server-stores-a-log)). Read the Breaking changes of
0.7.0 in `CHANGELOG.md` too. Then:

1. **Let running Runs finish.** A step or shared service that runs across the upgrade stores no
   log after it: its log gets the note "the rest of this log was not stored: this step was started
   by an earlier Scarab version, so its secret values are not known". When no step runs,
   `kubectl -n <step namespace> get pods -l scarab.io/run` lists no Pod.
2. **Keep `strategy.type: Recreate`**, the chart's default. Once migration 0099 has run, the
   database refuses log chunks from a 0.6 server, and a 0.6 server does not start. With
   `RollingUpdate`, the 0.6 servers still running store no log, and a step one of them launches
   gets the same note and no log.
3. **Upgrade the chart and the image together** (`helm upgrade --version 0.7.0`). A 0.7 server
   mounts its per-Pod Secrets under the `<pod>-v-…` names, and only the 0.7 chart's admission
   policy allows them ([above](#the-step-pod-admission-policy)).

The server runs two migrations before it listens. 0099 adds the log stream and value ledger
tables; its checks on `log_chunks` are `NOT VALID`, so it scans no stored chunk. 0100 builds the
index `attempts_started_at_idx` with `CREATE INDEX CONCURRENTLY`, outside a transaction, so writes
to `attempts` go on while it builds. A build that fails or is stopped leaves an invalid index
behind, and the next server to start drops it and builds it again before it listens.

After the upgrade:

- Forge tokens minted by 0.6 for steps that ran across the upgrade are not revoked: 0.7 revokes
  only tokens it finds in a value ledger. A GitHub App token expires an hour after it was minted.
- Never drop the `log_chunks_fenced` check on `log_chunks`. During a rolling update it is what
  stops a 0.6 server that is still running from storing output it cannot redact.
- Every replica must use the same master keys ([above](#master-keys-and-value-ledgers)).

### Rolling back to Scarab 0.6

A 0.6 server does not start on a database that ran migration 0099: its migrator finds version 99,
which it does not know, and stops. To go back:

1. Let Runs finish and stop new ones.
2. Scale the server to zero, so no 0.7 server runs while the revert runs or after it:
   `kubectl -n scarab scale deploy/scarab --replicas=0`.
3. Back up the database.
4. Run the revert below (a second run changes nothing). It is `crates/scarab-db-postgres/rollback/0099_revert.sql` in the
   repository, and it reverts migrations 0100 to 0103 too:
   `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f 0099_revert.sql`.
5. Install the 0.6 chart and image:
   `helm upgrade scarab oci://ghcr.io/thulasi-ram/charts/scarab --version 0.6.1 -n scarab -f values.yaml`.

The revert deletes the notes of logs stored by 0.7 and every value ledger. Output rows stay, and
0.6 reads them as before. Upgrading again runs 0099 to 0103 again.

```sql
BEGIN;

-- A second run changes nothing: the delete below runs only while the
-- `kind` column exists, and every other statement is safe to repeat.
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM information_schema.columns
             WHERE table_schema = current_schema()
               AND table_name = 'log_chunks' AND column_name = 'kind') THEN
    DELETE FROM log_chunks WHERE kind <> 'output';
  END IF;
END
$$;

DROP FUNCTION IF EXISTS scarab_append_log_row(
  TEXT, TEXT, TEXT, TEXT, TEXT, BIGINT, TEXT, TEXT, TEXT, BIGINT, BYTEA, BIGINT, TEXT, BIGINT);

DROP TABLE IF EXISTS log_unit_values;
DROP TABLE IF EXISTS log_units;
DROP TABLE IF EXISTS log_streams;
DROP TABLE IF EXISTS log_legacy_units;
DROP TABLE IF EXISTS log_store_epoch;
DROP TABLE IF EXISTS log_prune_pending;

ALTER TABLE log_chunks
  DROP CONSTRAINT IF EXISTS log_chunks_kind,
  DROP CONSTRAINT IF EXISTS log_chunks_reason,
  DROP CONSTRAINT IF EXISTS log_chunks_body,
  DROP CONSTRAINT IF EXISTS log_chunks_fenced,
  DROP COLUMN IF EXISTS kind,
  DROP COLUMN IF EXISTS reason,
  DROP COLUMN IF EXISTS writer_term,
  DROP COLUMN IF EXISTS values_gen,
  DROP COLUMN IF EXISTS digest,
  ALTER COLUMN object_key SET NOT NULL;

DROP INDEX IF EXISTS attempts_started_at_idx;

DELETE FROM _sqlx_migrations WHERE version IN (99, 100, 101, 102, 103);

COMMIT;
```

### Migration 0101

The first release after 0.7.0 runs migration 0101 when the server starts. It validates three of
the checks 0099 added to `log_chunks` (`log_chunks_kind`, `log_chunks_reason` and
`log_chunks_body`). Validating takes a lock that blocks no read or write, and scans `log_chunks`
once per check, so on a large table the server takes longer to start. `log_chunks_fenced` stays
`NOT VALID`.

The migration waits at most 5 seconds for that lock. Another session that holds a lock of the same
kind on `log_chunks` makes it wait: a manual `VACUUM` or `ANALYZE`, an autovacuum that runs to
prevent transaction ID wraparound, or a `CREATE INDEX CONCURRENTLY`. After 5 seconds the server
stops with `canceling statement due to lock timeout`, Kubernetes restarts it, and it runs the
migration again. The server starts once the other session ends; until then the Pod restarts
with Kubernetes' back-off, up to 5 minutes between tries. A plain autovacuum does not cause this:
it gives way to the migration after about a second. To see what holds the table:

```sql
SELECT pid, query, now() - query_start AS running
FROM pg_stat_activity
WHERE pid IN (SELECT pid FROM pg_locks WHERE relation = 'log_chunks'::regclass);
```

### Migrations 0102 and 0103

The same release runs migrations 0102 and 0103 right after 0101. It adds a third reason to the
`log_chunks_reason` check, `values_too_large`: a step whose secret values add up to more than
256 KiB gets a `not_stored` note in place of its log (see
[Run logs](/scarab-ci/usage/run-logs/#edges-of-a-value)). It drops the check and adds it again
`NOT VALID`, so it scans no row under its lock, which blocks reads and writes. Migration 0103
then validates that check again, in its own transaction, under the same lock as 0101 (it blocks
no read or write); it scans `log_chunks` once more, so on a large table the start takes longer.
Each waits at most 5 seconds for its lock, and a timeout restarts the server as for 0101. 0103
waits for the same sessions as 0101. 0102's lock waits for every other session that holds a lock
on `log_chunks`: any open transaction that read the table (a `pg_dump`, a long `SELECT`) makes it
stop with the lock timeout, and while it waits, up to 5 seconds, the log reads and writes of the
replicas still running wait behind it.

A 0.7.0 server does not start on a database that ran 0101, 0102 or 0103. To go back to it, scale
the server to zero, run `DELETE FROM _sqlx_migrations WHERE version IN (101, 102, 103);` and
install 0.7.0.
The checks stay, and 0.7.0 writes no row that breaks them. A 0.7.0 server shows a
`values_too_large` note with the text of the `no_ledger` note.

## The chart on a local kind cluster

`just stack up` installs the same chart on a local kind cluster, `scarab-dev`, with Postgres and
MinIO running in the cluster beside it. What differs from a live install is where the
binaries come from: the server and the workspace service run a `scarab-server` built from your
working tree and mounted into a small runtime image, and the step helper images are built
locally and loaded into the node. A code change needs a rebuild and a Pod restart
(`just stack reload`), not an image build.

```sh
just stack up          # build the server, create the kind cluster, install the chart
just stack reload      # rebuild and roll the server and workspace Pods onto the new binary
just stack up dogfood  # the same release in GitHub App mode, behind a Cloudflare tunnel
just stack down        # delete the cluster and its data
```

Every kubectl and helm call uses the cluster's own kubeconfig (`deploy/kind/.kubeconfig`),
checked against the cluster before each call. See
[Run locally](/scarab-ci/get-started/run-locally/) for a first run and `deploy/kind/README.md`
for the details.

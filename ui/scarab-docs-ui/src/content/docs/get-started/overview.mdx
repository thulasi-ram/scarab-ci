This page covers what Scarab needs and the two ways to bring it up. Every
pipeline step runs as a Pod, so either way you need a **Kubernetes cluster**:
kind or colima on your laptop works, and so does a remote production cluster.

Neither way is a cut-down version of the other; pick the one that fits what
you're doing.

If you only want to see what Scarab looks like, there is a third option that
installs nothing: the [live demo](https://demo-scarab.ahiravan.dev/). Sign
in with GitHub and you land as **Viewer**, which carries no Write, so you can
read a run but not dispatch one. To run a pipeline, pick one of the two
paths below.

## Which path?

Both run the same engine against a real cluster; they differ in how
`scarab-server` itself is deployed and how quickly you can iterate.

| If you want to… | Use | Where |
|---|---|---|
| Look at a running Scarab without installing anything | **Live demo** | [demo-scarab.ahiravan.dev](https://demo-scarab.ahiravan.dev/) |
| Deploy Scarab inside the cluster the way it ships, on kind/colima or a live/production cluster | **Helm chart** | [Installation](/scarab-ci/get-started/deploy-helm/) |
| Iterate on the server from source with a loop that rebuilds and reruns | **Proc-mode dev loop** | [Run locally](/scarab-ci/get-started/run-locally/) |
| Reproduce the exact deployment inside the cluster on your laptop before shipping | **Helm chart on colima** (`just local-helm`) | [Installation](/scarab-ci/get-started/deploy-helm/) |

The **same Helm chart** targets every environment: a local kind/colima cluster
and a live production cluster use the identical `helm upgrade --install`. There is
no separate "production build"; the proc-mode loop only swaps the packaged image
for a `scarab-server` you run straight from the tree, so you can rebuild and rerun
in seconds.

## What Scarab needs

Whichever path you choose, `scarab-server` needs:

- **Postgres**: the durable store that all run state and coordination go
  through. The server refuses to start without `SCARAB_DATABASE_URL`.
- **An S3-compatible object store** (AWS S3 or in-cluster MinIO) for logs,
  artifacts, and the content-addressed workspace snapshots that reruns restore
  from. The server refuses to start without one. For tests and dev loops you
  can point it at a local directory with an explicit `--object-dir`: a single
  directory with no replication.
- **A Kubernetes namespace with RBAC** so it can launch one Pod per pipeline step.

[Installation](/scarab-ci/get-started/deploy-helm/) sets all three up through
the chart; the [Run locally](/scarab-ci/get-started/run-locally/) recipes start
them for you on your machine.

## Where Scarab stops

Scarab is CI. It runs and governs the run that deploys (approvals, allowed refs, scoped
secrets), and it can wait inside that run until your CD tool reports the change live. It keeps
no record of what is live where after the run ends, and it doesn't detect changes made outside
it. Argo CD, Flux or your CD tool of choice answers those. See
[Deploying with Argo CD](/scarab-ci/usage/deploying-with-argo-cd/).

Scarab gives you a CI that plugs into your forge (pipelines in your repo, PR checks, secrets,
approvals, a UI) on a control plane that saves each run as durable **state**. If the control
plane restarts partway through a run, the run carries on from its last completed step.

Most CI tools give you one half of that. **Workflow engines** (Argo, Tekton, Temporal) have a
durable core that survives a crash, but forge integration, in-repo config, PR checks, identity,
secrets, the DSL and the UI are all yours to build. **CIs that live in your forge** (GitHub
Actions, GitLab, Woodpecker, Drone) hand you all of that, but underneath they are plain job
runners: if the control plane restarts mid-run, the run is orphaned or starts over.

## Why now

<AsciiScene name="dungroller" fontSize={3.33} class="ascii-accent" />

As pipelines get longer and more autonomous (agents, review gates that sit open for hours,
workflows that span days), "the job died, click re-run" stops being good enough. Scarab can hold
a paused run at almost no cost and pick up where it left off, and it keeps an event log that
only ever grows, so you can see everything that happened.
We also build Scarab with AI tools: a small team writing systems software at a pace that used to
need many more people.

![A Scarab run: the step DAG, live logs, and an event timeline showing a retried step and the run paused on a manual deploy gate](../../assets/run-detail.jpg)

## Lineage

Scarab owes its shape to [Woodpecker](https://woodpecker-ci.org/): lean CI that lives in your
forge, without enterprise overhead. It's shaped just as much by Woodpecker's *limits*: the many
backends it has to support, and the pace a volunteer project can sustain. Supporting only
Kubernetes drops that backend burden on purpose, and a small team using AI can now keep up a
faster pace.

:::note[Status]
Scarab is not a shipped product yet. **Tested against real Postgres, in CI:** the durable
engine, crash and resume, exactly-once execution, restarting a single step, gates, the
content-addressed workspace, `invoke`, secrets, and the OIDC issuer. `ci.yml` runs the
workspace suite on every push to main and on every PR that touches Rust code. **Tested against
a fake forge:** webhook → in-repo config → run → commit statuses posted back. **Implemented, and
run against real forges by hand:** the GitHub and Forgejo adapters (webhook ingest and commit
statuses); `just forgejo-verify` drives a real Forgejo from hook to Run, and the live demo takes
its webhooks from a GitHub App. **Implemented, and tested on a kind cluster:** Pod execution and
re-attach (`scarab-executor-k8s`) and the results-egress sidecar (`docker/sidecar/`).
`kind.yml` runs those tests for changes to the execution path, not on every PR (as of
2026-10-28 the job fails at image load, before the tests run; last green on main 2026-10-20). **Not proven
yet:** control-plane crash and resume with a real Pod in flight (the weekly e2e test for it
doesn't pass yet) and production-scale load. **Missing:** `on: cron` and `on: upstream`
triggers parse, but nothing produces those events yet.
:::

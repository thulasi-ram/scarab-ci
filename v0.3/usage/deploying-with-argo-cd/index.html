    Deploying with Argo CD

    Keep a deploy run open until Argo CD has rolled out your change, and fail it when Argo gives up, with one ordinary step after the deploy step.

    With GitOps, the step that deploys usually commits an image change to a gitops repository and exits. Argo CD applies the change later, and the rollout can still fail: an image that can’t be pulled, a migration hook that fails, Pods that never become ready, or a sync that Argo stops retrying. If the run ends when the commit lands, it is green before anyone knows whether the change is live.

    Scarab doesn’t track deploys after a run ends (that is Argo’s job), so the way to close the gap is to keep the run open: add a step after the deploy step that waits for Argo. Its exit code is the outcome, its log holds Argo’s messages, and its timeout bounds the wait. Scarab adds nothing for it; it is a step like any other.

    The pipeline

    Section titled “The pipeline”

    deploy: true on bump makes this a deploy run: it shows in the Runs tab’s deploys filter, and a newer push never cancels it half-way. See Deploys: deploy: true.

    The two traps

    Section titled “The two traps”

    A plain argocd app wait "$APP" --sync --health looks like it does the same job. It goes wrong in two ways, and the script above handles both.

    Synced and Healthy at an earlier commit. Argo polls the gitops repository every few minutes unless a webhook tells it sooner. Right after the merge, the app still reports Synced and Healthy, at the commit before yours, and a wait that trusts those two words passes at once. In a shared gitops repository the app can also be Synced at a later commit that doesn’t contain your change yet. So step 1 asks Argo for the app’s target manifests (argocd app manifests --source git, what Argo would apply now) and waits until they contain your image. Only then do Synced and Healthy describe your change.

    Use an image reference that only your change produces, such as a tag built from the commit SHA or a digest. grep -F matches substrings, so payments-api:1.2 also matches payments-api:1.20.

    A sync that fails never becomes Synced. When Argo’s sync operation fails (a hook fails, a manifest is rejected, the retries run out), the app stays OutOfSync, and argocd app wait --sync keeps waiting until its timeout. Adding --operation doesn’t change that: it waits for the operation to finish, not for it to succeed. Step 2 reads the operation’s phase instead, and fails as soon as the operation for the current target revision ends Failed or Error. It ignores a failed operation from an older revision, which Argo leaves in place until the next sync. It also fails when the app is Synced but Degraded, which is how a rollout that never becomes ready (an image that can’t be pulled, for example) shows up once the Deployment’s progress deadline passes.

    With automated sync and a retry policy, Argo keeps the operation Running while it retries, so the step waits through the retries and fails only when Argo gives up.

    When you don’t need a wait step

    Section titled “When you don’t need a wait step”

    If the deploy step applies the change itself, it can block until the rollout finishes, and no separate step is needed:

    • helm upgrade --install ... --wait --timeout 15m waits until the release’s Pods are ready, and fails the step if they aren’t by the timeout.
    • kubectl apply -f ... followed by kubectl rollout status deployment/payments-api --timeout=15m does the same for a plain manifest.

    Mark that step deploy: true.

    Waiting with the Argo CD plugin

    Section titled “Waiting with the Argo CD plugin”

    With Scarab’s Argo CD plugin installed in your org (for example as argocd-prod, with its argocd connection bound to your Argo CD; see Install the plugin), a pipeline can wait on the plugin’s wait-live gate instead of a wait step. No Pod waits and the pipeline holds no Argo token: the plugin reads the Application through Scarab’s credential broker.

    The plugin passes the gate when Argo CD reports the Application synced and healthy, with no operation running, and its target manifests render image. It fails the gate with Argo’s message when Argo gives up: a failed sync of the current revision, a failed hook, or a rollout past its progress deadline. For an Application outside Argo CD’s own namespace (apps in any namespace), write app as <namespace>/<name>, as the argocd CLI does. The plugin fails the gate at once when app or its namespace is empty, . or .., or app holds a second /, which no Application name does. The gate’s output revision is the git revision Argo synced; for a multi-source Application it is each source’s revision, in the order of spec.sources, joined by commas. The run fails when the gate expires. See Plugin gates.

    To see what the plugin asked Argo CD for, open Settings → Plugins, then the installation’s page, and read its Broker journal. It lists each request the broker forwarded or refused in the last 14 days, newest first: the path, the read rule that allowed it, the status, the bytes returned, and for a refusal the reason. Query parameter names are shown, their values are not. An org admin can read the same rows from GET /v1/orgs/{org}/plugins/{name}/broker-journal, filtered by phase (refused, head or end) or by denied=true, a page at a time with before.

    Install the plugin

    Section titled “Install the plugin”

    An org admin installs it like any other plugin (Install a plugin):

    1. Fetch its manifest from Scarab’s repository at the full commit of a release tag: github.com/thulasi-ram/scarab-ci//crates/scarab-plugin-argocd/manifest.json@<commit>. It asks for use_connection and resolve_gates, one connection slot argocd that allows only GET requests to a fixed list of Argo CD API paths, and the wait-live gate.

    2. Install it with its image pinned by digest. Scarab publishes the image as ghcr.io/thulasi-ram/scarab-plugin-argocd, for linux/amd64 and linux/arm64, tagged with the release version, and edge and sha-<commit> for each commit on main. Use the build from the same commit as the manifest, and read its digest:

      then install ghcr.io/thulasi-ram/scarab-plugin-argocd@sha256:<digest>. A tag can move; the digest you approve cannot. To run your own build, build docker/plugin-argocd/Dockerfile from the repository root and push it to a registry your cluster pulls from.

    3. Bind the argocd slot to your Argo CD’s URL with a bearer token, and add the installation to a plugin list (plugins_allowed, under Settings › Plugins › Plugin policies), which no plugin’s gates run without.

    What this doesn’t cover

    Section titled “What this doesn’t cover”
    • The wait costs a Pod and a secret. The wait step holds a Pod for as long as it waits, and the Argo token is an Environment secret that the steps naming it can read.
    • Nothing after the run ends. A rollout that fails an hour later, a hotfix applied by hand, or Argo’s self-heal reverting a change are not seen by Scarab. Argo CD’s UI and notifications cover those.
    • Manual sync. The recipe assumes the Application syncs automatically. With manual sync, nothing applies the change, and the step waits until its timeout.
    • Multi-source applications. They report .status.sync.revisions (a list) in place of .status.sync.revision, so step 2’s revision check needs adjusting for them.
    • OnDelete StatefulSets and DaemonSets. With updateStrategy: OnDelete, Kubernetes replaces a Pod only when someone deletes it, and Argo CD can report the Application Healthy while the old Pods still run the old image. Both the wait step and the plugin’s wait-live gate then say your image is live before it serves.
    • Correctness is yours. Scarab runs the step and reports its exit code; it doesn’t check what the step checks.

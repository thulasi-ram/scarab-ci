    Environments

    An Environment such as prod governs the Runs that name it, with approvers and an approval gate, allowed refs, a required reason, scoped secrets and privilege grants that an org admin owns and the engine enforces where they are used.

    What an Environment is

    Section titled “What an Environment is”

    An Environment (for example staging or prod) is an org-level set of rules and scoped secrets that governs the Runs which name it. A pipeline names one with a top-level environment::

    That one line pulls in approval, allowed refs, secrets and privilege grants, which an org admin defines once for every Project in the org. Because the rules live in the Environment and not in the pipeline YAML, you get separation of duties: the pipeline asks to run in prod, and the Environment decides whether it may, whatever the YAML says.

    Naming an Environment does not make a Run a deploy. A smoke test that needs staging credentials or a backup that needs prod credentials runs in an Environment too. To mark the Runs that deploy, use deploy: true. Scarab governs the Run that deploys and keeps no record of what is live where after that Run ends; that is your CD tool’s job. See Deploying with Argo CD for a pipeline that waits until its change is live.

    Protection is optional per Environment. An Environment with no rules (typically staging) only scopes secrets. Add approvers and it becomes gated.

    Who may run in it

    Section titled “Who may run in it”

    An Environment admits Runs only from the Projects on its eligibility list: all projects, or an explicit list (project-name globs allowed). Patterns match project names ignoring case, so Web* admits web-api. A pattern of only * is refused: choose all projects instead. A new Environment starts with no eligible Projects, and a pipeline that names an unknown Environment, or one that doesn’t admit its Project, is refused before any Pod starts. When a webhook-triggered pipeline is refused this way, Scarab posts a failure commit status under the pipeline’s scarab/<pipeline> context that says what an org admin must change and links to the org’s Environment settings. A push from a branch the Environment’s allowed_refs leave out posts no status.

    Org admins create Environments and change their eligibility and rules, under the org’s Settings › Environments (/orgs/<org>/settings/environments). New environment, at the right of the list’s header, asks for the name, a display name and a description; the new Environment has no baseline rule and admits no project until you set both on its page.

    Manage an Environment

    Section titled “Manage an Environment”

    Each Environment has one page, /orgs/<org>/settings/environments/<name>/manage, reached with Manage on its row. It holds the display name, the description, the baseline, the approval gate settings and Projects that may use it as one form: Save sends only the parts you changed, and Discard changes puts back what is stored. Below the form, Project overlays and grants lists each project’s overlay and privilege grant, with grant and withdraw, and the page ends with Duplicate and Delete. Deleting the Environment, or withdrawing a grant, asks you to type its name. While projects hold overlays, privilege grants or secrets in the Environment, a delete is refused and the dialog lists them; its button then deletes them with the Environment (DELETE …?cascade=true). The page’s former addresses, …/environments/<name> and …/<name>/edit, open it.

    Name and display name

    Section titled “Name and display name”

    An Environment’s name cannot be changed. It is the key every pipeline’s environment: uses, and the OIDC subject a Run presents to a cloud provider contains it (scarab:org/<org>/repo/<repo>/env/<name>/ref/<ref>), so cloud trust policies match on it.

    The display name is what lists, headings and pickers show, with the name beside it, for example Production (EU) · prod. It is optional (blank shows the name) and an org admin can change it at any time without a step-up. It may not hold control characters, or invisible bidi or zero-width characters that would make it read as another name.

    Duplicate an Environment

    Section titled “Duplicate an Environment”

    To move to another name, use Duplicate on the Environment’s page. It asks for the new name and, optionally, a display name (blank uses the old one’s with “ (copy)“ added), and needs a step-up, because it copies secrets and the projects that may use it. The new Environment gets:

    • the baseline protection rules and eligibility;
    • every project’s overlay and privilege grant;
    • the Environment’s secrets set per project, with their values.

    The old Environment is not changed; it stays until an admin deletes it. Run history, approvals included, and the Cache stay with it. When the copy is made, the page lists what it did not copy:

    • the projects whose Runs used the old Environment: their pipelines’ environment: must change;
    • the policies whose match.environments selects the old name and not the new one;
    • cloud trust policies: a role that trusts …/env/<old>/… must also trust …/env/<new>/….

    If the copy fails part-way, nothing is left behind: the secrets are copied first and removed again if the Environment cannot be created. A name already in use, or secrets already stored under the new name, is refused (409). So is a second Duplicate to a name while the first is still running, before it writes anything, and so is creating an Environment of that name while the Duplicate runs.

    The rules it holds

    Section titled “The rules it holds”

    An Environment’s baseline protection rules are:

    • approvers: the people whose approval is required, each typed as their handle (github:alice). A handle typed in another case names the same person when only one person matches. Scarab stores each person’s id, so the list keeps naming the same people whatever they are called later, and shows them by handle. Approvals are recorded on a gate, not in a separate table: the Run’s Environment approval gate collects distinct approver identities on the Run’s durable event log (GateApproved { step, by }), and the Steps after it wait until the approvals are in. This survives restarts, and approvals cannot be forged. See The approval gate.
    • allowed_refs: glob patterns for the git refs that may run here; checked at Run creation, so a disallowed ref is rejected before any Pod launches (blank = any ref).
    • require_reason: a human dispatch (manual/api) into this Environment must carry a reason; push, pull request, tag, release and cron are exempt.
    • wait_timer_s: a minimum wait in seconds on the Environment approval gate, counted from when the gate’s needs finished. The gate releases when the approvals are in and the timer has run out; an approval given early counts. The timer applies only with approvers: the API refuses a non-zero timer on an Environment with none, and a timer stored before that check does nothing.
    • Approval gate settings (baseline only): what happens when a pipeline has no gate (add one, the default, or refuse the Run), the expiry of the gate the Environment adds, how many of the approvers must approve (default: every one), and the maximum approval age (default 24 hours). Where only some of the approvers must approve, adding an approver needs a step-up, as removing one does.

    A baseline with no approver, any ref, no wait timer and no reason protects nothing; only each Project’s own overlay does. While such an Environment admits at least one Project, the Environment list counts it in a warning, its row says permissive baseline, and its page asks for a baseline. An Environment that admits no Project is not counted: it takes no deploy.

    On the Environment’s page these settings are in the Approval gate section: When a pipeline has no approval gate (Add an approval gate or Refuse the run), Added gate expiry (blank: no expiry), Required approvals (1 to the number of approvers; blank: every one) and Maximum approval age, all in seconds. The Wait timer field is disabled while the Environment has no approvers, and an Environment with a timer and no approvers shows a warning that the timer does nothing until approvers are added. Lowering the count, raising the age, or lengthening or removing the expiry loosens the baseline and needs a step-up.

    A Project’s admins can add a tighten-only overlay for their Project: more approvers (each one required, whatever the baseline’s count), a narrower ref pattern, require_reason, a longer timer. An overlay can make that Project’s Runs stricter than the org baseline, never looser.

    Two governed settings are granted to one Project within one Environment, and fail closed: the privilege whitelist (which image digests may use the add-capabilities or privileged grants) and permission for a raw k8s_overlay. Raw overlay permission gives that Project’s pipeline authors control of the step Pod spec, including privileged containers, host mounts and the Pod’s ServiceAccount, so grant it only where you would grant those.

    A Run that names an Environment is also never cancelled by newest-wins: a newer push to the same branch does not cancel it, and its concurrency group queues even if the pipeline declares cancel-in-progress.

    The approval gate

    Section titled “The approval gate”

    A Step uses the Environment’s authority when it declares secrets:, requests a governed grant or a k8s_overlay, asks for forge_token: write, or is marked deploy: true (itself, or its whole pipeline). In an Environment with approvers, no such Step runs until an approver releases an Environment approval gate upstream of it.

    An Environment approval gate is a gate: manual with a Step after it, through needs, that uses the Environment’s authority. Only these gates need the Environment’s approvers and a step-up. Any other manual gate in the Run is a plain gate: anyone with write on the Project releases it with one approval. Which gates are approval gates is decided when the Run is created and stored with it; the Run page marks them, and scarab validate lists them. On the Run page an approval gate reads Environment approval gate with the Environment’s display name and, beside it, its name (a display name is not unique, so the name says which Environment the gate guards), the gate the Environment added reads added by the Environment, and once the approvals are in, a gate with a wait timer shows when it releases.

    When a pipeline has no manual gate in front of a Step that uses the authority, the Environment adds one: a manual gate with the id environment-approval (with -2, -3, … appended if the pipeline uses that id), in front of the earliest such Steps, with their needs combined. Its origin names the Environment. It works like any other gate: approve, reject, expiry and rerun. A Step that never starts, because its when: is false or a Step it needs is excluded that way, gets no gate and adds none of its needs to the gate. With deploy: true on the whole pipeline the added gate comes first, before the build.

    To keep every wait in the YAML, set the Environment’s missing-gate mode to refuse: a Run with such a Step is refused, and the refusal names the Steps and the gate to add.

    Every launch of a Step that uses the authority checks the approval again, reruns and retries included. The launch is refused (the Step fails Config with the reason) when the Run’s ref is no longer in the allowed refs, or when no approval gate upstream of it has released with the approver set unchanged since its approvals were given and no longer ago than the maximum approval age. One such gate is enough: a QA approval gate released two days ago does not refuse a deploy whose own approval gate released a minute ago. An external, timer or plugin gate is never an approval gate, so a Step behind only those is refused at launch.

    The OIDC subject env=<name> is authority too: a cloud role that trusts it trusts the Step as the Environment. So any Step, whether it uses the authority otherwise or not, gets env=<name> only when an approval gate upstream passes the same checks; otherwise it gets env=none. Such a Step still launches. A rerun of it after the approval passed the maximum age, the approvers changed or the ref was taken out of the allowed refs gets env=none.

    The policy engine applies these rules, next to the org’s and the Project’s Policies. Each rule shows in the decision log under its own name:

    Checkpoint Rule What it decides
    run.create environment-approval-gate the gate the Environment adds, or the refusal in missing-gate mode refuse
    gate.resolve environment-approval-release whether an approval releases the gate: the approvers, how many, the wait timer
    step.admit environment-approval-recheck the check at each launch above

    An org Policy at gate.resolve or step.admit can deny where these rules allow, for example an approval by the person who started the Run. A denied approval is not recorded and answers 403; a denied launch fails the Step Config with the Policy’s message. At these two checkpoints a Policy can only deny, and cannot match on trigger_kinds. A step.admit Policy applies to every launch its match selects, including Steps of Runs that no Environment governs. In those Runs run.ref, run.environment and environment are absent: test has(run.environment) or environment != null before reading them.

    Policies over deploys

    Section titled “Policies over deploys”

    An Environment’s own rules are set on its page. CEL Policies, which can also match on environments, are under Settings › Policies (/orgs/<org>/settings/policies): each row shows the Environments a Policy matches, and each Policy’s page lists the decisions it made. See Policies.

    Scoped secrets

    Section titled “Scoped secrets”

    An Environment has two secret scopes: one shared by every eligible Project, and one per Project within the Environment. A step resolves a key most specific first: Project in the Environment → Environment → Project → Org. Prod credentials therefore exist only under the gated Environment, and editing pipeline YAML cannot move them. See Secrets.

    Admission at the point of use

    Section titled “Admission at the point of use”

    The engine enforces admission itself; a caller can’t satisfy it with a request body. Eligibility and allowed_refs are checked at Run creation, approvers is satisfied by the approvals the Run’s approval gate has collected, and require_reason is checked at the admission gate. Eligibility is checked again when each step launches and when a manual or external gate is released, so a Project removed from the list mid-Run stops before its next secret is used. The approval is checked again at each launch too (see The approval gate).

    API endpoints

    Section titled “API endpoints”

    Org Environments live under /v1/orgs/{org}/environments (writes need org admin):

    Method Path Purpose
    GET /v1/orgs/{org}/environments List the org’s Environments
    PUT / GET / DELETE /v1/orgs/{org}/environments/{env} Create or replace (display name and description), read, delete one (?cascade=true also deletes its overlays, grants and secrets)
    POST /v1/orgs/{org}/environments/{env}/duplicate Copy it under a new name; the answer lists what was not copied
    PUT / GET /v1/orgs/{org}/environments/{env}/protection The baseline protection rules
    PUT / GET /v1/orgs/{org}/environments/{env}/eligibility Which Projects may run in it
    PUT / GET / DELETE /v1/orgs/{org}/environments/{env}/projects/{project}/overlay One Project’s tighten-only overlay
    PUT / GET / DELETE /v1/orgs/{org}/environments/{env}/projects/{project}/privilege-grant One Project’s privilege grant
    GET /v1/repos/{org}/{repo}/environments The Environments a Project may use, with baseline, overlay and effective rules

    To list one Environment’s Runs, filter the Project’s Runs: GET /v1/repos/{org}/{repo}/runs?environment=prod, or the Environment filter on the Runs tab.
